## 1. 一文定義

**日本の商習慣に合わせた、パッケージでも SaaS でも使える「取引基盤」。**
物を売る・買い取る・定期で届ける・店頭で渡す・場を貸す・仕事を売り買いする、を
一つの核（Listing と Transaction）の上にモジュールとして載せる。

EC カートではない。海外で一番近いのは Sharetribe（物・サービス・レンタルの
マーケットを作れる基盤）だが、日本向けでセルフホストできるものは存在しない。

## 2. なぜ作るか

### 思想

個人や中小が大手プラットフォームに搾取されない構造を作る。
本製品が分解したい中抜きは次の 3 つ。

| 既存構造 | 手数料・拘束 | 本製品の答え |
|---|---|---|
| モール・フリマ（楽天、メルカリ） | 10〜20% ＋ 出店ルールの拘束 | 自分の店頭と顧客を自分で持つ |
| 仕事仲介の場 | 最大 20% の仲介料 | 仕事の取引フローを自前で回せる |
| 月額の EC の SaaS | 月額 ＋ 決済 3〜5%、データは借り物 | パッケージで所有、SaaS でも持ち出し自由 |

### 持ち込む知見

作り手の実務（中古の買取・店頭での受け取りと POS・産直の定期・一括見積もり・既存の EC の SaaS とパッケージの構築）から、査定と古物商の実務、注文の状態の移り変わり、定期と送料、提案と見積もりの流れ、テーマを差し替えたい需要を持ち込む。コードは流用しない。

## 3. 対象顧客

**販売者（取引を運営する側）が顧客。** 法人と個人事業主の両方。

| 層 | 例 | 導入形態 | 課金 |
|---|---|---|---|
| 個人事業主・小規模 | ハンドメイド作家、個人古物商、フリーランス | SaaS | 無料〜低額の月額 |
| 中小法人 | 古物商チェーン、産直生産者組合、飲食店 | SaaS または パッケージ | 月額 ＋ 有料モジュール |
| 受託クライアント | 業界特化マーケットを作りたい企業 | パッケージ（自社で納品・保守） | 構築費 ＋ 保守 |

B2B 取引（企業が企業に売る：掛け払い・会員別価格・承認フロー）は **対象外で開始**。
核の設計で排除はしないが、6 番目の縦として後で検討する。

## 4. 製品の形：4 つの運用モード

同じコードベースで、テナント設定の組み合わせだけが違う。

| モード | 店頭の持ち主 | 出品者 | お金の流れ | 配布 |
|---|---|---|---|---|
| A. 単店 | テナント自身 | テナント＝出品者 | 決済 → テナント | パッケージ / SaaS |
| B. 多店舗 SaaS | 各テナント（別ドメイン） | テナント＝出品者 | 決済 → 各テナント、月額 → 自社 | SaaS |
| C. マーケットプレイス（自社運営） | 自社 | 複数の出品者 | 決済 → エスクロー → 手数料控除 → 出品者 | SaaS |
| D. マーケットプレイス（受託） | クライアント | 複数の出品者 | 同上、手数料はクライアントへ | パッケージ |

モードを決める 3 つのテナント設定:

- `storefront_scope`: `own`（自分の店頭）| `shared`（複数出品者の商品が同じ店頭に並ぶ）
- `seller_model`: `single`（テナント＝出品者）| `multi`（テナント配下に出品者が複数）
- `settlement`: `direct`（決済が出品者へ直接）| `platform`（エスクローと手数料分配）

**C（自社でメルカリ対抗を運営）は当面やらない。** 流動性の問題は広告費と時間で解くもので、
一人開発の強みが効かない。「マーケットを作れる基盤」として A・B・D で売る。

### 4.1 1 つのパッケージを 2 つの軸で切り替える（2026-10-29 決定）

狙いは、1 つのパッケージでいろんな場面に対応できること。日本でいちばん優れた EC システムを目指しつつ、手軽さも大事にする。

- **既定は 1 システム・1 店舗**（2026-10-29、運営の判断。ふつうは 1 システム・1 店舗で使い、人によってマルチテナント・マーケットプレイス・SaaS として貸す形にも広げる）。インストーラーの既定は 1 店舗の形で、ショップは自分のドメイン（例 example.jp）、管理画面は別の名前（例 admin.example.jp）。ワイルドカードの DNS・証明書も、店のホストごとにその場で証明書を取る仕組みも要らない。管理画面は店が 1 つなら店の一覧を飛ばす。多店舗・マーケット・SaaS は、インストーラーの問いか、後から店を足すと広がる
- **使い方の軸**（上の 4 つのモード）はテナントの設定で切り替える
- **置き場の軸** はインストーラーで切り替える。核（商品・注文・お金の台帳・守り）はどの置き場でも同じコード・同じ守り。置き場の違いはインストーラーと入口の層に閉じ込め、核に「この置き場なら」の分岐を書かない
- **芯は崩さず、手軽さは「入れ方」と「入れた後の手間（自動の更新・戻し・控え）」で出す**。PostgreSQL・テナントごとの DB・読み取り専用のコードは、EC-SUGAR が優れている根拠そのものなので削らない
- 置き場によって守りが弱くなるなら、黙って弱くせず、その置き場の説明に書く

| 置き場 | 対象 | 守り |
|---|---|---|
| まっさらな VPS（install.sh） | 自分でサーバーを持つ人 | 最上 |
| 既存の Web サーバーの後ろ（Plesk など） | 自社のサーバーにほかのサイトがある人 | 最上（入口と証明書だけ前の Web サーバーに任せる） |
| VPS のアプリイメージ | ブラウザだけで始めたい人 | 最上 |
| SaaS | サーバーを持たない人 | 最上（自社で運用） |
| 共用サーバー（未決） | root も PostgreSQL も無いホスティング | 一段下（Web のプロセスがコードを書き換えられる・DB の権限で台帳を守れない・更新はその場の書き換え）。作るなら差をはっきり伝える |

MySQL への対応は、共用サーバー版を作ると決めたときにまとめて考える（VPS の利用者には DB が Docker の中に入るので差が無く、両対応は試験と守りの重荷が続く。2026-10-29）。


> 役割（運営・店の人・お客さん）が置き方ごとに誰に当たるかは ADR 0046 の対応表（2026-10-31）。自分で持つ形では運営＝店の持ち主、SaaS では運営＝私たちで、店の人は同じ管理画面の自分の店だけ。

## 5. 核のドメインモデル

### 5.1 全体像

```
Tenant ─┬─ Seller (1..n)  ── Listing (種類はプラグイン)
        ├─ Customer (0..n)
        ├─ Location (拠点) ── Inventory (数量 or 個体)
        └─ Transaction (状態機械はプラグイン)
               ├─ Ledger entries (お金の流れ)
               ├─ Fulfillment (受渡)
               └─ Document (帳票)
```

テナントは **常に存在する**。パッケージ配布時はテナントが 1 つなだけで、
単一テナント専用の分岐コードは書かない。

### 5.2 Party（当事者）

- `Tenant`: 運営主体。契約・課金・ドメイン・設定を持つ
- `Seller`: 出品者。モード A/B では Tenant と 1:1、モード C/D では複数
- `Customer`: 買い手（買取の場合は売り手になる。役割は Transaction 側で決まる）
- 共通属性: 本人確認（KYC）の記録。古物の買取と個人への報酬支払いで必須
- 個人情報の列はテナント鍵で暗号化し、検索はブラインドインデックスの完全一致のみ（ADR 0010、実装済み）

### 5.3 Listing（出品物）

「種類」がプラグイン。核が知っているのは価格の決まり方と受渡方法だけ。

| 種類 | 出す側 | 価格 | 受渡 | 縦 |
|---|---|---|---|---|
| `product` | Seller | 固定 | 配送・店頭・デジタル | 物販・店舗 |
| `subscription_plan` | Seller | 固定 × 周期 | 配送（繰り返し） | 定期 |
| `buyback_offer` | Seller（店が「買います」） | 査定で決まる | 顧客が送付・持込 | 買取 |
| `service` | Seller | 固定 or 見積 | 納品物・役務 | 仕事 |
| `job_request` | Customer（買い手が募集） | 提案で決まる | 納品物・役務 | 仕事 |

`offer_side`（`sell` | `buy`）を持ち、お金の向きは Listing ではなく
Transaction の `payer` / `payee` で決まる。核は「テナントが受け取る側」を前提にしない。

### 5.4 Transaction（取引）　✅ 合意済み（2026-10-26）

縦ごとに状態機械が違うが、**フェーズの語彙は共通** にする。縦はフェーズを並べ替えて使う。

| フェーズ | 意味 |
|---|---|
| Quote | 確定前の提示。査定額、見積、提案 |
| Agreement | 双方の合意。ここで金額と条件が固定される |
| Payment | 支払い。直接（`direct`）かエスクロー（`platform`） |
| Fulfillment | 受渡。配送・店頭・送付・納品 |
| Acceptance | 受取確認・検収。エスクロー解放の条件 |
| Settlement | 精算。送金、手数料控除、源泉徴収 |
| Cancel / Dispute / Refund | どのフェーズからも分岐できる横断フェーズ |

縦ごとの並び:

```
即時物販   : Agreement → Payment → Fulfillment → (Acceptance 自動) → Settlement
買取       : Quote(仮査定) → Agreement → Fulfillment(顧客が送付) → Quote(本査定) → Agreement → Settlement(店→顧客)
定期購入   : Agreement(親) → [Payment → Fulfillment → Settlement](子・周期ごと) ※スキップ・停止・再開
店舗受取   : Agreement → Payment(店頭 or 事前) → Fulfillment(店頭) → Settlement
マーケット : Agreement → Payment(エスクロー) → Fulfillment → Acceptance → Settlement(手数料控除→出品者)
仕事       : Quote(提案) → Agreement → Payment(エスクロー) → [Fulfillment → Acceptance → Settlement](マイルストーンごと)
```

核が保証すること:

- 親子関係（定期の子注文、仕事のマイルストーン）を持てる
- Quote は複数回・複数者から来てよい（本査定、複数提案）
- すべてのフェーズ遷移がドメインイベントとして記録される（監査・通知・帳票の源泉）。イベントは追記専用でハッシュ連鎖（ADR 0012）

実装済み（ADR 0011）: フェーズの語彙と横断フェーズの規則は核、主フェーズの並びは `TransactionFlows` に登録（核は `sale` のみ）。
明細は商品の行と調整行を同じ表に持ち、合意後は書き換えない。消費税は税率ごとに 1 回だけ丸める。

### 5.5 Ledger（お金の流れ）

Transaction に紐づく仕訳の列。決済代行の都合と税務帳票をここで吸収する。

- エントリ種別: `charge`（請求）、`payment`（支払いの受領）、`fee`（プラットフォーム手数料）、`tax`（消費税）、
  `withholding`（源泉徴収）、`payout`（送金）、`refund`（返金）、`adjustment`（調整）
- 複式の仕訳（1 仕訳の明細の合計が 0）。合意で charge / tax を自動で立て、取消・返金・合意のやり直しは逆仕訳（ADR 0011、実装済み）
- 決済代行への指示（分配・送金）はこの Ledger から生成する。逆（決済代行の明細を正とする）にしない。決済代行は差し替え可能なアダプタ
- **プラットフォームが資金を預からない設計** を基本にする（資金決済法の資金移動業を避ける）。
  エスクローは決済代行側の分配・送金機能（Stripe Connect の separate charges and transfers など）で実現し、自社口座を経由させない。**第一候補は Stripe（ADR 0019。まず単店モードを Checkout で、分配は後で Connect）**

### 5.6 Inventory（在庫）

- 拠点（`Location`）単位。店舗一体型と複数倉庫のため
- **数量管理**（SKU × 数）と **個体管理**（1 点ずつ ID）の両方。中古品は個体管理が必須
- 個体は 買取 → 検品 → 出品 → 販売 の履歴を持つ（古物台帳の実体）

### 5.7 Fulfillment（受渡）

- 方法: `shipping` / `pickup`（店頭）/ `digital` / `in_person`（役務）/ `inbound`（顧客からの送付）/ `none`
- 送り状連携（ヤマト・佐川）は後回し。最初は追跡番号の手入力

### 5.8 Document（帳票）

イベントから生成する。日本固有の要件はほぼここに集まる。

| 帳票 | いつ | 縦 |
|---|---|---|
| 領収書・納品書 | 物販 | 全部 |
| 適格請求書（インボイス） | 課税事業者が発行 | 全部 |
| 支払調書・源泉徴収の明細 | 個人へ報酬を払った時 | 仕事、買取（一部） |
| 古物台帳 | 買取・販売のたび | 買取 |
| 買取明細・返送通知 | 査定確定時 | 買取 |
| 特商法表記 | 店頭に常設 | 全部 |

## 6. プラグイン機構（核 ＋ プラグイン）　✅ 決定（2026-10-27）

WordPress 型の「基本システム ＋ プラグイン」で機能を増やす。縦（買取・仕事・定期・店舗・マーケット）も
決済や配送の連携も、すべて同じ機構に載せる。

### 6.1 WordPress から真似るもの、真似ないもの

| 真似る | 真似ない |
|---|---|
| フックで核に手を入れずに振る舞いを変えられる | グローバルな可変状態（どこからでも何でも書き換えられる） |
| 有効化・無効化・アンインストールのライフサイクル | 管理画面からの ZIP アップロードでコードが入る |
| 設定 API と権限（capability）の登録 | プラグインが核のテーブルを直接いじれる |
| プラグインストアという配布と収益の場 | 依存関係とバージョン互換の宣言がない |

WP の脆弱性の大半はプラグイン由来だが、原因は機構そのものではなく「管理画面からコードが入る」
「拡張点に互換性の約束がない」の 2 点。この 2 点だけを構造で潰す。

### 6.2 プラグインの形

- **配布単位は composer パッケージ**（サービスプロバイダ付き）。インストールは CLI か composer のみ。
  管理画面でできるのはテナントごとの有効化・無効化と設定だけ
- **マニフェストを必須にする**: 名前、バージョン、対応する核のバージョン範囲、必要な権限（触る拡張点）、
  設定スキーマ、マイグレーション。更新時の互換性検査（7.3）はこれを見る
  （→ 今の形〔2026-10-31、ADR 0025・0034〕: 必須なのは登録簿の定義〔名前・画面の名前・説明・合わせて作ったプラグイン API の版〕。マニフェスト〔composer.json の `extra.ec-sugar`〕は核の口〔差し込み・CSP・設定・公表・区画〕を使う App だけが書く。核のバージョンの範囲・権限・移行の宣言と、更新の前の互換の検査はまだ無い〔〕）
- **テーブルは自分の名前空間だけ**。核のテーブルへの書き込みは API 経由のみ
- **ライフサイクル**: install → enable（テナント単位）→ disable → uninstall（自分のデータを消す責任を持つ）
  （→ 今の形〔2026-11-11、ADR 0092〕: 入れる〔composer〕→ 店で使う・止める → 店で App のデータを消す〔止めた店のオーナーだけ。表は残して行とファイルを消す口 `PluginDataPurger`〕→ バージョンを上げる → composer から外す〔表と行は残り、状態は「入っていない」と扱う〕）
- コードはインスタンス単位で入り、有効化はテナント単位。SaaS では自社が入れるプラグインを決め、
  パッケージではクライアントが入れる

### 6.3 拡張点は 6 種類に限定し、バージョンを付ける

| 拡張点 | できること | 例 |
|---|---|---|
| イベント | ドメインイベント（取引のフェーズ遷移など）を購読する | 注文確定で Slack 通知 |
| フィルタ | 値を加工して返す（WP の apply_filters 相当） | 送料計算に割引を挟む |
| 取引の種類 | Listing の種類と Transaction のフェーズ並びを登録する | 買取、仕事 |
| ドライバ | 決済・配送・通知・ストレージの実装を差し替える | GMO-PG、ヤマト送り状 |
| 管理画面 | メニュー・ページ・設定パネル・一覧の列を足す | 古物台帳の画面 |
| 店頭 | テーマに差し込むブロックとデータ | 買取申込フォーム |

拡張点の集合を「Plugin API vN」として semver 管理する。WP の失敗（拡張点が無数にあり互換を約束できない）を避ける。
（→ 今は整数の版: プラグイン API 1・テーマ API 2。付け足しでは上げない。semver にするのは後で〔backlog の「いつか」〕）

### 6.4 管理画面の拡張（2026-10-27 決定）

API 中心で管理画面が SPA なので、PHP のプラグインが画面を足す手段を決めておく。

- **外部プラグインはサーバー駆動 UI のみ**: 画面を JSON（フォーム・一覧・アクション）で宣言し、SPA が描画する。
  安全で更新に強い。設定画面・一覧・詳細・簡単なウィザードはこれで足りる
- **自社プラグインだけ JS バンドル同梱を許す**: 買取の査定画面のような凝った UI 用

### 6.5 自社の縦もプラグインにする（2026-10-27 決定）

買取・仕事・定期・店舗・マーケットは核に入れず、同じプラグイン機構で実装する。最初のプラグインを
自分で書くことで拡張点の不足が早く分かり、外部開発者が来たときに「自社だけできること」が無い状態を保てる。

### 6.6 リポジトリの構成

```
core/        Tenant, Party, Listing(抽象), Transaction(フェーズ語彙), Ledger, Inventory, Fulfillment, Document, 認証, 設定, Plugin API
plugins/     buyback/ work/ subscription/ store/ marketplace/ ← 自社プラグイン。外部と同じ機構
channels/    admin(SPA) / storefront(テーマ) / pos / api / mcp(エージェント向け) ← 10.4
drivers/     stripe / gmo-pg(後) / carriers(後) / mail / storage / llm(claude, ollama) ← ドライバ型プラグイン
```

決定（2026-10-27）: (1) 自社の縦は核に入れず全部プラグインにする (2) 外部プラグインの管理画面はサーバー駆動 UI のみ (3) 管理画面からのコード投入は将来も作らない。

上の図は初めの案。**今の形（2026-10-31）**: 核は `app/Core/<文脈>`（Party・Listing・Transaction・Ledger・Inventory・Event・Payment など）、運営の管理画面の API は `app/Admin`、店頭は `app/Storefront`、管理画面の画面は `resources/admin`、自社のプラグインとテーマは `plugins/`（1 つ = 1 composer のパッケージ）。`core/`・`channels/`・`drivers/` の分け方は作っていない。Stripe のドライバも今は `app/Core/Payment/Stripe`（ADR 0026 の区切り 2 で `plugins/` へ出す予定）。

## 7. アーキテクチャ方針　（Laravel 13・DB 分割・API 中心は確定。残りは仮案）

| 項目 | 仮案 | 理由 |
|---|---|---|
| フレームワーク | **Laravel 13（決定）** / PHP 8.4.1 以上（開発機・本番のイメージ・CI は 8.5。2026-10-30 に 8.3 から上げた。ADR 0002 の追記）、モジュラーモノリス | 2026-03 リリース済み。バグ修正 2027 Q3、セキュリティ修正 2028 Q1 まで。一人で一番速く、配布先の中小企業サーバーは PHP が多い |
| テナント分離 | **DB 分割（決定）**。中央 DB ＋ テナントごとの DB | **攻撃・漏洩時の被害が 1 テナントに閉じる**。データの持ち出しが dump 一つで済む（思想に直結）。バックアップ・復元・削除もテナント単位 |
| API | **API 中心（決定）**。核は API のみで操作し、管理画面も店頭も API 経由 | 店頭を差し替え可能にして受託単価を上げる。テナント DB への経路を API の認可一点に絞れる |
| 管理画面 | SPA（Vue）。核と同じリポジトリ | 縦モジュールが画面を差し込める |
| 店頭 | テーマは Blade + Tailwind（ADR 0018）。JavaScript は核の部品（カート・動き。自分のオリジンだけ、Trusted Types の下）で、Alpine は使っていない（2026-10-31 に直した）。テーマは DB に触らず、店頭が渡すデータだけを出す（テーマ API: docs/design/theme-api.md） | PHP だけでホストできる。初めの「React テーマは後から別配布」は、本番で Node.js を常駐させない（ADR 0015）・テーマはコードを持ち込まない（ADR 0020）と合わないので、作るなら ADR を立てて決め直す |
| 決済 | **Stripe（ADR 0019）**。まず単店モードを Checkout で、分配は後で Connect。核は決済代行に依存しない抽象（Ledger） | 導入の速さ。カード情報に触れない形 |
| インフラ非依存 | ストレージは S3 互換、キューは Redis、メールは SMTP 抽象 | クライアントの VPS でも自前のサーバーでも同じ compose で立つ |
| 配布単位 | Docker compose 一式。`127.0.0.1:` 束縛が初期値 | 外へは入口（プロキシ）からだけ出す |
| アップデート | マイグレーションは前方互換のみ（公開の前は列を消す移行を許し、公開の版から二段にする。ADR 0006 の 2026-10-31 の追記）。テーマ API はバージョン固定 | 既存の設置型の EC が苦しんだ点。初期から決める |
| イベント | ドメインイベントを永続化 | 帳票・通知・監査・将来の分析の源泉 |

### 7.1 DB 分割の帰結（2026-10-26 決定）

単一 DB にまとめると SQL インジェクション一つ、認可バグ一つで全テナントの顧客情報が抜ける。分割の第一の理由はこの被害範囲の限定。

```
中央 DB   : Tenant, ドメイン, 契約・課金, 管理者アカウント, テナント DB の接続情報
テナント DB: Party, Listing, Transaction, Ledger, Inventory, Fulfillment, Document, イベント
```

今の中央 DB（2026-10-31）: 店（`tenants`。店の DB の接続のパスワードは暗号化）・ドメイン・運営（`operators` とパスキー・登録・店ごとの権限・回復用のコードと申し込み。ADR 0013・0024・0038）・監査ログ（`audit_events`）・Stripe Connect の店の対応（ADR 0022）・運営の数の控え（店ごとの日の件数と金額だけ。ADR 0042）・壊れたことの記録と知らせ（ADR 0043）・サーバーの様子（証明書・空き容量・更新）。契約・課金はまだ無い。

- **出品者はテナント DB の中に複数いてよい**。マーケットモード（C/D）は「運営者 1 テナント、出品者は Seller 行」なので、共有店頭でも DB をまたぐ検索は発生しない
- **パッケージ配布は中央 DB ＋ テナント DB 1 つ** の構成で動かす。モードが変わっても構成は変えない
- **データの持ち出し＝テナント DB の dump**。SaaS からパッケージへの移行がそのまま成立する。これは売り文句にする
- マイグレーションはテナント DB の数だけ走る。キュー・スケジューラ・検索インデックスは必ずテナント文脈を持って動かす
- Laravel での実装は stancl/tenancy（DB-per-tenant 対応）を第一候補にする。自前実装は避ける
- テナント横断の集計（自社 SaaS の売上や利用状況）は中央 DB に集約イベントを送って行う。テナント DB を直接なめない（→ 今の形は ADR 0042: 店が自分の文脈で数え、中央には件数と金額だけを置く）

### 7.2 セキュリティ方針（2026-10-27 決定）

既存の設置型の EC の重大な脆弱性は「管理画面からテンプレートやプラグインを入れられる（コード実行）」
「店頭の入力が管理画面でそのまま描画される（XSS → 管理者乗っ取り）」「決済情報の取り回し」の 3 系統。
国内 EC のカード情報漏洩の多くは、古いバージョンのまま放置された自社サイトで起きている。設計で先回りする。

| 方針 | 内容 |
|---|---|
| 管理画面からコードを入れられない | テーマとプラグインは composer / CLI でのみ入る。管理画面は設定と素材の差し替えまで |
| 店の人が書く HTML は動くコードにしない | カスタム区画の HTML は、許した形（要素・属性・class）だけにサーバーで整え、保存のときと描くときの両方で通す。CSP と Trusted Types は緩めない（ADR 0041） |
| Web プロセスはコードを書き換えられない | コードは読み取り専用イメージ。書き込めるのはアップロード領域と DB だけ。WP 型の自己書き換え更新はしない |
| カード情報に触れない | 決済代行のトークン化（ホスト型フォーム）で非保持。PCI DSS は SAQ A の範囲に留める |
| 管理画面は別の入口 | 別ホスト名か別ポート。MFA を既定で必須。IP 制限を設定一つで有効化できる |
| アップロードは再エンコード | 画像は変換して保存し、別オリジン（S3 互換）から配信する |
| 被害範囲の限定 | テナント DB 分割（7.1）＋ API 中心。テナントごとに DB ロールを分け権限を最小に（実装済み、ADR 0009）。パスワードは暗号化して中央 DB に保管（実装済み） |
| 依存関係の監視 | composer audit、Renovate、SBOM 生成を CI に入れる。供給網攻撃（パッケージ乗っ取り）への対処 |
| 監査ログ | ドメインイベントの永続化（7 の表）がそのまま監査証跡になる |
| 脆弱性の受付窓口 | security.txt（開発元の店のサイトにだけ置き、公開用のツリーには入れない。公開用の窓口は SECURITY.md の GitHub の非公開の報告）、報告方針、修正バージョンを全設置先へ届ける経路（7.3）を公開初日から用意する |
| 検査 | CI に SAST（PHPStan 系）と DAST（OWASP ZAP）。Phase 1 出荷前に第三者のペネトレーションテスト |

### 7.3 更新の仕組み（2026-10-27 決定）

**既定: セキュリティ修正は自動適用オン。マイナー・メジャーは任意。**（→ 署名つきの更新ができるまでは、本番の自動の更新を既定で切る。ADR 0006 の 2026-10-31 の追記）

更新経路そのものが攻撃対象になる（SolarWinds、3CX は更新配信が乗っ取られた）ので、「自動にする」より
「自動にしても壊れない・乗っ取られない」条件を先に揃える。

| 条件 | 内容 |
|---|---|
| 署名付き配布 | リリースはすべて署名（cosign / minisign 系）。更新側は署名を検証してからしか適用しない |
| 更新の単位はイメージ | Docker イメージの差し替え ＋ マイグレーション。コードの部分書き換えはしない |
| マイグレーションは前方互換 | 同一メジャー内は「追加してから削除」の二段階（expand / contract）。コードを戻しても DB が壊れない |
| 自動バックアップと健全性チェック | 更新前にテナント DB をバックアップ、更新後にヘルスチェック、失敗したら前のイメージへ戻す |
| カスタマイズと分離 | テーマとプラグインは別パッケージで、対応する核のバージョン範囲をマニフェストで宣言。更新前に全プラグインの互換を検査し、1 つでも外れたら止めて通知（→ 核のバージョンの範囲の宣言と互換の検査はまだ無い） |
| 更新チャネル | security: 自動（既定オン） / minor: 任意（既定オフ） / major: 手動 ＋ 移行ガイド。テナントごとにメンテナンス時間帯を設定できる |
| 更新状況の把握 | 設置先はバージョンと PHP バージョンだけを匿名で報告（パッケージでは opt-out 可）。脆弱性公開時に未更新の設置先数が分かる |

SaaS とパッケージの違い:

- **SaaS**: 自社が全部更新する。テナント DB の数だけマイグレーションを流す仕組みと、段階適用
  （自社テナント → 数件 → 全部）の運用があれば足りる
- **パッケージ**: 上の表が丸ごと必要。これが保守契約の中身になる（更新の監視と失敗時の復旧を月額で売る）。
  設置型の EC の世界で SIer が属人的にやっていたことを製品の機能にする

設置型の EC で店が古い版に置き去りになった最大の理由は「SIer がカスタマイズした核に更新を当てると壊れる」。
カスタマイズを核の外（プラグインとテーマ）に閉じ込める 6 章の設計が、更新を成立させる前提。

## 10. AI 機能　✅ 方針決定（2026-10-27）

AI の搭載は必須。ただし「載せる」ではなく「取引基盤に根付かせる」。多くの EC が後付けで
足しているのに対し、核の設計段階で置き場所を決める。

### 10.1 原則

- **AI は提案し、人が確定する**。査定額・審査・返信のどれも最終判断は人。法的責任（古物商、景表法）は人にある
- **提案と確定の両方をイベントとして残す**。どのモデルの何バージョンが何を言い、人が何に確定したか。説明責任と評価データの源泉
- **核は AI を知らない**。LLM はドライバ型プラグイン、機能は AI プラグインとして拡張点に差し込む

### 10.2 縦ごとの置き場所

| 縦 | 効くもの | やらないもの |
|---|---|---|
| 買取 | 写真からの査定支援（品目識別・状態判定・根拠付きの相場提示）、古物台帳の入力補助、本人確認書類の読み取り | 査定額の自動確定 |
| 物販・店舗 | 写真から商品名・説明・属性・カテゴリの生成、多言語化、問い合わせの分類と返信下書き | 生成文の無審査公開 |
| 仕事 | 募集文の見積項目への構造化、提案の下書き、検収チェックリスト、紛争時の経緯要約 | マッチングの自動決定 |
| 定期 | 解約予兆と次回提案（LLM より統計で足りる） | — |
| マーケット | 出品審査（禁制品・法令違反の表現）、レビュー要約 | 審査の最終判断 |
| 運営全体 | 管理画面の自然言語集計・操作、ドキュメント検索 | — |

### 10.3 構造

- **LLM ドライバ**: Claude API を第一。Ollama（自前のサーバー、開発・検証用）、他社をマニフェストで差し替え。
  能力（文章・画像・構造化出力・埋め込み）を宣言し、機能側は能力だけを要求する
- **AI プラグイン**: 「写真査定」「商品登録アシスト」などは個別のプラグイン。取引の種類・フィルタ・管理画面の拡張点に差し込む
- **テナント単位の設定**: 提供元の選択、BYOK（自分の API キー）か基盤キーの従量か
- **データ境界（決定）**: テナントのデータはテナントの文脈でしか LLM に渡さない。**本人確認書類などの個人情報は、既定では外部 LLM に送らない**。テナントが明示的に有効化した場合のみ
- **評価データ**: AI の提案と人の確定の差分を保存する。査定ではこれがそのまま評価セットと相場データの種になる
- **コスト（2026-10 時点の Claude API）**: 分類・抽出は Haiku 5.5（入力 $0.10/MTok）、判断は Opus 5.5（$4/MTok）。
  夜間一括はバッチで半額、カタログなど固定文脈はキャッシュ。写真査定 1 件で数円、商品登録 1 件で 1 円未満の桁

### 10.4 エージェントから使える基盤（決定）

人ではなく AI エージェントが買い手や運営者になる流れに備える。API 中心の設計がここで効く。

- **MCP サーバーをチャネルの一つにする**（6.6 に追加）。テナントが自分の Claude や他のエージェントから
  「今日の買取申込を一覧して」「この商品を 3 点出品して」と操作できる。管理画面の自然言語操作と同じ土台
- **エージェント向けの店頭**: 商品情報を構造化して返し、エージェントがカートから決済まで通れる経路を保つ。
  標準が固まるまでは「API がそのまま使える」状態を維持するだけでよい

「自分のデータを自分のエージェントに使わせる」は、この製品の思想（借り物にしない）と一致する。

### 10.5 課金（仮）

- SaaS: **従量課金を基本**にし、上位プラン（Pro）には一定枠を含める。確定は 8 章の収益モデルと同時に
- パッケージ: BYOK

### 10.6 Phase 1 で載せる 3 つ

1. **写真査定支援**: 品目と状態の推定、類似の確定済み査定からの相場提示、根拠の表示
2. **古物台帳の入力補助**: 本人確認書類と品物写真から台帳項目を埋める（確定は人）
3. **管理画面の自然言語集計**: 買取件数・単価・在庫への質問に答える。MCP サーバーの土台を兼ねる

## 11. 実装順序

縦は **一度に一つ**。ただしスキーマは 5 つ全部を見据える。

| 順 | 内容 | 狙い |
|---|---|---|
| 0 | 核の骨格: Tenant / Party / Listing(product) / Transaction(即時物販) / Ledger / Inventory(数量) / admin 基礎 / Docker | 核の抽象が物販で動くことの確認 |
| 1 | **買取モジュール**: buyback_offer、仮査定→送付→本査定→振込、個体在庫、KYC、古物台帳、買取申込の店頭。AI は写真査定支援・台帳入力補助・自然言語集計の 3 つ（10.6） | 競合不在、知見あり、決済と配送が軽い。1 社目を取る |
| 2 | **仕事モジュール**: job_request / service、提案→受注→マイルストーン→検収、エスクロー（決済代行の選定が前提）、源泉・支払調書 | 一括見積もりの知見を持ち込み、自分が 1 社目になる。個人への支払い帳票を買取と共用 |
| 3 | 定期購入、店舗一体型（pickup、POS 連携）、マーケットプレイス（`shared` 店頭、`multi` 出品者） | 順番は 1・2 の顧客の声で決める |
| 並行 | GMO-PG/SBPS、送り状連携、React テーマ（作るなら ADR で決め直す。7 の表の「店頭」） | 顧客要望が出た時点で |

### 最初の 3 か月（Phase 0 ＋ 1）の出口

- 単店モード（A）で、買取の申込から振込まで一通り回る
- Docker compose でクライアント VPS に置ける
- 古物台帳と買取明細が出力できる
- 1 社目の候補に触ってもらえる状態

## 12. やらないこと

- 自社でメルカリ対抗（モード C）を運営すること
- 管理画面からテーマやプラグインのコードをアップロードできるようにすること（将来も）
- AI に査定額・審査・マッチングを自動確定させること（提案まで。確定は人）
- 既存の EC と汎用カート機能の数で競うこと
- 最初から複数の決済代行に対応すること
- モバイルアプリ（店頭はレスポンシブで足りる。POS は後で）
- B2B 取引（掛け払い、承認フロー）を初期スコープに入れること

## 付録: 議論の経緯（2026-10-26）

1. EC パッケージか SaaS か → 同一コードで両方。テナントは常に存在する
2. 汎用カートは作らない → 縦に張る。買取・産直定期・店舗一体型が候補
3. フリマ型 → マーケットは「テナントの出し方」の違い。自社運営はせず、作れる基盤として売る
4. 仕事仲介型 → 仕事も Transaction の変種。一括見積もりの知見がある
5. 全部を束ねると「EC」ではなく「取引基盤」。核は Listing と Transaction のプラグイン構造
6. 最初の縦は買取、2 番目は仕事。定期・店舗・マーケットはスキーマだけ先行

2026-10-27:

7. Laravel 13、DB 分割（攻撃時の被害範囲）、API 中心を確定。決済代行は未定
8. 大手の設置型の EC と並ぶことは、「機能の広さ」なら到達可能、「実績」は時間、「エコシステム」は一人では無理。構造（マルチテナント・更新・ヘッドレス・逆方向の取引）で差を付ける
9. セキュリティと自動更新は「更新が安全に自動で当たる設計」として一体で扱う。セキュリティ修正のみ既定で自動
