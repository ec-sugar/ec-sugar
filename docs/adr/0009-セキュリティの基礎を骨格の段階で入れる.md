# 0009 セキュリティの基礎を骨格の段階で入れる

状態: 採用（2026-10-27）

## 文脈

決済と本人確認書類を扱う基盤であり、よくある設置型の EC の事故（放置された脆弱性、管理画面経由のコード実行、
テナント境界の破れ）を構造で防ぐのが製品の売り。後から足すと、設計の前提（誰が何に触れるか）を
変えることになり高くつく。セキュリティの検証は、どの段階でも省かない（運営の方針）。

## 決定

骨格の段階で次を入れ、以後の変更はこれを前提にする。

- **テナントごとに専用 DB ロール**（最小権限、NOINHERIT）。DB の所有者はそのロール。中央アプリは superuser ではなく CREATEDB / CREATEROLE のみ。中央ロールはテナントロールの権限を継承しない（INHERIT FALSE、DROP のための SET のみ）
- **テナント DB のパスワードは暗号化して保存**（encrypted キャスト、鍵は APP_KEY）
- **防御ヘッダをアプリ側で出す**（CSP は既定で自オリジンのみ、HSTS は HTTPS 時のみ、API 応答は no-store）。nginx にも同等を置く
- **信頼するプロキシを私有アドレス帯に限定**。`*` は使わない
- **レート制限の定義**（auth 10/分/IP、api 120/分/利用者、storefront 300/分/IP）
- **既知の脆弱性があるバージョンを入れられない**（roave/security-advisories）。composer audit と gitleaks は hook と CI の両方
- **コンテナの権限制限**（no-new-privileges、app 系は cap_drop ALL、非 root）
- **報告窓口**（SECURITY.md。/.well-known/security.txt は開発用〔私たちの本番〕にはあり、公開用の木には無い。公開用の窓口は SECURITY.md の GitHub の非公開の報告だけ。ADR 0098、2026-11-12）と **脅威モデル**（docs/security/threat-model.md）を置く
- テナント分離とヘッダは **テストで常に検証する**

## 結果

- 得たもの: テナント境界が DB の権限で担保される（アプリのバグだけでは越えられない）。中央 DB が漏れても平文の資格情報は出ない。以後の実装がこの前提に乗る
- 失ったもの: テナント作成が少し重い（ロール作成 ＋ 権限付与）。中央の接続からテナントのテーブルを直接読めないので、横断集計は集約イベント経由になる（もともと 7.1 の方針）。PostgreSQL 16 以上が必須
