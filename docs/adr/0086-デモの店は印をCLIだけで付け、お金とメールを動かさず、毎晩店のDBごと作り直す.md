# 0086 デモの店は印を CLI だけで付け、お金とメールを動かさず、毎晩店の DB ごと作り直す

状態: **採用**（2026-11-06。架空の 4 店〔酒蔵・コーヒー焙煎所・和菓子店・ライブハウス〕を本番に新しい店として公開する・写真は Unsplash・印は CLI だけ・帯と noindex・テストの鍵だけ・お客さんへのメールを送らず本人だけが見られる・使い捨てのデモの会員・毎晩戻す、は運営が決めた。形と細部は作りながら決めて下の「作って決めたこと」に書いた）。
ADR 0010（個人情報）・0019（Stripe）・0022（Connect）・0025（App）・0044（会員）・0053（入れたときのサンプル）・0061（検索と共有）の上に足す。置き換えるものは無い

## 要点（先に）

1. **デモの店の印**は中央の店の行（`tenants.data.demo`）に置き、付け外しは CLI の `php artisan shop:demo <店> --on|--off` だけ。印が効くのは店の ID が `demo` で始まるとき（例 `demosake`）だけ
2. デモの店では: ショップの全部の画面の上に**帯**（核の部品 `<x-storefront::demo-banner />`）と **noindex**（`X-Robots-Tag` と meta・robots.txt で全部止める・サイトマップは出さない）
3. Stripe は**テストの鍵だけ**（`sk_live_` は保存で断り、置いてあっても使わない。Connect も使わない）。銀行振込・代引きは「デモでは入金を確かめません」と出し、店の人の操作で進める
4. **メールは送らない**。送る直前に止め、宛先が来訪者のアドレスなら、その来訪者の受け箱（`/demo/mails`。そのセッションだけが開ける）に置く。店の人への知らせは捨てる
5. ショップの入力のメールアドレスは、どれも**来訪者だけのアドレス**（`demo-<受け箱>@example.com`）に置き換える（本文とクエリ文字列の両方。全角の＠や引用符つきの書き方も）。他人のアドレスへメールを送らせず、注文・会員・申し込みが来訪者ごとに分かれる
6. 「**デモの会員でログイン**」: その来訪者のアドレスの会員を作って入る（ほかの来訪者と分け合わない）。接続元ごとに 1 時間 20 回まで
7. **毎晩 04:50**（`demo:reset`）、店の DB を消して作り直し（マイグレーションと最初の行）、写真の置き場も消して、覚えておいた扱い・名前・写真のフォルダでスクリプトを流し直す。Stripe のテストの鍵だけ持ち越す
8. 中身は **`php artisan demo:shop <sake|coffee|wagashi|livehouse> --tenant=<店> [--name=…] [--photos=…]`**。流し直しても増えない（冪等）
9. 払わずに在庫を押さえ続けさせない: **来訪者ごとに注文は 1 日 5 件まで**、**1 時間ごと（`demo:restock`）に在庫・予約の枠・予約販売の数・席を作った時の数へ戻す**（2026-11-06、見直しで足した）
10. **外へ送る App**（店への知らせ・LINE・計測のタグ〔ADR 0034〕）はデモの店では使うにできない（2026-11-06、見直しで足した）

## 文脈

- 紹介のサイトから「実際に触れる店」を見せたい。業種ごとに、その店の困りごとを EC-SUGAR のどの機能で解いているかが分かる形にする
- 誰でも触れる公開の店なので、悪用を防ぐ必要がある: 他人のアドレスで注文して確認のメールを送りつける・本物のカードで払わせる・入れた名前や住所をほかの来訪者に見せる・検索に載ってふつうの店と間違われる・ゴミが溜まり続ける
- デモの店は誰でも注文でき、印を間違って動いている店に付けると、毎晩の戻しでその店の記録が消える。印の付け方と戻しの条件は何重にも守る

## 決定

### 1. 印（`App\Core\Shop\Demo\DemoShop`）

- 中央の店の行の data の `demo`（真偽）。書くのは `shop:demo` だけ（テストがリポジトリの中の書き手を数える）。管理画面の経路には印に触れる口が無い
- 効くのは印が真で、店の ID が `demo` ＋英小文字・数字の時だけ。`shop:demo --on` も同じ ID だけを受け、本物の鍵（live）や Stripe Connect のある店は断る。2026-11-06 の見直しで、取引・お客さんの台帳・デモの台本の外で作った商品（`listing.created` の actor が `cli:demo-shop` でない）・外へ送る App を使っている店も断る（動いている店の記録を毎晩の戻しで消さない）。もう印のある店に付け直す時は確かめない
- 付け外しは中央の監査ログ（`tenant.demo_on`・`tenant.demo_off`）

### 2. ショップ

- 帯は核の部品で、4 つのテーマの `layout` と `password` が `<body>` のすぐ後に置く（テーマ API の付け足し）
- 関所 `DemoVisitor`（店頭のミドルウェア群の中。デモでない店では何もしない）: セッションに来訪者の合い言葉（128 ビット）を置く・送られた入力（安全でないメソッドの本文・JSON・**クエリ文字列**。Laravel の `input()` は本文とクエリ文字列を合わせて読む）のうち、項目の名前に `email` を含む値（入れ子の下も、形を問わず）と、NFKC で寄せた後に `@` を含む 1 行の値（320 文字まで）を来訪者のアドレスに置き換える・深すぎる入れ子（7 段目から）は捨てる・`X-Robots-Tag: noindex, nofollow`。写真と robots.txt の群（`storefront-media`）にも `DemoNoindex` が同じ見出しを付ける
- 来訪者のアドレスの受け箱の名前は、合い言葉とアプリの鍵の HMAC の 24 文字。アドレスを知っても合い言葉は分からないので、ほかの人の受け箱は開けない

### 3. お金

- `PaymentGatewayService::configureStripe` はデモの店で live の鍵を断る（本番の環境でも）。`stripe()`・`stripeFor()` は、デモの店に live の鍵が置いてあっても null（支払いに進めない）。Connect の行は見ない
- `StripeConnectService` はデモの店では使えない（`available()` が偽、`connect()` が断る）

### 4. メール（`DemoMails`）

- Laravel の `MessageSending` で、店の文脈がデモの店なら必ず偽を返して送らない（受け箱に置けなくても送らない）。宛先・CC・BCC のうち来訪者のアドレスの受け箱にだけ、件名と本文の文字を置く（店の鍵で暗号化。HTML は文字にしてから）
- 置く数は受け箱ごとに新しい 50 通（古いものから消す）。店全体の上限 20,000 通は最後の守りで、ふだんは届かない（小さいと、受け箱を作り続けてほかの来訪者のメールを押し出せる。2026-11-06 の見直しで 30 / 3,000 から変えた）。`/demo/mails` はそのセッションの受け箱だけを、文字のまま（`{{ }}`）出す

### 5. デモの会員

- `POST /demo/member`: 来訪者のアドレスの台帳を会員にして（`CustomerLogin::joinVerified`。持ち主を確かめた後だけ呼ぶ口として、メールのコードの確かめから分けた）、核のログインの終わり方（`MemberSignIn::start`、入り方 `demo`）で入る
- 接続元ごとに 1 時間 20 回（使い捨ての会員を作り続けさせない）。店頭の回数制限（`throttle:storefront-member`）も掛かる

### 5b. 注文の数と売れる数（2026-11-06、見直しで足した）

- **来訪者ごとの注文の上限**（`App\Core\Shop\Demo\DemoOrders`）: 1 日 5 件。来訪者は注文のメールアドレス（来訪者のアドレスに置き換わる）の受け箱で見分ける。カートの注文の確定（`PlaceOrder`）と、ショップのお客さんの 1 品の注文（`PlaceSingleOrder`。actor が `storefront` のもの: チケット・予約・定期便の申し込み）の錠の中、二重送信の確かめの後で、先に数を足してから比べる（確定できなかった試みも数える。0 円の注文の上限と同じ形）。仕組みが作る注文（定期便の回・抽選の当選）は数えない。超えたら「デモのお店では、ご注文は 1 日 5 件までです」
- **1 時間ごとの売れる数の戻し**（`php artisan demo:restock`、毎時 20 分。`App\Admin\Demo\DemoRestock`）: 合い言葉を作り直せば別の来訪者になれるので、上限だけでは売り切れにできる。押さえた注文は取り消さずに、押さえた分だけ数を足して「残り」を作った時の数にそろえる
  - 在庫: 種類ごとに「在庫 − 押さえた数」を台本の在庫の数にする。核の `InventoryOperations::adjust`（理由は棚卸し、連鎖のロックとイベント、actor `system:demo-restock`）
  - App が数える売れる数: 核の口 `DemoRestockHandler`（`PluginDefinition::demoRestock`）に、台本の欄の値を渡す。予約の枠（定員 = 決まりの定員 + 押さえた人数。`Slots::setCapacity`）・予約販売（上限 = 台本の上限 + 予約の数。`PreorderListings::save`）・席（押さえた枚数の分だけ「追加<区分の順>-1〜」の席を足す。核の `ListingPanels::write`）
  - 戻しと同じ守り（中央の印・ID・店の DB の `built:…`）がそろう店だけ。本物の店は名指ししても断る。戻しの最中・戻しが途中で止まった店は飛ばす・断る

### 5c. 外へ送る App（2026-11-06、見直しで足した）

- `PluginStates::set` が、デモの店で店への知らせ（`shop-notify`）・LINE（`line`）・ショップの画面にスクリプトを差し込むタグの App（マニフェストの scripts のある App。ADR 0034）を使うにするのを断る（`PluginRefusedInDemo`、422）。管理画面も CLI もここを通る。止めるのは断らない
- 念のため、`ShopNotices::deliver` と `LineNotifier::send` もデモの店では送らない（印を付ける前から使う設定が残っていても）

### 6. 作る・戻す（`App\Admin\Demo`）

- 中身は入れたときのサンプルの形（`SampleSet`）で書き、同じ `SampleInstaller` で入れてから、印を「残した」で閉じてお店の物にする（管理画面に「サンプルをまとめて消す」を出さない）。App・商品の欄・App の画面の記録・クーポン・お知らせ・ページ・店の設定は、管理画面と同じ核のサービスを通す（actor は `cli:demo-shop`）
- 済んだ手順は店の DB の `demo_steps` に印。最後の `built:<扱い>` は「流し終えた」の印
- 戻すのは、①中央の印（読み直して確かめる）②ID が demo で始まる ③店の DB に `built:…` がある、の 3 つがそろう店だけ。名指ししてもほかの店は断る
- 同じ店の作る（`demo:shop`）・戻す・売れる数の戻しは、店ごとの錠（`Cache::lock`）で重ねない（手の `demo:reset` と毎晩の処理が重なったら後の方を断る）
- 戻しの途中で落ちても続きから（2026-11-06、見直しで足した）: 店の DB を消す前に、持ち越す Stripe のテストの鍵を中央の店の行（`demo_resetting`）にアプリの鍵で暗号化して控える。作り直した DB にはまず鍵を戻してから中身を入れる。落ちたら控えを残したまま止め、`report()` と運営の知らせ（incidents、場所 `demo:reset <店>`。ADR 0043）に出す。次の回は控えを見て、店の DB の `built:…` を確かめずに作り直しから続ける（控えは `built:…` を確かめた後にだけ付ける）。終わったら控えを消す
- 台本の手順（`once`）は、手順と印を同じトランザクションにする（印だけ残って手順が抜けることが無い）
- 戻しの途中の印（`demo_resetting`。`Tenant::REBUILDING`）が立っている間は、店ごとに回る見回り（`events:relay`・App の定期の処理・運営の様子の集めなど）がその店に入らない（ADR 0089 の作って決めたこと。2026-11-06 に足した）。途中で落ちて印が残った店は、次の戻しが終わるまで見回りの外

## 作って決めたこと（2026-11-06）

- **店の ID の頭は `demo-` でなく `demo`**: 店の ID は店の DB の名前にもなり、DB の名前の確かめ（英字・数字・下線）がハイフンを通さない（`shop:create` は ID のハイフンを受けるが、DB を作るところで断られる。範囲の外なので直していない）。アドレス（ドメイン）は `demo-sake.ec-sugar.jp` のようにハイフンでよい
- **戻しは店の DB ごと作り直す**: 台帳・イベント・在庫の記録は追記だけの表（トリガーで消せない）なので、行を選んで消す形は採らない。テナントの DB の係の `deleteDatabase` → `createDatabase` → マイグレーション → 最初の行 → 写真の置き場を消す、の順（店を作る・消すときと同じ道）。中央の店の行（データの鍵・テーマ・名前）はそのまま
- **店の名前は `--name` を付けたときだけ変える**（2026-11-12）: 前は `--name` が無いと、前に覚えた名前か扱いの名前の候補のはじめで中央の店の名前を書いていたので、`shop:create` で付けた名前が初めての流しで上書きされた（2026-11-09 の本番）。今は `--name` が無ければ中央の店の今の名前を使い（覚えにもそれを入れる）、名前が空の店だけ候補のはじめにする。変えるときは管理画面と同じ店の名前の道（`ShopNames`。デモの店だけを受ける `renameDemo`。店の記録 `shop.renamed` と中央の監査ログ `tenant.renamed`、actor は `cli:demo-shop`）を通し、中央の行を直に書かない。毎晩の戻しは覚えた名前で流し直すので、ふだんは何も書かない
- **日付は作る日から数える**（`+30d`・`+21d 19:00`）: 毎晩作り直すので、抽選の受付・予約の発売日・公演の日時がいつ見ても先になる
- **写真**: スクリプトは写真のフォルダ（`--photos`）から読む。無ければ入れたときのサンプルと同じく Unsplash から取る（取れない写真は無しで入れる）。毎晩の戻しは、覚えておいたフォルダがあればそれを使う（毎晩 Unsplash へ取りに行かない）。写真家は店の「写真のクレジット」のページ（`/pages/photo-credits`）に並べる
- **店頭受け取り**: 核に店頭受け取りの仕組みは無いので、和菓子店は送料 0 円の配送の方法「店頭でお受け取り（…）」を足し、生菓子をその方法に結ぶ（お客さんは配送か受け取りかを選べない。商品ごとに決まる）
- **ライブハウスのリセールの抽選**: 済（2026-11-06、main に入った に合わせた。運営の決定）。リセールの抽選は「ふつうの在庫が売り切れた区分」にだけ申し込めて、抽選販売の受付中の商品には出ないので、抽選の公演（10 周年。受付は 21 日先まで）でなく、**対バン（`friday`）を売り切れ（在庫 0）にしてリセールを使う**にした（`LivehouseDemo::panels()` の `resale`。手数料・締め切りは既定）。来訪者はデモの会員で「リセールの抽選に申し込む」からカードを預けて申し込める。売り切れなので誰もそのチケットを持たず、リセールに出ているチケットは無い。毎時の抽選（`lottery:run`）はデモの店でも走るが、回の記録だけで当てず請求もしない（商品の説明に「デモでは当たりません」と書いた）。毎時の戻しは在庫 0 へ戻すので売り切れのまま（ふつうに買える在庫を作ってリセールの抽選を閉じることはない）。カードを預ける画面は Stripe のテストの鍵の画面（デモの店は live の鍵を使わない）
- **個人情報の画面の印**（2026-11-06、main の ADR 0088 と合わせた時）: 受け箱（`GET /demo/mails`）と「デモの会員でログイン」（`POST /demo/member`）に `navigation-only` を付けた。受け箱はログインのコード・注文の名前と届け先を写したメールを出すので、ほかの個人情報の画面と同じく App のタグの JavaScript に読ませない。デモの会員は帯のフォームから送る時だけ（fetch で来訪者を会員にさせない・回数の枠を減らさせない）。`NavigationOnlyRoutesTest` に「道筋が `demo/` で始まる経路は印が要る」の規則と一覧の 2 行を足した
- **記録の受け手との関係**（2026-11-06、main の ADR 0089 の Outbox と合わせた時に確かめた）: デモの部品（`DemoMails`・`DemoOrders`・`DemoRestock`）は、記録の後の仕事を `DomainEventRecorded` や `afterCommit` で受けていない。メールを止めるのは送る直前の Laravel のイベント `MessageSending`（送る処理の中で同期に呼ばれる）なので、送り出し役が要求の後で送っても、毎分の見回り（`events:relay`、店ごとに店の文脈へ入る）が送っても、デモの店なら止まって受け箱に置く。外へ送る受け手（店への知らせ・LINE）は App に結びつき、デモの店では App を使うにできないので届かない。受け手ごとの印と届け直しの行は店の DB の表なので、毎晩の戻しで消えて初めからになる。作り直した店の最初のコミットの後で印ができ（5 分より前の記録が無いので 0 から）、台本の記録も受け手へ流れる（前の同じプロセスの知らせと同じ結果。贈り物・チケットなどの受け手は冪等）。1 時間ごとの戻しの在庫の記録も受け手へ流れる（再入荷のお知らせを使う店なら、知らせは来訪者の受け箱に置く）
- **レビュー**は見本を入れていない（レビューは注文したお客さんが書くもので、核の口が注文を求める）。App は「店が公開するまで出さない」にしてある（2026-11-06 の見直しで「すぐ出す」から変えた。誰でも書けるので、来訪者の書いた文をほかの来訪者に見せない）
- **main の守りと重ねる**（2026-11-06 の後に main を合わせた時）: 来訪者ごとの 1 日 5 件とデモの会員を作る 1 時間 20 回は、核の回数の部品 `Throttle`（ADR 0081。キーは `Throttle::shopKey`）で数える。まだ払われていない注文の上限（ADR 0085。同じメールの入金待ちは 3 つ・同じ接続元は 5 つ）はデモの店でもそのまま効く。デモの注文は入金を確かめないので、1 人の来訪者が銀行振込・代引きで作れるのは 3 件までで、4 件目からはテストのカードだけを選べる（1 日 5 件はカードを含めた数）。デモの店だけ外すことはしていない
- **管理画面の閲覧の運営**は作っていない（任意）。作るなら `php artisan operator create <メール> --name=…` のパスキーの登録の URL を、運営が手で渡す形（URL は 1 回だけ・期限つき）

## 結果

- 得たもの: 業種ごとの架空の店を誰でも触れる。お金・メール・個人情報がほかの人へ漏れず、毎晩きれいに戻る
- 失ったもの: デモの店ではメールアドレスの入力がどれも来訪者のアドレスに置き換わる（`@` を含む 1 行の値はまるごと置き換わるので、1 行の欄に `@` を含む文を書いた場合も置き換わる）。毎晩の戻しの間（数十秒〜数分）は店が開けないことがある。売れる数の戻しは押さえた分だけ数を足すので、1 日の中では台本の在庫・席より多く売れる（毎晩の戻しで消える）。デモの店では外へ送る App を試せない
