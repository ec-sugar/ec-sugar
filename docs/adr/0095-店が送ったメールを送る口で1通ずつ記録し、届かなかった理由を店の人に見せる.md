# 0095 店が送ったメールを送る口で 1 通ずつ記録し、届かなかった理由を店の人に見せる

状態: **採用**（2026-11-11。作ることを決めた〔3 つ目。お店の人向けのガイドの「困ったとき」で「メールが届かない → サーバーの人に」としか書けなかった〕。形と細部は作りながら決めて下に書いた）。ADR 0010（個人情報の暗号化）・0042（運営の様子）・0043（壊れたら知らせる仕組み）・0086（デモの店のメール）・0087（処理を追う ID）・0089（Outbox）の上に置く

## 要点（先に）

1. **記録は店の DB の新しい表 `mail_records`**（今の `sent_mails` は広げない）。注文の知らせのほか、会員のログインのコード・メールの変更・会員の守りの知らせ・App のメール・試しのメールを 1 通 1 行で
2. **書くのは送る口だけ**: Laravel の Mailer を差し替え（`RecordingMailer`）、実際に送る所（`sendSymfonyMessage`）で「送っている → 送った・送れなかった」を書く。どのメールかの札は、メールのクラスに付けたトレイト `RecordsMail` が送る直前の `MessageSending` で結ぶ（デモの店はその前に止まる）
3. **送れなかった理由は決まった語と SMTP の番号だけ**（`rejected`・`temporary`・`auth`・`connection`・`timeout`・`error` と `550`・`5.1.1`）。例外の文・SMTP の応答の文・本文・秘密は残さない。**宛先（JSON）と件名は店の鍵で暗号化**し、最初の宛先はブラインドインデックス（お客さんの台帳の `email_index` と同じ値）
4. 管理画面は「設定 › 記録 › メールの記録」。一覧と 1 通は閲覧から（宛先は返さない）、宛先と試しのメールは運用から。古い記録は 90 日で消す

## 文脈

- 送った記録が残っていたのは、注文の知らせ（`sent_mails`。「同じ注文の同じ知らせを 1 回だけ」の印で、状態は `sending`・`sent` だけ）と、App ごとの「送ったか」の印（`shop_notify_notices`・`newsletter_deliveries`・`cart_reminders`・`line_messages`・予約の `reminded_at`・会員ランクの `noticed_at` など）だけだった。会員のログインのコード・メールの変更の知らせ・再入荷・お問い合わせの受付と返信・ギフトカード・チケット・抽選・定期便などの多くは、送ったかどうかが店の人に見えなかった
- 送れなかった時はどこにも見えなかった: 注文の知らせは送った印の行のロックの中（トランザクション）で送るので、SMTP が断ると印の行ごと巻き戻り、記録が消える。キューの仕事がやり直し（5 回）の後に失敗すると、中央の `failed_jobs` と壊れたことの記録（`incidents`。例外のクラスと場所だけ）に残り、オーナーだけが運営の様子で見る。店の人（スタッフ）は理由も、どのメールが届かなかったかも分からなかった
- 送る所は 30 か所ほどに散らばっている（核の注文の知らせ・会員の 3 つ・App の 16 のメールのクラス）。1 か所ずつ記録を書くと、書き忘れが必ず出る

## 決めたこと

### 表（`mail_records`、店の DB）

- 種類（`<core か App の名前>.<何のメールか>`。形を CHECK で）・件名（暗号化）・状態（`sending`・`sent`・`failed`）・理由の語・SMTP の応答の番号（200〜599）と拡張の状態の番号（`5.1.1` の形）・試した回数・宛先（To・Cc・Bcc を 20 件まで。暗号化した JSON）・最初の宛先のブラインドインデックス・宛先の数・関係する注文の ID・送ったキューの仕事の ID・処理の ID（`trace_id`。ADR 0087）・作った時刻・最後に直した時刻・送った時刻
- 状態と時刻・理由の組は CHECK で守る（送ったなら送った時刻がある、送れなかったなら理由がある）
- 注文の ID に外部キーを付けない（記録が送ることを止めないように）。中央の表は使わない（宛先は店の鍵でしか暗号化できない。ADR 0010）
- **`sent_mails` を広げなかった理由**: あれは「同じ注文の同じ知らせを 1 回だけ」の印（注文と種類の一意・注文の ID は必須・送った印の行のロック）で、送れなかった時は巻き戻って消える形が冪等の守りの一部になっている。記録は「何が起きたか」を残す別の役なので、別の表にした。注文の画面の「メールの送信の履歴」は今のまま `sent_mails` を出す
- 状態（取引・在庫・お金）でなく、監査の源泉でもない「送ったか」の記録なので、連鎖のロックとイベントは使わない（conventions 3 の例外の一覧に足した）

### 書き方（送る口）

- `CoreServiceProvider` が `mail.manager` を `RecordingMailManager` に差し替え、Mailer を `RecordingMailer` にする。送り方（transport）は設定のまま（テストの `array` もそのまま読める）
- **札**: メールのクラスに `App\Core\Mail\RecordsMail` を付け、`recordKind()` で種類を返す。関係する注文は送る所で `->forTransaction($id)`。札は Laravel がメールの中身の値に添え（`additionalMessageData`）、送る直前の `MessageSending` で送るメールに結ぶ（`WeakMap`。プロセスの中だけで、メールが消えれば消える）。札の無いメール・店の文脈の外のメールは記録しない。札を結んだ店と送る時の店が違えば書かない
- **デモの店との食い違い**: デモの店を止める受け手と札を結ぶ受け手を **1 つの受け手**にして、止めるかを決めた後に結ぶ（受け手の順に頼らない）。止めたメールは送る口へ来ないので、記録に「送った」と出ない。来訪者の受け箱（ADR 0086）は今のまま
- `MessageSent` は使わなかった: 送る口が成功の後に書けば同じで、Laravel には「送れなかった」の出来事が無いので、送る所の例外を見る形にそろえた（例外は記録した後にそのまま投げ直す。キューのやり直し・呼んだ所の扱いは今のまま）
- **トランザクションの中で送るメール**（注文の知らせ）: 店の接続がトランザクションの途中なら、同じ設定の別の接続（`tenant_mail_records`）で書く。送れずに巻き戻っても「送れなかった」が残り、相手のトランザクションを壊さない（ADR 0043 の `central_incidents` と同じ考え）。別の接続は店の文脈が始まる・終わるたびに捨てる（ほかの店・作り直した店の DB へ持ち越さない）
- **キューのやり直し**: 処理しているキューの仕事の ID（`JobProcessing` で覚え、`JobProcessed`・`JobExceptionOccurred` で外す）を行に持ち、同じ仕事の同じ種類・同じ宛先の「送れなかった」の行があれば、新しい行を作らずに直して試した回数を 1 足す。一時的に断られて 2 回目で送れたメールは 1 行の「送った（2 回）」になり、一覧が赤い行で埋まらない
- **記録が失敗しても送ることは止めない**（例外を飲み、ログに例外の種類だけ）

### 送れなかった理由

- 例外とその前の例外のうち、送る口の例外（Symfony の `TransportExceptionInterface`）の番号と文を**読むだけ**で、残すのは語と番号: 504・530・534・535・538 か「認証に失敗」の文は `auth`、ほかの 5xx は `rejected`、4xx は `temporary`、「時間切れ」は `timeout`、「つながらない・閉じた・STARTTLS」は `connection`、ほかは `error`
- 文を残さない理由: SMTP の応答の文には宛先のアドレス（`<nobody@example.com>: Recipient address rejected`）、認証の失敗の文には送り口のユーザー名が入る。伏せ字は漏れる（ADR 0043 と同じ判断）。番号と語で、店の人が「アドレスの誤り」か「サーバーの設定」かを見分けるには足りる
- 1 時間を過ぎても「送っている」のままの行は、画面で「送れたか分からない」と出す（処理役が送る途中で落ちた時。運営の様子の送りかけのメールと同じ 1 時間）。キューの仕事がやり直しの全部で落ちた時は、最後の「送れなかった」が残る

### 一斉の配信（メルマガ）

- **本番の配信は送れなかった分だけを 1 通ずつ残す**（`recordBulk()`）。送った数はメルマガの App が配信ごとに数えて画面に出している（`newsletter_deliveries`）。全部を残すと、1 回の配信で購読者の数だけ行が増え（1 万人なら 1 万行）、90 日で数十万行になる。ホストの置き場の上限の考え方（ホストするなら制限は要る）に合わせ、店の人が要る「届かなかった人」だけを残す。試しのメールは 1 通ずつ残す

### 管理画面

- 「設定」の「記録」のまとまりに「メールの記録」（`settings-mails`）。一覧の型（絞り込みの箱に状態と種類、件数、50 件ずつ）で、送れなかったものは赤い札、この 7 日に送れなかったものがあれば上に知らせ。「開く」で 1 通の様子（理由の説明・SMTP の番号・試した回数・時刻）と、関係する注文・お客さん（宛先のブラインドインデックスが台帳の `email_index` に合えば）へのリンク
- 経路: `GET /api/tenants/{店}/mail-records`・`/{ID}`（閲覧から。宛先は返さない）、`/{ID}/personal`（運用から。お客さんの「名前と連絡先」と同じ段階。見た事実を中央の監査ログ `operator.personal_data_viewed` に、宛先は残さない）、`POST /mail-records/test`（運用から）
- **試しのメール**: ログイン中の運営のアドレスへ、お客さんへのメールと同じキューを通して 1 通（`SendShopTestMail`。宛先を入力で受け取らない＝他人へ送れない。積んだ中身は `ShouldBeEncrypted`）。運営ごとに 10 分に 3 通・店で 1 日 20 通まで（核の `Throttle`。数えてから比べる）。送れなかった時は記録に理由が出るので、仕事は失敗にしない（店の人の試しで壊れたことの知らせを鳴らさない）。店の人が `MAIL_*` の設定の誤りを自分で見つけ、理由をそのままサーバーの人に伝えられる
- 種類の名前は、核のメールは画面の言葉（「ご注文の確認」「会員のログインのコード」など）、App のメールは App の名前（「App「再入荷のお知らせ」」）。細かい違いは件名で分かる

### 掃除

- `mail-records:prune`（毎日 04:15。カートの掃除の後）が、店ごとに 90 日より前の記録を 1,000 件ずつ消す。作り直し中の店（`Tenant::serving`）には入らない

## 採らなかった案

- **`sent_mails` を広げる**: 上の理由（冪等の印と記録の役が違う）
- **中央の 1 表に置く**: 宛先を店の鍵で暗号化できない。店の境界（CONCEPT 7.2）
- **送る所ごとに書く**: 30 か所で書き忘れが出る。送る口の 1 か所にし、メールのクラスの札の付け忘れはテスト（`MailRecordCoverageTest`）が落とす
- **`MessageSending` で「送っている」を書く**: `MessageSending` は「最初に答えた受け手で止まる」形で、デモの店の止めと受け手の順が絡む。止めた後に書けば、止めたメールを「送っている」で残してしまう
- **相手に届いたか（返ってきたメール・開いたか）まで見る**: 送り口（借りたサーバーのメールの箱・メールのサービス）ごとに仕組みが違い、外のサービスの Webhook が要る。今は「送り口が受け取った」まで

## 結果

- 得たもの: 店の人が、送ったメールと届かなかった理由を自分で見られ、試しのメールで送る道を確かめられる。ガイドの「メールが届かない」に手順を書ける。送れなかったことがトランザクションの巻き戻りやキューのやり直しで消えない
- 失ったもの・気をつけること: メール 1 通につき店の DB に 1 行と 2 回の書き込み（注文の知らせは別の接続を 1 本開く）。「送った」は送り口が受け取ったという意味で、迷惑メールのフォルダに入ったか・返ってきたかは分からない。App を作る人は、メールのクラスに `RecordsMail` を付ける（付けなくても送れるが記録に出ない。自社の App は全部付けた）
- 残したこと: App のメールの関係する注文（今は核の注文の知らせだけ `forTransaction` を付けた。チケット・予約・ダウンロード・ギフトカード・抽選・定期便は注文の ID を持っているので、送る所で付ければ注文へ移れる）、返ってきたメール（バウンス）の取り込み、運営の様子の「送りかけのまま残った知らせのメール」を `mail_records` の数にするか（今は `sent_mails` のまま）、処理を追う画面（ADR 0087）に `mail_records` を並べるか
