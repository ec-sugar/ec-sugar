# 0022 SaaS 版の店は Stripe Connect でつなぐ

状態: 採用（2026-10-28）。ADR 0019 の「秘密鍵と Webhook の署名の鍵はテナントごと」と「Connect は後で」を、SaaS 版について置き換える（パッケージ版は 0019 のまま）

## 文脈

で、店が自分の Stripe の秘密鍵と Webhook の署名の鍵を管理画面に貼る形を作った。本物の Stripe（サンドボックス）で通しで動いたが、実際に設定してみて分かった:

- 鍵を 2 つコピーして貼る、Stripe の画面で送り先を作って通知を 3 つ選ぶ、は開発者でない店主には難しすぎる（手順は、お客さんにも分かる形で説明できなければならない）
- 署名の鍵の欄が空だと、ブラウザが保存を黙って止める。コピーの順を間違えると鍵が上書きされる

Stripe には、SaaS のプラットフォームが店の Stripe アカウントを作って「つなぐ」仕組み（Connect）がある。店主は Stripe の登録の画面で事業の情報と口座を入れるだけで、鍵も通知の登録も要らない。

## 決定

- **SaaS 版の店は「Stripe とつなぐ」ボタンで Stripe Connect の連結アカウントにする**。パッケージ版（運営がいない → ADR 0046 で「運営＝店の持ち主」と読み替え。ここでの意味は「Stripe のプラットフォームを持つ運営がいない」）は鍵を貼る形（ADR 0019）を残し、両方を選べる作りにする
- **売り手は店**（マーチャントオブレコード）。支払いは店の連結アカウントへの**ダイレクト支払い**（Checkout を `Stripe-Account` で店のアカウントに作る）。お金は店の口座へ直接入り、運営は預からない（資金移動業にならない。0019 の考え方のまま）
- **Stripe の手数料は店が払い、損（返金・不正の申し立てで残高がマイナスになったとき）は Stripe 側が負う**（`fees_collector: stripe`、`losses_collector: stripe`）。店は自分の Stripe のダッシュボードを持つ（`dashboard: full`）
- **Accounts v2 の API** を使う（Stripe が今すすめている形。入れた部品 stripe-php 22.0.0 と同じバージョン 2026-09-30.endive で呼べる）。v2 の呼び出しは 1 つのドライバに閉じ込め、変わっても直す場所を 1 か所にする
- **登録の画面は Stripe の画面へ移る**（Account Links）。管理画面に Stripe の JavaScript を読まない（管理画面の CSP は今のまま）
- **運営の取り分（支払いごとの手数料）は今は取らない**。収益モデルが決まったら `application_fee_amount` で入れられる作りにする（よくある設置型の EC と同じく、店の売上から決済の手数料を取らない方向。Stripe の紹介料は候補）
- 運営の Stripe の鍵（プラットフォームの秘密鍵）と、連結アカウントの通知の署名の鍵は、**サーバーの秘密（環境の変数）に置き、DB や画面には置かない**。置いていなければ（パッケージ版）Connect は使えず、鍵を貼る形だけになる
- 連結アカウントの通知は、**運営の 1 か所（中央のホスト）で受け**、通知の `account`（店の Stripe の ID）から店を引いて、その店のテナントの文脈で処理する。店の Stripe の ID と店の対応は中央 DB に置く（個人情報でも秘密でもない）

## 結果

- 得たもの: 店主は鍵に触れない（漏らす・貼り間違えるがない）。通知の登録も運営が 1 回だけ。店ごとの Stripe の画面と入金は店のもの
- 失ったもの・気をつけること:
  - 運営のプラットフォームの鍵は、全部の店の Stripe アカウントを操作できる強い鍵になる。漏れると全店に届く（脅威モデルに足す。置き場はサーバーの秘密だけ、ログに出さない、入れ替えの手順を と並べる）
  - 中央で受けた通知から店へ入るので、「通知の店の ID → テナント」の引き当てを間違えると別の店の注文に触れる。引き当ては中央 DB の一意の対応だけで行い、通知の中身の取引の ID がその店の支払いの画面と合うことも確かめる（ADR 0019 の突き合わせのまま）
  - Stripe の Connect のプラットフォームの登録と審査が要る（本番の前に）
