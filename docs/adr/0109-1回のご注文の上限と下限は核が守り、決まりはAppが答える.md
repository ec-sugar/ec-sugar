# ADR 0109 1 回のご注文の上限と下限は核が守り、決まりは App が答える

- 状態: 採用
- 日付: 2026-11-19
- 関わるもの: （最低購入金額と数の制限）、[ADR 0025](0025-プラグインは登録簿に載せ、店ごとに使う・使わないを選ぶ.md)（App の口）、ADR 0080（売り方を押さえる口）、[ADR 0093](0093-外に約束する口を決め、壊すときはAPIのバージョンを上げてCHANGELOGで知らせる.md)（互換の約束）

## 決めたこと

**「この商品は 1 回のご注文で 2 点まで」「ご注文は商品の合計 ¥3,000 から」は、決まりを App が答え、守るのは核がやる。**

| もの | 役目 |
|---|---|
| `Core\Plugin\Contracts\PurchaseLimitProvider` | App が答える口。`perOrder()`（商品ごとの 1 回の上限。**まとめて聞く**）と `minimumSubtotal()`（商品の合計の下限） |
| `Core\Plugin\Services\PurchaseLimits` | この店で使っている App の口を束ねる。2 つの App が答えたら**きびしい方**（上限は小さい方、下限は大きい方） |
| カート（`CartService`）・注文の確定（`PlaceOrder`）・1 品の注文（`PlaceSingleOrder`） | 守る所。カートの行に理由を出し、注文の確定は錠の中で読み直して断る |

決まりの中身（どの商品がいくつまでか、下限はいくらか）と、それを入れる画面は App（`plugin-purchase-limits`）が持つ。核に「購入の制限」の表も設定も無い。

## 決まり

1. **上限は商品ごと・1 回のご注文ごと**。同じ商品を種類やオプションの違いで何行に分けても、合わせて数える（行ごとに数えると、種類を変えるだけで抜けられる）。行の順に上限を分け、超えた行を止める
2. **「1 人 1 点まで」ではない**。注文を分ければまた買える。人ごとの制限は、会員でないお客さん（メールを変えれば別人）には守れず、守れない決まりを画面に出すことになるので、この口では扱わない
3. **下限は、今買える商品の合計（値引き・送料・ポイントの前）で比べる**。値引きの後で比べると「クーポンを入れたら注文できなくなった」が起き、お客さんに理由が伝わらない。売り切れなどで止まっている行は数えない
4. **下限はカートを通る注文だけ**。App の申し込みの画面から作る 1 品の注文（定期便・チケットなど）には掛けない。上限は、お客さんの申し込みなら 1 品の注文にも掛ける。**仕組みが作る注文（定期便の 2 回目から・抽選の当選）には掛けない**（申し込みの時の約束なので）
5. **決まりを読めない時は売らない**。App が例外を投げた・0 以下の上限や負の下限を答えた時、核は注文を受けない（カートの行に「ただいまご注文を受けられません」）。売り方を押さえる口（`SaleHolds`）が「落ちたら押さえていない扱い」なのとは逆に倒す。あちらは落ちるとほかの App の商品まで止まるが、こちらは決まりを付けた店だけが呼ばれ、落ちた時に売ってしまうと決まりそのものが破られるため。読めなかったことは記録に残し、壊れたら知らせる仕組み（ADR 0043）に乗る
6. **核は App の答えを信じない**。頼んでいない商品の答えは捨て、上限は 999・下限は 1 億円で絞る
7. **お客さんの手間を増やさない**。決まりの無い店・商品では何も変わらない。決まりに当たった時は、カートの行に「この商品は 1 回のご注文で 2 点までです。数を減らしてください。」、合計の欄に「ご注文は商品の合計 ¥3,000 から承ります（あと ¥1,200）。」と、直し方が分かる文を出す。数の入れ物の上限（`maxQuantity`）も決まりに合わせるので、テーマはそのままで超えた数を選べなくなる

## 見直しで足したこと（2026-11-19。取り込みの前の見直し）

- **定期便の数を後から増やす道でも上限を見る**（App の側で `PurchaseLimits::perOrder` に聞く）。申し込みの時は 1 品の注文が見ているが、マイページで数を増やすと次の回から上限を超えて届く道があった。減らす・届け先だけ変えるのは、決まりを読めない時も通す（お客さんを閉じ込めない）
- **抽選販売の商品は、抽選の「1 人が申し込める数」が決まり**。当選の注文は仕組みが作るので、この口の上限は掛からない。同じ商品に両方を付けた時は抽選の数が効く
- **App の答えが整数でない時（文字列・真偽・小数）も読めない扱い**。比べ方しだいで「上限なし」に化けるため
- **上限の枠を使うのは買える行だけ**。売り切れなどで止まっている行は、下限と同じく数えない
- カートの読み出しは、上限と下限を 1 回の問い合わせで聞く（`PurchaseLimits::forCart`）。商品の無いカートでは App に聞かない
- **残したこと**: カートに入れる時は上限を見ない（カートの画面で初めて知らせが出る。確定では守る）。役務だけ・無料の品だけの注文は、下限のある店では届かせる手が無い（下限を使う店は、役務と無料の品を別に考える。App の README に書く）。決まりを読めない間は、画面を開くたびに記録が出る（売り方を押さえる口と同じ形）。カートを通らない注文のテストは `place` だけで、来店の品・送らない品の 2 つの入口は同じ部品を呼ぶことをコードで確かめた

## テーマとの約束

- 上限は行の `notice`・`purchasable`・`maxQuantity` に入る。**テーマが足すものは無い**
- 下限の一言は核の部品 `<x-storefront::minimum-notice :cart="$cart" />`。カートの合計の欄に置く（公式テーマ 4 つは置いた）。置かないテーマでも、注文に進もうとした時にカートへ戻して同じ文を出す
- 付け足しなので、テーマ API とプラグイン API の番号は上げない（ADR 0093）

## 選ばなかった案

- **核に「最低購入金額」の設定を持つ**: 使わない店にも設定と画面が増える。核を小さく保つ（ADR 0107）
- **App がカートの行に直に理由を書く（売り方を押さえる口を使う）**: 押さえは「この商品は今は売らない」で、数によって変わる答えを返せない。カートの中身を App に渡すと、App ごとに数え方が食い違う
- **App がカートの画面と注文の確定をそれぞれ受け手で断る**: 守る所が 2 つに分かれ、片方を付け忘れた App が「画面では買えないが、直に送ると買える」になる。守る所は核の 1 か所にし、App は決まりを答えるだけにした
- **人ごとの上限（1 人 1 点）**: 上の決まり 2 のとおり。要るなら、会員だけに売る商品（ADR 0079）と組み合わせる形で別に決める

## 残る危険

- 注文を分ければ上限を超えて買える（決まり 2）。転売への守りとしては弱い。強く守りたい品は抽選販売（ADR 0080）を使う
- 口を持つ App が壊れると、その店は注文を受けられなくなる（決まり 5）。App を止めれば戻る
