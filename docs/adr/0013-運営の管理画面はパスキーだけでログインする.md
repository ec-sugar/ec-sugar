# 0013 運営の管理画面はパスキーだけでログインする

状態: 採用（2026-10-27）。一部置き換え（→ ADR 0031: 最初の運営の登録のリンクの期限を 24 時間に。→ ADR 0038: 登録のリンクを出すのは CLI だけでなく、オーナーのメンバーの画面・回復用のコード・メールでの戻し〔24 時間待ち〕からも）

## 文脈

管理画面の最初のバージョンは運営（自社）だけが使い、商品・在庫・取引というテナントのデータを触る。
運営アカウントは全テナントに立ち入れる、システムでいちばん強い権限になる。
パスワード ＋ TOTP はフィッシング（偽の管理画面にコードごと入力させる）に弱く、パスワードの漏洩・使い回しの面も残る。
管理画面の作り方（Vue の SPA ＋ API か Inertia か）も未決だった（CONCEPT 13 章）。

## 決定

- **管理画面は Vue の SPA ＋ API**（ADR 0004 のとおり、画面も API 経由でしか触れない）。画面は片 C で載せる
- **ログインはパスキーだけ**（WebAuthn、本人確認つき、discoverable credential）。パスワードの列は持たない。パスキーはドメインに結びつくので、偽サイトでは使えない
- 実装は Laravel 公式の `laravel/passkeys`（0.2 系。1.0 前なので `^0.2.1` で固定し、上げるときは差分を読む）。Fortify は使わない（パスワード・TOTP の機能を使わないため。依存が 4 つ減る）。パッケージのルートは使わず、`routes/admin.php` で自分のミドルウェアと監査を付けて登録する
- **運営アカウントは中央 DB**（`operators`）。消さずに止める（`disabled_at`）。止めた運営は次のリクエストでセッションごと締め出す
- **最初のパスキーは CLI が発行する登録トークンで登録する**（`php artisan operator create|enroll`）。30 分で失効、1 回限り、保存は SHA-256 だけ、URL の断片（`#`）で渡す。Web からは発行できない。パスキーを失くしたら同じ経路で再発行（`--revoke` で既存のパスキーを消す）→ ADR 0031（最初の運営は 24 時間）・ADR 0038（オーナーのメンバーの画面・回復用のコード・メールでの戻しからも出す）で一部置き換え
- **管理画面は別ホスト**（`ADMIN_DOMAIN`）。セッション Cookie は別名・ホスト限定・SameSite=Strict、無操作 30 分、ログインから 12 時間で強制的にログインし直し。接続元の制限（`ADMIN_ALLOWED_IPS`）は本番で空なら閉じる側に倒す
- **パスキーの追加・削除は直前の再確認（パスキー）が要る**（5 分）。最後の 1 本は削除できない。ログイン・登録・再確認は IP ごとに 1 分 10 回まで
- **中央の監査ログ**（`audit_events`）: 追記専用（トリガー）＋ ハッシュ連鎖（APP_KEY から HKDF で派生した鍵の HMAC）。ログインの成功・失敗、パスキーの増減、登録トークンの発行、セッションの打ち切りを残す。片 B でテナントへの立ち入りも残す

## 結果

- 得たもの: パスワードの漏洩・使い回し・フィッシングが成り立たない。運営の操作がすべて改竄を検知できる形で残る。認証の入口が 1 か所（管理画面のホスト）に集まる
- 失ったもの: 運営はパスキーに対応した端末が要る。パスキーを全部失くすと、サーバーで CLI を叩ける人しか復旧できない（運営ごとに 2 本以上の登録を勧める）→ ADR 0038 で置き換え（回復用のコードと、メールで申し込んで 24 時間待つ戻り方を足した）。`laravel/passkeys` は 1.0 前で、WebAuthn の依存（Symfony serializer など 17 個）が増えた
- APP_KEY を回すと監査ログの連鎖の検証鍵とパスキーのユーザーハンドルが変わる。回す前に `PASSKEYS_USER_HANDLE_SECRET` を固定し、監査ログの鍵の引き継ぎ手順を作る（未実装）
- 管理画面のホストを変えると登録済みのパスキーは使えなくなる（WebAuthn の仕様）
