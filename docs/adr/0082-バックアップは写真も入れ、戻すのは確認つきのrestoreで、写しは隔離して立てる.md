# 0082 バックアップは写真も入れ、戻すのは確認つきの restore で、写しは隔離して立てる

状態: **採用**（2026-11-06。作ることと形を先に決め、細部は作りながら決めて下の「作って決めたこと」に書いた。番号は取り込みの時に振り直す）。ADR 0029（ステージング）・0030（インストーラーと ec-sugar）・0043（壊れたら知らせる）・0052（段 1 の本番）の上に足す。置き換えるものは無い

## 要点（先に）

1. **`ec-sugar backup` は写真などのファイルも入れる**（storage の下を 1 つの tar に。DB の dump と同じ置き場・同じ名前の組）。**残すのは DB が 7 日・写真が新しい 3 世代**（2026-11-06）。中身の指紋（`SHA256SUMS`）を残し、取る前に空き容量を確かめる。更新の前のバックアップは DB だけ（更新でファイルは変わらない）。`--no-files` で DB だけにもできる
2. **`ec-sugar restore <名前>`** で中央と全部の店の DB と写真などのファイルを戻す。前のバージョンが無くても使える（`rollback --restore-backup` はロールバックと一緒の時だけ）。誤って本番に流さないよう、**戻す前に何も変えずに確かめ**（そろっているか・指紋・名前）、**何を戻すか・このサーバーがどれかを見せて名前を打たせ**、**戻す前の状態のバックアップを取る**。途中で止まったら、どこまで戻ったか・止まった所・戻し方を出す
3. **隔離した写し（`--isolated`）**: 本番のバックアップを使い捨ての VM に戻して確かめる形。app・キュー・定期の処理を外へ出る網から外し（compose の重ね書き `docker-compose.isolated.yml`）、定期の処理を止め、アプリの側でも Http の口・Stripe の口を閉じ、メールは Mailpit か送らない、ショップにタグを差し込まない、管理画面に帯を出す。env の外のサービスの鍵を空にする。**元に戻す道は作らない**（写しは VM ごと消す）。Cloudflare Tunnel の形のサーバーは断る
4. **本番の鍵は写しへ持ち込まない**。写しの `.env` は写しのインストーラーが作り直し、持ち込むのは **APP_KEY だけ**（店の個人情報の鍵を開けるのに要る。`--app-key-file` で root だけが読むファイルから。画面・引数・記録に出さない）
5. 戻した後の確かめは `ec-sugar restore-check`（`operations:restore-check`。店ごとの取引・台帳の行と合計・記録の数〔と鎖〕・写真の数と見つからないファイルの数。読むだけで本番でも流せる）。コマンドの説明は [docs/install.md](../install.md) の「バックアップから戻す」

## 文脈

- 外からの見直しの総評（2026-11-06）: 「バックアップからの復元、更新失敗時の復旧、通知後の対応手順を実地で確かめる」
- 今までの戻し方は `rollback --restore-backup` だけで、前のバージョンが無いと使えず、写真は戻らない（バックアップに入っていない）。サーバーが壊れて新しい機械に入れ直した時に、戻す道が無かった
- 訓練は本番のバックアップを別の機械（使い捨ての VM）に戻して行う。写しには本番の個人情報と、店の DB に入った店の鍵（Stripe・LINE・Slack の Webhook）が載り、APP_KEY があれば開ける。写しが本物のお客さんにメールを送る・本物の Stripe に請求する・定期便の請求を回す・本番の計測にページビューを送ることを、設定の書き忘れに頼らずに止める必要がある

## 決定

### 1. バックアップ

- 1 回分の置き場（`/srv/ec-sugar/backup/<日時>/`、root の 0700、中は 0600）に: 店ごとと中央の DB の dump（`pg_dump -Fc`）・ロール（`globals.sql`）・**写真などのファイル（`storage.tar`）**・**指紋（`SHA256SUMS`）**・`manifest`（時刻・理由・バージョン・DB の一覧・店の DB の前置き・店の数・ファイルの有無・管理画面のホスト）・終わった印 `.complete`
- ファイルは storage の名前つきの置き場の下を、画面の下書きと控え（`framework`）と記録（`logs`）を除いて tar に（店ごとの置き場 `tenant…/` も、これから入るダウンロード販売のファイルも同じ置き場なので入る）。app のコンテナが動いていれば中で、止まっていれば同じイメージ・同じ置き場の使い捨てで。tar は読めるかを目次で確かめる
- 取る前に、DB の大きさとファイルの大きさの 1.1 倍と 64 MB が置き場の空きに収まるかを確かめ、足りなければ取らずに失敗（最後のバックアップの結果に「失敗」が残り、運営の様子とメールで知らせる。ADR 0043）
- **世代**（2026-11-06。DB は 7 日・写真は 3 日）: DB の dump とロールは今の形と同じ 7 日分（いちばん新しいもの・戻すのに使っているものは残す）。写真などのファイルの tar は、tar を持つ世代の新しい方から 3 つだけ残し（毎朝 1 回なので 3 日分ほど。`EC_BACKUP_FILES_KEEP`）、古い世代からは tar だけを外す（指紋の行を外し、manifest の `files` を `none` に直すので、外した世代もそのまま戻せる＝DB だけ）。戻すのに使っているバックアップの tar は外さない。終わりに大きさと時間を出す
- 更新の前のバックアップは DB だけ（更新でファイルは変わらない。写真が多いと毎回の更新が遅くなり、置き場を倍に食う）

### 2. 戻す（`ec-sugar restore <名前> [--isolated] [--app-key-file <ファイル>] [--no-files] [--yes]`）

1. 何も変えずに確かめる: `.complete`・中央の dump・ロールがある、DB の名前がこのサーバーの店の DB の前置きと合う、**指紋が合う**（指紋の無い前のバックアップは注意を出して DB が読めるかだけ）、指紋の行が決まった名前だけで dump が全部載っている、tar の中の名前に storage の外を指すもの（絶対の道筋・`..`）・制御文字が無く、リンク（シンボリック・ハード）が無い（名前の文字は日本語なども通す。これから入るダウンロード販売のファイルの名前のため）
2. 確認: 戻すバックアップ（時刻・理由・バージョン・管理画面のホスト・店の数・ファイルの大きさ）とこのサーバー（管理画面のホスト・本番かステージングか・入口の形・今の店の DB の数・バージョン）を見せ、本番の形なら「最後の手段」と赤で出し、**バックアップの名前を打たせる**。端末でなければ `--yes` が要る。別のサーバーで取ったバックアップを隔離せずに戻す時・バックアップのバージョンが今より新しい時は注意を出す
3. 戻す前の状態のバックアップを取る（取れなければ何も変えずに止まる）。名前は終わりと失敗の時に出す
4. app・入口・キュー・定期の処理を止める → （隔離なら隔離の設定・印、鍵のファイルがあれば APP_KEY）→ ロール → 中央の DB → 店の DB（`pg_restore --clean --if-exists --create`）→ 写真などのファイル（一度横に広げ、広げられた時だけ入れ替える）→ マイグレーション（バックアップが前のバージョンの時に今の形へ）→ 起こしてヘルスチェック → 戻した後の数（`restore-check`）
- **写真の無い世代**（古い世代・更新の前のバックアップ）を選んだときは、`--no-files` と同じに DB だけを戻し、今の写真などのファイルは残す。確認の文に「このバックアップには写真などのファイルがありません … DB だけを戻し、今の写真などのファイルはそのまま残します」と出す（DB と写真の時点がずれるので、写真の見つからない商品は `restore-check` に出る）
5. 途中で止まったら（`ec_restore_fail`）: 戻した所（「DB ec_central・DB ec_t_…」）・止まった所・app などは止まったまま・直し方 3 つ（同じ restore をもう一度＝初めから同じ所へ戻る／戻す前のバックアップで戻す／今のまま起こす）を出す
- **ロール**: `globals.sql` から、店ごとの DB のロールの作成・属性とパスワード・アプリのロールへの付与の行だけを、決まった形の行だけ選んで流す。管理者（`ec`）・アプリ（`ec_app`）・組み込み（`pg_*`）の行は流さない（写しのサーバーのパスワードを本番の値で上書きしない）。強い属性（SUPERUSER・CREATEROLE・CREATEDB・REPLICATION・BYPASSRLS）を付ける行があれば、すり替えを疑って止める。もうあるロールは作らない
- バックアップの後に作った店の DB は消さない（中央の店の一覧から外れる。名前を出して知らせ、中身を確かめてから人が消す）
- `rollback --restore-backup` も同じ部品（確かめ・ロール・DB・止まった時の出し方）を使う。こちらは今までどおり DB だけ（ファイルまで戻すのは restore）

### 3. 隔離した写し（`--isolated`）

- **網**: `state/isolated` の印があると、`ec-sugar` の compose の呼び方（`ec_dc`）が `docker-compose.isolated.yml` を重ねる。app・queue・scheduler の網を内側（internal。db・redis・Mailpit だけ。外へ出られない）だけに置き換える（compose の `!override`。網そのものの形は変えないので、網を作り直さない・ホストの防火壁の網の一覧も変わらない）。nginx から PHP へは網でなくソケットなので、管理画面とショップはそのまま開ける。定期の処理のコンテナは眠るだけにする（起こしておく。ヘルスチェックと更新の形を変えない）。印があるのに重ねるファイルが無いバージョン（前のバージョンへロールバックした）では、compose を流さずに止める（隔離が外れないように）
- **アプリ**（`App\Core\IsolatedCopy`。印は env と compose の環境変数の両方の `EC_SUGAR_ISOLATED`）: Http の口は送る前に `ConnectionException` で断る（偽の答え〔`Http::fake`〕より外側に積む。網が届かない時と同じ失敗の道に乗る）・Stripe の口（`StripeApi::client`）は送らない・メールは Mailpit（ホストが mailpit の smtp）か送らずに捨てる（array。記録〔log〕には書かない）・ショップにタグの App を差し込まない（写しを開いた人のブラウザから本番の計測へ送らない）・管理画面の上に帯（`/auth/me` の `isolated`）
- **env**: `EC_SUGAR_ISOLATED=true`、メールは Mailpit（ステージングの形）か array（本番の形）、`PAYMENT_LIVE_KEYS_ALLOWED=false`、外のサービスの鍵（Stripe の運営の鍵と通知の署名の鍵・メールの送り先のサービス・Slack・ログの送り先・S3）を空に
- 印を消す道は作らない。写しは確かめ終わったら VM ごと消す（バックアップと APP_KEY のファイルも一緒に消える）
- Cloudflare Tunnel の形（答えの `FRONT=tunnel` か、トンネルのトークンがある）のサーバーは写しにしない（外から開ける形＝本番の見込み）。写しは `MODE=staging`・`FRONT=caddy` で入れる

### 4. 鍵

- 写しの `.env` は写しのインストーラーが作り直す（DB と Redis のパスワード・Mailpit の画面のパスワード・入口の証明書は写しのもの）。本番の `.env` を写さない
- APP_KEY だけは持ち込む（店の鍵〔中央の `data_key`〕と店の DB のロールのパスワードが APP_KEY で包まれていて、無いと店に入れない）。本番から root だけが読むファイルに、画面に出さずに直に流し込み（手順書）、`--app-key-file` で渡す。ほかの利用者から読めるファイルは断る。形（`base64:` で始まる 44 文字）が違えば中身を出さずに止める
- 運営のパスキーは管理画面のホスト（rpId）に結びつくので、本番のパスキーは写しで使えない。写しでは `ec-sugar operator enroll <メール>` で写しのホストのパスキーを足す（写しの中央の DB にだけ載り、VM ごと消える）

## 作って決めたこと（2026-11-06）

- 戻す部品は `deploy/lib/common.sh` に置いた（2,400 行を超えたが、分けると前のバージョンの道具の更新の道〔`ec_install_tools` が写すのは `ec-sugar` と `lib/common.sh` だけ〕で新しいファイルが入らず、新しい道具が起きない）。分けるのは、写すファイルの一覧を外から渡せる形にしてから
- 戻す前のバックアップの名前は「いちばん新しい名前」で探さず、取った時に覚える（`EC_BACKUP_LAST`）。別のマシンから写したバックアップの名前（日時）が、この機械の時計より先のことがある（手元の確かめで見つけた）
- 確認の前の DB への問い合わせには標準入力を渡さない（`docker compose exec` が標準入力を読み、先に打たれた答えを食べる。手元の確かめで見つけた）
- 指紋は `sha256sum`（無い macOS では `shasum -a 256`）。書き換えられないバックアップではない（root ならバックアップと指紋を両方書き換えられる）。壊れたものと、置き場の外で書き換えられたものを見つけるためで、書き換えられない控えは
- 戻した後の数（`operations:restore-check`）は管理画面の側（`app/Admin/Console`）。店に `initialize` で 1 つずつ入り、`finally` で閉じる。出すのは店の ID と件数と金額だけ。店に入れない（鍵が開かない）・台帳の合計が 0 でない・鎖が切れている（`--verify`）・写真のファイルが見つからない店があれば、終わりの番号を 0 でなくする
- 隔離の網の確かめは `docker/check-compose.sh` の 13（CI で毎回）、戻す道の通しの確かめは `docker/check-restore.sh`（手元の Docker で使い捨ての DB と置き場。**CI には入れない**。手元と訓練の前だけ。2026-11-06）
- 写しの VM を作る台本を正式に足すかは訓練の後に決める（今は手順書で CI の VM の台本を写して書き換える。2026-11-06）

## 結果

- サーバーが壊れても、新しい機械に入れ直してバックアップと APP_KEY から戻せる（写真まで）。前のバージョンが無くてよい
- 訓練は本番に触らずに、写しの VM で外へ何も出さずに行える
- バックアップは写真の分だけ大きくなる（写真は 3 世代、DB は 7 日分）。4 日より前の時点へ写真まで戻すことはできない（DB だけ）。空きが足りなければ取らずに知らせる。サーバーの外へのバックアップ（残り）と書き換えられないバックアップはまだ
