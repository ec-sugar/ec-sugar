# 0011 取引はフェーズの語彙と仕訳で表す

状態: 採用（2026-10-27）

## 文脈

物販・買取・定期・店舗・マーケット・仕事は状態機械がそれぞれ違う（CONCEPT 5.4）。縦ごとに状態の列挙を作ると、
帳票・通知・在庫・お金の処理が縦の数だけ分かれる。お金の流れも、物販は顧客 → 店、買取は店 → 顧客、
マーケットは顧客 → 決済代行 → 出品者と向きが違い、決済代行は未定（差し替え前提）。

## 決定

- **フェーズの語彙は 9 つで固定**（主 6: quote / agreement / payment / fulfillment / acceptance / settlement、横断 3: cancel / dispute / refund）。縦は新しいフェーズを足さず、主フェーズの遷移だけを `TransactionFlow` に書いて `TransactionFlows` に登録する。核が登録するのは即時物販（`sale`）だけ
- **横断フェーズの規則は核が持つ**: 取消は open の間どこからでも、紛争は入る前のフェーズを覚えて戻れる、返金は紛争中か完了後から。取消と返金で取引は終わる
- **お金の向きは取引の `payer` / `payee`**（customer か seller）。種類の定義が既定を決める
- **明細は合意の写し**。商品の行と調整行（値引き・送料・査定の減額など、負になりうる）を同じ表に持ち、合意後は書き換えない。金額を変えるのは提示（Quote）を採り直すときだけ。提示は何度でも、複数の出品者から来てよく、採られた出品者が取引の出品者になる
- **消費税は税率ごとに合計してから 1 回だけ丸める**（インボイスの記載に合わせる）。内税が既定、端数処理は取引ごと（既定は切り捨て）
- **Ledger は複式の仕訳**: 1 仕訳に 2 行以上、符号付きで合計 0（正 = 受け取る権利、負 = 払う義務）。口座は立場で表す（customer / seller / platform / provider / tax / withholding）。合意に入ると charge と tax を自動で立て、取消・返金・合意のやり直しで逆仕訳する。お金の動き（payment / payout / refund / fee / withholding）は決済のドライバや運用が記録する。CONCEPT 5.5 の種別に `payment`（支払いの受領）を足した
- **整合性は DB でも守る**: 仕訳の合計 0 は遅延制約トリガーでコミット時に検査、仕訳の更新・削除はトリガーで禁止（訂正は逆仕訳だけ）。合意額を超える支払いと、受け取った額を超える返金は記録できない
- **在庫は流れが決める**: 物を出す流れ（`reservesInventory`）は合意で確保、出す受渡の完了で出庫、取消・返金で未出庫分を解く。受ける受渡（買取の送付）は明細を持たず、届いた物は個体在庫として受け入れる

## 結果

- 得たもの: 縦が増えても帳票・通知・お金の処理は語彙と仕訳だけを見ればよい。決済代行を替えても Ledger は変わらない。取引ごとの残高の合計が常に 0 なので、取りこぼしが数字で分かる
- 失ったもの: 縦固有の状態（「検品中」「査定待ち」など）はフェーズで表せず、縦のプラグインが自分の表で持つ。仕訳の訂正は必ず逆仕訳になり、行数が増える。一部返金の扱い（adjustment の仕訳の組み方）はまだ決めていない
- 書き込みはすべてテナント内で直列になる（ADR 0012 の連鎖のロック）。中小の店の規模では問題にならない想定で、詰まったら見直す
