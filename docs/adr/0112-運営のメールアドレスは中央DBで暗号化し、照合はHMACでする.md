# 0112 運営のメールアドレスは中央 DB で暗号化し、照合は HMAC でする

状態: **採用**（2026-11-21）。ADR 0010（個人情報の列の暗号化）を、店の DB の外の中央 DB の運営アカウントへ広げる。2 つのリリースに分けて入れた（段階 1 は 2026-11-21 に本番へ、段階 2 はその次のリリース）

## 要点（先に）

1. 運営アカウント（`operators`）のメールアドレスを、APP_KEY で暗号化して持つ（Laravel の `encrypted` と同じ形。店の鍵を包むのと同じ方式）
2. 探すのと重複を防ぐのは、照合用の値 `email_index`（小文字にそろえた形の HMAC-SHA256）。HMAC の鍵は APP_KEY から HKDF で導いた別の鍵
3. **2 つのリリースに分ける**。更新が失敗するとイメージだけが前に戻り、DB は移行した後のまま残るので（ADR 0093 の 5 節）、前のバージョンが新しい DB の上で動ける形を保つ
4. 失敗した処理の記録（`failed_jobs.exception`）に残す例外の文から、メールアドレスを伏せる（送信サービスが宛先を文に入れて返すことがあるため）
5. 監査ログの接続元の IP アドレスは、今までどおり平文のまま（不正なアクセスを調べる時に、すぐ読める必要がある）

## なぜ

開発の DB を「盗まれた時に何が読めるか」の目で全件ダンプして確かめたところ（2026-11-21）、店の DB には平文の個人情報が 1 件も無かったが、中央 DB の運営のメールアドレスだけが平文だった。運営は数人で、ログインはパスキーだけなのでなりすましはできない。それでも、アドレスが分かれば狙い撃ちのフィッシング（「パスキーを登録し直してください」の偽メールなど）に使える。運営の判断で、メールだけを暗号化した。

最初は 1 回で暗号化する形で作ったが、見直しで、更新が失敗して前のバージョンに戻った時に管理画面にログインできなくなると分かった（前のバージョンは保存のたびにメールの列を平文のアドレスとして確かめるので、暗号文では例外になる）。そのため 2 つに分けた。

## 決めたこと

### 段階 1（PR 237。2026-11-21 に本番へ）

- 移行 `2026_11_21_000100_add_operator_email_index` が `email_index`（空を許す・一意・16 進 64 桁）を足し、今ある行に入れる。`email` には手を付けない
- `Operator` の `email` は `Casts\OperatorEmail`: 読むのは暗号文と平文の両方、書くのは平文
- 保存の時に、新しい行・アドレスを変えた時・まだ値の無い行で `email_index` を作る
- 探す時は `Operator::query()->whereEmail($email)`（結合した問い合わせは `Operator::matchEmail()`）。照合用の値で比べ、値の無い行（段階 1 の間に前のバージョンが足した行）だけ平文で比べる
- 前のバージョンがこの DB の上で動く: `email` は平文のまま、`email_index` は知らなくても困らない
- 歯止め: `OperatorEmailEncryptionTest` が、運営を `where('email', …)` や `'operators.email'` で探すコードを見つけたら落ちる

### 段階 2（段階 1 を本番に入れた後のリリース）

- 移行 `2026_11_21_000200_encrypt_operator_emails` が、値の無い行の `email_index` を埋めてから NOT NULL にし、`email` を `text` にして暗号化し直し、`operators_email_lowercase` を外して、`@` を含む値（平文）を DB が断る制約を足す
- `Casts\OperatorEmail` の書く側を暗号文にする（`Crypt::encryptString`）
- 段階 1 のコードがこの DB の上で動く: 読むのと探すのは両方の形で動き、ログイン（`last_login_at` だけを保存）も動く。メンバーを足す（平文で書く）ことだけは DB に断られる（戻っている短い間だけ。データは壊れない）
- 次の移行 `2026_11_21_000300_vacuum_operators_after_email_encryption` が `VACUUM FULL operators` をかける（UPDATE の前の行に平文が残らないように。行は数件。VACUUM はトランザクションの中で動かないので、この移行だけトランザクションの外）

### 鍵

- HMAC の鍵は `hash_hkdf('sha256', APP_KEY, 32, 'ec-sugar.operator-email-index.v1')`。鍵が無ければ、DB だけを見ても「このアドレスの運営がいるか」を総当たりで確かめられない
- 文脈の名前は、店の鍵のブラインドインデックス・記録の封印・監査ログの封印・回復のものと重ならない

### 失敗した処理の記録

- `queue.failer` を `App\Core\Mail\RedactedFailedJobs` で包み、記録する前に例外の文の中のメールアドレスの形を `<メールアドレス>` に伏せる。一覧・やり直し・消すは元の部品のまま
- 積む中身（payload）は、運営あてのメール（`OperatorSecurityMail`・`SendShopTestMail`）は APP_KEY で暗号化している（`ShouldBeEncrypted`）。お客さんへの注文のメール（`SendOrderMail`）は取引と配送の ID だけで、宛先は送る時に読み直す

## 受け入れたこと

- 照合用の値は「同じアドレスなら同じ値」。運営のアドレスは一意なので、結びつくものは無い
- APP_KEY を替えると、暗号文は前の鍵で読めても、`email_index` が合わなくなる（回復・CLI・重複の確かめが黙って外れる）。APP_KEY の入れ替えの手順に、暗号化し直しと `email_index` の作り直しを入れる
- 更新の前のバックアップ（手元 7 日・サーバーの外の保存先のロックの期間）には、段階 2 の前の平文が残る。期限が来れば消える
