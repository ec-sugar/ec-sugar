状態: **採用**（2026-10-29。決めてほしいことはすべて決まった）。ADR 0006（更新はイメージの差し替え）、ADR 0029（ステージング）の続き。一部置き換え（→ ADR 0035: main へはプルリクエストで入れる。本番が追うのは署名つきのバージョンのタグ、ステージングは main）

## 文脈

- ソースコードを受け取ったエンジニアも同じ手順を辿るので、なるべく分かりやすく設計する。インストーラーを作る
- 手で 20 手順を辿る形だと、守りの設定（ポートの束ね方・合言葉の作り方・持ち主だけ読める置き場・読み取り専用の根）をどこかで間違える。Docker は ufw を迂回するので、1 つの書き間違いでデータベースが世界に出る
- 入れた後も、更新・控え・戻し・運営の追加を同じ道具で行いたい（手で docker compose を打たせない）

## 決めること

### 1. 2 つに分ける

- **誰でも辿る手順（配布物の正式な入れ方）**: 「まっさらな Ubuntu のサーバー 1 台に SUGAR-EC を入れる」。SUGAR-EC のリポジトリの `deploy/` に置く。開発の環境のステージングの VM の中も、本番の DigitalOcean のサーバーも、配布先のエンジニアも、同じものを使う
- **置き場ごとの事情**: 開発の環境のサーバーに VM を作るスクリプトは配布物に入れない。VM は「まっさらなサーバー」の代わり

### 2. インストーラーは質問に答えるだけ

`sudo ./deploy/install.sh` を流すと、次を順に行う。止まった所から何度でも流し直せる（冪等）。

1. **確かめる**: Ubuntu のバージョン、CPU・メモリ・ディスク、80・443 番が空いているか、時計が合っているか。足りなければ理由と直し方を出して止まる
2. **聞く**（答えのファイル `install.answers` でも渡せる。2 回目からは聞かない）:
   - 使い方（本番／ステージング）
   - 管理画面の名前（例 `admin.ec-sugar.jp`）とショップの名前の付け方（例 `*.ec-sugar.jp`）
   - 最初の運営のメール（パスキーの登録の URL を出すため）
   - メールの送り先（本番）。ステージングは外へ送らない
3. **入れる**: Docker（公式の入れ方。バージョンを確かめる）、専用のユーザー `sugar-ec` と `/srv/sugar-ec`（`env`・`secrets`・`backup`）、ファイアウォール（本番は 22・80・443、ステージングは決めた LAN だけ）、自動のセキュリティ更新
4. **作る**: `APP_KEY`・DB と redis の合言葉をサーバーで作り、持ち主だけ読める `env` に置く（画面に出さない）。証明書（本番は Let's Encrypt、ステージングは渡された証明書）
5. **立てる**: イメージを取る（署名を確かめる。区切り 2 から）→ 移行 → systemd の unit で起こす → 健全か確かめる
6. **最後に**: 最初の運営を作り、パスキーの登録の URL を 1 回だけ出す。次にやること（DNS・Stripe の鍵・メール）を一覧で出す

### 3. 入れた後は `sugar-ec` という 1 つのコマンドで

`sugar-ec status`（動いているか・バージョン・控えの日時）、`sugar-ec update`（更新。ADR 0006 の順: 署名を確かめる → 控え → 移行 → 健全か → 駄目なら戻す）、`sugar-ec backup` / `restore`、`sugar-ec logs`、`sugar-ec operator create`。自動の更新は systemd の timer が `sugar-ec update --security-only` を呼ぶ

### 4. 分かりやすさの決まり

- 文はすべて日本語。何をしているか・なぜ止まったか・どう直すかを 1 行ずつ出す
- 壊れる操作（作り直し・消す）は明示の引数のときだけ。既定はいつも「足すだけ」
- 手順書（`docs/install.md`）は「インストーラーが何をするか」を、上の 1〜6 と同じ順で書く。手で辿る手順書は作らない（スクリプトが正本）

### 5. よくある設置型の EC の入れ方と比べて（2026-10-29）

よくある設置型の EC は「レンタルサーバーに FTP で上げ、ブラウザのウィザードで、要件の確かめ → ファイルの権限 → 店とメール → DB → 初期化 → 完了」。

- **取り入れる**: 準備するものの一覧を最初に出す（要件・サーバー・メールのアカウント）。要件を確かめて赤字で止める。**後から変えにくい設定をはっきり言う**（SUGAR-EC ではドメインの付け方と `APP_KEY`。`APP_KEY` を失うと暗号化した個人情報が読めなくなるので、インストーラーが控えの取り方を必ず案内する）。「失敗しがちなポイント」の節。動作を確かめたサーバーの一覧
- **真似しない**: ブラウザでサーバーを入れる形（Web のプロセスが設定ファイルを書き、DB の合言葉をフォームで受ける。入れ終わった後も開いていれば乗っ取りの入口になる。CONCEPT 7.2「Web プロセスはコードを書き換えない」にも反する）。FTP で上げる形と共用のレンタルサーバー（PostgreSQL・Redis・常駐の処理が要るので動かない。対象は VPS。サーバーを触れない店には段 2 の SaaS で応える）
- **良いとこ取り**: ブラウザの手順は**お店の開設**（店名・特商法・送料・支払い）に使う。管理画面の「ホームの開設の手順」。サーバーはインストーラー、お店はブラウザ

## 決めたこと（2026-10-29）

1. **配り方は git で取ってから流す**（中身を読める状態で `sudo ./deploy/install.sh`。署名つきのタグを確かめてから流す形にできる）。`curl … | bash` の 1 行は作らない
2. **区切りは自動の更新を先に**: 区切り 1 で「ステージングの VM に入れて立てる」と「署名つきのイメージの取り込みと `sugar-ec update`（自動の更新）」まで。区切り 2 で本番（Let's Encrypt・DigitalOcean）
3. 開発の環境の VM を作るスクリプトは、見直しを通してから流す
4. **管理の訓練は 2 か所で**（運営の判断。セキュリティに完璧はないので、手元とステージングの 2 か所でシステムを管理し、自動の更新を動かしながら、今後すべての EC-SUGAR を管理する訓練にする）。2 か所は **開発機の今の開発環境**（git で更新する作業場）と **ステージングの VM**（インストーラーで入れ、署名つきのイメージで自動の更新）。開発機の中に別の Ubuntu を作る案は採らない

## 自動の更新の形（2026-10-29）

```
[GitHub] main に push → CI が通る → イメージを作る → 署名 → 置き場（GHCR）
                                         ↓ 「新しいバージョン」の知らせ（これにも署名）
[サーバー] 定期のタイマー → 知らせを見る → 署名を確かめる → 取り込んでよいか判断
           → DB の控え → 新しいイメージで移行 → 入れ替え → 健全か確かめる
           → 駄目なら前のイメージへ自動で戻す → 記録して知らせる
```

- **署名は keyless**（cosign。GitHub の CI の身元で署名し、確かめるときは「EC-SUGAR のリポジトリのこの CI が作ったか」を見る。預かる鍵が無い）。知らせ（バージョン・中身の種類〔セキュリティ・機能・大きな変更〕・対応するプラグインとテーマのバージョン・イメージの digest）にも同じ署名
- **取り込んでよいかの判断**: セキュリティは自動、大きな変更は人が押す（ADR 0006）。入っているプラグインとテーマが新しい核のバージョンに合わなければ止める
- **戻せる移行**: DB の変え方は「足してから、後で消す」の二段。新しいイメージで移行した後でも、古いイメージに戻せば動く。この形を守る検査を入れる
- **更新の速さ**: ステージングの VM は **main が通るたびに自動**。本番は名前を付けたバージョン（タグ）だけを夜に
- **知らせ**: **管理画面に「更新の記録」、戻した・止めたときだけメール**（運営の知らせ用のアドレス。ステージングは外へメールを送らない決まりなので、知らせだけは別の道で送る）
- **失敗したら戻す**（更新に失敗したらロールバックできるように）:

  | 失敗の起き方 | 戻し方 | 自動か |
  |---|---|---|
  | 新しいイメージが立たない・健全の確かめで落ちる | 前のイメージ（digest を控える）に入れ替え直す。二段の移行なので古いイメージで動く | 自動 |
  | 移行が途中で失敗する | PostgreSQL は DB の形の変更も取り消せるので、移行は 1 つずつ丸ごと取り消す。入れ替える前に移行するので古いイメージが動き続ける | 自動 |
  | 一部の店だけ移行できた | 二段の移行なので古いイメージはどちらの店でも動く。止めて知らせ、次の回にやり直す | 自動（知らせつき） |
  | 動いているが後から問題に気づいた | `ec-sugar rollback` で前のバージョンへ | 人 |
  | DB の中身まで戻したい（最後の手段） | 更新の直前の控えから戻す。更新の後に入った注文が消えるので、確かめの文を出し、明示したときだけ | 人 |

  テストで「わざと立たないイメージ」「わざと失敗する移行」「一部の店だけ失敗する移行」を流し、戻ることを確かめる
- **関連パッケージの脆弱性の告知と更新**（重要な機能として、関連パッケージの脆弱性を知らせ、更新できる仕組み）:
  1. 知る: サーバーが毎日、入っている物（核・プラグイン・テーマ・composer と npm の依存）のバージョンを公開の脆弱性の一覧と照らす。自動の更新の「新しいバージョンの知らせ」（署名つき）にも「直した穴・影響するバージョン・深刻度」を載せる
  2. 知らせる: 管理画面のホームに「セキュリティのお知らせ」（どの部品に・どれだけ深刻な穴が・直ったバージョンがあるか・自動か人が押すか）。深刻なものはメールでも
  3. 直す: 画面からコードは入れない（CONCEPT 7.2）。画面の「更新する」はサーバーの `ec-sugar update` へのお願いを渡すだけで、入れ替えはサーバーが署名を確かめて行う（控え → 入れ替え → 駄目なら戻す）。セキュリティの修正は既定で自動
  - プラグインとテーマも composer のパッケージとしてイメージに入っているので同じ道で直る。外の作り手のプラグインの知らせを集める仕組みは後の段
- **OS と PHP などのバージョンの上げ方**（このシステムから OS や PHP などのバージョンも上げられるか）:
  - PHP・nginx・PostgreSQL・Redis はイメージの中にあるので、EC-SUGAR の更新と同じ道（署名つきのイメージ → 控え → 入れ替え → 駄目なら戻す）で上がる。店の人は何もしない
  - サーバーの OS（Ubuntu）は管理画面からは上げない（CONCEPT 7.2。root を Web に持たせると、Web が取られたときにサーバーごと取られる）。セキュリティの修正は OS の自動の更新（unattended-upgrades。インストーラーが有効にする）、起こし直しが要る更新はサーバーの側の定期の処理が夜の決めた時間に起こし直す
  - 管理画面は状態を見せるだけ: 溜まっている OS の更新の数・起こし直しが要るか・最後に起こし直した日。サーバーの `ec-sugar` が状態を書き、管理画面が読む（2026-10-29、開発の環境のサーバーに 139 個の更新が溜まっていたのに気づけなかった反省）
- 開発機の開発環境は git で更新する。`ec-sugar status` と同じ「バージョン・最後の更新・健全か」を開発機でも見られるようにして、2 か所を並べて確かめる
- **緊急の更新と止血**（2026-10-29。100 のサイトが使っていて、緊急の更新を求める場面を考える）:
  - **こちらから押し込まず、各サイトが見に来る**。私たちは配り先のサーバーの SSH の鍵を預からない（鍵が 1 つ盗まれると全部のサイトが取られる）。各サイトが署名つきの「知らせ」を 15〜60 分ごとに見に来て、署名を確かめてから自分で入れる。私たちの側が乗っ取られても、偽のバージョンと偽の知らせは署名で弾く
  - **緊急の印**: 知らせに深刻度・影響するバージョン・いつまでに、を載せる。影響を受けるサイトだけが、夜の決めた時間を待たずにすぐ入れる（控え → 入れ替え → 駄目なら戻す、は同じ）。入れたら管理画面とメールで運営に知らせる
  - **止血のスイッチ**: 直しが間に合わないとき、知らせで「前もって決めた項目（プラグインを止める・ある経路を閉じる・受付を止めて案内を出す）」だけを切り替えさせる。コードは送らない。切り替えも監査の記録に残し、管理画面に出す
  - **まだ入っていないサイトが分かる**: 各サイトがバージョンだけを匿名で知らせる（CONCEPT 7.3。パッケージでは止められる）。止めているサイトと自動の更新を切っているサイトには、管理画面の赤い帯と登録のメールで知らせる
  - **少しずつ広げる**: ふだんは先に数サイトで試してから全体へ。緊急のときはこの間を短くする（ゼロにはしない）
  - 管理画面から運営が「今すぐ更新する」を頼む形も同じ道（中央の DB にお願いを 1 行書くだけ。サーバーの root の仕組みが見つけて、署名を確かめて入れる。頼めるのはオーナーだけ、監査に残す）
- **リポジトリが乗っ取られても配れないようにする**（2026-10-29。リポジトリが乗っ取られると多くの人に迷惑がかかる。鍵を複数にする案を採る）。CI の身元の署名（keyless）だけでは、リポジトリや GitHub のアカウントを取った人が CI を動かして「本物の署名」を作れる。保留していた署名の方式は、どちらか一方ではなく **2 つの署名** に決める:
  1. **署名を 2 つ要求する**: CI の署名（Sigstore の keyless。どのリポジトリ〔変わらない番号〕の・どの CI の手順の・どの守られたタグから作ったかまで照らす）に加えて、**人が手元に持つ物理の鍵の署名**（YubiKey など。GitHub の中に無い）をバージョンごとに求める。各サイトは両方がそろったバージョンだけを入れる。緊急の印・止血のスイッチ・バージョンの取り消しは、とくに強い力なので 2 つを必須にする。人の鍵は 2 本以上（1 本を失くしても配れる・1 本を盗まれたら取り替えられる）、取り替えの手順も先に決める
  2. **冷却の時間と少しずつ広げる**: ふつうの更新は出してから数時間〜1 日待ち、先に数サイトで動かしてから全体へ。悪いバージョンは広がる前に、署名つきの「このバージョンは取り消し」で止め、入れてしまったサイトは前のバージョンへ戻る
  3. **勝手な署名に気づく**: keyless の署名は公開の透明性のログ（Rekor）に残るので、私たちの身元での身に覚えのない署名を常に見張り、出たらすぐ知らせる
  4. **乗っ取られにくくする**: GitHub のログインは物理の鍵かパスキーだけ、触れる人は最小、長く使う個人の合言葉（PAT）を作らない。main とタグは消す・書き換える・強制で上書きすることを禁じる（保護の決まり）。配るバージョンは守られたタグからだけ作る。依存はバージョンと中身の指紋で固定
  5. **知らせに期限**: 知らせ（どのバージョンが最新か）に期限を付け、古い知らせへの差し替え（更新を止めさせる攻撃）や、古いバージョンへの巻き戻しを断る
  - 考え方はソフトの更新の守りの決まった形 TUF（役割ごとに鍵を分ける・複数の署名・期限・取り替え）に沿う
  - **本番で配り始める前に必ず入れる**。今のステージングの自動の更新（署名なし・枝の先を取る）は、外に開いていない試験の環境だから許している形で、このまま配らない（高）

## 結果

- 得るもの: 配布先のエンジニアも私たちも同じ道で入れ、同じ道で更新する。守りの設定を人が書かない
- 気をつけること: インストーラーそのものが root で動く大事なスクリプトになる。テスト（まっさらな VM で毎回入れ直す）と、見直しを必ず通す

## 作って決めたこと（2026-10-31、「名前を EC-SUGAR に統一する」のうちサーバーまわり）

env の項目の名前を `SUGAR_EC_…` から `EC_SUGAR_…` へ「両方を書いて移す」形で替えた（運営の決まり）。入っているサーバーの更新の道を壊さないことを一番に、次の形にした。

- **更新の道の順番**: 更新を始めるのはサーバーに入っている前のバージョンの `ec-sugar`。取り出した新しいバージョンの `ec-sugar ensure-env` を最初に呼び（ここで移す）、その後は前の道具が `SUGAR_EC_IMAGE=<新しいイメージ>` を環境変数に置いて新しい compose を解き・入口のイメージを作り・マイグレーションし、切り替えでは env の `SUGAR_EC_IMAGE` の行だけを書く。成功したら新しい道具を入れ、新しい道具の `install-units` が呼ばれる（ここでもう一度移し、新しい名前の行もそろう）
- **前の名前の行がある間は前の名前の値を正とする**（compose は `${SUGAR_EC_X:-${EC_SUGAR_X…}}` の順、道具の読みも同じ順）。新しい名前を先に読むと、移した後の env の `EC_SUGAR_IMAGE` は今のイメージのままなので、マイグレーションが前のイメージで流れ、切り替えた後も前のイメージで動いてヘルスチェックに落ち、自動でロールバックしてそのバージョンが保留になる（`docker/check-deploy.sh` の 8 でわざと逆にして確かめた）
- **移し**（`ec_env_migrate`）: 前の名前の行ごとに、同じ値（引用符もそのまま）の新しい名前の行をすぐ後ろに足す。新しい名前の行があって値が違えば前の名前に合わせる。前の名前の行は消さない（前のバージョンへロールバックしても前の compose が読める）。ほかの行・並び・権限は変えず、直すことが無ければ書かない。呼ぶのは `ensure-env`・`update`・`rollback`・`backup`・`report`・`install-units` と、インストーラーの流し直し（移せなければ止める。DB の管理者のパスワードを「空」と取り違えて作り直さないため）。`status`・`start` は鍵が空いているときだけ（ほかの処理と同時に書かない）
- **書き**（`ec_env_set`）: 新しい名前で書き、前の名前の行があればそこにも同じ値。前の名前の行が無いサーバーには足さない。イメージを環境変数で渡すとき（`ec_with_image`）は両方の名前で渡す（env に前の名前の行があると compose はそちらを先に読み、ロールバックの先の前の compose は前の名前しか読まない）
- **新しく入れるサーバー**は見本（`deploy/production.env.example`）から env を作るので、新しい名前だけ。新しい名前だけのサーバーを `update --to` で名前を替える前のバージョンへ下げると、前のバージョンの `ensure-env` が管理画面のホストを読めずに「env に足りない」で止まる（壊れずに止まる。前の名前は足さない）
- **DB の管理者のパスワード**: app・queue・scheduler の環境変数で、新しい名前と前の名前の両方を空にする（env ファイルは丸ごとコンテナに渡るので、前の名前の行が残る間はそれも空にしないとアプリに渡る）
- **コンテナの中の名前は新しい名前だけ**（Caddy・nginx の雛形が読む `EC_SUGAR_…`）。Caddyfile と nginx の雛形は取り出したバージョンのソースから差し込むので、名前はバージョンの中で閉じる（入口の Caddy のイメージは作り直さない）
- compose の入れ子の既定値は compose 2.35 以上（インストーラーが求める最低）で使える。手元の v5.5.0 で、前の名前だけ・両方・新しい名前だけ・環境変数で上書き、を確かめた
- **入れ子の内側に必須の確かめ（`:?`）を置かない**（2026-10-31、PR 62 の CI で分かった）: 最初は `${SUGAR_EC_X:-${EC_SUGAR_X:?…}}` にしたが、compose の 2.40 系（自前の CI の走らせ役の Ubuntu の部品 `2.40.3+ds1-0ubuntu1`）は、外側に値があっても内側の `:?` を確かめて止まる（前の名前だけの env で `required variable EC_SUGAR_ENV_FILE is missing a value`）。5.x（手元の v5.5.0・ステージングの VM の v5.6.1）は止まらないので、手元では気づけなかった。Ubuntu の部品の compose を使う本物のサーバーでも更新が壊れる。そこで:
  - compose は `${SUGAR_EC_X:-${EC_SUGAR_X:-}}`（内側は空の既定値）にした
  - 必須の項目の確かめは ec-sugar の `ec_dc` に移した（`EC_REQUIRED_ENV`。compose のファイルが新しい名前で読む項目のうち、環境変数にも env にも値が無いものを「名前（説明）」で出し、compose を流さずに止める。値は出さない。前の名前だけで読む前のバージョンの compose は自分で確かめるので見ない）。サーバーに入っている前のバージョンの道具はこの確かめを持たないが、入れたサーバーの env は項目がそろっている
  - **受け口の住所（BIND）だけは compose の中でも止める**: 空だと compose はポートを住所の無い形（全部の住所）にする（2.40.3・5.5.0 とも確かめた）。IP でない印 `EC_SUGAR_BIND（受け口の住所）をenvファイルに書く` を内側の既定値にして、両方の版で `invalid IP address` で止まる（0.0.0.0 に倒れない）
  - 見張り: `docker/check-compose.sh` が書き方そのもの（入れ子の内側の `:?`）を見る（どの版の compose でも落ちる）。`docker/check-deploy.sh` と `check-compose.sh` は `EC_CHECK_COMPOSE=<compose の単体のバイナリ>` で compose を差し替えられる。GitHub の docker/compose の v2.40.3（darwin-aarch64、公開の sha256 と照らした）と手元の v5.5.0 の両方で、2 つの検査が通ることを確かめた。わざと内側に `:?` を戻すと、2.40.3 では check-deploy.sh が落ち、5.5.0 では check-deploy.sh は通るが check-compose.sh が落ちる。`ec_dc` の確かめを外す・受け口の住所の印を外すと、どちらの版でも落ちる
- 本番の compose の `name:` はインストーラーの `-p` と同じ `ec-sugar` にした（手で compose を流しても同じものを指す）。開発の compose は `ec-sugar` にし、手元の DB と写真の置き場（volume）は前の名前 `sugar-ec_db-data`・`sugar-ec_storage-data` を名前で指して使い続ける。前の名前のコンテナは `make up`・`make down` が先に片付ける（置き場は消さない）
- 前の名前を読む所（compose の入れ子・道具の読み・移し・空にする行）は公開の前に消す（公開の前にやることの 1 つ）

## 作って決めたこと（入れる側の確かめ、2026-11-12。配る側は ADR 0099）

- **更新の形を 2 つにした**（答えの `CHANNEL`）。公開版の形（`release`）は人の鍵で署名した semver のタグだけを入れ、イメージは公開用の CI が作って署名したものを確かめてから digest で取る。開発の形（`source`）は今までの形（コミットを取り、サーバーで組み立てる）で、私たちの本番はこれのまま（答えに `CHANNEL` が無いサーバーは開発の形）。既定は木で決める: 公開用の木にだけ `deploy/channel.default`（`release`）を書き出す
- **信じる鍵はサーバーの root の持ち物 `/srv/ec-sugar/trust/allowed_signers` だけ**。インストーラーが答えの `TRUST_SIGNERS_FILE` から置き、指紋を出して「公式サイトで公表している指紋と同じか」を人に確かめさせる（答えのファイルでは `TRUST_FINGERPRINTS` がちょうど同じであること）。リポジトリの中に鍵の一覧を置いて既定にする形は採らなかった（ADR 0099 の 4。乗っ取った人が一覧ごと書き換えられる）。1.0 の鍵の入れ替えは `sudo ec-sugar trust add|remove|list` の手で、最後の 1 つは外せない。鍵の種類では断らない（Secure Enclave の `ecdsa-sha2-nistp256` も物理の鍵も、一覧にあるかだけ）
- **タグの確かめ**は `git verify-tag` に、署名の形・道具（`ssh-keygen`）・鍵の一覧・信じる段階を `-c` で決め打ちして渡す（`.git/config` より強い。作業場所の持ち主の `ec-sugar` が設定を書き換えても効かない）。git の置き換えの印は `GIT_NO_REPLACE_OBJECTS=1` で読まない。署名に加えて、注記つきのタグであること・**中に書かれた名前がタグの名前と同じ**こと（署名は本物のまま古いタグを新しい名前で出し直す巻き戻しを断る）・コミットを直に指すことを見る
- **入れてよいか**: 今より古いバージョンは手の更新で `--allow-downgrade` の時だけ。同じ名前で別のコミットは断る（タグは付け替えない約束。ADR 0099）。新しいものは今のコミットから早送りのときだけ。今のバージョン（タグ）は `state/current_version`・`previous_version` に残し、ロールバックで入れ替える。`--to` が無ければ署名の通る最新を選び、通らない新しいタグは飛ばして記録と `status` に出す（飛ばして新しいものが無ければ stopped として運営の様子にも）。自動の更新は試しの版（`-rc.1`）とメジャーバージョンの上がるものを取らない（ADR 0006 の「大きな変更は人が押す」）
- **イメージ**: 2 つのタグが今指す digest を置き場に聞き（`docker buildx imagetools inspect`）、digest ごとに cosign で確かめる（身元・発行者・リポジトリ・ref・workflow のコミット＝タグの指すコミット）。確かめるのは digest なので、聞いた後にタグが付け替えられても通るのは署名したものだけ。2 つとも通ってから digest で取り、印 `org.opencontainers.image.revision` がコミットと同じかを見て、今までの名前（`ec-sugar:<コミット>`・compose の入口の名前）を付ける。ロールバック・片付け・compose は今までのまま動く。cosign は版（v3.1.4）と digest を固定した公式のイメージを `--read-only --cap-drop ALL --security-opt no-new-privileges:true`・使い捨ての `/tmp` で動かし、GHCR が非公開の間は root の docker のログインを読み取り専用で渡す
- **高の残り**: 開発の形の自動の更新は既定で切り（本番もステージングも。答えの `AUTO_UPDATE=yes` の時だけ動き、早送りのコミットだけ）、運用の道具と unit は確かめたコミットの git の中身から（`git archive` で root だけの一時の置き場へ。リンクのファイルは写さない）、取り出したバージョンの `ensure-env` もその写しで流す。新しい compose は今入っているバージョンの `check-compose.sh`（`ec_install_tools` が `/usr/local/lib/ec-sugar/` へ入れる。`EC_CHECK_TREE` でほかの木を見る）にかけてから起こす（公開版の形と自動の更新は通らなければ止め、開発の形の手の更新は注意だけ。検査が入っていない前のバージョンからの初めての更新は、取り出したバージョンの検査で。jq が要る）
- **中のうち、この流れで直したもの**: 取得元の URL にパスワード・トークンがあれば取りに行かず、URL を出さない（インストーラーも 1/5 で ✗）。途中で止まった時の半端な状態は、作業場所を切り替えた直後の印（`state/updating`）と終わりの trap で前のバージョンへそろえ、電源断などは次の update・rollback の始めにそろえる。手のロールバックが通らなければ元のバージョンへ戻し直す
- **compose の一式も root だけの置き場から**（2026-11-12 の見直しで直した）: 前は公開版の形でも、compose のファイルと compose が差し込むもの（入口の Caddy の設定・nginx の設定・DB の初めのスクリプト）を作業場所 `/srv/ec-sugar/src`（利用者 `ec-sugar` が書ける）から読んでいた。守りの検査の後から起こすまでの間や、その後の再起動・ロールバックで差し替えられた。今は公開版の形では、作業場所を切り替えるたび（`ec_src_checkout`。更新・ロールバック・途中で止まった時の戻し・インストール）に、そのコミットの `docker-compose*.yml`・`docker/`・`deploy/` を `git archive` で `/srv/ec-sugar/compose/<コミット>/` へ root が取り出し（root の持ち物・0644 と 0755・リンクのあるコミットは取り出さない・取り出してから名前を付ける）、どのコミットの置き場かを root の記録 `state/compose_commit` に残す。`ec_dc` の `--project-directory` と `-f`、守りの検査の `EC_CHECK_TREE` はこの置き場で、検査したものと起こすものが同じになる。記録が無ければ今のバージョン（`current_commit`）の置き場をその場で取り出し、それも分からなければ compose を流さない（作業場所へは落とさない）。片付けは今と前のバージョンの分を残す。開発の形（私たちの本番）は今のまま作業場所から（開発の形はイメージそのものも作業場所から組み立てるので、compose だけを移しても守りは閉じない。同じ形にするなら、組み立ても `git archive` の中身からにする）
- 見張り: `docker/check-release.sh`（CI の image の仕事）。配る側との約束の要点は docs/development/release.md の「入れる側の確かめ」
