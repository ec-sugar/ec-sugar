# 0019 最初の決済代行は Stripe（Checkout）

状態: 採用（2026-10-27）。CONCEPT 7「決済の第一候補は未定」を置き換える。一部置き換え（→ ADR 0022: SaaS 版の店は鍵を貼らず Stripe Connect でつなぐ。「秘密鍵と Webhook の署名の鍵はテナントごと」と「Connect は後で」を SaaS 版について。パッケージ版はこの ADR のまま）

## 文脈

注文の流れを作るには支払いが要る。CONCEPT では、決済代行は差し替えられるアダプタで、正は自社の仕訳（Ledger）。
プラットフォームが資金を預からない（資金移動業を避ける）。マーケットプレイスの分配は決済代行の機能で行う。
カード情報に触れない（CONCEPT 7.2）。導入の簡単さから Stripe を選んだ。

## 決定

- **最初の決済代行は Stripe**。決済代行のアダプタ（ドライバ）の 1 つとして作り、核と仕訳は Stripe に依存させない
- **支払いは Stripe Checkout（Stripe が用意する支払いの画面へ移る形）**。カード番号を入力する画面は Stripe 側にあり、私たちのサーバーにも画面にもカード情報が来ない。店頭に Stripe のスクリプトを読み込まない
- **注文の確定は Webhook で行う**。署名を必ず確かめ、同じ通知の二度目は処理しない（冪等）。お客さんが戻ってきた画面（成功の URL）を支払いの証拠にしない
- 支払いの受領は `LedgerService::recordPayment`（経路は決済代行が預かる形）で仕訳にし、Stripe の識別子は参照（reference）に残す。返金も Stripe の返金と仕訳の両方で行う
- **秘密鍵と Webhook の署名の鍵はテナントごと**（単店モードでは店の Stripe アカウント）。テナントの鍵で暗号化して保存し、ログ・イベント・画面に出さない（→ SaaS 版は ADR 0022 で置き換え）
- 金額は整数（円）のまま Stripe に渡す（JPY は小数の無い通貨）
- マーケットプレイスの形（モード D。2026-10-31 に誤記の「モード C」を直した。自社で運営する C は当面やらない、CONCEPT 4）の分配は、後で Stripe Connect（separate charges and transfers）で行う。それまでは単店モード（店の Stripe アカウントへ直接）だけ（→ SaaS 版の店の Connect は ADR 0022 で先に入れた。マーケットの分配はまだ）

## 結果

- 得たもの: カード情報を扱わないので、カード業界の基準への対応が最小（支払いの画面を持たない形）。導入が速い。Stripe の画面はカード以外（コンビニ・Apple Pay など）にも広げやすい
- 失ったもの: 支払いの画面の見た目は Stripe 側の設定までしか変えられない。Stripe の手数料。Webhook を受けるため、外から届くアドレスが要る（開発中は Stripe CLI の転送、本番とステージングは公開の URL）
