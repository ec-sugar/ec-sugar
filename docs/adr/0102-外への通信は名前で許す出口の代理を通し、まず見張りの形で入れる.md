# 0102 外への通信は名前で許す出口の代理を通し、まず見張りの形で入れる

状態: **採用**（2026-11-13。リリース 1.0 の R11）。本番へ入れるのは、復元の写しで試し、運営に確かめてから。

## 要点（先に）

1. アプリのコンテナ（app・queue・scheduler）から外への https は、本番の compose の**出口の代理 `egress`** を通す（`HTTPS_PROXY`）。代理は HTTP の CONNECT の**名前とポート 443 だけ**で決める
2. 許す一覧は `docker/egress/allow.txt`（コードの中の外へ出る所。下の表）と、サーバーごとに足す env の `EC_SUGAR_EGRESS_ALLOW`
3. 形は env の `EC_SUGAR_EGRESS_MODE` で選ぶ。**既定は見張りの形（watch）**: 一覧に無い宛先も通して名前と数を記録する。**止める形（enforce）**: 断り、アプリの網から外へ直に出る道も外す。逃げ道に代理を使わない形（off）。切り替えは `sudo ec-sugar egress <形>`
4. 名前を引くのは代理で、引いた住所が 1 つでも内向き（LAN・ホスト・コンテナ・クラウドの設定の口）なら**どの形でも断る**。確かめた住所につなぐ（引き直さない）
5. メールは、止める形でアプリの `MAIL_HOST` を代理の住所に向け、代理が `MAIL_HOST:MAIL_PORT` へ**だけ**中継する（TLS はアプリと送り口の間で閉じたまま）
6. 数（この 24 時間に通した・一覧に無い・断った・つながらなかった・メールの中継）は運営の様子の「外への通信」に出す。止める形で断った・代理が止まったは要対応のメール。中身は残さない（記録は名前・ポート・決めたことだけ）

## なぜ

外のレビュー（2026-11-06）の「中を取られても外へ出せない」の残り。アプリ（PHP・App・依存の部品）のどこかが取られると、今はどの宛先へも何のポートでも送れ、DNS でも送れる。店の DB の中身・鍵・お客さんの情報が出ていくのを、出口で止めたい。

一方で、許す一覧が足りずに支払い（Stripe）やメールが止まるのが、いちばん困る事故。だから「まず見張りの形で入れ、数日の記録を見てから止める形へ」の 2 段にする。

## 外へ出る所（2026-11-13 にコードから洗い出したもの）

`grep` で `Http::`・Stripe の部品・`curl_`・`fsockopen`・`stream_socket_client`・`file_get_contents(http…)` を app/ と plugins/ から探した。

| 宛先 | 何のため | どこから | 一覧 |
|---|---|---|---|
| `api.stripe.com` | 支払いの作成・返金・Connect の口座の画面の URL・Webhook の確かめ直し | `app/Core/Payment/Stripe`（Stripe の部品。libcurl が `HTTPS_PROXY` を読む） | allow.txt |
| `api.line.me` | LINE ログインのトークン・友だちの確かめ・知らせの送信 | `plugins/plugin-line` | allow.txt |
| `hooks.slack.com` | 店への知らせ（Slack の Incoming Webhook。宛先はこの形だけ） | `plugins/plugin-shop-notify` | allow.txt |
| `zipcloud.ibsnet.co.jp` | 郵便番号から住所 | `app/Storefront/Postal/ZipcloudPostalLookup.php` | allow.txt |
| `unsplash.com`・`images.unsplash.com` | 入れたときのサンプルの写真 | `app/Core/Shop/Samples/SamplePhotos.php` | allow.txt |
| 店の人が CSV に書いた写真の取得元 | 商品の CSV の写真の列 | `app/Core/Media/RemoteImages.php` | **入れない**（店の人の入力で決まる。要る取得元はサーバーごとに `EC_SUGAR_EGRESS_ALLOW` へ） |
| `MAIL_HOST:MAIL_PORT` | メールの送り口（SMTP） | Laravel のメール | 代理の中継（止める形） |

ブラウザが直に読むもの（タグの App・地図・動画の埋め込み・Stripe Checkout・LINE のログインの画面）は、サーバーから外へ出ないので代理と関係ない。

### 名前で決められない・コンテナの外のもの（代理を通さない）

| 宛先 | 理由 |
|---|---|
| 入口の Caddy → Let's Encrypt（`acme-v02.api.letsencrypt.org`）・Cloudflare の DNS の API（`api.cloudflare.com`）・OCSP | Caddy は 80・443 番を外へ出すので外へ出る網に居る必要がある。名前で絞るなら Caddy の中の代理の設定が要り、証明書が取れないと止まるので 1.0 では入れない |
| cloudflared → Cloudflare の拠点 | 拠点は IP の幅と UDP・TCP の 7844 番で、名前の CONNECT にならない |
| nginx（web） | 外へ出る用は無いが、Caddy と同じ網（front）に居る。網を分けると nginx が接続元を信じる住所の決まりを変えることになるので 1.0 では触らない |
| ホストの root の更新（GHCR・Sigstore・GitHub・Docker Hub・apt） | コンテナの外（`ec-sugar update`）。ホストの防火壁の話 |

## 形

### 代理（`docker/egress/proxy.php`）

- アプリと同じイメージの PHP で動かす（新しいイメージ・新しい言語を足さない）。台本と一覧は compose の置き場から読み取り専用で差し込む（公開版の形では root だけが書ける置き場）
- env ファイルを渡さない（秘密を持たない）。読み取り専用・cap_drop ALL・no-new-privileges・www-data。網は `egress`（外へ）と `egress_in`（アプリと代理だけ・外へ出られない・代理の住所を固定）
- 1 つの接続に 1 つの子の処理（`pcntl_fork`、同時に 128 まで）。親が子の終わりの番号で数え、10 秒ごとに状態のファイル（メモリの上の置き場 `egress_state`。アプリは読み取り専用）に書く
- 受けるのは CONNECT と `/healthz` だけ。平文の http の代理（GET http://…）は 405
- 決め方: 名前の形でない → 断る。住所の直書き → 内向きは断る、外の住所は「一覧に無い」と同じ。443 以外のポート・一覧に無い名前 → 見張りの形は通して記録、止める形は断る。その後、名前を引いて 1 つでも内向きなら断る（確かめの台本の偽の宛先だけ `EC_SUGAR_EGRESS_INTERNAL_OK` で許す）。引いた住所へ順につなぐ
- 200 を返した後、TLS の握手の始め（ClientHello）の名前（SNI）を読み、CONNECT の名前と違えばどの形でも切る（許した名前の陰で別の名前へ握手させない）。TLS でないもの・名前の無い握手は、見張りの形では記録して通し、止める形では切る
- IPv4 だけにつなぐ（今の網は IPv4 だけ）
- 止める合図（SIGTERM。アプリのイメージの既定の SIGQUIT でも）で受け口を閉じ、途中の接続が終わるのを最大 80 秒待つ（compose の `stop_grace_period: 90s`）。更新のたびに代理が作り直されても、途中の Stripe への要求を切らない。流れている接続は長さで切らず、黙って 120 秒で切る
- app・queue・scheduler は代理が healthy になってから起きる（`depends_on`）

### 止める形（`docker-compose.egress.yml`）

`ec-sugar`（`ec_dc`）が `EC_SUGAR_EGRESS_MODE=enforce` のときだけ重ねる。app・queue・scheduler を `internal` と `egress_in`（どちらも外へ出られない。`egress_in` はホストの側に住所も持たない `gateway_mode_ipv4: isolated`。Docker 28 から）だけにし、`MAIL_HOST` を代理の住所に向ける（`extra_hosts`）。外へ出られない網だけにいるコンテナは、Docker の中の DNS が外の名前を引かない（Docker 26 から。インストーラーは 28.1 以上）ので、外の名前を引かせて中身を DNS で運ぶ道も無い。

### 前からある網は変えない

`internal`・`edge`・`egress` の設定（`internal` の真偽など）は変えず、新しい網 `egress_in` を足した。網の作り方を変えると、動いているサーバーで網を作り直せずに更新が止まる（docker-compose.prod.yml の網の注）。見張りの形では、アプリの網は今までどおり（外へ直に出る道もある）で、`HTTPS_PROXY` を足しただけ。

## 選ばなかった案

- **ホストの防火壁（DOCKER-USER）で IP の幅を許す**: Stripe・LINE・Slack の住所は変わり、CDN の後ろで名前と住所が 1 対 1 にならない。名前で決められない
- **Squid・tinyproxy など既製の代理**: 公式のイメージが無い（作るか、外の人のイメージを固定して取る）。見張りの形の「一覧に無いが通した」を数えるのに記録を読み解く仕組みが要る。PHP で 400 行ほどの自前の代理なら、決め方を PHP のテストで確かめられ、phpstan も掛かる
- **Caddy の forward_proxy の部品**: 入口の Caddy の作り直しになり、メールの中継（TCP）も別の部品が要る
- **見張りの形でも網を切る**: 代理を通らない直の接続（今は無いはず）があると、見張りの形の間に止まる。見張りの形は「止めない」を守る

## 本番へ入れる手順（要点。詳しくは docs/install.md の「外への通信」）

1. このバージョンへ更新すると見張りの形で入る（代理が増え、アプリは `HTTPS_PROXY` で代理を通る。代理が起きなければヘルスチェックで前のバージョンへ戻る）
2. 先に、復元の写し（`ec-sugar restore --isolated`）で、代理が起き、アプリが代理を通ること（隔離の形では外へは出ない）を確かめる
3. 本番で数日、運営の様子の「外への通信」と `sudo ec-sugar egress` の「一覧に無かった名前」を見る。要る名前は `EC_SUGAR_EGRESS_ALLOW` に足す
4. `MAIL_HOST` が名前であることを確かめ、運営の了承の後に `sudo ec-sugar egress enforce`。テストの注文とメールを 1 通通す。困ったら `sudo ec-sugar egress watch`（すぐ戻る）

## 作って決めたこと（2026-11-13）

- 知らない形の値（`EC_SUGAR_EGRESS_MODE=block` など）は見張りの形とみなす（止めない方に倒す）。代理の記録に `unknown-mode` を出す
- `MAIL_HOST` が住所（IP）だと、止める形で中継へ向けられない（`extra_hosts` は名前だけ）。`ec-sugar egress enforce` は断って理由を出す。ステージングの Mailpit（`mailpit`）は内側の網で直に届くので向けない
- 写真の取り込み（`RemoteImages`）は、代理があるときは名前を自分で引かずに代理を通す（止める形のアプリは外の名前を引けない）。内向きの住所を断るのは代理。URL の形の確かめ（https だけ・内向きの名前・住所の直書きの内向き）とリダイレクトごとの確かめは今までどおり
- 運営の様子: 代理を使う形で状態のファイルが 5 分より古い・読めない → 要対応（代理が止まると外への https が全部止まる）。止める形で断った → 要対応。見張りの形で一覧に無い・断った → 近いうちに。代理を使わない形 → 札に「使っていません」だけ
- 代理が止まっても（見張りの形でも）外への https は止まる（`HTTPS_PROXY` が向いたまま）。そのため代理にヘルスチェックを付け、更新のヘルスチェックに入れ、`restart: unless-stopped` にし、逃げ道の `off` を用意した
- 確かめ: `docker/check-compose.sh` の 14（形）と `docker/check-egress.sh`（本番の形を使い捨ての名前で立て、偽の宛先で。CI の image の仕事と公開の CI の scripts の仕事）
- 見直し（PR 185）で足したこと:
  - **代理の見張りはホストから**: 止める形では代理が止まるとメールの道も切れ、運営の様子の「代理が止まった」のメールも届かない。`ec-sugar watch`（10 分ごと）が代理の様子を見て、止まった・unhealthy なら作り直し、ホストの記録（`state/history.log` の `egress_restart` と systemd の記録）に残す
  - **更新のヘルスチェック**に「app から egress_in を通って代理の `/healthz` に届く」を足した（代理が healthy でもアプリから届かなければ外への https は止まる）。`ec-sugar egress <形>` も同じに確かめ、代理が起きなければ `off` を案内する
  - **運営の様子**: 直近 1 時間に、代理を通った先へつながらない（failed）のに 1 本も通っていないなら要対応（名前を引けない・代理から外へ出られない）
  - **写真の取り込み**は、代理を任せる印を専用の `EC_SUGAR_EGRESS_PROXY`（config の `egress.proxy`）にした（開発機の `HTTPS_PROXY` を代理と取り違えない）。名前を引ける形（見張りの形）ではアプリでも内向きを断る（二重の守り）
  - **許す一覧**で、住所とその欠けたもの（`10.0.0`）・終わりが数の名前・ラベルが 1 つの `*.`（`*.com`）は捨てる
  - **コンテナからホストへ届かない**（2026-11-13）: 外へ出られない網でも、bridge の住所（gateway）からホストの待ち受け（SSH・DNS・メールの送り口）へ届いていた。
    新しい網 `egress_in` は compose で `gateway_mode_ipv4: isolated` にし、前からある網（`internal`・`edge`・`front`・`egress`・Tunnel の網。設定を変えると動いているサーバーで作り直せない）は、
    ホストの防火壁（`ec-sugar firewall`、deploy/lib/common.sh の `ec_host_guard_apply`）で塞ぐ: INPUT の先頭に EC-SUGAR の網の bridge ごとに鎖 `EC-SUGAR-HOST` への飛び先を入れ、
    鎖は「返り（ESTABLISHED・RELATED）と DNAT された接続は通す → env の `EC_SUGAR_HOST_ALLOW_PORTS` の TCP のポートだけ INPUT の続き（ufw）へ → ほかは REJECT」。
    IPv4 と IPv6。要るホストへの道は今のところ無い（Docker の中の DNS 127.0.0.11 はコンテナの中、コンテナどうしは bridge の中）。MAIL_HOST をホストの Postfix に向けるときだけ、
    そのポートを `EC_SUGAR_HOST_ALLOW_PORTS` に書く。当てるのは今までの防火壁と同じ時（入れた時・更新のヘルスチェック・毎晩の更新の確かめ・`sudo ec-sugar firewall`・起動時）で、
    消されたら `status` が ✗ を出す。確かめは check-deploy（偽の iptables）と check-egress（本物の Docker のホストの iptables に、確かめの網だけ別の鎖の名前で当てる）
  - 代理のイメージ（公式の php-fpm）の止める合図は SIGQUIT だった（`STOPSIGNAL`）。SIGTERM だけを受けていたので、止める時に 90 秒待って殺されていた（確かめの台本で見つけた）。両方を受け、compose で `stop_signal: SIGTERM`

## 残り

止める形が守るのは「決めた名前の外へは出せない」まで。次の道は残る（中を取られたアプリが使える）:

- **許した宛先そのものを使って送り出す**: 攻める人が自分の Slack の Incoming Webhook（`hooks.slack.com/services/…`）・自分の LINE のチャネルの鍵・自分の Stripe の鍵で、許した名前へ中身を送る。名前とポートしか見ない（中身は暗号のまま）代理では見分けられない。Slack は店の設定の宛先の形だけを送る口があるが、取られたアプリはその口を通らない
- **メールの中継**: 宛先（MAIL_HOST:MAIL_PORT）は決まっているが、メールの受け取り手は自由。攻める人の宛先へ中身をメールで送れる（送り口の送れる数・記録で気づくしかない）
- **domain fronting**: 握手の名前（SNI）は CONNECT の名前と合わせるが、TLS の中の Host の見出しは見えない。許した名前が共用の CDN の上にあると、同じ CDN の別のサイトへ行かせられる。そのため許す一覧に共用の名前（`*.amazonaws.com`・`*.cloudfront.net`・`*.googleapis.com` など）を書かない（install.md）
- 入口の Caddy・nginx・cloudflared は外へ出る網に居たまま（上の表）
- 止める形の DNS の守りは Docker 26 からの動きに頼る（`docker/check-egress.sh` で毎回確かめる）
- 代理は IPv4 だけ。IPv6 だけの宛先にはつながらない
- （DB・Redis との通信の暗号化）は別のタスク
