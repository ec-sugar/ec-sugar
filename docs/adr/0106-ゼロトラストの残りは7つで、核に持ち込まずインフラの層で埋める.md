# 0106 ゼロトラストの残りは 7 つで、核に持ち込まずインフラの層で埋める

採用（2026-11-18）

## 文脈

外のレビューの総評（2026-11-06）は「設計の方向は良い。ゼロトラスト対応済みとはまだ言えない。最小権限・テナント分離・明示的な認可を重視した設計が今の正しい言い方」だった。
運営の目標（2026-11-18）: ゼロトラストに完全に対応する。核の機能は、単純で拡張しやすく、セキュリティも担保された状態にしておく。

棚卸しすると、原則のうち次は**すでに満たしている**。

| 原則 | 今あるもの |
|---|---|
| すべての入口で認証する | 運営はパスキーだけ（ADR 0023）、お客さんはメールのコードとパスキー（ADR 0044）、AI エージェントは鍵か OAuth（ADR 0100・0101） |
| 明示的な認可 | 店ごとの閲覧・運用・お金（ADR 0024）、店の文脈に入るのは `EnterTenant` と `AuthenticateAgent` の下だけ、経路に `auth:…` か公開の印（conventions.md） |
| 最小権限 | 店ごとに DB とロールを分ける（ADR 0009）、Web のプロセスはコードを書き換えない・管理画面からコードを入れない（CONCEPT 7.2）、読み取り専用のイメージ |
| 継続的な検証 | 壊れたら知らせる（ADR 0043）、おかしな動きを毎分数える（ADR 0103）、入られた後の書き換えに気づく（ADR 0105） |
| 供給網を信じない | 人の鍵で署名したタグと CI の keyless の署名の 2 つ（ADR 0099） |

管理画面の接続元の制限（`ADMIN_ALLOWED_IPS`）は「網の位置だけで信じる」形ではなく、IP ＋ パスキー ＋ 権限の三重なので原則に反しない。**直さない。**

## 決めたこと

残っている穴は 7 つ。段 1 は 1.0 の前（2026-11-13 に決めた「外への通信と SSH だけ 1.0 の前」の線のまま）、段 2 は 1.0 の直後に続けてやる。

| # | 穴 | 埋め方 | 置く層 | 段 | タスク |
|---|---|---|---|---|---|
| 1 | 外への通信が止まっていない（持ち出しを防げない） | 出口の代理で宛先だけ許し、**見張りの形から止める形へ** | `docker/`・`deploy/`（代理のコンテナと防火壁） | **1** | ・ADR 0102 |
| 2 | 本番へ入る SSH の鍵がソフトウェア | Secure Enclave と物理の鍵へ移し、入れる鍵を棚卸しする | 手順（install.md・ops）と運営の手元 | **1** | |
| 3 | 内部の通信が平文（app ↔ db ↔ redis が同じ Docker の網にいれば話せる） | PostgreSQL と Redis を TLS にし、証明書で互いに確かめる | `docker/`・`deploy/`（設定と証明書の作り方） | 2 | |
| 4 | 鍵が回らない（APP_KEY・テナントのデータ鍵・パスキーのユーザーハンドル） | 入れ替えの手順と `ec-sugar` のコマンド（古い鍵で読めるうちに包み直す） | `app/Core/Crypto` の中と運用の道具 | 2 | |
| 5 | 監査ログが外に出ない（ローカルのハッシュ連鎖だけなので、サーバーごと取られると末尾を切られる） | 連鎖の先頭（番号と hash）を、上書きも削除もできない置き場（Cloudflare R2）へ定期に控える | `app/Core/Event` の中とバックアップの道具 | 2 | （R7 と一緒） |
| 6 | 重要操作が 1 人で通る（返金・お金の宛先の変更） | 複数の承認と待機の時間。**新しい仕組みを作らず、AI エージェントの案（ADR 0101 の承認）を人の操作にも広げる** | 核（ただし表と状態を増やさない） | 2 | |
| 7 | 設計を実物で検証していない | 手元の攻撃テストと、CI の DAST（OWASP ZAP） | `tests/` と CI | 2 | |

**置く層の決まり（2026-11-18。核は単純で拡張しやすく）**: 7 つのうち 6 つは核（`app/Core`）に新しい概念を増やさずに埋める。インフラ（Docker の網・Caddy・PostgreSQL・Redis・systemd・防火壁）か、すでにある文脈（`Crypto`・`Event`）の中で閉じる。核に入るのは 6 だけで、それも ADR 0101 の承認の仕組みを広げる形にし、新しい表・新しい状態・新しい言葉を作らない。

**名乗り方は変えない**: 公式サイト・説明書・画面に「ゼロトラスト」とは書かない（2026-11-06 の決定のまま）。書くのは「最小権限・テナント分離・明示的な認可」と、実際にやっていること。

## 採らなかった案

- **端末の状態を見る動的なポリシー**（NIST SP 800-207 の原則を全部満たす形）。パッケージで配る製品では、入れる人が端末管理の仕組みを持っている前提になり、お店の人の手間が増える。運営の方針「堅牢さは攻撃への守りで、お客さんや店の人に手間を増やさない」（ADR 0034 の考え）と合わない。1.0 の後に、ホストする形（SaaS）を作るときに考える
- **サービスメッシュ（Linkerd・Istio など）で内部の mTLS**。常駐するものが増え、1 台のサーバーに入れる製品には重い（「本番で Node.js を常駐させない」ADR 0015 と同じ理由）。PostgreSQL と Redis が持っている TLS の設定で足りる
- **核に「承認」の層を新しく作る**。ADR 0101 の案の仕組み（期限つき・押した時に値が変わっていれば反映しない・パスキーの再確認）がそのまま使えるので、増やさない
- **7 つ全部を 1.0 の前にやる**。内部の暗号化と鍵の回転は設計から入るので短くならず、1.0 が遅れる（2026-11-12 に、範囲を絞らないといつまでもリリースできないと判断した）

## 結果

- 1.0 の前にやるのは 2 つだけなので、1.0 の時期は動かない
- 核のコードは増えない。増えるのは `docker/`・`deploy/`・設定と、`Crypto`・`Event` の中
- 「ゼロトラスト対応済み」と言える条件がこの 7 つに定まった（埋まったら脅威モデルの版を上げ、外のレビューに出す）
