# 0020 サードパーティのテーマはコードを含まない形で受け付ける

状態: 採用（2026-10-27）。ADR 0018 の「テーマは composer のパッケージ」を、公式テーマ（自社）に限ると読み替える

## 文脈

ADR 0018 で、テーマは composer のパッケージ（Blade ＋ サービスプロバイダ）にした。公式テーマ（`default`、`kinari`）はこの形で作っている。
運営の指摘: サードパーティのテーマでは、ハッキングなどの恐れがある機能を使えないようにすべき。

今の形のままでは、サードパーティのテーマを安全に受け付けられない。

- Blade の `{{ }}` の中は PHP の式がそのまま動く。テーマは `.env` の秘密を読み、DB に触り、他の店のデータを狙える。サービスプロバイダは PHP のクラスそのもの
- テーマの JavaScript は店頭のオリジンから配られるので、CSP（`script-src 'self'`）を素通りする。お客さんの画面で動き、入力や表示された情報を盗める
- `ThemeTest` は画面のファイルを文字の並びで調べるだけ（`DB::`、`{!! !!}` など）。自分たちのテーマの書き方の決まりには役立つが、`('sys'.'tem')('id')` のような書き方ですり抜けられ、悪意のある作者は止められない

他社の大きな EC の SaaS には、サーバーのコードを書けないサンドボックスの言語（Liquid）でテーマを作らせ、支払いとアカウントの画面をテーマから切り離し、公式のテーマのストアに載せるテーマを審査しているものがある。テーマの JavaScript は許している。

## 決定

テーマを信頼の段階で 2 つに分ける。

**公式テーマ（自社）**: 今の形のまま（composer ＋ Blade ＋ PHP）。核と同じくリポジトリでレビューし、核のコードと同じ扱いにする。

**サードパーティのテーマ**: コードを含まない「データだけ」の包みにする。

- **中身**: テンプレート（Liquid）、ビルド済みの CSS、画像・書体、設定の JSON（マニフェスト）。PHP は入れられない。composer の autoload もサービスプロバイダも使わず、核のテーマの読み込み役が読む
- **テンプレート**: サンドボックスの言語 Liquid。関数の呼び出しや PHP は書けず、渡された値を出すだけ。出力は自動でエスケープし、生の HTML は出せない。描画には上限（時間・繰り返しの回数・出力の大きさ）を掛ける
- **渡すデータ**: テーマ API と同じ中身を、ただの値（配列・文字・数）にして渡す。メソッドを持つオブジェクトは渡さない（そこから逃げ道ができる）
- **JavaScript**: 既定では入れられない。メニュー・写真の切り替え・カートなどの動きは、核が用意した部品を `data-` の印で呼ぶ。**審査と署名を通ったテーマだけ** JS を許す
- **CSS**: ビルド済みのものだけ。外部の `url()`・`@import` は入れるときの検査で断る（CSP でも止まる）
- **核が描く画面**: 支払い（Stripe Checkout へ移る。ADR 0019）、注文の確認、お客さんのアカウントなど個人情報を出す画面は、どのテーマでも核が描く。テーマは色や書体（トークン）で見た目を合わせるだけ
- **入れ方**: 管理画面からは入れない（CONCEPT 7.2）。運営が CLI で入れ、そのときに検査する: ファイルの種類の許可リスト（PHP・JS は断る。JS は審査済みの印があるときだけ）、SVG の中のスクリプト、大きさと数の上限、マニフェストの形とテーマ API のバージョン。SaaS では、審査と署名のあるマーケットから入れる
- **いつ作るか**: サードパーティのテーマを受け付ける前に、この形式と検査を作る。それまではサードパーティのテーマを入れない。形式ができたら、公式テーマもこの形式に移し、自分たちで形式を確かめる

## 結果

- 得たもの: テーマの作者を信頼しなくても、仕組みとして秘密・DB・他の店・個人情報の画面に届かない。審査の手間は JS を使うテーマにだけ掛かる
- 失ったもの: サードパーティのテーマは Blade や PHP を使えず、Liquid と核の部品の範囲で作る。テーマ API の値を Liquid 向けに渡す層と、テーマの検査を作る手間が増える。公式テーマを後で形式に移す手間
- 今の `ThemeTest` は「公式テーマの書き方の決まり」として残す。安全の境界はサンドボックスと入れるときの検査で作る
