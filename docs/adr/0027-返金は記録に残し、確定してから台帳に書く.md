# 0027 返金は記録に残し、確定してから台帳に書く

状態: 採用（2026-10-28）。（取消と返金）の作りを直す。

## 文脈

外部の AI のレビュー（2026-10-28）で 2 つの不整合を指摘され、コードとテストで確かめた。

- **A1 競合**: 取消は「Stripe へ返金（DB のロックの外）→ ロックの中で取り消せるか確かめ直す」の順だった。返金の通信中に別の運営が発送すると確かめ直しで弾かれ、Stripe の返金は実行済みなのに、取消も台帳の返金も残らない（お金は返ったのに記録が無い）
- **A2 保留**: Stripe の返金の答えが `pending`（保留。残高不足などで後から成功か失敗が決まる）でも成功として扱い、すぐ台帳に返金を書いていた。返金の後の知らせ（Webhook）も扱っていないので、後で失敗しても台帳は返金済みのまま。返金が要る支払いの返金も同じ

Stripe への問い合わせ中に DB のロックを握り続けない、という決まり（外の遅さでロックを握らない）は保つ。

## 決定

- **返金は記録（`refunds`、店の DB）に残す**。目的（取消・返金が要る支払い）、金額、支払いの ID、Stripe のアカウント、冪等キー、Stripe の返金の ID、状態を持つ。状態は 4 つ: `requested`（頼む前・頼んだが答えが分からない）／`pending`（Stripe が保留）／`succeeded`／`failed`（→ 今は 6 つ。成功の後に戻された `reversed`〔下の「運用で気をつけること」〕と、額が違って止めた `held`〔2026-10-29 の追記〕を足した。DB の制約 `refunds_status`）。理由（Stripe の失敗の符号）を残し、個人情報は入れない
- **台帳に返金を書くのは `succeeded` になったときだけ**。保留や失敗の間、台帳は「まだお金を預かっている」のまま（実際と合う）
- **取消は 3 段で行う**:
  1. ロックの中で、取り消せるかを確かめ、返金の記録を `requested` で作る。この記録がある間は、発送と完了を断る（A1 の窓を閉じる）
  2. ロックの外で Stripe に返金を頼む（冪等キーは今までどおり取引ごと）
  3. ロックの中で答えを記録する。`succeeded` なら台帳に返金を書いて取り消す。`pending` なら取り消す（返金は確定待ち。台帳には書かない）。Stripe がはっきり断った（4xx）・答えが `failed` なら、記録を `failed` にして取り消さない（今までの「断られたら何も変えない」を保つ）
- **答えが分からないとき**（通信の失敗・5xx・429 など）は、記録を `requested` のまま残し、発送も止めたまま。もう一度押すと、同じ冪等キーで続きから進む（Stripe は同じ返金を返すので二重にならない）。はっきり断られた後にやり直すときは、新しい冪等キー（`-2`、`-3`…）を使う
- **返金が要る支払いも同じ記録を使う**。`succeeded` になってから「返金済み」にする
- 確定（保留 → 成功・失敗）は、区切り 2 で Webhook（`refund.updated` など）と、取りこぼしを拾う定期の問い合わせで行い、管理画面に「返金の途中」「返金が失敗（要対応）」を出す

## 運用で気をつけること（区切り 2）

- 保留の確定は Webhook の `refund.updated`・`refund.failed`（古い形の `charge.refund.updated` も受ける）で行う。**Stripe の側の送り先に、この 2 つを足す必要がある**:
  - 店の鍵を貼る形（パッケージ版）: 店が作る送り先。管理画面の「選ぶイベント」と説明のページに 5 つ（支払いの 3 つと返金の 2 つ）を出した
  - Stripe へ接続する形（SaaS 版）: 運営が 1 か所で受ける Connect の送り先（ADR 0022）。運営が Stripe のダッシュボードで足す
  - 手元の確かめ（`stripe listen --events …`）にも足す
- 知らせを取りこぼしても、定期の確かめ直し（`storefront:reconcile-refunds`、10 分ごと）が、保留のまま 30 分過ぎた返金を Stripe に問い合わせて確定し、答えが分からないまま 10 分過ぎた返金を同じ冪等キーで頼み直す
- 成功の後に戻された返金（`reversed`）は台帳を自動で戻さない。概要の「確かめが要る返金」に出るので、人が Stripe のダッシュボードと台帳を確かめる（台帳の打ち消しの仕組みは後で）

## 結果

- 得たもの: Stripe で返金が実行されたのに記録が無い、という状態が起きない。台帳は実際のお金の動きと合う。失敗した返金が見える
- 失ったもの・気をつけること: 答えが分からないまま押し直されない注文は、発送できない状態で残る（区切り 2 の定期の問い合わせで拾う）。保留の間は「取消済み・返金は確定待ち」という状態があり、画面で分かるように出す必要がある

## 追記（2026-10-29）: 額が違う返金は止めて人が見る

- Stripe の答え（頼んだ直後の答え・知らせ・定期の問い合わせのどれでも）の返金の額が、頼んだ額と違ったら、`requested`・`pending` の返金を **`held`（止めて人が見る）** にする。理由は `amount_mismatch`、Stripe の返金の ID は残す。台帳には書かない
- `held` は途中の返金と同じ扱い（取引ごと・返金が要る支払いごとに 1 つ）。この間は **発送・完了・取消のやり直し・新しい返金をすべて断る**（Stripe に別の額の返金が実在するかもしれない。お金を返したうえに品物も送る事故を防ぐ）。管理画面ではボタンを出さず、概要の「確かめが要る返金」にすぐ出す
- `held` は自動では進めない。定期の確かめ直しは `requested`・`pending` だけを見て、`held` は数だけ出す。正しい額の知らせが後から来ても進めない
- 終わった返金（`succeeded`・`failed`）への知らせは、額が違っても今までの進め方のまま（成功の後の失敗は `reversed`）。額の違いはログに残す
- DB でも守る: `held` なら理由は `amount_mismatch`、`held` は終わった状態ではない（`settled_at` は空）。止めた返金があるうちは、この移行を戻さない
- 前は「`failed` にして発送できる状態に戻す」だったのを置き換える
- 残り: 人が Stripe で確かめた後に、止めた返金を片付ける画面（成功として台帳に書く／失敗として扱う）。お金の権限と、操作の直前のパスキーの確かめを要る形で作る（残りの作業「止めた返金を片付ける」）。それまでは運営が DB で直す

## 作って決めたこと（Stripe の画面で直接した返金、2026-10-31）

- 決済代行の画面で直接した返金（外でした返金）は、知らせを捨てずに残す。前は `provider_ref` で記録が見つからなければ受け取るだけで、台帳は「受け取ったまま」、運営全体の売上も売れたままになっていた（ADR の見直し 2026-10-31 の高）
- 受ける知らせに `refund.created` を足した（Stripe の画面での返金はまずこれが来る。店の Stripe の送り先の設定の一覧 `STRIPE_EVENTS` にも足した。前から設定している店は、送り先に足すと届くようになる）
- 知らない返金は、返金した支払いの ID（`payment_intent`、`pi_`）から取引に引き当てる。台帳の受領の記録（`ledger_journals` の payment の `reference`）か、返金が要る支払い（`stray_payments.payment_ref`）から引く。引き当てられたら、目的 `external`・状態 `held`・理由 `external_refund` の返金の記録を作り、イベント `payment.external_refund_held` を残す。**台帳には書かない**（店の人が確かめてから。片付けの画面は ）。引き当てられなければ受け取るだけでログに残す
- 外でした返金は止めたまま。DB の制約 `refunds_external_held` で、目的が external なら状態は held・理由は external_refund に決まる（知らせで勝手に成功へ進めない）
- 取消の返金の held と違い、外でした返金は発送・完了・取消を止めない（店が一部だけ返金して品物を送ることがある）。確かめが要る返金として、店のホームと運営全体の困りごとに出す
- **こちらが頼んだ返金の取り違えを防ぐ**: 返金を頼むのは DB のロックの外なので、Stripe の返金の ID を残す前に知らせが届くことがある。同じ支払いの ID・同じ額で、途中（requested）で ID の無い返金があれば、それに当てる（外の返金として残さない）
- テスト: `ExternalRefundTest`（外の返金を止めて残す・台帳に書かない・同じ知らせは 1 回・発送を止めない、返金が要る支払いへの引き当て、ほかの店の支払いと ID・額の無い知らせは残さない、頼んだばかりの返金と取り違えない、DB が止めたままを守る、知らせから支払いの ID を読む）。頼んだ返金に当てる所・止める所・返金が要る支払いを引く所を外すと落ちる
