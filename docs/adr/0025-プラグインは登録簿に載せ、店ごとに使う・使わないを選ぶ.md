# 0025 プラグインは登録簿に載せ、店ごとに使う・使わないを選ぶ

状態: 採用（2026-10-28）。ADR 0005（核 ＋ プラグイン）の最初の形。

## 文脈

ADR 0005 で「コードは composer で入れ、有効化は店ごと」と決めたが、仕組みはまだ無かった（入っているのはテーマだけ）。
プラグインとテーマの一覧の次に、店ごとの「使う・使わない」と、使わない店でプラグインの画面・経路・定期の処理が動かないことを作る。
見本の最初のプラグインは「商品ページのよくある質問」（選択肢から選んだ。核の「お知らせ」と重ならないもの）。

## 決定

- **登録簿**: プラグインは自分のサービスプロバイダで `PluginRegistry` に定義（名前・表示名・説明・プラグイン API のバージョン・ショップの経路）を登録する。プラグイン API のバージョンが合わない・名前が二重・形の違う名前は受け付けない（テーマの登録簿と同じ）。今のプラグイン API は 1
- **店ごとの状態は店の DB**（`plugin_states`。プラグインの名前・使うか・変えた日時）。変えるのは `PluginStates` だけで、`EventStore::lock()` を先に取り、`plugin.enabled` / `plugin.disabled` を同じトランザクションで残す。入っていないプラグインは使えない。止めてもプラグインのデータは消さない（消すのはアンインストールで、後で）
- **使わない店では動かない**: ショップの経路は核がプラグインの代わりに登録し、`storefront`・`public`・`plugin:<名前>` の印を必ず付ける（使わない店では 404）。定期の処理は `PluginTenants::each()` で使う店だけを回す。ショップへの差し込み（後の区切り）も使う店だけで描く
- **変えるのは管理画面の店の「プラグイン」**（運用の段階、直前の再確認）。入れる・外すは今までどおり composer だけ（CONCEPT 7.2）

## 結果

- 得たもの: プラグインを入れても、使うと決めた店だけで動く。何を使っているかは店の記録（イベント）に残る
- 失ったもの・気をつけること: 店の数だけ状態の行が要る（無ければ「使わない」）。プラグインの表は店の DB に置くので、移行はどの店にも流れる（使わない店では空のまま）。プラグインのコードは核と同じ権限で動くので、入れるのは審査したものだけ（外部のプラグインの審査と隔離は後で）

## 作って決めたこと（2026-10-30 区切り 5「App の画面」）

- **App の目的（`category`）をマニフェストに書く**（App の一覧を目的別に並べるため）。composer.json の `extra.ec-sugar.category` に、核が決めた言葉（`App\Core\Plugin\Manifest\AppCategory`）を 1 つ: `analytics`（アクセスの解析）・`marketing`（集客と広告）・`page`（ページの部品）・`selling`（売り方。定期便・予約・買取）・`products`（商品と在庫）・`payment`（お支払い）・`shipping`（配送）・`customers`（お客さん）・`operations`（店の運営）・`other`（そのほか）。並びは管理画面に出す順
  - 知らない言葉（打ち間違い・大文字・並び・空）は**登録で断る**（`AppManifest::fromArray`。テーマの theme.json と同じく、アプリが起動しない）。黙って「そのほか」に落とすと、打ち間違いに誰も気づかないため
  - 書かなければ「そのほか」。マニフェストを渡さないプラグインも「そのほか」。目的は見せ方だけで、動き・権限・店の境界には何も関わらないので、プラグイン API は 1 のまま
  - 言葉は「今ある App」と「これから来る縦（買取・定期・予約・お支払い・配送）」が入る数にした（10 個）。足すのは核の変更（ここに書く）。消す・意味を変えると今の App が読めなくなるので、しない
  - 今ある App: タグの解析（GA4・Clarity・見本）は `analytics`、広告の計測タグ 8 つは `marketing`、動画・地図・よくある質問は `page`。よくある質問は、目的を書くためにマニフェスト（composer.json）を渡すようにした（ほかの宣言は無い）
- **店の App の一覧の API**（`GET /api/tenants/{店}/plugins`）は、目的の言葉の並び（`categories`: `key`・`label`・`description`）と、App ごとの `category`、設定のある App の `settings.complete`（入れるべき項目〔`required`〕がそろっているか。秘密の項目は入っているかで見る）を返す。言葉と並びは核が持ち、画面は写さない。読むのは今までどおり閲覧の段階から、使う・使わないは運用の段階で直前の再確認の後（変えていない）
- 画面は目的ごとのまとまりに札で並べ、言葉で探す・使っている App だけに絞る（条件は URL）。App は多くても数十なので、絞り込みは画面の中で行い、API に絞り込みは足さない（docs/design/admin-ui.md の「App の画面の型」）

## 作って決めたこと（2026-10-31、「名前を EC-SUGAR に統一する」）

- **マニフェストのキーを `extra.ec-sugar` に改め、旧名 SUGAR-EC のころのキー `extra.sugar-ec` も当面は読む**。キーは外の人が作るテーマや App も使う約束（テーマ API・プラグイン API）なので、いきなり読まなくすると古いキーのパッケージが入らなくなる。読むのは核の 1 か所（`App\Core\Plugin\Manifest\PackageManifest`）で、入っている一覧（`InstalledPackages`）と登録簿（`PluginRegistry`）がそれを使う。`ec-sugar` が無いときだけ `sugar-ec` を読み、両方あれば `ec-sugar` だけを見る（古い方を混ぜない。新しい方が壊れていても古い方に戻らない）。誤りの文は読んだキーで言う。公式のプラグインとテーマと文書の例は新しいキーにした。テーマの登録（`ThemeRegistry`）は theme.json を読み、このキーは読まない。古いキーをいつ読まなくするかは、外のパッケージが出てから決める
- **自社の見分け（`first_party`）は新しい作り手の名前 `ec-sugar/` だけ**（このリポジトリの `plugins/` から path で入ったもの、は今までどおり）。旧名の `sugar-ec/` は自社と見ない。名前の読み替えで見分けを緩めないため
- composer の作り手の名前は `ec-sugar/…`、名前空間は `EcSugar\…` にした。店の DB には短い名前（`ga4`・`fashion` など）しか保存していないので、店のデータは移さない。暗号の鍵を派生する文脈の名前（`sugar-ec.blind-index.v1` など）は、保存したブラインドインデックスと記録の封印が合わなくなるので旧名のまま

## 作って決めたこと（2026-11-01 定期便）

## 作って決めたこと（2026-11-04、App「商品レビュー」）

- 公式の App「商品レビュー」（`plugins/plugin-reviews`、名前 `reviews`、目的 `customers`）を、核の口だけで作った: 表は店の DB の `reviews`（プラグインの移行）、管理画面は App の画面と直すだけの欄（ADR 0051 の作って決めたこと）、ショップは商品の画面の説明の下の口に星と返信を足したもの（ADR 0050 の作って決めたこと）、会員のマイページの入口（`AccountLink`）、ご注文の確認の画面の入口（新しい口。ADR 0050 の作って決めたこと）。使う店だけで動き、止めてもレビューは消さない。プラグイン API は 1 のまま
- **書けるのは買った人だけ**: ショップで確定した物販の注文（ショップの注文の印がある `sale`）で、**発送済みか完了**（取引の段が受渡・受取確認・精算で、取消・返金をしていない）の注文の、商品の行の商品だけ。払っただけ（発送の前）では書けない（届く前の感想を混ぜない）。1 つの注文の 1 つの商品に 1 つ（DB の一意でも守る）。同じ商品の種類違いは 1 つと数える
- **会員とゲストの入口**: 会員はマイページの「レビュー」（`/p/reviews/account`。自分と、店の人がまとめた記録の注文の、新しい 30 件）。ゲストはご注文の確認の画面の「レビューを書く」で、App が自分の経路に**署名と 24 時間の期限と店の ID**をつけて渡す（ご注文の確認の画面は、核が注文を見てよいと確かめた後だけ描く）。書く欄とその送り先も同じ署名つきの道筋。会員は自分の注文なら署名なしで開ける。どちらでもない・期限切れ・ほかの店は、注文があるかを教えずにご注文の確認へ
- **公開は店が決める**: 既定は「店が公開するまで出さない」（確認待ち）。App の設定 `publish`（`manual`・`immediate`）で「すぐ出す」も選べる（出した後でも非公開にできる）。状態は確認待ち・公開・非公開・消した。**消すと行は残して題・本文・表示名・返信を空にする**（同じ注文の同じ商品にもう一度書かせない。中身は残さない）。書いた人には、非公開・消したことを見せない（どれも「書きました」）
- **文の決まり**: 星 1〜5、題 50 文字（1 行）、本文 1000 文字（改行はよい）、表示名 20 文字（1 行。空なら「購入者」。`@`〔全角も〕は断る）。制御文字・文字の向きを変える印（LRM・RLM・ALM・埋め込み・上書き・分離）・幅の無い空白・BOM を断る。つないだ絵文字に要る U+200D は通す。長さと空でないことは DB でも守る
- **個人情報**: 表は注文と商品の ID・星・文・表示名・状態・返信だけで、名前・メール・届け先・お客さんの台帳の ID は持たない（書いた人は注文でつながるだけ）。表示名はお客さんが「出してよい」と書いた名前なので平文で置く。記録（`review.written`・`review.published`・`review.hidden`・`review.replied`・`review.deleted`）は ID・星・状態だけで文を入れない。お客さんの書き込みの actor は `storefront`
- **回数の上限**: 書くのは接続元ごと・店ごとに 1 時間 10 回まで（欄の誤りで断った回も数える）。経路にも `throttle:storefront-cart`。数の上限は注文の数で決まる（1 つの注文の 1 つの商品に 1 つ）ので、店ごとの件数の上限は置かない
- ショップの並びは公開したレビューの新しい 20 件と、公開した全部の平均（10 倍した整数で四捨五入。浮動小数を使わない）と件数。商品の一覧に平均の星は出さない（テーマ API の商品のカードを広げるのは、要るとなってから）

## 作って決めたこと（2026-11-04、App「商品フィード」）

- **App「商品フィード」（`plugins/plugin-product-feed`）を核の口だけで作った**: ショップの経路（`/p/product-feed/{google|meta}/{トークン}.xml`。核が storefront・public・plugin の印を付ける）、店の DB の表（`product_feed_feeds`・`product_feed_listings`）、App の画面（ADR 0051）、商品の画面の欄（ADR 0050）、設定（ブランドと Google の商品カテゴリの既定）。核に足したのは App の画面の「写す」の印だけ（ADR 0051 の作って決めたこと）
- **公開の URL は推測されないトークンで守る**: Google と Meta はログインできないので、URL に 160 ビットの乱数を入れる。店の人が作る・作り直す・止める（作り直す・止めるは直前の再確認の後。イベントにトークンは入れない）。トークンは店の鍵で暗号化して置き（管理画面に URL を出すため）、照らすのは SHA-256 の値どうしで。違う・止めた・公開していない店はどれも同じ 404。店と接続元ごとに 1 時間 60 回まで（トークンを確かめる前に数える）
- **出すのはショップに出ている商品だけで、読むのは核のショップの窓口（`Catalog`）から**: 下書き・終了・見積もりの商品・止めた出品者・止めた種類・0 円を売らない店の 0 円の品は、ショップの商品の画面と同じ決まりで入らない。決まりを App の中に写して持たない（ずれないように）
- **キャッシュは 1 時間、鍵に店の記録の連鎖のいちばん新しい番号を入れる**: 商品・種類・在庫・写真・設定・App の欄を直すとどれもイベントが残るので、次の読み込みから新しい鍵になる（消して回る処理が要らず、消し忘れも起きない）。イベントを残さない書き込み（カートなど）はフィードに関係しない。キャッシュに置くのは文字と配列だけ（`serializable_classes` が false）
- **準備中の店は、核の関所（`RequireShopAccess`）が先に「準備中です」の画面へ送る**（302）。パスワードを入れた人にもフィードは出さない（404）。関所の外に出す（準備中でも 404 で答える）には核の一覧に App の経路の名前を書くことになるので、今はしていない

## 作って決めたこと（2026-11-04、App「再入荷のお知らせ」）

- 公式の App「再入荷のお知らせ」（`plugins/plugin-restock`、目的は「商品と在庫」）を、核の口だけで作った: 表は店の DB の `restock_requests`、ショップは商品の画面の買い方の口（売り切れの時にも出す印を足した。ADR 0050 の作って決めたこと）と自分の画面（`/p/restock/…`）、管理画面は App の画面（種類ごとの数だけ。操作は無い）。核のコードで変えたのは、買い方の口の印と、4 つのテーマの売り切れの枝に部品を置いたことだけ
- **在庫が戻ったことは、核の記録の知らせ（`DomainEventRecorded`）で知る**（核に新しい口は足さない）: `inventory.received`・`inventory.adjusted`（増やす向き）・`transaction.phase_changed`（取消・返金。確保していた在庫が戻る）。聞いた側は待っている登録のある種類だけをキューに回し（在庫を変えた要求を待たせない）、知らせるかは「ショップでカートに入れられるか」（`Catalog::purchasableVariants`）で決める。記録の残らない変わり方（見積もりの受け入れで確保を解く・`StockService` を直に使う直し）と、商品を公開し直した時の分は、1 時間ごとの `restock:run` が拾う（遅れは最大 1 時間）
- **登録の表は、連鎖のロックとイベントの決まりの例外**（conventions.md の 3 の 3 つの条件を満たす）: 取引・在庫・お金の状態ではなく、監査の源泉にもならない「お客さんが頼んだ知らせの予約」で、公開の受付から誰でも作れる行のため、追記だけの記録（イベント）に積まない（いたずらの登録で、消せない記録が膨らむのを防ぐ）。守りは行のロック・部分の一意の索引・1 文の条件つきの更新
- **一度に知らせる数は絞らない**（待っている人の全部へ、古い順に 1 通ずつキューで）。在庫の数で絞ると、残りの人は在庫が残っている間「0 から戻る」が起きず、知らせが来ないため。先に買えるかは早い者勝ちで、メールにそう書く
- **ゲストは確かめのメール（ダブルオプトイン）、会員はすぐ有効**: 会員のメールはログインのコードで確かめてあるため。確かめ・取り消しのリンクの画面は開いただけでは変えず、ボタン（POST）で変える（メールのリンクを先に開く仕組みで勝手に確かめない）。ゲストへの答えは、送った・もう登録がある・回数の上限のどれでも同じ（登録があるかを、ほかの人が確かめられない）
- **知らせた・取り消した登録からはメールを消す**（数だけが残る）。管理画面にもアドレスは出さない（店の人の連絡先の一覧にしない。宣伝に使えない）

## 作って決めたこと（2026-11-05 App「お問い合わせ」）

- 公式の App「お問い合わせ」（`plugins/plugin-contact`、目的は「お客さん」）を核の口で作った: 表は店の DB の `contact_inquiries`・`contact_replies`、ショップは自分のフォーム（`/p/contact`・商品を付ける `/p/contact/product/{商品}`・注文を付ける `/p/contact/order/{注文}`）と、商品の画面の買い方の口（「この商品について問い合わせる」。売り切れでも出す。行き先を持てる商品の画面の口はこれだけなので、買い方でない入口もここに置いた）と、ご注文の画面のリンクの口（「この注文について問い合わせる」。署名と期限と店の ID つき）。管理画面は App の画面（一覧・1 件・状態・消す・返信）。核のコードで変えたのは App の画面の 2 つの印（個人情報の印と、直す欄の言葉。ADR 0051 の作って決めたこと）だけ
- **お問い合わせは、連鎖のロックとイベントの決まりの例外にしない**（再入荷のお知らせの登録とは逆）: 店の人の返信（店の名前で、お客さんへメールを送る）と、状態の変更・消すは「誰がしたか」を問われる。お客さんの受け付けもイベント（`contact.received`）に残す。公開の受付から作れる行なので、記録が膨らむのは回数の上限（接続元・メール・店全体で 1 日 300 件）とボットよけで抑える。イベントの中身は ID と種類・状態だけ（名前・メール・本文・返信の文は入れない）
- **受け付けのメールに、お客さんの書いた文の写しを載せない**（名前も本文も）: フォームには好きなアドレスを書けるので、写しを載せると店のメールで他人へ好きな文を送れる。店への知らせのメールも本文を載せない（店の外の受信箱に残るため）。知らせの宛先は App の設定の秘密の項目（店の鍵で暗号化。空なら送らずホームにだけ出す）。店の設定にメールのアドレスの欄は無いので、App の設定に置いた
- **済んでから 1 年（設定で半年・3 年）で行ごと消す**（毎日の `contact:prune`。使うのをやめた店でも、消す分が残っていれば回す。`PluginTenants::each` の残りの仕事の印）。済んでいないお問い合わせは消さない（返事をしないまま消さない）。店の人が頼まれて消す「消す」（直前の再確認の後）もある
- **ボットよけは見えない欄と書き始めの時刻**（署名つき。3 秒より前は落とす）で、CAPTCHA は使わない（お客さんの手間を増やさない。運営の方針〔2026-10-30〕で、堅牢さは攻撃への守りであり、お客さんに手間を増やすことではない）。落としたものにも受け付けと同じ画面を返す
- 済みの状態と済んだ時刻はいつもそろう（DB の制約）。返信は 1 件に 20 通・1 時間に 10 通、同じ文の押し直しは 10 分のうち断る（メールを 2 通送らない）

## 作って決めたこと（2026-11-05、App「メルマガ・一斉メール」）

- 公式の App「公開の予約と販売期間」（`plugins/plugin-sale-period`、名前 `sale-period`、目的 `selling`）を作った。核に足した口は 1 つ: **商品を「今はショップに出さない」「今は売らない」と App が答える口**（`App\Core\Plugin\Contracts\ListingVisibilityProvider`、`PluginDefinition::$listingVisibility`。窓口 `App\Core\Plugin\Services\ListingVisibility`。ショップの窓口 `Catalog` が、`published()` で出さない商品を除き、札と商品の画面で売らない商品を売り切れにする。何個の App でも持てる）。プラグイン API は 1 のまま（口は足しただけ）
- **見せ方の口と、断る口を分けた**: 「出さない・売らない」は見せ方だけで、カートに入れさせない・注文を確定させないのは前からある売り方を押さえる口（`SaleHoldProvider`。ADR 0080）に任せた。断りの文をお客さんに見せられ、App の 1 品の注文（チケット・定期便）にも同じ決まりが効くため。どちらも同じ読み出し（`SalePeriodSchedule`）を見るので食い違わない
- **商品の状態（`listings.status`）は変えない**: 「公開の予約」を状態の書き換え（下書き → 公開）で作ると、核の表を App が書くことになり、店の人が決めた状態も上書きしてしまう。期間は App の表（`sale_period_windows`、1 商品に 1 行）だけに持ち、出す・売るの判断をショップの読み出しのたびに今の時刻と比べる（見張りの処理が無いので、秒の単位でそのとおりに変わる）
- 境界は「出す日時のちょうどに出る・終わる日時のちょうどに終わる」（終わりは半開区間）。日時は店の人が日本時間で入れ、置くのは UTC（`SalePeriodTime`）
- App が落ちた時は「出さない・売らない商品は無い」として扱い、ショップを止めない（`ListingVisibility` が `report()` とログを残す）。公開の前の商品が早く見えるより、ショップが落ちる方が重いという判断（会員だけの商品〔ADR 0079〕は逆に、誤りをそのまま上げる）
- 一覧は札ごとに「今は売らないか」を聞くので、要求の中で覚え（`WeakMap`）、一覧とカートの読み出しはまとめて先に聞く（商品ごとの問い合わせを並べない）
## 作って決めたこと（2026-11-18 App「並び順と絞り込み」）

- 公式の App「並び順と絞り込み」（`plugins/plugin-catalog-sort`、名前 `catalog-sort`、目的 `products`）を作った。表は店の DB の `catalog_sort_items`（商品ごとに 1 行の並びとタグ。並びは一意〔DEFERRABLE〕、タグは jsonb の配列で GIN の索引）、管理画面は App の画面（一覧・1 件・上へ・下へ・一覧から外す。ADR 0051）、設定はマニフェストの `settings`（どの絞り込みを出すか・価格の帯の区切り・はじめから「おすすめ順」で出すか）。ショップの経路は持たない
- **核に足した口は 1 つ**: ショップの一覧の並びと絞り込みの口（`App\Core\Plugin\Contracts\CatalogBrowseHandler`、`PluginDefinition::$catalogBrowse`。店で 1 つの App だけ）と、それを読む窓口 `App\Core\Plugin\CatalogBrowse`。プラグイン API は 1 のまま（口は足しただけ）
- **絞り込みの決まりは核が持ち、何を出すかは App が決める**: 核は「決まった列で並べる・決まった列で絞る」だけ（並びは商品の ID の配列、価格は札の値段と同じ式、在庫は在庫の表）。App が返した選択肢の `key`（英小文字・数字・ハイフンで 24 文字まで）と同じ文字がお客さんの入力に来た時だけ受け、違えば「選んでいない」と同じに扱う（断らない）。**列の名前や SQL をお客さんの入力から作らない**
- **数の上限は核が決めて削る**: 手で並びを決められるのは 500 点（`CatalogBrowse::MAX_ORDER`。それより後ろは今までの並び）、絞り込みの選択肢は 20 個、1 つのタグで絞り込める商品は 1,000 件、選択肢の名前は 24 文字。上限を超えた分・形の違う商品の ID は捨てる
- **App が落ちたら絞り込みも並べ替えも出さない**（一覧は今までの新着順・価格の順のまま。会員だけの商品〔ADR 0079〕と違い、見えてはいけないものを出す向きの失敗にはならないため）
- テーマ API は番号を上げない（`ProductListView::filters()` は付け足しで、絞り込みを出さない店では空の配列。今のテーマはそのまま動く）

## 作って決めたこと（2026-11-19 セット商品）

- 公式の App「セット商品」（`plugins/plugin-bundle`、名前 `bundle`、目的 `selling`）を作った。核に足した口は区切り 1 の 1 つだけ（`Contracts\StockComponentsProvider`。この商品の在庫はどの品からいくつ引くか）で、売り切れの見せ方は `ListingVisibilityProvider` を使い回した
- **入れ子は保存のときに断る**（読むときに辿らない）: 核は構成を 1 段しか辿らないので、辿る深さを核に持ち込むより、App が「セットの中にセットを作れない」ようにする方が簡単で安全。断る 3 方向（自分自身・構成の品が別のセット・この商品がほかのセットの構成）を連鎖のロックの中で確かめ、**DB の CHECK と引き金でも守る**（在庫とお金に関わる決まりなので二重にする）
- **構成の品は品番（SKU）で書く**: 核の商品の画面の App の欄は文・切り替え・選ぶの 3 つだけで、選ぶ欄の選択肢は 20 個まで（`AppManifest::MAX_OPTIONS`）。商品が何千ある店では選ばせられないので、「品番*数」をコンマで区切って書く形にした（品番を付けていない品は種類の ID でも書ける）。商品を探して選ぶ部品を核に足すかは 1.0 の後
- **セットの値段はセットの商品が持つ**（構成の品の値段を足し合わせない）。返品・返金は注文の行ごとなので、セットは 1 行・1 つの値段のまま変わらない（お金の按分は出てこない。調べ）
- **セットの商品そのものに在庫は入れない**: 最初の作りでは核の注文の割り当てが商品の在庫の行から拠点を決めていたため、セットにも「売れても減らない在庫」が要った。これは店の人への手間なので核を直した（買えるかの判定・拠点の決定・押さえる所が構成する品を拠点ごとに数える。[ADR 0108](0108-自分の在庫を持たない商品は構成する品から数え、核は口を1つだけ持つ.md)）
