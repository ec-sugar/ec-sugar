# 0006 読み取り専用イメージと署名付き更新

状態: 採用（2026-10-27）。署名つきの更新はまだ作っていない。署名ができるまで本番の自動の更新は既定で切る（下の「作って決めたこと（2026-10-31）」）

## 文脈

国内 EC のカード情報漏洩の多くは、古いバージョンのまま放置された自社サイトで起きている。
よくある設置型の EC では、SIer がカスタマイズした核に更新を当てると壊れるため、店が置き去りになった。
更新経路そのものも攻撃対象になる（SolarWinds、3CX）。

## 決定

- コードは読み取り専用のイメージとして配布する。Web プロセスはコードを書き換えられない。WP 型の自己書き換え更新はしない
- 更新はイメージの差し替え ＋ 前方互換マイグレーション（expand / contract。公開の前は列を消す移行を許す、下の追記）。更新前にバックアップ、更新後にヘルスチェック、失敗したら前のイメージへ戻す
- リリースは署名し、更新側は検証してからしか適用しない（→ 未実装。下の追記）
- カスタマイズ（テーマ・プラグイン）は核の外に閉じ込め、更新前に互換範囲を検査する
- 既定: セキュリティ修正は自動適用オン、マイナー・メジャーは任意（→ 署名ができるまでは、本番の自動の更新を既定で切る。下の追記）

## 結果

- 得たもの: 放置された設置先を守れる。更新が保守契約の中身として売れる
- 失ったもの: 開発中はバインドマウントで動かすため、本番と開発で起動の形が少し違う（docker-compose.prod.yml で揃える）

## 作って決めたこと（2026-10-31、ADR の見直し。選択肢を比べて決めた）

- **署名つきの更新はまだ無い**。今のサーバーは取り先の git の枝を追い（ステージングは main を 15 分ごと）、署名を確かめずに取り込む。署名つきのイメージとタグ（ADR 0030 の 2 つの署名）は で作る。ADR 0030 の「今のステージングの自動の更新（署名なし・枝の先を取る）は、外に開いていない試験の環境だから許している形で、このまま配らない」のとおり
- **本番の自動の更新は既定で切る**: 署名ができるまで、本番（`MODE=production`）には更新のタイマーを入れず、運営が手で `ec-sugar update` する（控え → 移行 → 入れ替え → 健全か → 駄目なら戻す、は今までどおり）。ステージングは 15 分ごとの自動のまま。インストーラーの直しは別に作る
- **列を消す移行**: 公開（先行公開 v0.1.0）の前は、列を消す・名前を変える移行を許す。公開の版からは二段（足す → 次の版で消す）を守る。列を消す・名前を変える移行を見つける検査を CI（GitHub での自動の検査）に入れ、公開の前は「許す印」を付けた移行だけを通す（検査は別に作る）
- 列を消す・名前を変える移行の見張り（2026-10-31）: `tests/Unit/MigrationsExpandContractTest.php` が、移行の `up()` の中の列や表の削除・名前の変更を落とす。公開の前の例外は、その行の上に「// 公開の前の例外（ADR 0006）: 理由」の印を書く（今は 3 つ: ヒーローの写真・店の設定の古い項目・品番の移し）。公開した日を `tests/Support/launched-on.txt` に `YYYY_MM_DD` で書くと、それより後の移行は印があっても通らない
- 本番の自動の更新を既定で入れない（2026-10-31）: インストーラーの答えに `AUTO_UPDATE`（既定はステージングが yes、本番が no）。no なら自動の更新の時計を入れず、前に入れていた時計も止める。`tests/Unit/InstallerAutoUpdateTest.php` が見張る
