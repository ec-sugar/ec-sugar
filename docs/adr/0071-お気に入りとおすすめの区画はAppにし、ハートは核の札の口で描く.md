# 0071 お気に入りとおすすめの区画は App にし、ハートは核の札の口で描く

状態: **採用**（2026-11-05。運営が作ることを決めた。要点の 1〜3 を先に決め、細部は作りながら決めて下の「作って決めたこと」に書いた）。ADR 0010（個人情報）・0025（プラグイン）・0039（ページビルダー）・0040（App が区画を足す口）・0044（会員）・0050（商品の画面の買い方の口）・0051（App の画面）・0067（お知らせのメールの同意）の上に足す。置き換えるものは無い

## 文脈

- お客さんが気になった商品を残しておく所が無い（会員のマイページは注文の履歴と届け先だけ）。値下げや再入荷を待つ人に、店から知らせる道も「再入荷のお知らせ」（種類ごとに 1 回）しか無い
- ページビルダー（ADR 0039）で置ける商品の並びは、店の人が選んだ商品・新着・カテゴリだけ。お客さんごとに変わる並び（最近見た商品）や、売れた数の並びが無い
- 核の口でできること: 商品の画面の「カートに入れる」の近くに App がリンクを置く（ADR 0050）、マイページに入口を置く、ページに区画を足す（ADR 0040。今の公式の App は外から埋め込む区画だけ）、宣伝のメールの同意を聞く（ADR 0067）。一覧の札（商品のカード）に App が何かを置く口は無い

## 決定

1. **App「お気に入り」**（`plugins/plugin-favorites`、名前 `favorites`、目的は「お客さん」）: 会員が商品の画面と一覧の札でハートを押して足す・外す（JavaScript の有り無しのどちらでも動く。POST と CSRF）。マイページに一覧。会員でない人が押すとログインへ（戻り先は自分のショップの中だけ）。1 人 500 件まで。お気に入りの商品が**値下げ・再入荷したら知らせる**（会員が選ぶ。既定は切。値下げは毎日の処理で前の日の値段と比べる。広告にあたる知らせなので、お知らせのメールの同意〔核の口 `MarketingConsent`〕がある人だけ。再入荷の App があれば重ねて 2 通にしない）。App の画面はお気に入りの多い商品の順位（個人情報は出さない）
2. **App「おすすめの区画」**（`plugins/plugin-recommendations`、名前 `recommendations`、目的は「ページの部品」）: ページビルダーの区画を 3 つ足す（ADR 0040 の口）: 関連商品（同じカテゴリから。無ければ新着）・最近見た商品（ブラウザの Cookie に商品の ID だけ、20 件まで。会員でもサーバーに履歴を残さない）・売れ筋ランキング（直近 30 日の払った注文の数。毎時に数えて持つ。ショップを開くたびに数えない）。どの区画も公開中で買える商品だけ、見た目はテーマに合わせる
3. どちらも管理画面のヘルプを足し、App の一覧の目的のまとまりに入れる

## 結果

- 得たもの: お客さんが商品を残して見返せ、値下げ・再入荷を選んだ人へ 1 日 1 通にまとめて知らせられる。ページに、お客さんごとに変わる並びと売れ筋の並びを置ける。核には「札に App のボタンを置く口」と「押す・戻すのボタンの部品」ができ、ほかの App（比べる・あとで買う など）も使える
- 気をつけること: 公式の 4 つのテーマの札の形を変えた（リンクを外枠で包み、外枠の中・リンクの外にボタンを置く）。他社のテーマは、札に核の部品を置くまでハートが出ない（ほかは今までどおり動く）。お気に入りの知らせはメルマガの App を使っている店でしか届かない。商品の画面に関連商品を置く場所はまだ無い（下の「作って決めたこと」）

## 作って決めたこと（2026-11-05）

### 核の口（小さく 3 つ。`PluginDefinition` は変えない）

- **押す・戻すのボタン（トグル）**: `PurchaseOption` に `pressed`（`?bool`）を足した。`null` なら今までどおりのリンク、真偽があれば核の部品 `<x-storefront::toggle-button>` が行き先へ POST するフォーム（CSRF の合い言葉・押した後の形 `pressed=0|1`・戻る先 `back`）で描き、`aria-pressed` を付ける。商品の画面の買い方の部品（`purchase-options`）はトグルをこの部品で描く（テーマの変更は要らない）。押した後の形を送るので、2 つの画面で押しても、同時に 2 回押しても同じ結果になる
- **札の口** `App\Core\Plugin\Contracts\CardOptionProvider`（`forCard(string $listingId): ?PurchaseOption`）: 買い方の口（`purchaseOptions`）に渡した係が同じオブジェクトで実装した時だけ使う（`MarketingConsent` と同じ形。並んで動く仕事と `PluginDefinition` の形がぶつからないように）。札に出すのはトグルだけ（ほかの形は核が捨てる）。核の窓口 `App\Storefront\Catalog\CardOptions` が、この店で使っている札の口の App を**1 回の要求で 1 度だけ**決める（札の枚数だけ「使っているか」を引かない。要求ごとに `WeakMap` で覚え、要求が終われば消える）
- **札の部品** `<x-storefront::card-options :listing="$listing->id" />`: テーマの札（`partials.product-card`）が、札の外枠 `<div class="sugar-card">` の中、リンクの**外**に置く（フォームはリンクの中に置けない）。見た目は核の CSS（`apps.css` の `.sugar-card`・`.sugar-card-options`。写真の右上に重ねる。色はテーマのトークン）。ボタンが無ければ部品の中身（`$slot`）を出す（kinari の前からの飾りのハートは、App を使わない店ではこの形で残した）。4 つの公式テーマに置き、`ThemeTest` が見張る
- **JavaScript**（核の `resources/storefront/toggles.js`。`cart.js` から読む）: `form[data-sugar-toggle]` を画面を移らずに送り、答え `{pressed, label}` で形と文字を替える。同じ行き先のボタン（商品の画面と、その下の並びの札）は全部そろえる。401 と `login`（自分のオリジンの道筋だけ）ならそこへ移る。ほかの失敗はフォームのまま送り直す（JS の無い時と同じ道）
- **埋め込まない App の区画もショップに出す**: 今までは「埋め込むものがある時だけ出す」（ADR 0040）で、埋め込まない区画は出なかった。`AppSectionView::$embeds`（宣言に `embed` があるか）を足し、埋め込まない区画は、出してよく設定がそろえば出す（中身が空の時に何も描かないのは App の Blade が決める）。埋め込む区画は今までどおり

### App「お気に入り」

- **表**（店の DB。名前・メールは置かない。会員は台帳の ID）: `favorites_items`（会員 × 商品で一意）・`favorites_settings`（会員ごとの選択）・`favorites_prices`（前の日に見た値段と売り切れか）・`favorites_notices`（会員 × 日で一意の送った記録。載せた商品と変わり方は ID と金額だけ）。会員や商品が消えたら一緒に消える（App の表のために核の消す操作を止めない）
- **連鎖のロックとイベントの例外**（conventions.md の 3 の条件）: お気に入りは会員が付けた印で、状態でも、お金と在庫でも、監査の源泉でもない。会員ごとの `pg_advisory_xact_lock` の中で数えて足し（500 件を同時の 2 つでも越えない）、会員 × 商品の一意の制約が二重を拒む
- **足せる商品**: ショップに出ている商品だけ（`Catalog::isPublished`。下書き・終了・ほかの店・知らない ID は 422）。公開を終えた商品は一覧に名前だけ残り（「いまはショップに出ていません」）、外せるが足し直せない。知らせにも載らない
- **会員でない人**: 足そうとした商品の ID（ショップに出ているものだけ）をセッションに覚えて、核のログインへ `?return=/p/favorites/back/{商品}`（核のログインは App の道筋 `/p/…` だけへ戻す）。戻ってきた GET は、覚えていた商品と同じ時だけ足して商品の画面へ（足すのは CSRF の合い言葉つきの POST で頼まれた分だけ。戻り先の URL を踏ませても足さない）
- **戻る先 `back`**: 自分のショップの中の道筋だけ（`/` で始まり、`//`・`/\`・制御文字・外のホストは商品の画面へ）
- **回数の上限**: ハートと選択の保存は、接続元ごとに 1 分に 60 回（カートの書き込みと同じ枠 `storefront-cart`）
- **ショップの重さ**: 札の枚数が多くても、会員の印は 1 回の要求で 1 度だけ読む（`Favorites::ids` を要求ごとに覚える）。ゲストは読まない。テストが「札 8 枚で 1 回」を見張る
- **知らせ**（毎日 10:15 の `favorites:notify`。使う店だけ）:
  - 値下げ＝札の値段（種類のいちばん安い値段、税込み）が前の日に見た値段より安い。再入荷＝前の日は売り切れで今は買える。見た値段は商品ごとに**日に 1 回だけ**書き換える（同じ日の 2 回目はもう見た商品を飛ばす）。初めて見た商品は控えるだけ。値上げは知らせない
  - 1 通にまとめて会員 × 日で 1 行（一意。日に 1 通まで）。20 品まで載せる
  - 送らない: 選んでいない・退会した・まとめられた会員、お知らせのメールの受け取りに同意していない会員（`MarketingConsents`。答える App〔メルマガ〕を使っていない店では誰にも）、送り主の表示（特商法の表記）が足りない店。送る仕事は送る直前にもう一度確かめる（選びをやめた・同意をやめた・商品が出ていない）
  - **再入荷の App と 2 通にしない**: 再入荷の App を使っている店では、同じ商品について、その会員（台帳の ID か、同じメールの索引）の登録が「入荷を待っている」か「3 日のうちに知らせた」なら、こちらの再入荷は載せない。App 同士を直につながない決まりの例外で、再入荷の App の表（`restock_requests`）を読むだけ（表が無ければ見ない）。核の口にするほどの広さが無いので、今は読むだけにした（運営に確かめる点）
  - 1 店の処理は店ごとの錠の中の 1 つのトランザクション（落ちたら全部戻り、次に流した時にやり直す）
  - メールは文の形だけ。商品の今の名前・値段の変わり方（「値下げ: ¥1,800 → ¥1,500（税込）」）・商品の画面のリンク・お気に入りの一覧のリンク。特定電子メール法の表示（送り主の名前・住所・問い合わせ先）と、ワンクリックの配信の停止（List-Unsubscribe / List-Unsubscribe-Post。RFC 8058）。送り主の表示はメルマガ・カゴ落ちの App の `SenderFacts` と同じ決まりを写して持った（3 つ目の写し。核へ移すかは後で決める）。**2026-11-19 で核の `App\Core\Mail\SenderFacts` へ畳んだ**
  - **配信の停止** で止めるのは、その会員のお気に入りの知らせ（値下げ・再入荷の両方）。メルマガの購読は止めない（お気に入りの知らせは会員が別に選んだもの）。合い言葉は 32 バイトの乱数で、記録にはハッシュだけ。準備中のショップでも受ける（`RequireShopAccess::OUTSIDE`）
- **App の画面**: お気に入りの数の多い順の商品（順位・数・最後に追加された日時）と、1 件の画面（ショップに出ているか・値下げ／再入荷を知らせてほしい人の数）。誰が付けたかは出さない。操作は無い
- **退会**（`CustomerLeft`）で、その会員の印・選択・送った記録を消す

### App「おすすめの区画」

- **区画**（composer.json の `sections`。外から埋め込まないので、公表と係は要らない）: `app_recommendations_related`・`app_recommendations_recent`・`app_recommendations_ranking`。パターンは「格子」「横に流れる」、欄は見出しと並べる数（4・8・12。選ぶ欄）
- **商品を読むのは composer**（`RecommendationsComposer`）: App の Blade は表示だけ（`ThemeTest` が App の views でも DB への参照を断る）なので、`View::composer('*::sections.app_recommendations_*')` で並べる札を `$recommended` に渡す。1 つの形で App の部品にもテーマが描き直す同じ名前の部品にも当たる（形を 2 つ並べると App の部品で 2 度動く。テストが見つけた）
- **見た目**は核の区画「商品の並び」（`sections.css` の `sugar-products`）に合わせ、「横に流れる」の形（`sugar-products__grid--scroll`）を核の CSS に足した。札にはお気に入りのハート（核の札の部品）も置く。テーマは同じ名前の部品で描き直せる
- **並べる商品**: どれもショップに出ていて売り切れでない札（`Catalog`）。関連商品は「最近見た商品」の先頭（最後に見た商品）のカテゴリの 1 つ目の商品を、新しい順に（その商品自身は除く）。足りない分とまだ見ていない人には新着。プレビュー・試し見では、並べる商品が無くても形と案内の一言を出す
- **最近見た商品の Cookie** `sugar_recent`: 商品の画面を開いた時（`storefront.product` が 200 の時だけ）に、App がショップのミドルウェアの群の終わりに足した係（`RememberViewed`。Cookie の暗号化の内側）が、ID を先頭に足して 20 件までにする（HttpOnly・SameSite=Lax・30 日・https なら Secure）。読む時は改ざんされた前提で確かめる: 長すぎる値は丸ごと捨て、ULID の形の小文字だけを 20 件まで。知らない ID・ほかの店の ID は商品を読む時に落ちる（この店の DB だけを読む）。お店の側には何も残さない。ほかの画面では経路の名前を見るだけで DB を引かない
- **売れ筋**（毎時 45 分の `recommendations:rank`。使う店だけ）: 直近 30 日に受けた物販の注文のうち、いまお支払いの済んだ段（支払い・受渡・受取確認・精算）にあって取消・返金でないものの、商品の明細の数（オプションの行は除く）。上位 50 件を `recommendations_ranks` に丸ごと入れ替える（店ごとの錠）。ショップの画面はこの表を 1 回読むだけで、注文の明細も取引も読まない（テストが見張る）
- **商品の画面に関連商品を置く場所**: 今のテーマ API では、ページの区画を置けるのはトップと自由なページ（`theme.json` の `pages`）だけで、商品の画面（product）は決まった並びの画面。置くには、テーマ API に「商品の画面の下の区画の並び」（例: `pages.product` の `types` と、核が今の商品を区画に渡す口〔`$section->product`〕）を足し、4 つのテーマの商品の画面がその並びを描くようにする。関連商品の区画は今の商品があればそれを基に、無ければ今の形（最後に見た商品）で並べる。それまでは、トップや特集の自由なページに置く（ヘルプに書いた）
