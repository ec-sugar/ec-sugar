# 0110 バックアップと連鎖の先頭は、暗号化してサーバーの外の消せない置き場へ送る

状態: **提案中**（2026-11-19。リリース 1.0 の R7）。送る・取るの道具（ホストの側）は入った。消せない期間の長さと、暗号化の道具（gpg）でよいかは、運営する人がまだ決めていない。ADR 0082（バックアップと戻す）・0012（記録の連鎖）・0043（壊れたら知らせる）・0102（外への通信）・0105（中の照らし）の上に足す。置き換えるものは無い

## 要点（先に）

1. 毎朝のバックアップ（中央と全部の店の DB・写真などのファイル）を、**S3 互換の置き場**へ送る。置き場の側で**一定の期間、削除も上書きもできない**形にしておく（Cloudflare R2 ではバケットのロック）
2. 送るのは**ホストの root**で、道具は入っている `curl`（`--aws-sigv4`）と `gpg` だけ。新しいイメージも PHP の部品も足さない。鍵はどのコンテナにも渡さない
3. 送る前に**公開鍵で暗号化**する。サーバーに置くのは公開鍵だけで、開ける鍵は運営する人がサーバーの外で持つ。**APP_KEY は送らない**
4. 送る側は **PUT しか使わない**。サーバーに置く鍵は書く用、戻す時に使う読む鍵は別に作り、ふだんはサーバーに置かない
5. 店ごとの**記録の連鎖の先頭（番号と hash）**も、10 分ごとに変わった時だけ同じ置き場へ送る（平文。個人情報は入らない）
6. 送れなかった・48 時間送れていない・置き場のロックが効いていないは、運営の様子とメールで知らせる。**置き場を設定していないサーバーでは何も出さない**
7. 戻すのは `ec-sugar offsite pull` で取って開き、今までの `ec-sugar restore` に渡す。復元の訓練で、外の置き場から戻せることまで確かめる

## 文脈

- バックアップはサーバーの中（`/srv/ec-sugar/backup`）にしか無い。機械が壊れる・盗まれる・root を取られて消されると、一緒に失う（ADR 0082 の結果の「まだ」。脅威モデルの「消せるバックアップ」）
- 記録の連鎖の先頭は中央の DB に控えるようになった（ADR 0012 の「作って決めたこと」）。中央の DB も一緒に書き換えられる場合（サーバーごと取られた場合）は、まだ気づけない
- 外への通信は出口の代理で名前を絞っている（ADR 0102）。置き場の名前を許す一覧に足すと、アプリのコンテナからも置き場の事業者の入口へ届くようになる
- 一度きりのコンテナは、運用の錠を持っている間だけ許している。錠は 30 分を超えると困りごとになる（ADR 0105）。大きなバックアップを細い回線で送ると 30 分を超える
- ホストには `curl`・`gpg`・`openssl` が入っている（インストーラーが入れる）。ホストの root が、root だけが読む鍵で外の API に聞く形は、トンネルの見張りで前例がある

## 決定

### 1. 送るもの・名前

| 種類 | 中身 | いつ | 暗号化 |
|---|---|---|---|
| `db` | DB の dump・ロール・`manifest`・指紋（`SHA256SUMS`）を 1 本の tar の流れに | 毎朝のバックアップと、手で取ったバックアップ | する |
| `files` | 写真などのファイル（`storage.tar`） | 同じ時 | する |
| `heads` | 店の ID・連鎖の先頭の番号・hash・控えた時刻 | 10 分ごと。前に送った中身と同じなら送らない | しない |

更新の前・戻す前のバックアップは送らない（頻度が読めず、消せないものが増える）。

- 名前は `<種類>/<サーバー>/<年>/<月>/<バックアップの名前>.<送った時刻>/` の下に `part-0001…` と `INDEX`。先頭は `heads/<サーバー>/<年>/<月>/<日>/<時刻>.tsv`。`<サーバー>` は既定で管理画面のホスト
- 種類を名前の頭に置くのは、置き場の側の「消せない期間」と「消す時期」を種類ごとに決められるようにするため
- 暗号化した流れを決まった大きさ（既定 1 GiB）で切り、切れ端ごとに 1 つのオブジェクトにする（分けて送る API は使わない。1 回の PUT の上限に当たらない）
- `INDEX`（形の版・バックアップの名前・切れ端ごとの大きさと SHA-256）を**最後に**送る。`INDEX` の無い組は途中で切れたものとして数えない
- やり直しは**新しい名前**で初めから送る（暗号化は毎回違う中身になり、上書きはできない）
- どの PUT にも「まだ無い時だけ書く」（`If-None-Match: *`）と中身の指紋（`x-amz-content-sha256`・`Content-MD5`）を付ける
- 時刻として信じるのは置き場の側の時刻（名前の時刻・送った時刻は送る側が書ける）。取る側は、いちばん新しいものを置き場の側の時刻で選ぶ

### 2. 送る道具と流れ

- `ec-sugar backup` は、取れた後に錠を持ったまま**送る分の控え**を作る（バックアップの置き場の外の同じファイルシステムへハードリンク。掃除が元を外しても控えは残る）
- 送るのは別の unit（`ec-sugar-offsite.timer`、10 分ごと。`ec-sugar offsite run`）。運用の錠は取らず、自分の錠だけを取る。設定が無ければ黙って終わる
- 先頭 → 控えを古い順に送る → ロックの確かめ → 結果を state に書く → 変わっていれば運営の様子へ報告、の順
- 鍵は bash の中だけで読み、`curl` へは設定を標準入力で渡す（引数・環境変数・記録に出さない）。平文はディスクに増やさない（切れ端は暗号化した後のものを 1 つずつ書いて、送って、消す）
- 送れないまま溜まった控えは 3 つまで（古いものから外して知らせる）
- 部品は `deploy/lib/common.sh` に置く（前のバージョンの道具の更新の道で、新しいファイルは入らない。ADR 0082）

### 3. 暗号化と鍵

- 暗号化は `gpg` の公開鍵の形。サーバーには公開鍵のファイルだけを置き、鍵束には取り込まない。圧縮はしない
- 公開鍵が無ければ送らない。平文で送るのは、答えに `OFFSITE_ENCRYPT=no` と書いた時だけ
- 置き場の鍵は `/srv/ec-sugar/secrets/offsite/`（root の 0700、中は 0400）。どのコンテナにも差し込まない
- **サーバーに置かないもの**: 読む鍵・開ける鍵・置き場の設定を変えられる鍵。戻す時だけ、戻す先の機械へ root だけが読むファイルで渡し、終わったら消す
- APP_KEY は送らない。運営する人が、置き場とは別の所に控える（無いと、戻しても店の個人情報を開けない）
- **戻す先・訓練の機械には、戻し終わるまで書く鍵を置かない**（答えに `OFFSITE_…` を書いて入れない。取るのは `--endpoint`・`--bucket`・`--prefix` と読む鍵で）。入れたての空のバックアップを、本物の置き場へ同じ名前の頭で送らないため。隔離した写しからは、送る回も確かめ（`offsite test`）も置き場に何も置かない
- 公開鍵は指紋を見せる（インストーラー・`offsite status`・`offsite test`）。流し直しで元のファイルが別の鍵になっていたら、黙って入れ替えずに止まる。鍵と公開鍵の元のファイルは、root の持ち物で、ほかの人が書けないものだけを読む

### 4. 置き場の側の決まり（運営する人が置き場の画面で決める）

- 削除も上書きもできない期間を、種類の前置きごとに決める。期間が過ぎたものは置き場の側の決まりで消す
- サーバーに置く鍵には、その期間や決まりを変える権限を持たせない
- 送る側は、バックアップを送れた回ごとに小さな印を置いて上書きと削除を試し、断られることを確かめる（置き場のロックが外れた・掛かっていないことに気づく）。置き場によって答えが違うので、`OFFSITE_LOCK_CHECK` で切れる（既定は、Cloudflare R2 の入口なら入れる・ほかの置き場では入れない）

### 5. 知らせ

- ホストは、置き場の鍵がある時だけ、結果（送れた・失敗、最後に送れた時刻、ロックの確かめ、先頭）を運営の様子へ渡す。無ければ何も渡さない
- 運営の様子は、行が無ければ「サーバーの外のバックアップ」の札そのものを出さない（Cloudflare Tunnel の見張りと同じ）
- 最後の回の失敗は、置き場に置けなかっただけなら近いうちに、待っても直らない理由（設定・道具・公開鍵・回数の上限）とまだ 1 回も送れていないサーバーの失敗は要対応。48 時間送れていない・ロックが効いていないは要対応

### 6. 戻す

- `ec-sugar offsite pull <名前|--latest> --credentials-file <読む鍵> --decrypt-key-file <開ける鍵>`: `INDEX` のある組を取り、切れ端の SHA-256 を照らし、開いて、バックアップの置き場に広げる
- **置き場の中身は信じない**（書く鍵を持つ人が足せる）:
  - `--latest` は置き場の側の時刻でいちばん新しいもの。名前の時刻・送った時刻・置き場の側の時刻が食い違う組（先の日付を名乗る・先回りで置いた）は「疑わしい」として選ばない
  - 同じ名前の組が 2 つ以上あれば黙って選ばず、一覧を見せて `--sent <送った時刻>` を打たせる
  - 取れた時は、置き場の側の時刻と、中の `manifest` の取った時刻・管理画面のホストを見せる
  - 暗号化された組は、gpg が本当に暗号を開けたこと（`DECRYPTION_OKAY`）を確かめる。開ける鍵を渡しているのに平文の組は取らない
  - tar は決まった名前のふつうのファイルだけ、指紋（`SHA256SUMS`）と `manifest` は決まった形の行だけ、開けた大きさは切れ端の合計まで
- その先は今までの `ec-sugar restore`（指紋・確認・戻す前のバックアップ・隔離した写し）。指紋の確かめが、取った時から戻す時までの端から端の確かめになる
- 先頭は、今の店の記録に同じ番号・同じ hash があるかを照らす（照らすコマンドは、先頭を出すコマンドと一緒に足す）

## 選ばなかった案

- **アプリのイメージの PHP と S3 の部品で送る**: 大きな部品が 2 つ増え、置き場の鍵がアプリのコンテナ（いちばん攻められる所）に載る。出口の代理の許す一覧に置き場の名前を足すことになり、アプリから置き場の事業者の入口へ届く道ができる
- **送る専用のコンテナを足す**: 外から取るイメージが 1 つ増える。一度きりのコンテナは錠の中でしか動かせず、長い送信とぶつかる
- **S3 の署名を bash と openssl で自分で書く**: 鍵が `openssl` の引数に出る。署名の誤りを自分で持つことになる
- **出口の代理を通す**: ホストの root の通信は代理の外（更新と同じ）。代理を通すには置き場の名前を一覧に足すことになる
- **暗号化しない**: 置き場によっては書くだけの鍵を作れず、サーバーの鍵で読めてしまう。外の事業者の置き場に個人情報を平文で置かない
- **`age`・PHP の sodium・`openssl cms` で暗号化する**: 順に、ホストに足すものが増える・形が自前になり開ける道具が自分たちのコードだけになる・証明書が要り大きなファイルの扱いに不安
- **バックアップ全体を 1 本の流れにする**: 単純だが、DB と写真で消せない期間を分けられない
- **先頭を毎朝のバックアップと一緒に 1 日 1 回だけ送る**: 前の回より後の最大 24 時間ぶん（跡を消したい人がいちばん消したい所）が守りの外になる
- **先頭も暗号化する**: 個人情報が無く、開ける鍵が無くても照らせる方が役に立つ

## 残る危険

- サーバーの鍵を取られると、**偽のバックアップと偽の先頭を足せる**（公開鍵は秘密でない）。消す・上書きする・開けることはできない。侵入の後に足されたものは信じず、置き場の側の時刻で侵入の前のものを選ぶ
- **置き場の中身に、本物の証しは無い**（署名していない）。上の確かめで断れるのは形の違うものだけで、次の 2 つは残る:
  - (a) **時刻のそろった偽の組**（今の時刻の名前・送った時刻で、形の正しい中身を置く）は、名前が 1 つなら `--latest` がそのまま取る。偽の dump を戻せば、店の全部（運営・パスキー・決済の設定）を握られる。戻す人が、置き場の側の時刻が侵入に気づいた時より前のものを、名前で選ぶことに頼る
  - (b) **先回り**（明日以降のバックアップの名前の組を先に置く）は、名前の時刻より 14 時間あまり前までなら時刻の食い違いに当たらない（サーバーの時刻の帯が分からないため）。同じ名前が 2 つになるので黙っては取らないが、どちらが本物かは置き場の側の時刻と中身（`manifest`・戻した後の `restore-check`）で人が見分ける。書く鍵だけが漏れた場合でも、漏れた後のバックアップは疑って扱うことになる
- 同じ鍵で大きなごみを足して費用を増やせる（消せない期間の間は消せない）
- 置き場の設定を変えられる人（置き場のアカウント）は、消せない期間を短くできる。守りは、その権限をサーバーに置かないことと、アカウントの守りに頼る
- 先頭を送る間（10 分）より短い間の切り落としは見えない。取られた後の先頭は取った人が決められる
- APP_KEY と開ける鍵をなくすと、置き場の中身は使えない
- 置き場の事業者・回線が止まっている間は送れない（手元のバックアップは今までどおり取れる。知らせが出る）

## まだ決まっていないこと

- 消せない期間と消す時期（種類ごと）
- 暗号化の道具は `gpg` でよいか（入っている道具で足りるので `gpg` で作った。替えるなら `ec_offsite_seal` と `ec_offsite_open` の 2 つ）
- 開ける鍵と APP_KEY の控えの置き場・だれが持つか
- Ubuntu 22.04 の扱い（下の「作って決めたこと」の 1。今は「送れません」と断る）
- **置き場の中身に署名を付けるか**（上の「残る危険」の (a)(b) の根の直し）。案: `INDEX` に、書く鍵とは別の鍵の署名を付け、取る側が信じる公開鍵で確かめる。鍵をサーバーに置けば root を取られた時は守れないが、書く鍵だけの漏れ（渡した元のファイル・置き場の画面）と置き場の事業者には効く。サーバーの外で持つ鍵なら強いが、毎朝のバックアップに人の手が要る。入れていない（運営する人の判断待ち）
- 置き場の中身を、サーバーと別の機械（外の見張り。ADR 0105）が読む鍵で定期に照らすか（1.0 の後）
- 先頭を公開の時刻の証明に載せるか（1.0 の後）

## 作って決めたこと（2026-11-19 送る・取るの道具）

1. **`curl` は 8.5.0 以上**。`--aws-sigv4` の PUT を、手元の S3 互換の置き場（RustFS 1.0.4）へ実際に送って確かめた: Ubuntu 24.04 の 8.5.0 と 26.04 の 8.18.0 は通る（中身の指紋 `x-amz-content-sha256`・`Content-MD5`・`If-None-Match: *` を付けた PUT、GET、一覧）。**Ubuntu 22.04 の 7.81.0 は通らない**（`x-amz-content-sha256` を自分で足さず〔置き場の答えは 400〕、こちらから渡すと署名に入らないので合わない〔403〕。PUT だけでなく GET も）。回り道（署名を自分で書く・別の道具を足す）はせず、足りない版では `ec-sugar offsite test` と `pull` が理由を出して断り、送る回は `failed`（理由 `curl-old`）を残す。8.5.0 より前で通る版があるかは確かめていない（確かめた版を下限にした）
2. **`gpg --recipient-file` は、空の一時の homedir で鍵束に取り込まずに使える**（22.04 の 2.2.27・24.04 の 2.4.4・26.04 の 2.4.8）。一時の homedir は `/run/ec-sugar/`（root だけ・ディスクに残らない）に作って消す
3. **リージョンの答え `OFFSITE_REGION` を足した**（既定 `auto`。Cloudflare R2 は `auto`、ほかの S3 互換の置き場は署名に本当のリージョンが要る）
4. **置き場のロックの確かめは、バックアップを送れた回だけ**（1 日 1〜2 回）。10 分ごとに印を置くと、消せない小さなオブジェクトが月に 4,000 個あまり増える。消せない期間の決まりは前置きごとなので、印は `db/`・`files/`・`heads/` の 3 つに置き、どれか 1 つでも上書きか削除が通れば `open`。印の名前は時刻と乱数（消せない前の印とぶつからない）
5. **取る側は置き場の中身を信じない**（決定の 6）。初めは「同じ名前が 2 つ以上なら置き場の側の時刻がいちばん古いものを取る」にしていたが、先回りで置かれると偽の方が古くなるので、黙って選ぶのをやめて `--sent` を打たせる形に替えた（見直しの指摘）。`--latest` も名前の順から置き場の側の時刻へ替えた。写真の組は、DB の組の中の指紋と合うものを使う（合わない組は飛ばして次を試す。3 つまで）。写真の組が置き場に無ければ、注意を出して DB だけのバックアップとして置く
6. **写真の組だけ失敗した時は、次の回に DB の組を送り直さない**（控えの中に送り済みの印を置く。消せないものを二重に増やさない）
7. **隔離した写し（復元の訓練）からは送らない**（控えも作らない）
8. **運営の様子へ渡す引数はまだ出さない**。動いているアプリが知らない引数は報告ごと断られるので、アプリが受けるようになる時に一緒に足す。結果は `state/offsite` に、引数と同じ名前で残してある（`offsite`・`offsite_at`・`offsite_tried_at`・`offsite_lock`・`offsite_heads`・`offsite_heads_at`。ほかに `last_backup`・`reason`）
9. **連鎖の先頭は口だけ**。アプリに `operations:chain-heads` があるかを、入っているバージョンごとに 1 回だけ聞き、無ければ飛ばす（state にも書かない）。あれば、1 行が「店の ID・番号・hash・時刻」のタブ区切りであることを確かめてから送る
10. **unit は `ec-sugar-offsite.service`・`.timer`**（毎時 5・15…分。見張りの 0・10…分とずらす）。`install-units` が入れて有効にし、中の照らしは自分の unit として控え直す。前のバージョンへ戻した時は、タイマーを止めて unit を消す（置き場を設定していたら、送られなくなることを知らせる）。置き場を設定していないサーバーでは、unit の条件（`ConditionPathExists`。鍵のファイル）でタイマーそのものを動かさない（10 分ごとの記録を出さない）。送る回の待ち時間は決めない（切れ端がいくつもある写真を細い回線で送り終えられるように。止まった送信は `curl` が切る）
11. **確かめ**は `docker/check-offsite.sh`（CI の image の仕事）。外へ出られない網に RustFS を立て、使い捨ての Ubuntu の中から本物の部品で送って取る。置き場のロックそのもの（断りの 409）は RustFS では確かめられないので、偽の答えで語だけを見る。本物は `sudo ec-sugar offsite test`
12. **失敗のやり直しは、間を倍々に空け、回数に上限**（見直しの指摘）。途中まで置いた切れ端は消せないので、切れる回線で 10 分ごとに初めから送り直すと、消せないごみが増え続ける。控えごとに失敗を数え、次に試すのは 10 分後・20 分後…6 時間後まで（1 日に多くて 4 回ほど）、8 回で止めて理由を `gave-up` にする。原因を直したら `sudo ec-sugar offsite run --retry`。公開鍵で暗号化できない時（期限切れ・壊れた）は、置き場の失敗と分けて `bad-recipient` にし、回数に数えない
13. **前のバージョンの道具からの更新で、中の照らしが誤報を出さないようにした**（見直しの指摘）。更新を走らせるのは前の道具のプロセスで、その「自分の unit」の一覧にこのバージョンで足した unit は無い。前の道具はそれを「足された unit」に分けて控えないので、そのままでは更新した全部のサーバーで要対応が出る。新しい道具の `install-units` が、更新の中から呼ばれた時も自分が入れた unit の分だけは控える（前の道具は、控えにある項目を前の控えのまま残す）。`docker/check-integrity.sh` が、前の道具の一覧での控え直しをはさんで確かめる（この先、unit を足す時も同じ道で通る）
14. **暗号の公開鍵は中の照らしの対象に入れていない**。入れると、前のバージョンへ戻した時（前の道具はこの項目を知らない）に「控えにあるのに無い」の誤報になる。代わりに、指紋を見せることと、別の鍵に黙って入れ替えないことで守る
15. **`ec-sugar status` に 1 行**（置き場を設定した時だけ。送れたバックアップの名前と時刻か、送れていない理由）。運営の様子とメールでの知らせは、アプリが引数を受けるようになる区切りで足す（それまで、失敗を人が知る道は `status`・`offsite status`・unit の記録だけ）
16. **強く切られた回の消し残し**（gpg の一時の homedir・切れ端・開けた途中のもの）は、次の回が自分の錠を取った直後に片付ける。控えを作る段（運用の錠の中）は、送る回が動いている間は溜まった控えを外さない（送っている最中の控えを消さない）

## 作って決めたこと（2026-11-20 運営の様子に出す）

上の 8 と 15 の「まだ出さない」を、ここで出す側に変えた。

1. **引数は 7 つ**: `--offsite=<ok|failed>`・`--offsite-tried-at=<時刻>`（この 2 つは組）・`--offsite-at=<最後に送れた時刻>`・`--offsite-reason=<理由の語>`（failed の時だけ）・`--offsite-lock=<ok|open|unknown>`・`--offsite-heads=<ok|failed>`・`--offsite-heads-at=<時刻>`。置き場の鍵のファイルがあり、state に結果がある時だけ出す（鍵のファイルを消せば、state が残っていても 1 つも出ない）。バックアップの名前（`last_backup`）は渡さない
2. **理由は決まった語だけ**（`config`・`curl-old`・`no-gpg`・`no-recipient`・`bad-recipient`・`put`・`gave-up`）。ホストの一覧（`EC_OFFSITE_REASONS`）・コマンドの一覧・DB の制約の 3 か所が同じであることをテストが見張る。ホストは知らない語を渡さず（理由なしの失敗になる）、アプリは知らない語を報告ごと断る。語を人の言葉に直すのは画面
3. **置き場は表 `host_checks` の種類 `offsite`**。行は 4 つまで: name が空（最後の回。`at` は最後に送れた時刻、`checked_at` は最後に試した時刻）・`reason`・`lock`・`heads`
4. **長く送れていないは 48 時間**（決定の 5 のとおり。手元のバックアップの古さと同じ）。数えるのはアプリの側で、最後に送れた時刻から。ホストは結果が変わった時と毎晩しか報告しないので、ホストの語（ok）は古さの判定に使わない（送る回が止まっても 48 時間で出る）。**まだ 1 回も送れていないサーバーは、比べる時刻が無いので「長く送れていない」を出さない。代わりに、そのサーバーの失敗は理由を問わず要対応にする**（最初から設定を誤ったサーバーが、メールの出ないまま送れずにいる穴を塞ぐ）。待っても直らない理由（設定・道具・公開鍵・回数の上限）の失敗も、48 時間を待たずに要対応にする。近いうちにのままなのは、前に送れたことがあり、置き場に置けなかっただけ（回線のこともある）の失敗
5. **ロックを確かめられなかった（`unknown`）は困りごとにしない**（札の文にだけ出す）。確かめを入れていない置き場（`OFFSITE_LOCK_CHECK=no`）は語そのものが無い
6. **連鎖の先頭の語（`--offsite-heads…`）は、受けて持つだけ**で、困りごとにも札の文にもまだ出さない。先頭を出すアプリのコマンドが無い間は、ホストがこの引数を出さない。引数を先に受けておくのは、コマンドを足す時に、前のバージョンのアプリへ渡し直す段をもう 1 つ増やさないため
7. **送る回は、渡す値が前の回と変わった時だけ報告する**（結果・理由・最後に送れた時刻・ロック・先頭の語。最後に試した時刻だけが動いた回は報告しない。毎晩の報告が新しくする）。渡せなかった時（app が動いていない間）は印（`state/offsite_report_pending`）を残し、次の回に渡し直す。報告の失敗は、送る回の結果を変えない
8. **前のバージョンのアプリへ渡し直す段は 3 つ**になった（新しい値から外す: サーバーの外のバックアップ → 中の照らしと外の見張り → トンネルの見張り）。注意の文には、実際に外したものだけを書く
