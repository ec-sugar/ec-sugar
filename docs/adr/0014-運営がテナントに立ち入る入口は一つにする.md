# 0014 運営がテナントに立ち入る入口は一つにする

状態: 採用（2026-10-27）。一部置き換え（→ ADR 0024: 運営はオーナーとスタッフに分け、スタッフは与えた店にだけ、閲覧・運用・お金の段階で入る）

## 文脈

管理画面は運営だけが使い、商品・在庫・取引というテナントのデータを触る（ADR 0013）。
「中央からテナント DB を直接なめない」「テナントのデータに触るコードは必ずテナント文脈の中で動かす」（開発の規約、CONCEPT 7.1）を守りながら、
運営がテナントの中に入る経路が要る。経路が散らばると、認可の付け忘れや文脈の閉じ忘れ（次のリクエストに別テナントの文脈が残る）が起きる。

## 決定

- **入口は `/api/tenants/{tenant}/…` に付けた `EnterTenant` ミドルウェアだけ**。ログイン済みで有効な運営（`auth:operator` ＋ `EnsureOperatorIsActive`）の後に置く
- **テナント ID は経路の引数だけから取る**。形（`[a-z0-9][a-z0-9_-]{0,62}`）を確かめてから中央 DB で探し、無ければ 404。読んだら経路の引数から外し、controller は `tenant()` だけを見る
- **例外でも必ずテナント文脈を閉じる**（`finally`）。テナント文脈の中からさらに入ることは禁止
- **1 リクエストごとに中央の監査ログへ 1 行**（`operator.tenant_request`: 運営・テナント・メソッド・経路・応答の状態）。読み取りも残す（個人情報の閲覧の記録）。見つからない ID は `operator.tenant_denied`
- **テナントの中での変更は、ドメインイベントの actor を `operator:<id>` にする**（`TenantActor::of($request)`。入口を通っていないと例外）。中央の監査ログ（誰が入ったか）とテナントのイベント（何が変わったか）の両方に残る
- 運営は全テナントに入れる（運営ごとの権限は持たない）。必要になったら別の ADR で足す → ADR 0024 で置き換え（全店に入れるのはオーナーだけ）

## 結果

- 得たもの: 認可・文脈の出入り・監査が 1 か所に集まり、テストで確かめられる（A の文脈で B が見えない、例外の後に文脈が残らない、記録が両方に残る）。片 D〜F の API はこの入口の下に足すだけでよい
- 失ったもの: 管理画面の読み取りのたびに中央の監査ログが 1 行増える（運営だけが使う画面なので量は小さい想定。増えたら読み取りの記録の粒度を見直す）。運営ごとに「このテナントだけ」「読み取りだけ」といった絞り込みはまだできない（→ ADR 0024 で塞いだ）

## 作って決めたこと（2026-11-12、ADR 0100）

- AI エージェントの MCP の入口（`POST /mcp`）は、セッションを持たないので `EnterTenant` を通らず、`AuthenticateAgent` の下で鍵が決めた店に入る。2 つ目の入口だが、守りは同じ形（店は経路や引数で選ばせない・毎回今の段階で確かめる・例外でも文脈を閉じる・1 回ごとに中央の監査ログ）。この 2 つ以外から店に入る経路は作らない（`RouteAudit` の規則 5・6・16）
