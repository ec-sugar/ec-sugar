# 0107 核の文脈を責務ごとに割り、商品の CSV と決済の実装はプラグインへ出す

採用（2026-11-18）

## 文脈

核の機能は、単純で拡張しやすく、セキュリティも担保された状態にしておきたい（2026-11-18）。そのために今の核を実測して評価した。

**健全だったところ**（直さない）:

| 観点 | 実測 |
|---|---|
| 核の中心（Listing・Transaction・Ledger・Event・Inventory） | 6,594 行 = 核の 14%。CONCEPT の「ひとつの核」が肥大していない |
| 最大のファイル | 921 行。1000 行超えは 0 |
| 依存の向き | `tests/Unit/ArchitectureTest.php` の 4 つの規則が機械で見張る（核は Admin・Storefront・HTTP を知らない／文脈の循環を増やさない／下の段は Order を知らない／Admin と Storefront は互いに依存しない） |
| 拡張性 | `plugins/` が 52,906 行で核（46,875 行）より大きい。App 30 個以上・テーマ 4 つ・タグの App 10 個が同じ口で動く＝「自社の縦も核に入れずプラグイン」が実際に守られている |
| 書き込みの安全 | `lock()` が 186 箇所（ADR 0021 が実装で守られている） |
| テスト | Feature 80,150 ＋ Unit 6,160 ＋ e2e 7,620 = 93,930 行（核の約 2 倍） |

**直すところ**（3 つ）:

1. **`Shop` が 11,469 行で核の最大**。中に区画・テーマ・サンプル・店の写真・送料・SEO と転送・デモの店・店の設定・ページ・配送日の **10 の責務が同居**している。文脈ではなく「その他」になりかけており、新しい機能がここへ入る引力がある
2. **`Payment` 6,405 行が核にある**。ADR 0026 でプラグイン化を決めたが区切り 2・3 が残り、「Ledger は決済代行に依存しない」と言いながら Stripe の実装が核にある。しかも **`plugins/` の 38 ファイルが `Core\Payment` を参照**しており、1.0 で互換を約束した後に動かすと壊す変更になる（ADR 0093「公開の前は約束の口も 1 回で変えてよい」）
3. **商品の CSV が核（`Core\ProductCsv` 3,347 行）にあるのに、配送の CSV は App（`plugin-shipping-csv`）**。同じ形の機能で居場所が違う

## 決めたこと

安い順に 3 段で整える（2026-11-18。安い順に全部を今やる）。**1.0 の前にやる**（口を 1 回で変えられるうちに。ADR 0093）。

### 段 1 商品の CSV を App へ

`Core\ProductCsv`（3,347 行）→ `plugins/plugin-product-csv`。配送の CSV と揃える。核の外からの参照は管理画面の 3 ファイルだけなので安い（`plugins/` からの参照は 0）。

App は店ごとに「使う・使わない」を選ぶもの（ADR 0025）なので、**すでに入っているサーバーでは更新のときに自動で有効にする**（そのままだと商品の CSV の画面が消える）。移行を 1 つ足し、1.0 の前の例外の印を付ける（ADR 0006）。CHANGELOG には「商品の CSV が App になった（今まで使えていた店では自動で有効）」と書く。

### 段 2 `Shop` を責務ごとに割る

| 新しい置き場 | 移すもの |
|---|---|
| `Core\Section` | 区画とページの雛形とページ（`Sections/`・`ShopPageService`・`ShopPage`） |
| `Core\Theme` | テーマの中身とバージョン（`Themes/`・`ThemeContentService`・`ThemeVersion`・`ThemeCategoryUsage`・`StaleThemeVersionException`） |

| `Core\Shop`（残る） | 店そのもの（設定・公開の状態・送料・SEO と転送・配送日・AI エージェントの設定） |

### 段 3 決済の実装をプラグインへ

`Core\Payment` に**口（ドライバのインターフェースと値）だけ**を残し、Stripe の実装を `plugins/payment-stripe` へ出す（ADR 0026 の区切り 2・3）。

**棚卸しの結果（2026-11-18）**。思っていたより近い所にいた。

| 中身 | 行数 | 決済代行に依存するか |
|---|---|---|
| `Contracts/`（`PaymentDriver` 54・`StoredPaymentDriver` 59・`PaymentCredentials` 18・`StoredCardHolder` 20） | 151 | **しない（これが口。すでにある）** |
| `Services/`（台帳・返金・預けたカードの管理・返品の精算） | 3,620 | しない（核に残す） |
| `Models/`・`Events/`・`Enums/`・`Jobs/` | 926 | しない（核に残す） |
| **`Stripe/`**（`StripeApi`・`StripeCheckout`・`StripeConnect`・`StripeDriver`・`StripeStored`・`StripeWebhook`） | **1,234** | **する（出す）** |

つまり**出すのは 1,234 行（Payment の 19%）だけ**で、6,405 行を動かすわけではない。残りの穴は次の 3 つ。

1. **核の `Services` が Stripe を直接知っている**（`PaymentService`・`StoredPayments`・`PaymentGatewayService`・`StripeConnectService` の 4 ファイル）。口（`PaymentDriver`・`StoredPaymentDriver`）を経由していない
2. `app/Storefront/Http/Controllers/WebhookController.php` が `StripeWebhook` を直接呼ぶ。**Webhook の受け口をドライバに委ねる**形にする
3. `app/Core/IsolatedCopy.php`（隔離した写し）が Stripe を参照している。口経由にする

**やること**（1.0 の前にやる分は下の「段 3 を 3a と 3b に割った」のとおり）:

1. 核の `Services` 4 ファイルが口だけを見るように直す（Stripe の名前を核から消す）。`StripeConnectService` は Stripe 固有なので App へ移す
2. Webhook の受け口をドライバに委ねる（経路は核が持ち、どのドライバに渡すかは店の設定で決める）
3. `Stripe/` 6 ファイルと `StripeConnectService` を `plugins/payment-stripe` へ
4. App が `PaymentDriver` を登録する仕組みを作る（App の manifest の `type` に `payment` を足す）
5. **Stripe の鍵は核の暗号化された保存のまま**（`PaymentCredentials` の口で読む）。お金に関わる秘密を App の設定へ移さない
6. `plugins/` の 38 ファイルが使っている 18 種類（`StoredPayments` 13・`PaymentUnavailableException` 13・`Events\PaymentConfirmed` 9・`Models\PaymentAttempt` 7・`PaymentService` 6・`Contracts\StoredCardHolder` 4 など）を**プラグイン API として明記**し、ADR 0093 の約束に載せる（1.0 で固める前に）

### 段 3 を 3a と 3b に割った（2026-11-18、実際に手を付けて分かったこと）

**この ADR が「段 3 は 1.0 の前」とした理由は、実測で成り立たなかった。** 「`plugins/` の 38 ファイルが口を見ているので、後で動かすと壊す変更になる」と書いたが、`plugins/` から Stripe の具象（`Core\Payment\Stripe\*`・`StripeCredentials`・`StripeConnectService`・`StripeConnectedAccount`・`Stripe\` の部品）への参照は **0 件**だった。App が見ているのは下の 18 種類で、そこに Stripe の名前は 1 つも無い。`Stripe/` をいつ動かしても App は壊れない。

逆に、動かせない理由が 1 つ見つかった。**鍵の置き場（`PaymentGatewayService`、282 行）と管理画面の決済の設定が Stripe の形そのもの**で、これを `plugins/payment-stripe` へ出すには、

- 鍵の形の確かめ（`sk_` / `rk_` / `whsec_`）・公開の前に試す鍵の枠（ADR 0096）・つなぐ手順（Connect、ADR 0022）を**ドライバが申告する設定の仕組み**
- 管理画面の「決済」の画面を、その申告から組み立てる形に作り直すこと

の 2 つが要る。これは居場所を動かすだけでなく**新しい仕組みを足す**ので、ADR 0098（1.0 まで新しい機能を足さない）に触れる。

**決めたこと**: 段 3 を 3a と 3b に割る。

| | 中身 | いつ |
|---|---|---|
| **3a** | 核の金の流れ・店頭・App が**口だけを見る**ようにする。ドライバの登録簿・Webhook の受け口の口・鍵の置き場の口・機械の見張り・プラグイン API の明記 | **1.0 の前（済）** |
| **3b** | `Stripe/` 6 ファイル＋`StripeConnectService`＋`PaymentGatewayService` を `plugins/payment-stripe` へ。ドライバが設定の欄を申告する仕組みと、それで組み立てる管理画面 | 1.0 の後 |

3a を先に入れたので、3b は**居場所を動かすだけ**になる（口はもう 1.0 で固まる）。

### 共通の決まり

- **機能は足さない**（ADR 0098 のまま）。動かすのは居場所だけで、画面・API・DB の形・移行は変えない
- 各段で `ArchitectureTest` に規則を足し、**割った文脈が再び混ざらないように機械で見張る**
- 1 段 = 1 PR。核を 3 方向に同時に動かすと、落ちたときに切り分けられない

## 採らなかった案

- **`ProductCsv` を `Core\Listing\Csv` にする**: 核に残るので軽くならず、配送の CSV との一貫性も取れない
- **`Shop` をそのままにして、新しいものだけ別の文脈に置く**: 既にある 11,469 行が「その他」として残り、引力も残る
- **段 3 を丸ごと 1.0 の後に回す**: 口が固まらないまま 1.0 を出すと、後で動かすときに App の書き直しが要る。~~`plugins/` の 38 ファイルが口を見ているので、後で動かすと壊す変更になる~~（2026-11-18 に実測。App からの Stripe の具象の参照は 0 件で、この理由は成り立たなかった。代わりに 3a と 3b に割った）
- **段 3b も 1.0 の前にやる**: 鍵の置き場と管理画面の決済の設定を作り直す＝新しい仕組みを足すことになり、ADR 0098（1.0 まで新しい機能を足さない）に触れる
- **全部を 1 つの PR で**: 切り分けられない
- **中心（Listing・Transaction・Ledger・Event・Inventory）も見直す**: 実測で 14% に収まっており、触る理由がない

## 結果

- 核は 46,875 → 約 31,000 行（34% 減）の見込み。**中心は動かさない**
- `plugins/` が 2 つ増える（`plugin-product-csv` は段 1 で済、`payment-stripe` は 3b で）
- 1.0 の必須（R4・R7・R9・R11）とゼロトラストの段 1（ADR 0106）は、この整理の後に続ける

## 作って決めたこと

### 同じコードが散っていないかの検査（2026-11-18。同じようなコードがあちこちに書かれていないかも確かめる）

10 行の同一ブロックで複数ファイルにまたがるものを機械で数えた（phpcpd と同じ原理の手元の台本）。

| 範囲 | 結果 |
|---|---|
| `app/` ＋ `plugins/`（Blade を含む 1,491 ファイル） | 43 組。**上位はほぼ全部、公式テーマ 4 つが同じ Blade を持っていること**（`layout`・`cart`・`checkout`・`product`・`products`・`order`・`legal`・`password` など）→ 既知の課題（ADR 0028 の区切り 2d「親テーマ」） |
| PHP だけ（1,232 ファイル・約 10 万行） | **9 組だけ**。重複はほとんど無い |

PHP の 9 組のうち、直す価値があったもの:

1. **お金の按分が 2 箇所にコピーされていた**（直した。下の節）
2. `SenderFacts` が 3 つの App に同じ内容（`plugin-cart-reminder`・`plugin-favorites`・`plugin-newsletter`、各 75 行）。コメントに「App 同士を直につながないので写して持つ。直すときは 3 つとも」とあり**意図的な重複**だが、3 つ同時に直す前提は事故を招く → `Core\Mail` へ寄せた（2026-11-19 に済。コメントが既に「両方」「3 つとも」「注意書き無し」で食い違っていた）
3. App のメールの定型（`BookingMail`／`SubscriptionMail`、`CartReminderMail`／`FavoriteNoticeMail`）と入力の検証の定型（`ContactInput`／`ReviewInput`）→ App の共通の部品にできる（1.0 の後）
4. サンプルのデータの定型（`BotanicaSamples`／`FashionSamples`／`SweetsSamples`）→ 段 2 で `Core\Sample` に移すときに見る

### お金の按分を 1 つに集めた（2026-11-18）

`App\Core\Money\Allocation::byWeight()` を作り、同じ計算を持っていた 2 つを消した。

- 前の形: `CouponService::allocate()`（クーポンの文脈にお金の汎用の計算があり、注文・カート・ポイント・送料の按分が Storefront から 7 箇所これを使っていた）と `ReturnSettlement::split()`（返品の精算）
- **重複が不整合を隠していた**: 負の額の扱いだけが違い、クーポンの側は `$amount === 0` だけを 0 にしていたので、**負の額が検査をすり抜けて負の按分を計算した**。1 つに集めるときに安全な側（`$amount <= 0` なら全部 0）へ揃えた
- 付け替えたのは 18 箇所（`PlaceOrder` 4・`CartService` 4・`ReturnPlanner` 4・`ReturnSettlement` の中 3・テスト 6 ＝ 延べ。`plugins/` からは使われていなかった）
- テスト `tests/Unit/AllocationTest.php`（5 件・5,950 の検査）: 端数は余りの大きい順・鍵と並びが変わらない・0 と重み 0 と空の配列・**負の額は全部 0**・重みを越える額は例外・300 通りの乱数で「配った合計がちょうど額と同じ」「重みを越えて配らない」。わざと壊した 3 通り（負の守りを前の形に戻す／端数を小さい順に配る／越える額の検査を外す）がどれも落ちることを確かめた
- 名前が同じで別物の `PlaceSingleOrder::allocate()`（在庫の割り当て）は触っていない。紛らわしいので 1.0 の後に名前を見直す

### 段 3a: 核の金の流れを口だけに向けた（2026-11-18）

核（`app/Core`）・店頭（`app/Storefront`）・App（`plugins/`）から Stripe の具象を全部外し、機械で見張る形にした。**機能・画面・経路の URL・DB の形は変えていない。**

**足した口（3 つ）**

| 口 | 中身 |
|---|---|
| `Contracts\PaymentCredentials::mode()` | 本物の鍵か試しの鍵か（'live' / 'test'）。前は `StripeCredentials` の公開の属性 `$mode` を核と App が直に読んでいた |
| `Contracts\PaymentCredentialStore` | 鍵の置き場。`credentials()`・`credentialsForAttempt()`・`primaryMode()` の 3 つだけ。実装は `PaymentGatewayService`（3b で App へ出す） |
| `Contracts\PaymentWebhookReceiver` | 通知の受け口。`receive()`・`receiveForPlatform()`・`signatureHeader()`。署名の確かめ方も載る見出しの名前もドライバの側 |

**足した登録簿**: `Core\Payment\PaymentDrivers`。ドライバ自身のサービスプロバイダ（`Stripe/StripeServiceProvider`）が `register('stripe', StripeDriver::class, StripeWebhook::class)` を呼び、核は `config('payment.driver')`（登録が 1 つなら省略可）で選ぶ。`CoreServiceProvider` に Stripe の名前は無くなった。3b では `bootstrap/providers.php` の 1 行を App の `composer.json` の `providers` へ移すだけになる。

**付け替えたところ**

- `PaymentGatewayService::stripe()` → `credentials()`、`stripeForAttempt()` → `credentialsForAttempt()`（決済代行に依らない名前へ。App「ギフトカード」が `->stripe()?->mode` を呼んでいた＝Stripe の名前が App の口に漏れていた）
- 注入の型を `PaymentGatewayService` から `PaymentCredentialStore` へ: 核 5 ファイル（`PaymentService`・`StoredPayments`・`PaymentRefunds`・`PaymentMethodSettings`・`RefundReconciler`）、`Core\Shop\Services\ShopSetup`、店頭 1（`CartGiftCards`）、App 1（`plugin-gift-cards`）
- `PaymentService` の 2 つの私的なメソッドの引数を `StripeCredentials` → `PaymentCredentials`、`StoredPayments` の `instanceof StripeCredentials` を `mode()` へ
- `WebhookController` は `PaymentWebhookReceiver` だけを見る。**経路の URL（`/webhooks/stripe`・`/webhooks/stripe-connect`）と経路の名前は変えていない**（Stripe のダッシュボードに登録済み。ADR 0093 の約束）

**機械の見張り**: `ArchitectureTest::test_only_the_payment_driver_and_its_settings_know_stripe`。`app/` のどのファイルも、名前に `Stripe` を含むクラス（`Stripe\` の部品も）を読み込まない。例外は一覧 `STRIPE_ALLOWED` の **7 か所だけ**（ドライバ `Stripe/`・鍵の値・鍵の置き場・つなぐ手順・鍵を貼る画面の API・問い合わせ直しのコマンド・中央 DB の連結アカウント）で、この一覧は減る方向にだけ動かす。わざと壊して（店頭のカートに `use App\Core\Payment\Stripe\StripeApi;` を 1 行）落ちることを確かめた。

**テスト**: Unit 581 件（18,362 の検査）・決済まわりの Feature 72 件（1,319）・返金と定期便とギフトカードと抽選と取消 133 件（1,652）＝ 786 件すべて通過。新しいテストは足していない（振る舞いを変えていないので、既存のテストが通ることが確かめになる）。

**App が見る決済の口（18 種類）を ADR 0093 の約束に載せた**。3a で `PaymentGatewayService`（Stripe の名前）が一覧から消え、`PaymentCredentialStore` に替わった。

（段ごとに足す）
