# 0096 公開の前に試すテスト用の鍵はふだんの鍵と別に置き、準備中のあいだだけ使う

状態: **採用**（2026-11-11。作ることと形は運営が選んだ〔「テストの鍵を別に持つ」〕。中身は作る時に決めた）。
ADR 0019（Stripe の支払い）・0022（Stripe Connect）・0076（ギフトカードとテストの鍵）・（準備中の店は本番の鍵で支払いの画面を作らない）の上に足す。置き換えるものは無い

## 要点（先に）

1. 支払いの設定に**「公開の前に試すテスト用の鍵」**の欄を足す。ふだんの鍵（店の鍵か Stripe へ接続）とは別の行（`payment_gateways` の `stripe_test`。Stripe のテストのモードの鍵 `sk_test_` / `rk_test_` だけ。DB でも `mode = 'test'` に限る）
2. **新しい支払いにテスト用の鍵を使うのは、ショップが準備中で、ふだんの鍵が本番か無いときだけ**（`PaymentGatewayService::stripe()`）。公開したら使わない。ふだんの鍵がテストのモードなら、今までどおりそれを使う
3. 支払いの試み（`payment_attempts`）に**作ったときのモード（`test_mode`）**を残し、返金・問い合わせ・画面を閉じるのは**作ったときのモードの鍵**で行う（`stripeForAttempt`）。支払いの画面の使い回しも、同じアカウント・同じモードの画面だけ
4. 店の通知の受け口（`/webhooks/stripe`）は、ふだんの鍵とテスト用の鍵の**両方の署名の鍵で確かめ**、確かめられた鍵のモードで扱う。**テスト用の鍵で確かめた通知は、署名を信じずに同じ通知を Stripe に問い合わせ直した中身で処理する**。どの通知も、指す支払いの試みとモードが違えば断る
5. 試した注文は管理画面の注文に**「テストの支払い」**と出す。開設の手順の「支払い」は、テスト用の鍵だけでは済みにしない

## 文脈

- で、準備中のショップは本番の鍵で支払いの画面を作らないと決めた（本物のお金を、公開の前に動かさない）。そのため、最初から本番の鍵を入れた店は、公開するまで注文を最後まで試せなかった（公式の店を作った 11-11 に分かった。お店の人向けのガイドでは「公開した後に 1 回注文して返金・取消」と案内していた）
- 前は支払いの試みにモードが無く、返金と問い合わせは「そのとき置いてある鍵」で送っていた。テストの鍵で受けた注文の後に本番の鍵へ替えると、テストの注文の返金が本番のアカウントへ送られて失敗していた（ずれは Stripe が断るのでお金は動かないが、店の人には分かりにくい）

## 決定

### 鍵の選び方

| ショップ | ふだんの鍵 | テスト用の鍵 | 新しい支払いに使う鍵 |
|---|---|---|---|
| 準備中 | 本番 | あり | テスト用の鍵 |
| 準備中 | 本番 | なし | 本番（ただし とおり支払いの画面は作らない） |
| 準備中 | なし | あり | テスト用の鍵 |
| 準備中 | テストのモード | どちらでも | ふだんの鍵（今までどおり） |
| 公開中 | 本番 | どちらでも | 本番 |
| 公開中 | なし | あり | なし（払えない。テスト用の鍵に落ちない） |

- Stripe へ接続した店（ADR 0022）も、テスト用の鍵は店の鍵として置ける（接続のテストのモードは使わない）
- デモの店（ADR 0086）はふだんの鍵もテストのモードだけなので、表の「テストのモード」の行になる

### 作ったときの鍵

- 試みの `test_mode` は作ったときの鍵のモード（支払いの画面・預けたカードの請求）。店が受け取る支払い（銀行振込・代金引換）は Stripe を通らないので偽のまま
- 店の鍵で作った試み: テストなら「テスト用の鍵、無ければテストのモードのふだんの鍵」、本番なら「本番のふだんの鍵」。合う鍵が無ければ null（返金は人が確かめる道に乗る）
- 接続した店で作った試み: 今の接続が同じ連結アカウントで、同じモードのときだけ
- 今ある行は、支払いの画面の ID（`cs_test_` / `cs_live_`）から、それが無い行（預けたカードの請求）は移行のときの鍵のモードから埋めた

### 通知

- 受け口は、ふだんの鍵 → テスト用の鍵の順に署名を確かめる。確かめられた鍵と `livemode` が合わなければ断る（今までの守り）
- **テスト用の鍵の署名の鍵は、ふだんの鍵より広く扱われがち**（試す人に渡す・開発の手元に置く）。署名の鍵だけを持つ人が「払われた」を作って、お客さんが支払いの画面の URL で知っている本番の画面の ID を入れると、本番の注文が払われたことになりうる。そこで:
  - テスト用の鍵で確かめた通知は、同じ ID の通知を**テスト用の鍵で Stripe に問い合わせ直し**、返った中身で処理する（届かない・見つからない・種類や livemode が違えば断る。Stripe が送り直す）。テストのアカウントの品物の ID は本番と重ならないので、問い合わせ直した通知は本番の試みを指さない
  - 重ねて、支払いの画面と支払い（PaymentIntent）の通知は、指す試みの `test_mode` と通知の `livemode` が食い違えば断る（ふだんの鍵・接続の通知も同じ）
- 公開した後も、テスト用の鍵を外すまでは、試した注文の知らせ（期限切れ・返金）を受け取る

## 作って決めたこと

- 試した注文は自動では取り消さない（店の人が中身を確かめてから取り消す。取り消すとテストのモードで返金し、在庫を戻す）。注文の画面の札と知らせで「商品を送らない」ことを伝える
- 公開したときに、準備中に作ったテストの支払いの画面を閉じることはしない（使い回さないので新しい支払いには渡らず、Stripe の画面は期限で切れる。払われても「テストの支払い」の注文になる）
- テスト用の鍵の欄は、ふだんの鍵と同じく「お金」の段階と直前の再確認（経路は同じ群）
- ホーム・売上の数字のテストの注文の見分けは、前からの「テストのモードの支払いの画面の ID（`cs_test_`）」のまま（Stripe のテストのモードの画面は必ずこの頭なので、テスト用の鍵の注文も外れる）。`test_mode` で見分けると、テストのモードのふだんの鍵で動く開発・デモの店の数え方が変わるので、今は変えない

## 結果

- 本番の鍵を入れた店でも、公開の前にテストのカードで注文・支払い・知らせのメール・取消と返金まで通しで試せる
- 返金と問い合わせが、作ったときのアカウントとモードに結びつく（鍵を替えた後の取り違えが無くなった）
- 気をつけること: テスト用の鍵の通知は 1 件ごとに Stripe へ 1 回の問い合わせが増える（テストだけなので数は少ない）。試した注文はホーム・売上の数字に入らない（テストのモードの画面の ID で外す）が、確かめ終えたら取り消す
- 残り: 預けたカードの請求（定期便）をテストのモードで行った注文は、画面の ID が無いので売上の数字に入る（`test_mode` で外すのは、数え方をそろえるときに）。公開する操作のときに、残っているテストの注文を知らせる
