# 0088 ショップの個人情報の画面は、ブラウザが画面を開く時だけ通す

状態: **採用**（2026-11-06。外の点検の「重」: タグの JavaScript が同じオリジンから個人情報の画面を読める）。ADR 0034（App はショップに決まった形でタグを差し込む）を補う

## 文脈

- タグの App（GA4・広告のピクセルなど。ADR 0034）は、店で使うにするとショップのふつうの画面（トップ・商品・カート・特商法の表記・自由なページ・お知らせ）と購入の完了で、**同じオリジンの JavaScript**として動く。外のタグの中身はこちらで管理できない
- 個人情報の画面（マイページ・注文の入力と確かめ・ご注文の状況など）にはタグを差し込まないと決めていた（ADR 0034）。しかし差し込まないだけでは、ふつうの画面のタグが**お客さんの Cookie を持ったまま `fetch('/account')`・`fetch('/account/addresses')`・`fetch('/orders/…')` を読み**、名前・住所・メール・注文を外へ送れた（CSP の connect-src はタグの送り先を許している）
- さらに Laravel 13 の CSRF の確かめは、`Sec-Fetch-Site: same-origin` の要求を合い言葉なしで通す。タグの JavaScript は届け先を足す・メールを変える手続きを始めるなどの**書き込み**も fetch でできた
- 管理画面には Sec-Fetch-Site の確かめ（`ConfigureAdminSession`）があるが、ショップには無かった。同じオリジンの読みは Sec-Fetch-Site では分けられない（タグも same-origin）

## 決めたこと

1. **個人情報を出す経路に印 `navigation-only`**（`App\Storefront\Http\Middleware\NavigationOnly`）を付ける。印の経路は、ブラウザが画面を開く要求（`Sec-Fetch-Mode: navigate` と `Sec-Fetch-Dest: document`。リンク・アドレス欄・フォームの送信・その後のリダイレクト）**だけ**を通し、ほか（fetch・XHR の cors / no-cors / same-origin、宛先 empty、枠〔iframe〕・object・embed、画像やスクリプトとしての読み込み）は**中身の無い 403** にする。どの画面か・ログインしているかを見せない。この見出しはブラウザが付け、JavaScript から変えられない
   - 読む（GET）だけでなく送る（POST）も同じ。画面のフォームからの送信は navigate なので通り、タグの fetch での書き込みは止まる
   - 関所は回数の上限（throttle）より前、会員のログインの確かめの後に動く（タグの fetch でお客さんの回数の枠を減らさせない。ログインしていない時の動き〔ログインの画面へ〕は今のまま）
2. **通した応答に付けるもの**
   - `Cache-Control: no-store, private`: タグが `fetch(…, { cache: 'force-cache' })` や `only-if-cached` で、ブラウザの控え（HTTP のキャッシュ）から前に開いた画面を読まないように。ふつうの応答の `no-cache` は控えに残る
   - `Cross-Origin-Opener-Policy: noopener-allow-popups`: タグが `window.open('/account')` で開いた窓の中身を読めないように（同じオリジンの窓でも切り離す値）。この値を知らないブラウザでは unsafe-none になるが、ふつうの画面は `same-origin` なので値が食い違い、やはり窓は切り離される。枠はショップの CSP の `frame-ancestors 'none'` と `X-Frame-Options: DENY`、関所の宛先（document だけ）の 2 重で止まる
   - `Vary: Sec-Fetch-Mode, Sec-Fetch-Dest, X-Sugar-Page-Key`（間の控えへの念押し）
3. **Sec-Fetch を送らない古いブラウザ（見出しの `Sec-Fetch-Mode` が無い要求）は通す**。断ると、その人はマイページも注文の入力も開けなくなる。今の主なブラウザ（Chrome・Edge・Firefox・Safari 16.4 以降）は送るので、守りはほとんどのお客さんに効く。見出しを送らないのはブラウザでない呼び出し（その時はお客さんの Cookie を持たない）か古いブラウザで、古いブラウザのお客さんにはこの守りが無い（タグを差し込まない・CSP・公表の守りは残る）。値はあるが空・知らない値（`Sec-Fetch-Mode: ''` など）は断る
4. **画面の中の核の JavaScript が同じ画面の一部を読む所**（パスキーのオプション〔マイページのパスキー・本人の再確認・チケットの購入と券面〕と、入場の QR の取り直し）は `navigation-only:page-key` にし、**画面の鍵**（`App\Storefront\Access\PageKey`）の付いた同じオリジンの要求も通す
   - 鍵は「店の ID・このセッションの CSRF の合い言葉」の HMAC（APP_KEY から用途ごとに作った鍵）。合い言葉はふつうの画面にも出ていてタグも読めるが、APP_KEY を知らないので鍵は作れない
   - 鍵を画面に書くのは**関所を通った画面の中だけ**（`PageKey::forPage` は印の無い画面では空を返す）。印の画面には App を差し込まない（`StorefrontView` が印の経路では画面の種類を個人情報の画面に倒す）。タグが鍵を手に入れるには印の画面を読むしかなく、それを関所が断る
   - 核の部品（パスキーのフォーム）と App の画面（券面の動く QR。全部の画面に渡す `$pageKey` を使う。App の画面は核のクラスを直に呼ばない）が `data-sugar-page-key` に書き、`passkeys.js`・`live-qr.js` が見出し `X-Sugar-Page-Key` で添える。ほかのサイトからの要求（`Sec-Fetch-Site` が same-origin でない）は鍵があっても通さない
5. **印を付ける経路**（2026-11-06。一覧は `tests/Feature/Storefront/NavigationOnlyRoutesTest` の `MARKED`）
   - 核: 会員の画面の全部（`auth:customer` の群。マイページ・届け先・再確認・メールの変更・パスキー・退会・ログアウト）、ログインのコードの画面（送ったメールを出す）、注文の入力と確かめ（`/checkout`・`/checkout/confirm` と、その送信・支払いへ進む）、ご注文の状況（`/orders/{orderId}`）
   - App: 定期便・予約・抽選販売・デジタルチケット・ギフトカード・贈り物（買う人と受け取る人）・ダウンロード販売（画面とファイル）・レビュー（注文とマイページ）・会員ランク・領収書・お気に入りの一覧と知らせの選択・友だち紹介の画面・LINE 連携のメールのコードとマイページ・お問い合わせのフォーム（会員のメール・注文を出す）・メルマガの受付とマイページ・再入荷のお知らせの受付（入れ直しのメールを出す）
   - 付けないもの: ふつうの画面とカート（タグを差し込む画面。個人情報を出さない）、購入の完了（タグを差し込む。番号と金額だけ）、ログインの画面とパスキーのログイン、照会の受付（`/orders`）、商品のお気に入りのハート（商品の画面の `toggles.js` が送る。押したかだけを返す）、メールのリンクの画面（確かめ・配信の停止。個人情報を出さない）、LINE の認可の行き来と Webhook、商品フィード、写真・App のファイル・robots.txt・サイトマップ
6. **付け忘れの見張り**（`NavigationOnlyRoutesTest`。PR の検査で落ちる）
   - 機械の規則: `auth:customer` の経路・道筋に `account` の区切りを持つ経路（`account/login…` を除く）・道筋に `{orderId}` を持つ経路は印が要る。印は 1 経路に 1 つ、セッションのある店頭の群の中だけ、回数の上限より前。`page-key` は一覧の分だけ
   - そのうえで、印の付いた経路の全部が一覧と同じであること（外す・足すときはここと、この ADR の一覧を見直す）

## 選ばなかったもの

- **見出しが無ければ断る**: 古いブラウザのお客さんが買えなくなる。守りの穴は「古いブラウザ × タグを使う店 × タグの中身が悪い」の重なりだけで、ほかの守りも残る
- **既定で全部の経路に掛け、外す経路に印を付ける**: 守りは強いが、カート・郵便番号・ハート・プレビューの断片など核の JavaScript が fetch する経路が多く、外し忘れで買い物が止まる。個人情報の経路は「会員・account・注文」の形でほぼ機械で決まるので、付ける側の印と見張りにした
- **CSRF の合い言葉で JavaScript の読みを通す**: 合い言葉はふつうの画面のフォームにも出ていて、タグが読める
- **Referer で自分の画面からの要求を見分ける**: fetch の `referrer` で同じオリジンの道筋に変えられる
- **個人情報を画面の HTML でなく別の API で渡す**: 画面の作りを全部変えることになり、守りは同じ見出しに頼る

## 結果

- タグの JavaScript は、お客さんの Cookie を持っていても、マイページ・届け先・注文の入力と確かめ・ご注文の状況・App の会員の画面を fetch・枠・別の窓のどれでも読めず、fetch での書き込みもできない
- 印の画面はブラウザの控えに残らない（戻るで見える早さは少し落ちる。会員の画面は前から no-store）
- テーマと App の JavaScript は、印の経路を fetch できない（`docs/design/theme-api.md`）。同じ画面の一部を読む作りは画面の鍵を使う核の部品だけ
- 残る穴: Sec-Fetch を送らない古いブラウザ。タグを差し込む画面（ふつうの画面・購入の完了）に出ているもの（カートの中身・注文の番号と金額）はタグに見える（ADR 0034 のまま）

## 作って決めたこと（2026-11-06、main〔取り込みの後〕に合わせた時）

- 秘密の道筋の宣言（`secret-link`。ADR 0081）と同じ経路に付く所（ご注文の状況・お問い合わせの注文から・ダウンロード・贈り物・領収書・レビュー）は**両方**付ける。`secret-link` は参照元・控え・検索の守り、`navigation-only` は同じオリジンの JavaScript からの読み書きの守りで、役目が違う。どちらも `no-store` を付けるが、重なってよい
- 経路の回数の上限は main でも Laravel の `ThrottleRequests`（数える中身だけ核の `AtomicRateLimiter` に差し替え）なので、関所の並び（`ThrottleRequests` の前）はそのまま
- main で入ったリセールの経路（抽選の `p/lottery/resale/…` の 4 つ、チケットの `p/tickets/account/{id}/resale`・`…/resale/withdraw`）も会員の画面・フォームなので印を付け、`NavigationOnlyRoutesTest` の一覧に足した
- デモの店（ADR 0086）の受け箱（`GET /demo/mails`。来訪者に届くはずだったメール〔ログインのコード・注文の名前と届け先〕を出す）と「デモの会員でログイン」（`POST /demo/member`。帯のフォームから）にも印を付けた（2026-11-06、デモの店の枝を main に合わせた時）。見張りに「道筋が `demo/` で始まるショップの経路は印が要る」の規則を足した
