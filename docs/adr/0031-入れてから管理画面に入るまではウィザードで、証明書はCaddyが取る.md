# 0031 入れてから管理画面に入るまではウィザードで、証明書は Caddy が取る

状態: **採用**（2026-10-29）。ADR 0030（インストーラー）の続き。ADR 0013（ログインはパスキーだけ）・ADR 0029（ステージング）に関わる

## 文脈

- 2026-10-29、ステージングの VM に入れたとき、管理画面に入るまでに手で踏んだもの: 証明書を自分で用意して道筋を答えに書く → 自前の認証局を開発機に信頼させる（Brave は信頼せず、パスキーが「時間切れ」とだけ出て断られた）→ DNS を移す → API の鍵を作る → TXT を手で足す → 30 分以内に登録の URL を開く
- この手間では一般の利用者は使い始められない。インストールしてから管理画面に入るまでをウィザードの形で分かりやすくし、最初に環境の確かめも要る
- 今の入口（nginx）は証明書を 1 枚だけ読み、それは管理画面と `*.ショップのドメイン` を含むワイルドカードでなければならない。ワイルドカードは DNS の手作業か DNS の API の鍵が要る。ここが一番の壁

## 決めたこと

### 1. 入れる人の手順は 3 つ

1. ドメインの A レコード 2 行（管理画面の名前と `*.ショップのドメイン`）をサーバーへ向ける
2. `sudo ./deploy/install.sh` を流し、端末のウィザードに答える
3. 最後に出るアドレスをブラウザで開き、ブラウザのウィザードに沿ってパスキーを登録する

これ以上を求めない。手で証明書を用意する道（答えの `TLS_CERT`/`TLS_KEY`）は、上級者向けに残す。

### 2. 端末のウィザード（install.sh）

番号つきの段で進め、各段の頭に「何をするか」、終わりに ✓ を出す。

1. **環境の確かめ**: OS のバージョン、CPU・メモリ・ディスク、時計、80・443 番が空いているか、外へ出られるか（Let's Encrypt・Docker Hub・GitHub）、ほかの Web サーバーが動いていないか。**全部を一度に ✓／✗ の一覧で見せ**、✗ には直し方を 1 行ずつ。✗ があれば何も変えずに止まる。`install.sh --check` で確かめだけを流せる（何も変えない）
2. **聞く**: 管理画面の名前・ショップのドメイン・最初の運営のメールと名前・最初のショップの名前と住所（例 `demo`）。使い方（本番／ステージング）は既定で本番
3. **DNS の確かめ**: 2 つの名前が公開の DNS でこのサーバーの IP を指すか。指していなければ、足す行（種類・名前・値）をそのまま出し、向くまで待つ（数十秒ごとに見直す。Ctrl-C で抜けて後で流し直せる）。外から届かないステージングは、DNS の API の鍵を渡したときだけこの段を飛ばす
4. **入れて立てる**: 今までの ADR 0030 の 3〜5（Docker・置き場・合言葉・移行・systemd）。最初のショップもここで作る（`php artisan shop:create`。DB を作る力は CLI〔root〕だけが持ち、Web のプロセスには持たせない）
5. **仕上げ**: 証明書が取れて https が開けることを外から確かめ、**「このアドレスをブラウザで開いてください」の 1 行**（一度きりの合言葉つき）と、それが切れたときの出し直し方（`sudo ec-sugar operator enroll <メール>`）だけを出す

途中で止まったら、どの段で何が足りないかと直し方を出し、直して流し直せば続きから進む（冪等）。

### 3. ブラウザのウィザード（最初の登録の画面）

端末に出た一度きりの合言葉（URL の `#` の後ろ。サーバーの記録に残らない）を持つ人だけが開ける。先に URL を見つけた他人が乗っ取る Web インストーラーの穴を作らない。

1. **ようこそ**: 何をするか（パスキーを登録して管理画面に入る）を 3 行で
2. **このブラウザで登録できるかの確かめ**: 信頼された https か（`isSecureContext`）、パスキーが使えるか（`PublicKeyCredential`、端末の認証器）。だめなら理由と直し方（証明書の警告を飛ばして開いた・古いブラウザ・など）を出し、先へ進ませない
3. **パスキーの説明と登録**: パスキーとは何か（指紋・顔・端末の暗証番号で入る。合言葉は無い）を短く、登録のボタン。断られたら、取り消し・時間切れ・信頼されない接続・この端末で使えない、を分けて言う
4. **できた**: 管理画面のホームへ。予備のパスキー（別の端末）を足すことを勧める

最初の運営の登録の期限は、DNS の反映を待つことがあるので通常より長くする（24 時間。2 人目からは今のまま）。

### 4. 証明書は Caddy が取る

- 入口に **Caddy**（Go 製の Web サーバー。Let's Encrypt の取得・取り直し・失敗の再試行を自分で行う）を置き、TLS（https の暗号）を受け持たせる。nginx は後ろに残し、今の守り（管理画面の IP の制限・ファイルの拒否・ヘッダ）をそのまま使う
- **店のホストごとにその場で取る**（on-demand TLS）。初めて来た名前は、取りに行く前に EC-SUGAR の内側の経路に「この名前は管理画面か、ある店か」を聞き、違えば断る（知らない名前で証明書を取らせない。Let's Encrypt の回数の上限を食い潰させない）。店の独自ドメインも同じ仕組みに載せられる形にする（今はまだ受けない。入口の nginx と問い合わせの経路を広げるときに決める。見直し）
- 外から届かないステージングは、DNS の API の鍵（Cloudflare）を渡したときだけ、DNS で確かめる形でワイルドカードを取る。Cloudflare の部品を足した Caddy はバージョンを固定して自分たちで作る
- 本当の接続元の IP: Caddy が付けた 1 段だけを nginx と Laravel が信じる（Caddy は外から来た `X-Forwarded-For` を信じない設定にする）。管理画面の IP の制限と回数の制限はこれに頼るので、偽れないことをテストで確かめる
- 証明書と ACME のアカウントの鍵は Caddy のボリュームの中だけ。Web・PHP のコンテナからは見えない

### 5. すでにある Web サーバーの後ろに置く形（2026-10-29 追記。ほかのサイトが動いている管理パネルのサーバーでも動かせるようにする）

- 文脈: 一般のエンジニアが自社のサーバー（Plesk など。nginx と apache2 が 80・443 番でほかのサイトを公開中）に入れたい。そこで「Web サーバーを止める」を勧めると、ほかのサイトがすべて止まる
- 決めたこと: 答え `FRONT=proxy`（既定は今の `caddy`）。80・443 番がほかに使われていれば、端末のウィザードの 2/5 でこの形にするかを聞く（答えのファイルでも選べる）。1/5 は Plesk・cPanel などを見分け、Web サーバーを止めることを勧めない
  - EC-SUGAR は Caddy を起こさず、入口の nginx を **TCP では待たせず、ホストの Unix ソケット（`/var/lib/ec-sugar/front/web.sock`）だけで待たせる**。置き場は root の持ち物・専用のグループ `ec-sugar-front`（nginx のコンテナが足してソケットを作る）の 2770 で、前の Web サーバーの働き手のグループには ACL で通り抜けだけを許す（グループは 443 番を本当に持っているプロセスの働き手から見分け、見分けられなければ聞く。答え `PROXY_GROUP`。共有のグループ・働き手のほかの利用者が所属するグループ・同じグループで PHP などが動くサーバーでは止まる。最後のものは答え `PROXY_GROUP_SHARED_OK=1` で分かったうえで進められる）。ファイアウォール（ufw・DOCKER-USER）には触らない。証明書はすでにある Web サーバーが取る。DNS の確かめ（3/5）は残す
  - 本当の接続元: ソケットから来た要求（前の Web サーバー）が付けた `X-Forwarded-For` の最後の住所だけを使う（`set_real_ip_from unix:`。付け足す形でも付け直す形でも正しい。前の方は外から偽れる）。Laravel の `TRUSTED_PROXIES` は空のまま。`X-Forwarded-Proto` が https でなければ https へ送る（PHP には https と伝えるため）
  - 前の Web サーバーの設定の確かめは `ec-sugar check-front`（管理画面とショップの両方を https で通し、偽の `X-Forwarded-For` と `X-Forwarded-Proto` を見る）。5/5・`status`・自動の更新の後に流し、通っていなければ登録の URL を開かないよう強く出す
- 2 回目の見直しで変えたこと: 最初は 127.0.0.1 の 1 つの番号で待ち、入口の前の網の gateway から来た要求の `X-Forwarded-For` を信じていた。ホストから 127.0.0.1 へ来る接続は利用者に関わらず全部 gateway に見えるので、同じサーバーの root でない利用者（契約者の PHP・cron・SSH の利用者）が許された住所を名乗れた。前の Web サーバーにだけ秘密の見出しを付けさせる案は、その秘密を置く設定のファイルを契約者が読めないかが Plesk ごとに違うので選ばず、OS の権限（ソケットの置き場のグループ）で分けた
- 3 回目の見直しで足したこと（後ろに置く形に限らない）: php-fpm を TCP で受けず、nginx とだけ分け合うソケットで受ける。ホストの防火壁で、root でない利用者からこの compose の網へ出る通信を断る（同じサーバーの契約者などが、app・db・redis・nginx の住所へ直に送れないように）
- 結果: 前の Web サーバーと同じグループで PHP などが動くサーバーは、分かったうえでの印が無ければ入れない（入れたときは status に出し続ける）。前の Web サーバーの設定の誤り（`X-Forwarded-For` をそのまま渡す）は `check-front` で見つけるが、入れた後に人が設定を変えると、次の `status` か更新までは気づけない。前の Web サーバーの前に CDN があると、最後の住所は CDN になる（手順書）

## 選ばなかった案

- **今の nginx のまま acme.sh を定期で流す**: 部品は増えないが、ワイルドカード 1 枚のため DNS の鍵が必須のまま（ふつうの人には壁）。取り直し・nginx の読み直し・失敗の扱いを sh で書くことになり、自前の量が増える
- **Web のインストーラー（よくある設置型の EC の形）**: 最初に開いた人が乗っ取れる。DB を作る力を Web のプロセスに持たせることになる（CONCEPT 7.2 の「Web プロセスはコードを書き換えない」に近い危うさ）
- **パスキーのほかに合言葉のログインを足す**: ADR 0013 を崩す。壁は https の信頼であってパスキーではない

## 結果

- 入れる人が触るのは DNS の 2 行と、2 つのウィザードだけになる
- 部品が 1 つ増える（Caddy）。バージョンの固定・更新・脆弱性の告知の対象に入れる
- 脅威モデルに、入口の 2 段（IP の受け渡し）、on-demand TLS の問い合わせの経路、最初の登録の合言葉の期限を足す
