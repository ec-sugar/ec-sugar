# 0073 予約販売は、発売日の前の商品を在庫によらず予約の数で受け、発売日まで発送しない

状態: **採用**（2026-11-05。作ることと要点の 1〜7 は運営が決めた。「予約の注文は在庫を減らさない（届いた在庫の割り当ては次）」「発売日の前の発送は断る」も確かめて決めた。細部は作りながら決めて下の「作って決めたこと」に書いた）。ADR 0025（プラグイン）・0050（商品の画面の App の欄）・0051（App の画面）・0059（お届け日時）・0064（送料と便）・0068（ポイント）の上に足す。置き換えるものは無い

## 要点（先に）

1. App「予約販売」（`plugins/plugin-preorder`、名前 `preorder`、目的 `selling`）。店が商品ごとに**発売日**（発送を始める日）・**予約の受付の終わり**（任意）・**予約の数の上限**（任意。在庫とは別に。空なら上限なし）を入れる。発売日の前は商品の画面とカートに「予約商品（11月20日ごろ発送）」、ボタンは「予約する」
2. **支払いは注文の時（先払い）**。お金・支払い・返金・メールは今の物販の流れのまま。予約の数は注文を作る錠の中で数え（上限を超えない）、払われずに消えた注文で戻る。在庫が 0 でも予約の上限まで受ける
3. **予約商品とふつうの商品が混ざったら、分けずに全部を発売日にまとめて送る**（発売日の違う予約商品どうしは、いちばん遅い日）。カート・注文の入力・確かめの画面に「予約商品の発売日（◯月◯日ごろ）にまとめてお送りします」。送料は今のまま 1 回
4. 予約の品のある注文は、**発売日まで発送できない**（店の人の発送の操作を**断る**）。発売日になったら管理画面のホームのやることに「発送を始められる予約の注文」。お届け日時の指定（ADR 0059）は出さない
5. 店が発売日を変えると、予約したお客さん（払った注文）にメールで知らせる（前の日・新しい日）。取り消しはお客さんが店に連絡し、店の人が今の取消と返金で。お客さんの自分での取消は今回は無し
6. ポイント（ADR 0068）は今どおり発送で付く
7. App の画面: 予約の商品ごとの予約の数・上限・発売日と、発売日の変更

## 文脈

- 新作・限定品・入荷待ちの品を、届く前から売りたい店が多い（日本の店でよくある「予約商品」）。今は在庫が無いとカートに入らない
- 在庫（`inventory_stocks`）は「押さえた数 ≦ 物理的にある数」を DB の制約で守る（負の在庫を作らない）。届く前の品を在庫として押さえると、この決まりを曲げることになる

## 決定

### 1. 核に足した口（最小）

- **予約販売の口**（`App\Core\Plugin\Contracts\PreorderHandler`、`PluginDefinition::$preorder`。店で 1 つの App だけ。登録簿が 2 つ目を断る）: `terms(商品の ID)` が発売日の前の商品の決まり（`App\Core\Plugin\Preorder\PreorderTerms`: 発売日・残り・受け付けているか）を返し、`reserve(注文, 商品 => 数)` が注文の確定の錠の中で数え直して残す（超えれば `PreorderUnavailable`）。核の窓口は `App\Core\Order\Preorders`（使っている店でだけ App に聞く。App が落ちたら「予約でない」として扱い、ショップは止めない）
- **受渡の発送を始める日**（`fulfillments.ships_on`。日本の暦の日付。空なら今までどおり）。`FulfillmentService` が、その日の前は発送・完了にしない（`TransactionException`。管理画面には 409 と文）。日を変えるのは `FulfillmentService::reschedule`（発送の前の受渡だけ。`fulfillment.ships_on_changed`）。受ける受渡（買取の送付）には持たせない（DB の制約）
- 予約の品のある注文の印は、注文の確定と同じトランザクションのイベント `order.preorder_placed`（発送を始める日と商品ごとの数。個人情報は無い）

### 2. 在庫と予約の数

- **予約の品は在庫を押さえない**: 注文の商品の行を拠点の無い行にする（`TransactionService` の確保・取消の戻し・`FulfillmentService::complete` の出庫は、拠点のある行だけを動かす今の決まりのまま）。在庫の数は予約で動かない
- ショップの窓口（`Catalog`）は、発売日の前の商品の「利用可能な数」を在庫の代わりに予約の残り（上限が無ければ十分に大きい数、受付を終えていれば 0）にする。カート・注文の確定は同じ窓口を通るので、確かめの画面と錠の中の答えが同じ決め方になる
- 予約の数は App の表（`preorder_items`）の、今の回の、取り消し・返金で終わっていない注文の数の合計。払われずに消えた注文は取消になるので、数え直すだけで戻る（戻す処理を持たない）。上限は錠の中で数え直す（連鎖のロックの中なので同時の注文は順になり、カートの行ごとの確かめをすり抜けた同じ商品の種類違いも App が足して断る）

### 3. 混ざったカートと便

- 予約の品のある注文は、拠点で分けずに便（配送の方法。ADR 0064）ごとに 1 つの受渡にまとめ、いちばん遅い発売日を発送を始める日にする。方法の違う品は今までどおり便で分ける（送料も便ごと）
- 確かめの画面の指紋に、まとめて送る日を入れる（確かめた後に発売日が変わったら確定しない。特商法の最終確認の「引き渡しの時期」と食い違わせない）

### 4. 発送の前の操作

- **断る**（確かめの一文を挟む形は採らない）。発売日の前に送ると、届く前の品を出したことになるか、店の人が押し間違えた時に戻せない。品が早く届いた時は、発売日を今日に前倒しすれば、その場で発送できる
- 管理画面の注文の画面は、発売日の前の受渡を発送の選択肢から外し、「◯ から発送（予約の品の発売日）」を添える

## 採らない案

- **届く前の品を在庫として押さえる（負の在庫・取り寄せの数）**: 在庫の DB の決まり（押さえた数 ≦ ある数）を曲げる。在庫の画面・CSV・再入荷のお知らせのどれもが「負の在庫」を知らない
- **予約の品と在庫の品を分けて送る（送料を 2 回）**: 運営の決定でまとめて送る。分けて送る形は下の「次」
- **お客さんが自分で取り消す**: 今回は無し（店に連絡）

## 次（今回はしない）

- 予約の品とふつうの品を分けて送る（先に在庫の品を送り、予約の品は発売日に。送料を便ごとに 2 回取るか店が選ぶ）
- お客さんの自分での予約の取消（発売日の前まで）
- 届いた品を予約の注文に自動で割り当てる（在庫の受け入れで予約の分を差し引く）
- 払わない注文での上限の占有: コンビニ払いの入金待ちなど、払われるまでの注文も予約の数に入る（払いの期限で消えれば戻る）。期限の短い入金待ちで上限を埋められる心配があれば、予約の商品だけ入金待ちの手段を出さない形を考える
- 複数の拠点: 予約の品のある注文は拠点で分けずに 1 つの受渡にまとめる（受渡の拠点は便の中の在庫の品の拠点か、出品者のはじめの拠点）。拠点ごとに発送を分けたい店が出たら、予約の品の拠点を決める欄を考える
- App を止めた時の前倒し: App を使うのをやめると、受けた予約の注文の発送を始める日を直す画面が無い（発売日まで発送できない）。止める前に発売日を今日にするか、App を使い直して直す。核の注文の画面から日を外す口は、要るとなってから

## 結果

- 得たもの: お金・台帳・支払い・返金の道を変えずに、在庫の無い品を予約で売れる。上限は錠の中で守れる。予約の品のある注文は DB の列とサービスの確かめで発売日まで出ない（App を止めても日は残る）
- 失ったもの・気をつけること: **予約の注文は在庫を減らさない**ので、発売日の後のふつうの販売の在庫には、届いた数から予約の分を除いた数を入れる（App の画面と商品の画面の欄の案内に予約の数を出す）。予約の品とふつうの品をまとめて送るので、ふつうの品も発売日まで届かない（カートと確かめの画面で知らせる）

## 作って決めたこと（2026-11-05）

- **日付は日本の暦**（Asia/Tokyo。ADR 0059 と同じ）。発売日の当日の 0 時から予約でなくなり、発送できる。受付の終わりは「その日まで」（その日の 23:59:59 まで受け、次の日の 0 時から受けない）
- **決まりの形**: 発売日は始める時に明日から 2 年先まで、続けて直す時は今日から（今日にすると発送できる）。受付の終わりは発売日より前の日。上限は 1〜100,000 点で、今の予約の数より下げられない。DB でも上限の範囲と「受付の終わり < 発売日」を守る
- **回（round）と発売日の後の延期**（見直しの中 1 で直した）: 発売日を過ぎても、今の回に**発送の前の予約の注文が残っている間は同じ回の続き**（品が届かず延ばす）として扱い、発売日を延ばすと注文の日と受渡の発送を始める日を直し、知らせる（商品はまた予約になり、受けた予約を数え続ける）。発売日の前にやめて始め直すのも同じ回の続き。発売日を過ぎて発送も済み、この回に予約がある時は、欄からは始め直せない（前の回の予約を数えてしまうため、理由つきで断る）。App の画面の 1 件の操作「次の予約を始める」（`preorder.next_round`）で回を進めてから、新しい発売日を入れる。この回にまだ予約が無ければ（受けないまま発売日を過ぎた・次の予約を始めた後）、そのまま新しい発売日を入れられる。商品の決まりの行は消さずに止める（前の注文の予約をたどるため）
- **発売日を変えた時**: 今の回の、取引が開いていて発送の前の受渡がある予約の注文に約束した日（`preorder_items.release_date`）を直し、受渡の発送を始める日を注文の中のいちばん遅い日に直す（同じトランザクション。`preorder.release_date_changed`）。知らせのメールは、**まとめて送る日が変わった**払った注文（受渡・支払いの段）にだけ、書き込みの後にキューで 1 通ずつ（`SendPreorderMail`。宛先は仕事の中で読む。どの商品の発売日が変わったかを注文の時の品名で書く。延びた時だけお詫びの一文）。ほかの予約の品のもっと遅い日にまとめて送る注文は、日が変わらないので送らない。お支払いの前の注文（払われずに消えることがある）には送らず、払った時の注文のメールに今の発送の予定と注文の時の日を載せる（下の「お客さんへの見せ方」）
- **やめた時**: 新しい予約を受けず、すぐにふつうの在庫の販売に戻る。受けた予約の注文はそのまま（発売日から発送できる）
- **見せ方**: 受付を終えた・上限に届いた商品は「予約の受付を終えました」（カートに入らない）、残りが少なければ「予約商品（11月20日ごろ発送）・残り 2 点」。テーマ API に `ListingCard::$preorder`（発売日）・`preorderLabel()`・`availabilityLabel()`・`addToCartLabel()`、`CartView::preorderShipDate()` を足し、まとめて送る一言は今の送料の添え書き（`shippingNote()`）に入れた（4 つのテーマのカート・注文の入力・確かめの画面がもう出している）。4 つの公式テーマの商品の画面とカートの行、核の商品の区画を合わせた（docs/design/theme-api.md）
- **App の画面**: 記録は予約の商品。絞り込みは「予約を受付中」「発送を始められる」「すべて」。直す欄（足す欄は無い。予約販売にするのは商品の画面の欄）で発売日・受付の終わり・上限。1 件の画面に予約の注文の新しい 200 件（注文へのリンク・数・状態・約束した発売日）。ホームのやることは「発送を始められる予約の注文」（払った・開いている注文で、発送を始める日が今日までの発送の前の受渡があるもの）
- **在庫を見るほかの仕組み**（見直しの中 2〜4）: ショップの窓口の答え（`purchasableVariants`）に `preorder`（発売日）を足し、App「再入荷のお知らせ」（登録の対象・入荷の見方）と「店への知らせ」の在庫の少ない知らせは予約の商品を除く（予約の残りは在庫ではない）。管理画面のホームの「在庫切れ」は発売日の前の予約の商品を数えず、「発送を待つ注文」は発送を始める日の前の注文を数えない（発売日から App のやることと一緒に出る）。App「配送の CSV」の書き出しは発送を始める日が今日までの受渡だけで、取り込みの下見は「発売日の前の予約の注文です」と理由を出す
- **商品フィードと構造化データ**（見直しの中 3）: 予約を受けている予約の商品は、商品フィード（Google・Meta）の在庫を `preorder` にし `availability_date`（発売日の日本の 0 時。`2026-11-20T00:00+09:00`）を添える。受付を終えたら `out_of_stock`。JSON-LD の Offer は `https://schema.org/PreOrder` と `availabilityStarts`。フィードのキャッシュ（1 時間、店の記録の番号が鍵）は日付が変わっただけでは作り直さないので、発売日の当日は最大 1 時間 `preorder` のまま
- **お客さんへの見せ方**（見直しの中 5）: 注文のメール（文と HTML）・ご注文の状況（4 つのテーマ。核の部品 `<x-storefront::delivery-summary>` に `:preorder`・`:ordered-on`）・マイページの注文の履歴に「発送の予定 11月20日ごろ発送（予約商品）」を出す（発送の前の受渡の発送を始める日。発送・取消の後は出さない）。注文の時の日（`order.preorder_placed`）と今の日が違えば「発売日が変わりました。ご注文の時は ◯」を添える（お支払いの確定の知らせのメールで気づけるように）
- **確定で断る文**（見直しの軽 1）: App が錠の中で断る時は商品名を入れる（「「限定のフィギュア」の予約の数が上限に届きました。…」）
- **App の失敗**（見直しの軽 2）: 注文の確定のトランザクションの中で App（`reserve`）が落ちると、注文ごと巻き戻って 500 になる（間違った書き込みは起きない）。ショップの読み出し（`terms`）で落ちた時だけ「予約でない」に倒してショップを止めない
- **残り**: 定期便の申し込み（カートを通さない 1 品の注文、`PlaceSingleOrder`）は予約の品を扱わない（在庫で確かめる今のまま）
