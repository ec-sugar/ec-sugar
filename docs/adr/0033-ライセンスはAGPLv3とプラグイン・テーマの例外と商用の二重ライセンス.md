# 0033 ライセンスは AGPL v3 ＋ プラグイン・テーマの例外 ＋ 商用の二重ライセンス

状態: **方向は採用**（2026-10-29）。~~条文は公開の前に専門家（弁護士・弁理士）に確かめてから確定する~~（2026-11-12: 専門家の確認は待たず、運営が読んで決める。ADR 0098。条文の案は `LICENSE-EXCEPTION.md`、下の「作って決めたこと」）。CONCEPT 8 章（オープンコア）の「OSS ライセンスの種類は未決」を置き換える

## 文脈

- CONCEPT 8 章: 核・既定のテーマ・管理画面は無料で公開（オープンコア）、縦のモジュール（買取・仕事・定期・店舗・マーケット）は有料、SaaS は月額、構築と保守は受託
- 目標: 日本で一番優れた EC にする・手軽に使える・1 つのパッケージでいろいろな場面に（CONCEPT 4.1）。自分の SaaS の事業も持つ
- 比べた選択肢（2026-10-29）: MIT（ゆるい。他社が改造を閉じたまま SaaS で貸せる）、AGPL v3（ネットで貸すなら改造の中身も公開する義務）、FSL / BSL（ソース公開。競合の SaaS を禁止し、2〜4 年で MIT などへ。「オープンソース」とは名乗れない）

## 決めたこと

1. **核は AGPL v3**。「オープンソース」と名乗れる。他社が改造して閉じたまま SaaS で貸すことを防ぐ（改造して貸すなら、改造の中身も公開する義務）
2. **プラグイン・テーマの例外**を条文に足す: 核の公開の口（テーマ API・プラグイン API）だけを使うテーマと App は、核の派生物とみなさず、作り手が好きなライセンス（有料・非公開を含む）で配れる。WordPress の GPL 論争（有料のプラグインやテーマもコピーレフトか）を避け、有料の縦のモジュールと他社の App・テーマが育つようにする
3. **商用ライセンスも選べる（二重ライセンス）**: AGPL を避けたい会社に、別の条件のライセンスを有料で出す
4. **外からの直しを受け取るときは CLA（著作権の同意）**をもらう。二重ライセンスを続けるため
5. **名前とロゴは商標で別に守る**: コードは自由に使えても、「EC-SUGAR」の名前とロゴは勝手に使わせない（改造版は別の名前にする）。商標の登録を考える

## 部品のライセンス（2026-10-29 に確かめた）

- PHP の部品（本番）: MIT・BSD・Apache 2.0。「BSD か GPL を選べる」形のものは BSD を選ぶ。AGPL v3 と組み合わせられる
- Node の部品は組み立てのときだけ使い、配る中身には入らない（MPL 2.0 の lightningcss など）。→ 古い（2026-10-31 に直した）: ADR 0037 から、ビルドして配る JS に入る部品がある（管理画面の vue・vue-router・@lucide/vue・motion-v とその依存、ショップの motion とその依存。MIT・ISC・0BSD。一覧は docs/development/dependencies.md）。これは NOTICE に載せる。組み立てだけに使う部品（Vite・Tailwind・lightningcss など）は今も配る中身に入らない。テーマが同梱するフォント（OFL 1.1）は、OFL の文を添える
- **EC-SUGAR 自身のテーマと見本の App（plugins/ の theme-* と plugin-faq）は MIT**（2026-10-29）。テーマや App を作る人が下敷きにして自由に写せるように。~~composer.json の license は今 "proprietary" のままで、公開の準備のときに MIT と LICENSE のファイルに直す~~（2026-11-12 に直した。下の「作って決めたこと」）。有料の縦のモジュールはこの限りでない
- plugins/ のほかの App（タグの App 10 個・`plugin-tag-sample`・`plugin-video`・`plugin-google-map`）のライセンスはまだ決めていない（2026-10-31。~~今は全部 "proprietary"~~ → 2026-11-12 から、決まるまで核と同じ `AGPL-3.0-only`。下の「作って決めたこと」）

## 結果

- 得るもの: オープンソースの売り文句、SaaS の事業を守る、有料のモジュールと他社の App・テーマの道、商用ライセンスの収入
- 気をつけること: AGPL を嫌う会社がある（商用ライセンスで応える）。例外の条文の書き方は、専門家に確かめる。CLA が無いと外からの直しを取り込めない
- 公開の前にやること: LICENSE と例外の条文・商用ライセンスの条件・CLA・商標・SECURITY.md（脆弱性の報告の窓口）・部品のライセンスの一覧（NOTICE）・plugins/ のライセンス

## 作って決めたこと（2026-11-12。リリース 1.0 の必須 R2「ライセンスの一式」。ADR 0098）

条文は専門家に確かめずに、運営が読んで決める（ADR 0098 の 4。上の状態の「専門家に確かめてから確定」を置き換える）。案は開発の中で書いた。

- **`LICENSE` は GNU AGPL v3 の全文**（gnu.org の agpl-3.0.txt をそのまま。書き換えない。SHA-256 を `tests/Unit/LicenseTest.php` が見張る）
- **核の composer.json と package.json の license は `AGPL-3.0-only`**（前は composer.json が Laravel の雛形のまま "MIT" だった）。**`-or-later` にしない**: 「or later」にすると、FSF が後に出す AGPL の新しい版の条件でも使えることになり、二重ライセンス（3）の前提の「条件を決めるのは著作権を持つ側」が、こちらの知らない条件に開く。新しい版へ移るときは、著作権を持つ側が自分で選んで出し直せる（CLA を受けた分も含めて）ので、-only で失うものは無い
- **例外の条文は `LICENSE-EXCEPTION.md`**（「EC-SUGAR Extension Exception 1.0」。英語の条文と日本語の手引き）。AGPL v3 の **7 条の追加の許可**として書いた（AGPL を狭める条件ではなく、許すことを足すだけなので AGPL と矛盾しない。改造した人は自分の版から消してもよい）。形は GCC Runtime Library Exception（決まった口を定義で指す）と Classpath Exception（独立したモジュール・消してよい）にならった
  - **公開の口**を 2 つで決めた: (a) 文書に挙げた口（theme-api.md・plugins/README.md・making-apps.md・app-sections.md・tag-apps.md・ADR 0093 の 1 の表）と、(b) **ひな形（`make:plugin`）が出すコードと MIT の見本（公式テーマと plugin-faq）が使っている核の部品**。(b) を足したのは、ひな形が `EventStore`・`OperatorAccess`・`StorefrontView` を、見本の faq が核の `Listing` のモデルを使っていて、ADR 0093 の表だけだと、ひな形どおりに作った App が例外の外に出てしまうため
  - ひな形が出したコードも、出した人が好きなライセンスにしてよい（3。ひな形の元の文は AGPL の核の一部なので、許しを書かないと出したコードが AGPL の写しになる）
  - 入らないもの: 核のファイルを書き換える・核の中のサービスを差し替える・核の DB の表を直に読み書きする・核のコードを写す。名前とロゴの許しは含まない（5 の商標）
  - Docker のイメージは `*.md` を入れないので、`.dockerignore` で `LICENSE-EXCEPTION.md` だけを入れる（LICENSE・NOTICE は拡張子が無いので入る）
- **plugins/ の license**: 公式テーマ 4 つと plugin-faq は `MIT` で、各ディレクトリに MIT の `LICENSE`（著作権の表示は composer.json の作り手と同じ「Fivenine design」）。**ほかの App は運営が App ごとに決める途中**なので、決まるまで核と同じ `AGPL-3.0-only`（"proprietary" のままだと、公開したときに「ソースはあるが使ってよいか分からない」になるため）。決まったら `LicenseTest` の許す値と表を直す。`make:plugin` のひな形が出す composer.json は "proprietary" のまま（ほかの人が作る App のライセンスは作った人が決める。例外の 3）
- composer.lock の自社のパッケージ（path）の license も合わせた（`composer update 'ec-sugar/*' --no-install`。依存の版は変えていない。変わったのは license の欄と path の中身のハッシュだけ）
- **NOTICE** は `release/notice.sh` で作る。PHP は composer.lock の本番の依存（自社の ec-sugar/* を除く）、JavaScript は**ソースマップつきで使い捨ての場所へビルドして、実際に配る JS に入った部品**（と package.json の dependencies）、CSS に残る見出しの部品（Tailwind CSS の下地）、テーマの CSS が読む @fontsource の書体。JavaScript と書体は、ビルドで縮めると著作権の表示が消えるので、ライセンスの全文も NOTICE に添える（PHP の部品は vendor に各々の LICENSE が残る）。作り直し方は docs/development/dependencies.md
  - 本番の PHP の依存は MIT・BSD-3-Clause・Apache-2.0 で、AGPL v3 と組み合わせられる（Apache-2.0 は GPL v3 系と合う）。nette/schema と nette/utils は「BSD か GPL を選べる」形で、BSD-3-Clause を選ぶ（NOTICE に「used under BSD-3-Clause」）。配る JS は MIT・ISC、書体は OFL-1.1。組み立てだけの lightningcss（MPL-2.0）は配る中身に入らない（2026-11-12 にソースマップで確かめた）
  - **見張り**（`tests/Unit/LicenseTest.php`）: 核と package.json が `AGPL-3.0-only`・LICENSE が元の文のまま・テーマと faq が MIT で LICENSE がある・ほかの App が許す値・composer.lock の自社の license が composer.json と同じ・NOTICE の PHP の部品が composer.lock の本番の依存とちょうど同じ（名前とライセンス。版は比べない: Dependabot の版上げのたびに CI が落ちないように。版はリリースの前に作り直してそろえる）・package.json の dependencies とテーマの書体が NOTICE にあり全文が添えてある
- **SECURITY.md** を書き直した: 受けてからの目安・公表の流れ・対象のバージョン・対象の範囲。窓口は GitHub の非公開の報告（Private vulnerability reporting）だけ（2026-11-12。メールの宛先は書かない。`public/.well-known/security.txt` は公開に出さない。ADR 0098 の作って決めたこと）
- 公開用の **README と CONTRIBUTING の案**は `release/public/README.md`・`release/public/CONTRIBUTING.md`（書き出すときに根に重ねる。ADR 0098 の作って決めたこと）。1.0 は外のプルリクエストを受け付けず Issue だけ（ADR 0098 の 5）
