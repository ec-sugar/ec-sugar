# 0012 ドメインイベントは追記専用でハッシュ連鎖にする

状態: 採用（2026-10-27）。定期の検証と壊れたときの知らせは 2026-10-30 に入った（結果の「運用」）。ロックを取らない書き込みの例外の条件と今の一覧は docs/development/conventions.md の 3（2026-10-31）

## 文脈

ドメインイベントは監査・帳票・通知・AI 評価データの源泉で（CONCEPT 7・7.2）、古物台帳や取引の記録として
後から「書き換えられていない」と言える必要がある。一方、テナント DB の所有者はそのテナントのロールで、
トリガーも外せる。DB の権限だけでは改竄を防ぎきれない。

## 決定

- **状態の変更と同じ DB トランザクションで書く**。コミットしなかった変更のイベントは残らず、イベントの無い変更も残らない。プラグインへの通知（`DomainEventRecorded`）はコミット後に出す
- **追記専用**: `domain_events` の UPDATE / DELETE / TRUNCATE をトリガーで拒否する（Eloquent 側でも拒否）
- **ハッシュ連鎖**: 各イベントは 1 からの連番と前のイベントのハッシュを持ち、`hash = HMAC(テナント鍵から HKDF で派生した鍵, 正準化した本文)`。鍵はブラインドインデックスとも暗号化とも別の派生。鍵を持たない者は、トリガーを外して書き換えても連鎖を作り直せない。`EventStore::verify()` が最初に壊れた位置を返す
- **分岐を DB で拒否**: `prev_hash` と `hash` に一意制約
- **直列化**: 追記は 1 テナント DB の中でアドバイザリロック（連鎖のロック）を取って行う。デッドロックを避けるため、書き込む操作はすべて最初に連鎖のロックを取り、それから取引・受渡・在庫の行をロックする（例外は、状態でない・お金と在庫に触れない・イベントが要らない書き込みだけ。今はカート〔ADR 0021〕・見回りの時刻の印・送ったメールの記録。条件と一覧は conventions.md の 3）
- **payload は整数・文字列・真偽値・null とその配列だけ**（浮動小数は jsonb の往復で表現が変わる）。平文の個人情報は入れず、ID で参照する（ADR 0010）

## 結果

- 得たもの: 監査証跡が DB の dump だけで検証できる。アプリのバグで履歴が消えたり書き換わったりしない。プラグインは核のテーブルに触らずイベントで連携できる
- 失ったもの: テナント内の書き込みが直列になる。アプリサーバーごと乗っ取られ鍵も取られた場合は、連鎖ごと作り直せる（防げるのは DB 単体の改竄まで）。連鎖の先頭（最新の hash）を中央や外部に定期的に控える仕組みはまだ無い（末尾を切り落とす改竄は今は検知できない。2026-10-31 もまだ。運営の数の控え〔`shop_digests`、ADR 0042〕に先頭を控える案がある）
- 運用: 定期的に verify を回す仕組み（スケジューラ）と、壊れていたときの通知は未実装 → 2026-10-30 に入った: `operations:collect --verify` が毎日 3:40 に店ごとに店の文脈で検証し（ADR 0042）、壊れていれば運営の様子の困りごと（要対応）に出して、オーナーへメールで知らせる（ADR 0043）。中央の監査ログ（`audit_events`）の定期の検証はまだ（残り）

## 作って決めたこと（2026-11-19 の案 1）

- **連鎖の先頭を中央に控える**: 10 分ごとの回（`operations:collect`）のたびに、店ごとの最後のイベントの番号と hash を中央の `shop_digests` に控え、次の検証で「前に控えた番号のイベントが、同じ hash で今もあるか」を見る。無ければ `chain_rolled_back`（運営の様子の要対応・オーナーへの知らせ）。連鎖の検証は「つながっているか」しか見ないので、**末尾を切り落とされても残りは無傷に見える**（テストで実際に確かめた）。これで「まだできていないこと」のうち、店の DB だけを触られた場合が塞がる（気づくのは次の回＝10 分以内。前の回より後に積まれて、次の回の前に切り落とされた分は気づけない）。**全件の検証（1 日 1 回）の時だけ控える形にしなかった**のは、前の検証より後に積まれた記録（最大 24 時間ぶん。跡を消したい人がいちばん消したい所）が守りの外になるため（取り込みの前の見直しの指摘）。先頭を読むのも、控えた番号の hash を読むのも 1 行
- **巻き戻しを見つけたら控えを進めない**。進めると次の検証で「無傷」に戻り、知らせがひとりでに消える（切り落とした側の思うつぼ）。連鎖が切れている時も進めない（壊れた記録の先頭を正しい先頭として覚えない）。新しい注文で番号が元の所まで戻っても、同じ番号で hash が違うので消えない
- **正当に戻る場合は控えを忘れる口を通す**: デモの店の毎晩の戻し（店の DB を作り直す）は `DemoShops` が自動で忘れる。店 1 つだけをバックアップから戻した時は `php artisan operations:accept-chain-head <店の ID>`（監査ログに `tenant.chain_head_accepted` が残る）。サーバーごと戻す時は中央の DB も同じ時点に戻るので、控えも一緒に戻って合う
- **同時に走る回と、悪い知らせの扱い**: 控えを読むのは鍵の外なので、鍵の中で「読んだ時から控えが動いていないか」を確かめ、動いていれば（ほかの回が進めた・忘れた）古い読みで決めた控えと判定は書かない。巻き戻しと連鎖の切れは、同じ晩に別の回が先に書いていても時刻に関係なく書く（悪い知らせを捨てない）。控えを忘れる操作も同じ鍵を取り、忘れる前の控えを監査ログに残す
- **サーバーごと戻す時に控えが合うのは、バックアップが中央の DB を先に取るから**（DB の名前の順。既定の店の DB の頭 `ec_t_` は中央 `ec_central` より後）。店の DB の頭を中央より前に並ぶ名前にすると、戻した後に誤って知らせることがある
- 中央に置くのは番号・hash（店の鍵の HMAC。中身は分からない）・真偽だけ。DB の制約で形を決めた（hash は 16 進 64 桁、番号と hash は組）
- **まだ塞がっていないこと**: 中央の DB も一緒に書き換えられる場合（運営のサーバーごと乗っ取られた場合）。同じ値を上書きも削除もできない外の置き場へ送る（案 2。Cloudflare R2 のロック）は R7 と一緒に
