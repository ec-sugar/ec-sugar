# 0098 開発用と公開用のリポジトリを分け、リリースごとに許したものだけを書き出す

状態: **採用**（2026-11-12）。
- リリースはパッケージを配る形にし、範囲を絞る（運営の判断。範囲を絞らないといつまでもリリースできないため。選択肢で「パッケージを配る」「必須 4 つ＋色だけ」）。
- 配り方は運営の案（新しい公開のリポジトリを開き、開発用と公開用を分ける）。
- ADR は整えて載せる、1.0 では外の PR を受け付けない、例外の条文は運営の判断で出す（どれも運営が選択肢で決めた）。

ADR 0033（AGPL v3 ＋ 例外 ＋ 商用の二重ライセンス）・ADR 0030（自動の更新）・（配る道の守り）の上に足す。決めることに残っていた「リポジトリを公開するか」（2026-10-29 はまだ早いと見送った）はこれで決まった。

## 要点（先に）

1. **今のリポジトリは開発用のまま非公開**。公開用に新しいリポジトリを開く（名前は作るときに決める）
2. 公開用には、**リリースごとに許したファイルだけを書き出す**。1 リリース 1 コミットにし、開発の履歴は出さない。書き出す前に、秘密と内輪の言葉で止める検査を通す
3. 公開用のリポジトリの CI（GitHub の走らせ役。公開なので無料）がイメージを作り、keyless で署名して **GHCR に公開で置く**。タグには保守する人の物理の鍵で署名する。お客さんのサーバーは両方を確かめてから入れる（形を公開用に移す）
4. **ライセンスは ADR 0033 のとおり**（核は AGPL v3、App とテーマの例外、商用ライセンス）。例外の条文は案を作り、運営が読んで決める（専門家の確認は待たない）
5. 1.0 では**外からの PR を受け付けない**（Issue だけ）。直しは開発用で作って書き出す。CLA は受け付けるときに作る
6. **ADR は整えて載せる**: 開発の設備・内側の網・お客さんの名前・個人の連絡先などの内輪の話を取り除いた版を、書き出しのときに公開用に入れる

## 書き出すもの・書き出さないもの

| 書き出す | 書き出さない |
|---|---|
| `app/`・`bootstrap/`・`config/`・`database/`・`plugins/`・`public/`・`resources/`・`routes/`・`storage/` の骨組み・`tests/`・`docker/`・`deploy/`・`ops/` のうち配るもの・`composer.*`・`package*.json`・ビルドの設定 | `docs/daily/`・`docs/tasks/`・開発の道具の設定・開発の設備の台本と記録・開発用の CI の設定（自前の CI の走らせ役） |
| 使う人・作る人向けの文書（install・テーマ API・App の作り方・管理画面の部品・用語・脅威モデル）・整えた ADR・`CHANGELOG.md` | 内輪の文書（サーバーへの入り方・デモの店の本番の手順・開発の進み具合の画面など）、整える前の ADR |
| `LICENSE`・例外の条文・`NOTICE`・`SECURITY.md`・`README.md`（公開用に書く） | 開発用の決まりの文書（公開用には作る人向けの CONTRIBUTING を書く） |

- 何を出すかは**許す一覧**（書き出さないものを並べる形ではない）で決める。一覧に無いファイルは出ない
- 検査（どれか 1 つでも見つかれば書き出さない）: gitleaks、内側の網の IP アドレス・内輪のホスト名・お客さんの名前・個人のメールアドレスの一覧、`.env` などの秘密のファイルの形

## 1.0 までの必須

1. 書き出しの仕組みと検査
2. ライセンスの一式（LICENSE・例外の条文・NOTICE・SECURITY.md・composer.json の license・公開用の README）
3. ADR を整える
4. 配る道の守り（公開用の CI のイメージ・keyless の署名・物理の鍵で署名したタグ・更新側の確かめ）とインストーラーの高の指摘
5. まっさらな VM に、公開用のリポジトリから install.md だけを見て入れ直す
6. 決済まわりの中くらいの穴
7. 本番（公式の店）のバックアップをサーバーの外へ（Cloudflare R2）と復元の訓練
8. 色・字・角の丸み（ADR 0097。PR 169）
9. 1.0 の印（CHANGELOG・公開日 `tests/Support/launched-on.txt`）

それ以外（外への通信を絞る・DB と Redis の暗号化・ほかの Linux・入れた後に App を足す道・多店舗・ヘッダーの区画・新しい App）は、1.0 の後に回す。

## 採らなかった案

- **今のリポジトリをそのまま公開する**: 開発の記録・作業の一覧・開発の設備の話が履歴ごと出る。履歴を書き換えて消すのは危なく、手間も大きい
- **非公開のまま、買った人に読むだけの鍵を渡す**: お客さんごとの鍵の管理と取り消しが要る。ADR 0033 の「オープンソースで出す」とも合わない
- **最初は設置代行の客だけに配る**: 運営はパッケージを配る形を選んだ

## 守り

- 公開用のリポジトリは、GitHub の走らせ役だけで CI を回す（自前の CI の走らせ役で外のコードを動かさない）。main とタグの保護、Actions の権限は最小に
- 署名は 2 つ（CI の keyless ＋ 物理の鍵のタグ）。CI の署名だけのバージョンは入れない
- 書き出しは手元か開発用の CI で行い、公開用のリポジトリへ書ける鍵は書き出しの道具だけが持つ

## 作って決めたこと（書き出しの仕組みと検査、2026-11-12）

- 道具は `release/export.sh`（bash。要るのは git と gitleaks だけ）、許す一覧は `release/public-paths.txt`、内輪の言葉の一覧は `release/forbidden.txt`。`release/` の中は許す一覧に書いても出さない。手順と直し方は docs/development/release.md
- **開発用のコミットの ID は公開のコミットに書かない**（題は「EC-SUGAR <版>」、本文は空）。ID だけでも、非公開のリポジトリとその中の位置を外に知らせる。対応は開発用の手元の軽いタグ `export/v<版>` に残す
- 取り出しは `git archive` でなく使い捨ての索引から（`.gitattributes` の `export-ignore` が CHANGELOG.md などを黙って落とすため）
- 公開用にだけ置くファイル（公開用の README・公開用の CI）は `release/public/` に置き、根へ重ねる。取るのは追跡しているものだけ
- 書き出しのコミットの書き手（名前とメール）とパスの名前も内輪の言葉の検査に掛ける。gitleaks は既定の決まりで流し、木の中の `.gitleaks.toml`・`.gitleaksignore`・`gitleaks:allow` では緩めない
- 内輪の言葉の種類ごとに、直すべきでないファイル（外の部品の記録 `composer.lock`、テストの見本の宛先・住所）だけを `!` で除ける。開発に使う機械そのものの住所と内輪のアドレスは、テストも含めて見る

## 作って決めたこと（検査が止めた所の片付け、2026-11-12）

- **設計の正本（`docs/CONCEPT.md`）・コードの書き方の決まり（`docs/development/conventions.md`）・入れたライブラリの一覧（`docs/development/dependencies.md`）も公開に入れる**。CONCEPT はコードのコメントから多く指され、決まりと一覧は App とテーマを作る人に要る。ADR と同じ決まりで、作り手の経歴・お客さんの案件・他社の製品名・開発の設備・内輪の文書への参照を外した（設計の意味は変えない）。公開しない運用の道具の部品の記録は、その道具の README へ移した
- **脅威モデルは製品の守りだけにする**。私たちの運用の設備に限る話は、開発用だけの文書へ移した。公開の脅威モデルの複数の店の節は `example.jp` の形で書く。開発の中の分担の言葉は「見直し」などのふつうの言葉に
- コードのコメント・テスト・移行の他社の製品名は、形の説明（「左に区画の一覧・真ん中にプレビュー」「灰の地に白いカード」「日本の EC の受注でよく使う言葉」）に言い換えた。テストの開発の環境の住所は、意味を保った別の私設の住所に、設定の見本の内輪のホスト名は `example.jp` に、LAN の範囲の例は `192.168.0.0/24`（範囲そのものなので [例外]）にした
- 内輪の言葉の一覧で除けたのは、インストーラーのテスト `docker/check-deploy.sh` の私設の住所の種類だけ（`tests/` の外にあるテストで、私設の住所を断ることを見本の住所で確かめる。開発の環境の機械の住所は除けずに見る）
- `.gitattributes` から `CHANGELOG.md export-ignore` を外した（GitHub が作る取り出しのアーカイブから変更履歴が落ちないように）。書き出しの道具は `git archive` を使わないので、どちらでも書き出しには効かない。`/.github` と `.styleci.yml` の `export-ignore` は Laravel の既定のまま残す

## 作って決めたこと（公開の準備を 1 本にまとめる、2026-11-12）

- **定期便・予約・デジタルチケット・抽選販売の App（`plugin-subscription`・`plugin-booking`・`plugin-tickets`・`plugin-lottery`）は 1.0 の公開に入れない**（運営の判断）。有料にするかは後で決める。AGPL で一度出したものは取り消せないため、決めるまで出さない。開発用ではコードも依存もそのままで、開発と本番の店では今までどおり動く。許す一覧から外し、その App だけを確かめるテストも除いた。公開する文書に残る 4 つの App の話は直さず、公開用の README に「1.0 の公開には入っていない」と書いた
- 外した App の composer の依存は、**書き出しの道具が書き出す木の `composer.json` と `composer.lock` から外す**（`release/strip-packages.php`。`content-hash` は Composer と同じ求め方で付け直す。残るパッケージが外した App に頼っていたら止める）。公開用の上書きの `composer.json`・`composer.lock` を `release/public/` に置く形は採らなかった（依存の版上げのたびに手で合わせ続けることになり、ずれても気づけない）。外した App があるときだけ、書き出しに PHP が要る
- **脆弱性の報告の窓口は GitHub の非公開の報告（Private vulnerability reporting）だけ**（運営の判断）。`SECURITY.md` にメールの宛先は書かない（公開用のリポジトリの名前が決まる前なので、URL でなく「このリポジトリの Security タブ」と書く）
- **`public/.well-known/security.txt` は公開に出さない**（許す一覧で `!` で除く）。私たちの店（ec-sugar.jp）で配る連絡先で、公開に入れると入れた人のサーバーからも配られ、届かない宛先や私たちの宛先を外へ広げてしまうため。開発用の中身は前の宛先に戻した
- 公開用の README と CONTRIBUTING は `release/public/` に置き、書き出しで根に重ねる（開発用の README は出さない）。ライセンスの一式（`LICENSE`・`LICENSE-EXCEPTION.md`・`NOTICE`）を許す一覧に足した
- 著作権の表示の名前は「Fivenine design」（運営の判断。NOTICE・例外の条文・MIT の LICENSE・自社の App の composer.json の作り手と composer.lock。`LicenseTest` が見張る）

## 作って決めたこと（4 つの App が無い公開の木、2026-11-12）

- **公開の木は、定期便・予約・チケット・抽選販売の App が無くても、テスト・デモの店・管理画面が動く形にする。決め手は「その App が入っているか」だけで、開発用の木では何も飛ばさない**（デモの店は入っていない App とその扱いの商品を作らない、ヘルプは入っていない App の説明のページを出さない、テストは理由の文つきで飛ぶ。パッケージがあるのに登録簿に無ければ落ちる）。形は docs/development/release.md の「公開の木で 4 つの App が無いときの扱い」

## 作って決めたこと（公開の木の phpstan、2026-11-12）

- **公開の木でも phpstan を開発用と同じ決まりで流し、0 件にする。検査は緩めない**（数えない設定・無視の印を使わない）。開発用の `phpstan.neon` は書き出さない `release/` も見るので、書き出しの道具が書き出す木の phpstan の設定から木に無い path の行だけを外す（`release/strip-phpstan-paths.php`。composer の依存を外すのと同じ考えで、決まりそのものは変えない）
- テストの中の 4 つの App のクラスを使う所は、許す一覧で除く名前（`Booking*`・`Lottery*`・`Subscription*`・`Ticket*`）の部品のファイルへ分け、使う側は `class_exists` で囲んで呼ぶ（phpstan は囲みの中の無いクラスを数えない。開発用の木では部品の型のまま全部見る。App が入っているのに部品が無ければ落ちる）。形は docs/development/release.md の「公開の木で 4 つの App が無いときの扱い」
