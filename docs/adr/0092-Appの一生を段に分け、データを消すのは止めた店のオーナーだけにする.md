# 0092 App の一生を段に分け、データを消すのは止めた店のオーナーだけにする

状態: **採用**（2026-11-11。作ることを決めた〔App の一生の約束〕。形は既定どおりに作った）。
ADR 0005（核 ＋ プラグイン）・0025（登録簿と店ごとの使う・使わない）・0024（オーナーとスタッフ）・0086（デモの店）の上に足す。
ADR 0025 の「止めてもプラグインのデータは消さない（消すのはアンインストールで、後で）」の「後で」を、この ADR の「店で App のデータを消す」で置き換える（止めても消さない、は変えない）

## 要点（先に）

1. App の一生は 5 つの段: **入れる**（composer）→ **店で使う・止める**（今のまま）→ **店で App のデータを消す**（新しい）→ **バージョンを上げる** → **composer から外す**。段ごとに App がしてよいことと核が保証することを下の表に決めた
2. **データを消すのは、その店で App を止めている時だけ・オーナーだけ・直前のパスキーの再確認の後**（`DELETE /api/tenants/{店}/plugins/{名前}/data`、CLI は `php artisan plugin:purge <店> <名前>`）。デモの店では断る
3. App は `PluginDefinition` に**データを消す口**（`purger:`、`App\Core\Plugin\Contracts\PluginDataPurger`）を任意で渡す。口の無い App は消せない（ボタンも出ない）。口のある App は今「よくある質問」（`faq`）と「ダウンロード販売」（`downloads`）
4. 核（`App\Core\Plugin\Services\PluginDataPurge`）が、連鎖のロック → 状態の行のロックの中で「止めた」を確かめ、App の口で App の表の行を消し、App の設定（秘密も）を消し、`plugin.purged` を同じトランザクションで残す。**ファイルはコミットの後**に App の口で消す
5. 消すのは App の表の**行だけ**。表・状態の行（止めたまま）・記録（追記だけの鎖）は残す

## 文脈

- CONCEPT 6.2 のライフサイクルは「install → enable（テナント単位）→ disable → uninstall（自分のデータを消す責任を持つ）」。今あるのは入れる（composer）と店で使う・止める（ADR 0025）だけで、止めた App のデータ（お問い合わせの中身・売るファイル・App の設定の秘密など）を店が消す道が無かった
- App の表は店の DB に置き、移行はどの店にも流れる（使わない店では空。ADR 0025 の作って決めたこと）。だから「アンインストール」で表を消すことはできない（ほかの店で使っている）。消せるのは店ごとの**行**
- composer から外すのは家（サーバー）ごとの操作で、店ごとではない。外した後は App のコードが無いので、App の表の形も消し方も核には分からない

## 決定: 段ごとの約束

| 段 | 誰が・どこで | App がしてよいこと | 核が保証すること |
|---|---|---|---|
| 入れる | サーバーを管理する人が composer で（管理画面からは入れない。CONCEPT 7.2） | 登録簿に定義を登録する（名前・表示名・プラグイン API のバージョン・移行のフォルダ・口）。店の DB に自分の頭の表を作る移行を渡す | プラグイン API のバージョンが合わない・名前が二重・形の違う名前・マニフェストの誤りは**登録で断る**（アプリが起動しない）。移行は全部の店に流れる（`tenants:migrate` と店を作る時）。どの店でも、使うまでは動かない |
| 店で使う・止める | 店の運用以上の段階の人（直前の再確認）。ADR 0025 | 使う店でだけ画面・経路・定期の処理・差し込みが動く。止めた店でも「止めても開く」と宣言した経路（`keptStorefrontRoutes`）と、残りの片付け（`PluginTenants::each` の残りの仕事）は動いてよい | 切り替えは `PluginStates` だけが連鎖のロックの中で行い、`plugin.enabled` / `plugin.disabled` を残す。**止めても App のデータは消さない**（もう一度使えば戻る） |
| 店で App のデータを消す（新しい） | **その店のオーナーだけ**（直前の再確認）。管理画面の App の画面か CLI | 口（`PluginDataPurger`）で、**自分の表の行と自分の置き場のファイルだけ**を消す。表は消さない。核の表に触れない。まだお客さんが使う物があれば `refusal()` で断ってよい | 店の文脈の中だけで呼ぶ。止めていない（使っている）店・口の無い App・デモの店は断る。切り替えと同じ連鎖のロックの中で確かめるので、消している間に「使う」にならない。App の設定の行（秘密も）を消す。`plugin.purged` を同じトランザクションで残す（中身は App の名前・表ごとの数・設定を消したかだけ）。ファイルはコミットの後に消す。中央の監査ログに誰がどの店のどの App を消したかを残す |
| バージョンを上げる | サーバーを管理する人が composer で（イメージの差し替え） | 移行は**前へだけ**（列を消す・名前を変える移行は書かない。`MigrationsExpandContractTest` が App のフォルダも見る）。プラグイン API が変わったら合わせて上げる | プラグイン API のバージョンが合わない App は登録で断る（壊れたまま動かさない）。店ごとの状態・設定・行はそのまま引き継ぐ。核のバージョンの範囲の宣言と更新の前の互換の検査はまだ無い |
| composer から外す | サーバーを管理する人が composer で | （コードが無いので、何もできない） | 表と行は残る（核は消さない。形を知らないため）。状態の行が残っていても「入っていない」と扱い、使わない（`PluginStates::enabled` は登録簿に無い App を偽にする）。管理画面の App の一覧・App の画面のメニュー・ショップは落ちない（`PluginDataPurgeTest` が確かめる）。データを消したい店があれば、**外す前に** `plugin:purge` を流す |

## 決定: 店で App のデータを消す

- **経路**: `DELETE /api/tenants/{店}/plugins/{名前}/data`（`EnterTenant` の下。`RequireOwner` と `RequireRecentConfirmation`）。入れたときのサンプルを消す `DELETE /samples`と同じ形。スタッフは「お金」の段階でも 403
- **断る**（どれも何も変えない）: 入っていない App（404）／消す口の無い App（422）／デモの店（422。毎晩作り直す見本の店なので来訪者に消させない。`PluginRefusedInDemo`）／その店で使っている App（422。先に「使わない」に）／App の口が断った（422。文は App が出す）
- **一度も使っていない店**でも消せる（行が無いだけ）。その時は止めた状態の行を作ってから記録する（記録の集約を `plugin_state` の行にそろえるため）
- **2 回目**は消す物が無いだけで断らない（ファイルの消し残しを拾うため）
- **App の設定**（`plugin_settings` の行。秘密の項目も）は核が消す。App の口は自分の表だけを見る
- **記録**: `plugin.purged`（集約は `plugin_state`、中身は `{plugin, rows: {表の名前: 数}, settings: 真偽}`）。核は App が返した表の名前が App の頭（名前のハイフンを `_` にしたもの）で始まり、数が 0 以上の整数かを確かめ、違えばトランザクションごと落とす（記録に変な名前を入れない・核の表の名前を返す App に気づく）。中央の監査ログは `tenant.plugin_purged`（App の名前・行の合計・ファイルの数。CLI は `via: cli`）
- **ファイルはコミットの後**: 先に消してトランザクションが落ちると、行が残ってファイルだけ無くなる（お客さんが受け取れない）。後に消して落ちたら、報告して結果に「残った」（`leftover`）を返す。行はもう無いので、App の口は「この店の置き場のうち、どの行も指さないファイル」を消す形にし、もう一度消すと残りを拾う
- **画面**: App の 1 件の画面（`TenantPluginPage`）の、止めた状態のときだけ「この App のデータ」の欄と「この App のデータを消す」（`ConfirmButton`。元に戻せないことを文に）。口を持たない App とオーナーでない人には出さない（ボタンを隠すのは見た目のためだけで、サーバーが断る）。一覧の API は App ごとに `purgeable` を返す
- **CLI**: `php artisan plugin:purge <店> <名前>`（確かめてから。`--force` で確かめずに）。actor は `cli:plugin-purge`。断る決まりは画面と同じ（同じサービスを通る）

## 結果

- 得たもの: 使うのをやめた App のデータ（お客さんの情報を含むもの）を、店ごとに消せる。composer から外す前に消しておけば、表の行が残らない。段ごとの約束が 1 つの表になり、App を作る人が「何をしてよいか」を読める
- 失ったもの・気をつけること:
  - App のコードは核と同じ権限で動くので、「自分の表の行だけを消す」は約束で、DB の権限では止めていない（ほかの決まりと同じく、入れるのは審査した App だけ）。核が確かめられるのは、返した表の名前の形と、店の文脈の中で呼ぶことだけ
  - 消した App の記録（`faq.created` など）は鎖に残る（追記だけ。中身は ID と数だけの決まりなので、個人情報は残らない）
  - 口の無い App のデータは消せない。口を足すのは App ごとの仕事（下の「口のある App」）
  - composer から外した後は消せない（コードが無い）。外す前に流すことを手順に書いた（plugins/README.md）

## 口のある App（2026-11-11）

| App | 消すもの | 断るとき |
|---|---|---|
| よくある質問（`faq`） | `faq_items` | — |
| 並び順と絞り込み（`catalog-sort`） | `catalog_sort_items`（並びとタグ。商品〔核の `listings`〕は消さない） | — |
| ダウンロード販売（`downloads`） | `downloads_grants`・`downloads_listings`・`downloads_files` の行と、置き場 `downloads` の `tenants/<店>/files` のうちどの行も指さないファイル。商品（核の `listings`）は消さない | お客さんがまだ受け取れるリンク（止めていない・期限の前・回数が残る）がある／払われたのにまだ渡していない注文がある（App を止めても、払ったお客さんは受け取れる約束。ADR 0084 の見直し） |
| 公開の予約と販売期間（`sale-period`） | `sale_period_windows`（商品ごとの出す日時と終わる日時）。商品（核の `listings`）は消さない | — （止めた時点で期間は効かず、商品はふだんどおり売れる） |

| セット商品（`bundle`） | `bundle_components`（セットの商品と構成の品と 1 セットあたりの数）。商品（核の `listings`）は消さない | — （止めた時点でセットは効かず、セットの商品は自分の在庫で売れるふつうの商品になる） |
| 購入の制限（`purchase-limits`） | `purchase_limits_listings`（商品ごとの 1 回のご注文の上限）。商品（核の `listings`）は消さない。店の最低購入金額は App の設定に残る | — （止めた時点で決まりは効かず、いくつでも・いくらからでも買える） |

ほかの App は口を持たない（ボタンが出ない）。口を足したらこの表に書く。

## 作って決めたこと（2026-11-11）

- 口は 3 つの関数（`refusal`・`purgeRows`・`purgeFiles`）にした。「断る理由」を分けたのは、払ったお客さんの受け取りのように「今は消してはいけない」を App が錠の中で言えるようにするため（核は App の中身を知らない）
- 状態の行に「消した日時」の列は足さなかった（記録 `plugin.purged` で足りる。店の DB の移行を増やさない）
- `PluginRefusedInDemo` に文を渡せるようにし、データを消す時は「デモのお店では、App のデータは消せません。」と出す
- 管理画面の App の画面のヘルプ（`resources/admin/help/apps.js` の「App のデータを消す」）に手順と注意を書いた
