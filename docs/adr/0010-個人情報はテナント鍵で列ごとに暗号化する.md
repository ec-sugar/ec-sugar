# 0010 個人情報はテナント鍵で列ごとに暗号化する

状態: 採用（2026-10-27）

## 文脈

「攻撃で情報が流出しても大丈夫な DB 設計は可能か」という問い。絶対の意味では不可能だが、
「流出したデータが役に立たない」状態は設計で作れる。条件は、持たない・アプリ側で暗号化する・
鍵を DB の外にテナントごとに置く、の 3 つ。ディスク暗号化は dump の持ち出しに無力で、
後から足すと全テーブルを作り直すことになるため、核の最初の一手で入れる。

## 決定

- **持たない**: カード番号は決済代行のトークンのみ。本人確認書類は S3 互換に暗号化して置き、保存期間後に消す。不要な個人情報の列は作らない
- **列ごとに暗号化**: 個人情報の列（name / email / phone / address / notes、document_ref）は `TenantEncrypted` / `TenantEncryptedJson` キャストで、アプリがテナント鍵（XChaCha20-Poly1305）で暗号化してから保存する
- **鍵は 3 層**: テナント DB には暗号文だけ。中央 DB には APP_KEY で包んだテナント鍵（`Tenant::data_key`）。APP_KEY は環境変数。3 つすべてを取られて初めて読める。1 テナントの鍵が漏れても他には及ばない
- **検索はブラインドインデックス**: 正規化した平文の HMAC（HKDF で派生した別鍵）を `*_index` 列に持ち、完全一致だけできる。並べ替えと部分一致はできない。それが必要な項目は暗号化の対象にしない（設計時に選ぶ）
- **テナント文脈の外では暗号化できない**（例外）。中央からテナントの個人情報を扱う経路を作らない
- **鍵は発行後に消さない・上書きしない**。失うと暗号化した列が二度と読めない。ローテーションは「新しい鍵で再暗号化してから古い鍵を捨てる」手順を別途設計する（未実装）

## 結果

- 得たもの: テナント DB の dump が漏れても個人情報は暗号文。中央 DB が漏れても鍵は APP_KEY で包まれている。テナント間で暗号文もインデックスも異なる（テストで検証）
- 失ったもの: 暗号化した列は並べ替え・部分一致・集計ができない。鍵のローテーションと、APP_KEY 漏洩時の全テナント再暗号化の手順が必要。アプリサーバーごと乗っ取られた場合は守れない（別の層の対策）
- 性能: 1 行あたり数十マイクロ秒の暗号化と、インデックス列の分だけ行が太る。一覧表示は復号を伴うため、ページサイズを抑える
