# 0090 1 店舗の形から複数の店の形へは `ec-sugar shops` で広げ、今の店のホストを変えない

状態: **採用**（2026-11-08。本番を、お客さんの URL を変えずに複数の店の形へ移し、デモの店 4 つ〔ADR 0086〕を足せるようにする、新しい店のホストは `demo-sake.ec-sugar.jp` の形〔ID は `demosake`〕、は運営が決めた。道具の形と細部は作りながら決めて下に書いた）。
ADR 0031（入口の 2 段と証明書）・0052（段 1 の本番は Cloudflare Tunnel）・0086（デモの店）の上に足す。置き換えるものは無い（docs/install.md の「広げる道はまだない」を書き直す）

## 要点（先に）

1. **道具**: `sudo ec-sugar shops multi --domain=<ショップのドメイン>`（戻すのは `sudo ec-sugar shops single`、見るだけは `sudo ec-sugar shops`）。答えと env と入口を書き換えて作り直すだけで、バージョン・イメージ・DB には触らない。答えの書き方は install.sh と同じなので、後で `sudo ./deploy/install.sh` を流し直しても同じ形のまま
2. **今の店のホストを変えない**: 答えの `SHOP_HOST`（1 店舗のショップのホスト）がショップのドメインの直下の 1 段（`shop.ec-sugar.jp` と `ec-sugar.jp`）のときだけ広げる。広げた後も最初の店はそのホスト（`ec_shop_host` が `SHOP_HOST` を使う。店の ID と 1 段目が違ってもそのまま）。店の DB・データの鍵・Stripe の通知先・管理画面のホスト（パスキー）は変わらない。合わない形（ショップがドメインそのもの〔apex〕・2 段下）は断る
3. **新しい店のホストは ID と違ってよい**: 複数の店の形の `shop:create` は、ショップのドメインの直下の 1 段だけを受け、管理画面・中央のホスト（`api`）・同じドメインのほかのサイトやメールの名前（`www`・`dev`・`mail` など）を断る。`demosake` の店を `demo-sake.ec-sugar.jp` で作れる（店の DB の名前にハイフンを使わないため）
4. **DNS は店ごとの名前の CNAME を勧める**（Cloudflare Tunnel の形）。cloudflared の行き先はワイルドカード `*.<ドメイン>` のまま（店を足すたびに設定とトンネルを作り直さない）。DNS に足す行は道具が出し、足すのは人
5. **店の Cookie はその店のホストだけ、https では `__Host-` の名前だけ**: ショップの Cookie（セッション・CSRF・カート・会員の印・App の Cookie）は env の `SESSION_DOMAIN` によらず Domain 属性を付けない（`HostOnlySessionCookie`）。https ではショップと管理画面の Cookie を `__Host-<名前>` でだけやり取りし、隣のホストから置かれた頭の無い Cookie を読まない（`HostPrefixedCookies`。見直しの中 1）。道具も `SESSION_DOMAIN` が空でなければ広げない
6. **駄目なら自動で戻す**: 作り直した後にヘルスチェックか、管理画面と最初の店を入口から https で開けるか（dns の取り方は 5 分まで待つ）、Tunnel の形では外（Cloudflare）から開けるか（替える前に開けたとき）が通らなければ、前の形へ戻して当て直す

## 文脈

- 本番（ADR 0052）は 1 店舗の形（`SHOPS=single`・`SHOP_HOST=shop.ec-sugar.jp`・`SHOP_ID=shop`）で、Cloudflare Tunnel・証明書は DNS の鍵（か Origin CA）。デモの店 4 つを同じ本番に足したい（ADR 0086）
- 1 店舗の形は、入口（Caddy・nginx・cloudflared）が管理画面とショップのホストの 2 つちょうどしか受けない。新しい店を作っても開けない
- ec-sugar.jp のゾーンには、別のサーバー（紹介のサイトなど）の apex・`www`・`dev` の明示の行がある。お客さんのブックマーク・Stripe の通知先（`https://shop.ec-sugar.jp/…`）・パスキー（`admin.ec-sugar.jp`）は変えられない
- 前は「答えを `SHOPS=multi` に直して流し直す」しか道が無く、そのとき最初の店のホストは `<SHOP_ID>.<SHOP_DOMAIN>` で決まっていた（ID とホストがたまたま同じ `shop` なので本番は合うが、一般には URL が変わる）

## 決定

### 1. 道具は `ec-sugar shops`（答えを直して install.sh を流し直す形は、同じ結果になる控えの道）

- `shops multi --domain=<ドメイン>`: 確かめ（何も変えない）→ 確かめの文（今の店の URL は変わらない・新しい店の名前の形・数秒止まる・駄目なら戻す）→ 端末でドメインを打ったときだけ（端末でなければ `--yes`）→ 鍵（`ec_lock`）→ 答え → env → cloudflared の行き先 → `web`・`app`・`queue`・`scheduler`・`caddy`・`cloudflared` を作り直す → ヘルスチェック → 最初の店を入口から https で（証明書がその名前を覆い、500 未満）→ DNS に足す行を出す
- 確かめること: ドメインの形・管理画面のホストと同じでない・今のショップのホストがドメインの直下の 1 段・env の `SESSION_DOMAIN` が空か `null`・証明書が手で渡したもの（manual）なら入口の証明書が `*.<ドメイン>` を覆い、答えの `TLS_CERT` が入口のものと同じ（新しい証明書を置いたのに流し直していないなら先に install.sh）。もう同じドメインで複数の店の形なら確かめの文を出さずに当て直す（途中で止まった続き）。別のドメインの複数の店の形は断る（店の URL が変わる）
- `shops single`: 最初の店のほかの店のホストを出し（開けなくなる。データは消さない）、`single` と打ったときだけ戻す。答えに `SHOP_HOST` が無い（初めから複数の店で入れた）なら、今の最初の店のホストを書く。`SHOP_DOMAIN` は残す（`SHOPS=single` があるので 1 店舗と読む）
- **選んだ理由**: install.sh を流し直す形は、1/5 の環境の確かめ・apt・Docker の確かめ・イメージを作る・運営の登録の URL まで全部を通るので長く、止まった時にどこまで変わったかが分かりにくい。広げるのに要るのは答え・env・入口の作り直しだけなので、`admin-ips`（答えと env を書いて app を作り直す）と同じ流儀の小さい道具にし、確かめと自動の戻しを付けた。書くのは install.sh と同じ関数（`ec_env_put_shops`・`ec_tunnel_put_config`）なので、流し直しても形がずれない（`docker/check-deploy.sh` が、インストーラーが同じ関数で書くことを見張る）

### 2. 今の店のホスト

- `ec_shop_host`（最初の店のホスト）は、複数の店の形でも答えの `SHOP_HOST` がショップのドメインの直下の 1 段ならそれを使う。そうでなければ前と同じ `<SHOP_ID>.<SHOP_DOMAIN>`。install.sh の 4/5（`shop:create <SHOP_ID> --domain=$(ec_shop_host)`）・ヘルスチェック・証明書の期限の見張り・DNS の案内がこれを使うので、広げた後に流し直しても最初の店は「もうあります」で通る
- `shop:create` は、もうある店を同じ内容で流し直すときは複数の店の決まり（下の 3）を当てない（1 店舗の時に作った店のホストがその決まりに合わなくても、流し直しを止めない）

### 3. 新しい店のホスト（`shop:create --domain`）

- 複数の店の形（config の `tls.shops` が `multi` でショップのドメインがある）で新しく作る店は、ホストが `<1 段>.<ショップのドメイン>` だけ（入口の nginx・Caddy・cloudflared が受けるのは `*.<ドメイン>` だけなので、ほかの名前の店は開けない）。1 段は英小文字・数字・ハイフンで、先頭と末尾は英数字・63 文字まで・3〜4 文字目に `--` を含まない（`xn--` など。見た目の似た名前で店を装わせない）
- 断る 1 段目: 店の ID の予約（`admin`・`api`・`app`・`www`・`mail` など 14 個）に、同じドメインに置かれやすいほかのサイト・メール・DNS の名前（`autoconfig`・`autodiscover`・`blog`・`cpanel`・`dev`・`docs`・`ftp`・`imap`・`mx`・`ns1`・`ns2`・`plesk`・`pop`・`pop3`・`webmail`）を足したもの。前からの「管理画面のホスト・中央のホストと同じでない」「ほかの店が使っていない」はそのまま
- 1 店舗の形（と開発の `*.localhost`）では前のまま（見ない）
- 証明書の問い合わせの経路（`/internal/tls/allowed`）は変えない（domains にある名前だけ。予約の名前で断ると、1 店舗の時に作った店の証明書が取れなくなる）

### 4. 証明書

| 取り方 | 広げる時にすること |
|---|---|
| dns（Cloudflare の DNS の鍵。本番の今） | 何もしない。Caddy が作り直しの時に `*.<ドメイン>` のワイルドカード 1 枚を DNS の確かめで取る。取るまで 1〜2 分、**店だけでなく管理画面も** https が開けないことがある（複数の店の形では管理画面も `*.<ドメイン>` に覆われる）。道具はヘルスチェックの https の確かめ（約 1 分）を外し、管理画面と最初の店の https を 5 分まで待つ。新しい店を足しても取り直さない |
| manual（Cloudflare の Origin CA など） | 先に `*.<ドメイン>` を含む証明書を作り直し、答えの `TLS_CERT`・`TLS_KEY` に書いて install.sh を流す（1 店舗のまま。新しい証明書は今の 2 つの名前も覆う）→ それから広げる。道具は覆っていなければ断る |
| auto（Let's Encrypt。Tunnel では使えない） | その場で取る形（on-demand）に替わる。取る前に問い合わせの経路で絞る（今までの複数の店の形のまま） |

- **ワイルドカードを先に取っておく形は入れなかった**（見直しの中 2 の検討）: 1 店舗のうちに Caddy の場所に `*.<ドメイン>` を足して取らせ、取れてから形を替える形を考えたが、Caddy 2.10 からは（リリースノートの読み）、設定にワイルドカードの場所があると、覆われる名前（管理画面とショップのホスト）に個別の証明書を使わずワイルドカードを待つ。先に足す時に同じ 1〜2 分が来るだけで、止まる時間は減らない。加えて、空のときの場所の書き方・Caddy の設定の見張り（`docker/check-compose.sh`）・切り替えの 2 段の戻し方が増える。止まる時間が 1〜2 分で、空いている時間に流せば足りるので、待つ形にした（Caddy の挙動は手元で本物を動かして確かめてはいない。本番の写しで止まる時間を測る）
- インストーラーの「証明書がワイルドカードを覆うか」の確かめ（`ec_check_tls`）は、前は `shop.<ドメイン>` で見ていた。本番の店の名前が `shop` なので、`shop.ec-sugar.jp` だけを含む証明書でも通ってしまう。どの店の名前にもならない `ec-sugar-tls-probe.<ドメイン>` で見るように直した

### 5. Cloudflare Tunnel と DNS

- cloudflared の行き先（`config.yml`）は前からの複数の店の形のまま、管理画面と `*.<ドメイン>`（ほかは 404）。ワイルドカードにしたのは、店を足すたびに行き先を書き直して cloudflared を作り直さないため。トンネルに届くのは DNS がトンネルへ向けた名前だけなので、行き先がワイルドカードでも、ほかのサーバーの `www`・`dev` には影響しない
- **DNS は店ごとの CNAME を勧める**（`shop`・`demo-sake` など。値は `<トンネルの ID>.cfargotunnel.com`・プロキシ済み）。ワイルドカードの CNAME（`*.ec-sugar.jp`）は明示の行（apex・`www`・`dev`）を食わないが、**明示の行の無い名前が全部このサーバーへ来る**（打ち間違い・消し忘れたサイトの名前・将来ほかのサーバーに足す名前の行を忘れた時）。届いても開くのは domains にある店だけだが、届く名前を DNS で絞る方が、知らない名前で入口と PHP を叩かれにくく、ほかのサイトの名前を取り違えて出さない。手間は店を足すたびに 1 行（道具が出す）
- 中央のホスト `api.<ドメイン>` は、複数の店の形で env の `CENTRAL_DOMAINS` に入る（前からの形）。DNS の行は **Stripe Connect を使うときだけ**足す（使わなければ行が無くてよい。Connect は運営の鍵が無ければ使えない）

### 6. 店の境界

- **Cookie**: 前は、ショップのセッションと CSRF の Cookie は config の `session.domain`（env の `SESSION_DOMAIN`。本番は `null`）、カートと会員の印は `cookie()` の既定のドメイン（起動の時に `session.domain` から決まる）に従っていた。`SESSION_DOMAIN` を `.ec-sugar.jp` にすると、どれもほかの店・管理画面・`www`・`dev` へ送られる（試験で、カートの Cookie にも `.ec-sugar.jp` が付くことを見つけた）。ショップのミドルウェアの群の Cookie の前に `HostOnlySessionCookie` を置き、両方を空にする。管理画面は前から `ConfigureAdminSession` が同じことをする
- 持ち込まれた Cookie: カートの合い言葉・会員の印・Laravel のセッション（本番は Redis で店ごとの頭が付く）は店の DB・店の頭で引くので、ほかの店へ持ち込んでも何も開かない（試験で確かめた）
- **入ってくる Cookie（cookie tossing。見直しの中 1）**: 上の 2 つは「出す Cookie を広げない」「持ち込まれても開かない」で、**同じホストに置かれる Cookie**は防がない。`*.ec-sugar.jp` のどこか（デモの店・ほかのサーバーの `www`・`dev`）で JavaScript か Set-Cookie を動かせる人は、`Domain=.ec-sugar.jp; Path=/checkout` の Cookie を置いて `shop.ec-sugar.jp` へ届けられる。Laravel は知らないセッションの番号もそのまま使うので、攻める人が自分のセッションの番号を置くと、お客さんがそのセッションで注文の入力（名前と連絡先）をし、攻める人が読める（セッション固定）。**SameSite は同じサイト（ec-sugar.jp）の中を分けない**ので守りにならない
  - https では、ショップと管理画面の Cookie を **`__Host-<名前>`** でだけやり取りする（`App\Http\Middleware\HostPrefixedCookies`。ショップは `StorefrontHostPrefixedCookies`）。ブラウザは `__Host-` の頭の Cookie を Secure・Path=/・Domain なしのときだけ受け取るので、隣のホストからは置けない。要求の頭の無い Cookie は内側へ渡さない。内側（Laravel・各 Cookie の部品・App）は今までの名前のまま書け、応答で名前を付け替える（値は内側の名前で暗号にしたまま）。管理画面の JavaScript は https で `__Host-XSRF-TOKEN` だけを読む（`resources/admin/api.js`）
  - http（手元の `make up` の `http://*.localhost:8080`・e2e・PHP の試験の多く）では付け替えない（`__Host-` は Secure が要る）
  - 重ねて、注文の入力（`checkout`）を初めてセッションに置くときにセッションの番号を作り直す（`CheckoutController`）
  - **前の名前からの移り**: カート・会員の印・準備中のパスワード・タグの同意の Cookie は、`__Host-` の方が無ければ古い名前を一度読み、`__Host-` の名前で出し直して、古い名前（このホストだけのもの）を消す。読むのは **1 店舗の形の間だけ**（隣のホストに店が並ぶのは広げた後。1 店舗の間に同じドメインにあるのは持ち主のほかのサーバーの `www`・`dev` だけ）。Laravel のセッション・CSRF・管理画面のセッションは移さない（置かれた番号を使わない。このバージョンに更新した時に、入力の途中の注文は入れ直し・運営は一度ログインし直し）。なので本番は、このバージョンへ更新し、1 店舗のまま数日おいてお客さんの Cookie が移ってから広げる（すぐ広げても壊れないが、移っていないカートとログインは落ちる）。**古い名前を読む作りは、カートの Cookie の期限（30 日）を過ぎた後のバージョンで消す**
  - 置かれた頭の無い Cookie は消せない（Domain つきは別の Cookie）が、読まないので効かない。ブラウザの Cookie の数の上限を食わせて本物を押し出す攻め（cookie jar の溢れ）は、ブラウザ側の問題で、ここでは防げない（押し出されたらログインし直しになるだけで、読まれはしない）
- CSRF・CSP・`Permissions-Policy`・防御ヘッダは応答ごとで、店のオリジン（ホスト）ごとに効く。回数の上限は店の文脈のキャッシュ（Redis の店の頭）で数える。接続元の制限は管理画面のホストだけ。どれも店をまたがない
- HSTS の `includeSubDomains` は、店と管理画面のホストの下（`*.shop.ec-sugar.jp` など）にしか効かない。EC-SUGAR は apex（`ec-sugar.jp`）を受けないので、ほかのサーバーの `www`・`dev` に HSTS を押し付けない

### 7. 戻す道と冪等

- `shops single` で戻す（上の 1）。広げた後に足した店は開けなくなるが、店の DB・データは残り、もう一度広げれば開ける。毎晩の `demo:reset` などの定期の処理は店を順に回るので、開けない店でも走る（止めるなら `shop:demo <店> --off` か店を消す）
- `ec-sugar rollback`（前のバージョンのイメージへ）は店の数の形を戻さない（env は複数の店のまま。前のバージョンも複数の店の形を知っている）。形を戻すのは `shops single`。どちらも、もう一方を呼ばない
- 何度流しても同じ（答えと env は値が同じなら同じ中身、cloudflared の行き先は中身が同じなら置き換えない）。答えは仮のファイルに全部書いてから入れ替えるので、途中で止まっても前の形か新しい形のどちらか。止まった後に同じコマンドを流すと、もうその形なら確かめを飛ばして当て直す
- 当て直しも戻しも失敗したら（ショップが止まっている恐れ）、`sudo ec-sugar status`・`logs` と、一時のこと（証明書を取るのが遅い・回線）なら同じコマンドをもう一度流す手、答えの `SHOPS` を前の値にして install.sh を流し直す手を出す
- **Cloudflare Tunnel の形の終わりの確かめ**（見直しの軽 5）: 中から接続元を偽れないこと（`ec_check_tunnel`。偽れたら当たらなかったとする）と、外（Cloudflare）から管理画面の `/up` が 200・最初の店が 500 未満で 404 でないこと。替える前に外から開けたのに替えた後に開けなければ、替えたせいなので前の形へ戻す。替える前から外から開けなかった（DNS がまだ・回線）なら、戻さずに大きく注意を出して `check-front` を促す
- 確かめで、ショップのドメインに公開の接尾辞（`co.jp`・`tokyo.jp`・`co.uk` など。1 段のものは形の確かめで断る）を断る。中央のホストの `/`（疎通の確かめ）は web の群を外し、セッションも Cookie も出さない（見直しの軽 6）
- 記録: `state/history.log` に `shops_multi`・`shops_single`・`shops_reverted` の行（最後の更新の結果〔運営の様子〕は変えない）

## 比べた案

- **install.sh を流し直すだけ（答えを手で直す）**: 道具を足さずに済むが、長く・確かめが無く・止まった時に元へ戻らない。結果は同じなので、手で直した答えで流し直しても壊れない形にはした（同じ関数で書く・最初の店は「もうあります」で通る）
- **店ごとの名前を入口に並べる**（`*.<ドメイン>` でなく）: nginx・Caddy・cloudflared の設定を店ごとに書き直して作り直すことになり、店を足す操作が CLI の `shop:create` だけで済まなくなる。入口はワイルドカードのまま、届く名前は DNS で絞る形にした
- **新しい店のホストを `<ID>.<ドメイン>` に決める**（ID とホストを同じに）: ID にハイフンが使えない店（デモの店）で `demosake.ec-sugar.jp` になる。運営が `demo-sake` の形を選んだので、ホストを ID と分けて持てる今の作り（domains の表）をそのまま使い、形の確かめを足した

## 人がすること（本番で）
