# 0034 App はショップに決まった形でタグを差し込む（タグごとの App と、核の口・同意・公表）

状態: **採用**（2026-10-29。公式のタグの連携はプラグインで作る。よく使われるタグはそれぞれ App で足し、公式の資料があるものはなるべく多く足す）。作りながら確かめる点（下の「確かめること」）は、確かめた結果をこの ADR に書き足す。ADR 0005・0020・0025 の続き。**2026-10-30 に 4（同意）を置き換えた**（同意の帯は既定で出さず、店の設定で入れた店だけ。置き換えた所に、もとの判断を残した）

## 文脈

- お店の人がいちばん欲しがるのは、アクセスの解析と広告の計測のタグ（GA4・Google 広告・Meta ピクセル・LINE タグ・Yahoo! 広告・TikTok・Clarity）。今のショップは CSP で自分のオリジンのスクリプトしか動かさず、テーマも App も外のスクリプトを入れられない（ADR 0020）
- よく入れられる JavaScript の整理: docs/design/storefront-scripts.md
- 運営の判断: タグの連携は核に直に作らず、App（プラグイン）で作る。App の口（拡張点）を育てる最初の 1 本にする
- 守る線: お客さんの個人情報を扱う画面（注文の入力・確認・ご注文の状況・アカウント）では、どの App のタグも動かさない。管理画面から任意の JavaScript は入れない（CONCEPT 7.2）

## 決めたこと

### 核に足す口（どの App も使える。1〜3 が口、4・5 は核が持つ同意と公表。区画を足す口は後で ADR 0040 で足した）

1. **ショップへの差し込み口（決まった形だけ）**
   - App は「このスクリプトのファイルを、この画面の種類で読みたい」と、値（宣言）で頼む。HTML の文字は渡せない（核が `<script src>` の要素を作り、属性はエスケープする）
   - 読めるスクリプトは、App のパッケージに入った**同じオリジンから配るファイル**だけ（審査した App のコード）。外のスクリプト（googletagmanager.com など）は、そのファイルが読み込む
   - App に渡す設定（ID など）は `data-` の印で渡す。画面の中にスクリプトを直に書かない（CSP のまま）
   - 画面の種類は核が決める: ふつうの画面（トップ・商品の一覧と詳細・カート・特商法の表記・自由なページ〔ADR 0039 で足した〕）・購入の完了・**個人情報の画面（注文の入力と確認・ご注文の状況・アカウント）**。個人情報の画面には、App が何と言っても差し込まない
   - 購入の完了の画面で App に渡すのは、注文の番号・金額・通貨・品の ID と数だけ（名前・メール・住所・電話は渡さない）
   - テーマのレイアウトに差し込む場所を 1 か所置く（テーマ API に足す。4 つのテーマに 1 行ずつ）
2. **CSP への足し込み（前もって書いた宛先だけ）**
   - App のマニフェスト（composer.json の extra）に、使う宛先を種類ごとに前もって書く（script-src・connect-src・img-src・frame-src）
   - 核が形を確かめる: https だけ・`'unsafe-*'`・`data:`・`*` 単独・IP の住所は断る。サブドメインの `*.` は許す
   - その App を使う店の、差し込む画面の種類にだけ足す。お店の人の入力では宛先を増やせない
3. **App の設定の画面（宣言から作る）**
   - App はマニフェストで設定の項目を宣言する（テーマの区画と同じ考え方。種類は文字・切り替え・選ぶ。文字には形の決まり〔正規表現〕と長さ）
   - 管理画面の店の App の画面に、宣言から作った設定の欄を出す。値は店の DB に、サービス経由で、`EventStore::lock()` を取って、イベント（`plugin.settings_changed`）と同じトランザクションで保存する
   - 値はサーバーで宣言どおりに確かめる（形の合わない ID・スクリプトの文字は断る）

4. **同意（核）**（**2026-10-30 に置き換え**）: **同意の帯は既定で出さない**。計測・広告のタグは、ショップのふつうの画面と購入の完了の画面に最初から読み込み、外部送信の公表（5）だけを置く。**店の設定「同意の帯」で「出す」にした店**（海外のお客さんを相手にする店）だけ、もとの形（下）で、受け入れたお客さんにだけ読み込む。同意の種類（「解析」「広告」）は各 App がマニフェストに書くまま（帯を出す店で使う）
   - 置き換えの理由（2026-10-30。堅牢にしたいのは攻撃への守りで、お客さんに不便をかけたいのではない。日本では YouTube などの動画の埋め込みはよくある）: 堅牢さは攻撃への守りで、お客さんの手間を増やすことではない。日本の電気通信事業法の外部送信規律（2023 年）が求めるのは**公表**（通知か公表、または同意・オプトアウトのどれか）で、事前の同意ではない。日本のお客さんを相手にする店の多くは帯を出していない。欧州の GDPR などで事前の同意が要る店は、設定で入れる
   - 変えない守り: CSP の宛先は App が宣言した分だけ・個人情報の画面（注文の入力と確認・ご注文の状況など）には、帯の有無にかかわらず差し込まない・購入の完了に渡す値は番号・金額・通貨・品の ID と数だけ・公表は必ず・管理画面から JavaScript を入れない
   - **今ある店も「出さない」になる**（移行で列の既定を「出さない」にした）。前は同意が要る App を使う店には帯が出ていたので、その店では、次の表示から帯が消え、タグが最初から読み込まれる。前に帯で「同意しない」を選んだお客さんの Cookie も、帯を出さない店では見ない（店が帯を出さないと決めたため）。もう一度「出す」にすれば、その Cookie の決めたことがそのまま効く
   - もとの判断（2026-10-29。帯を出す店では今もこの形）: 計測・広告のタグは、お客さんが同意してから読む。同意の帯と、同意をやめる道は核が描く（テーマの色に合わせる）。同意の種類は「解析」「広告」。各 App はマニフェストで自分の種類を書き、核は同意のある種類の App だけを差し込む。同意の状態はクッキーに
5. **外部送信に関する公表（核）**: 改正電気通信事業法（2023 年）の外部送信規律に合わせる。各 App がマニフェストに「送り先の事業者・送る情報・目的・その事業者の案内のページ」を書き、核が、その店で使っている App から「外部送信に関する公表」のページを自動で作り、ショップのフッターから辿れるようにする（文の雛形は専門家に確かめる）

### タグごとの App（公式の資料があるものは、なるべく多く）

- **1 つのタグに 1 つの App**（`plugin-ga4`・`plugin-meta-pixel`・`plugin-lineyahoo-ads` など。初めの例の `plugin-line-tag` は、LINE タグを作らないと決めたので 2026-10-31 に直した）。お店の人は使うタグの App だけを有効にして ID を入れる
- 作る前に、そのタグの**公式の資料**で、読み込みの手順・許す宛先・購入の計測の送り方・同意の扱い（Google の同意モードなど）を確かめ、`docs/design/tag-apps.md` にまとめる。公式の資料が無いものは足さない
- 最初の組（公式の資料の調べ docs/design/tag-apps.md の作る順）: GA4 → Google 広告 → Microsoft Clarity → Meta ピクセル → LINEヤフー広告（計測タグ）→ Pinterest タグ・Microsoft 広告（UET）→ TikTok ピクセル → X ピクセル。**LINE タグは作らない**（LINE 広告は 2026-10-26 に配信を終えて LINEヤフー広告に統合。LINE への広告の計測は LINEヤフー広告の App で受ける）。次の組: アフィリエイト（A8.net・バリューコマース・楽天）、ほかのヒートマップ
- 購入の完了の計測は、金額と注文の番号だけで送る
- Google タグマネージャーと接客の道具のような「何でも入れられる箱」は、App にしない（開発者モード へ）
- 次の段: サーバーから成果を送る形（Meta の Conversions API・Google の Measurement Protocol・LINE の CAPI）

## 確かめること（作りながら）

- **Trusted Types とのぶつかり**: ショップは `require-trusted-types-for 'script'`。外のタグがスクリプトや HTML を差し込むときに止まる恐れがある。App の読み込みの部品に「既定の関所」（default policy）を置き、許した宛先のスクリプトの URL だけを通す形で、実物のタグで動くかを確かめる。HTML の差し込みをそのまま通すしかない場合は、その App を使う店のふつうの画面だけ Trusted Types をゆるめるかを決め、ここに書く
- 同意の前に何も送らないことを、ブラウザのテストで確かめる（外への通信を見張る）→ で書いた（`tests/e2e/consent-banner.spec.js`。帯を出す店では同意の前に外へ何も送らず、出さない店では宣言の宛先だけへ送る）

## 結果

- 得るもの: お店の人は ID を入れるだけで計測と広告が使える。核には、ほかの App（チャット・レビューなど）でも使える 3 つの口ができる（区画を足す口を ADR 0040 で足した）
- 気をつけること: App のコードは核と同じ権限で動くので、入れるのは審査したものだけ（ADR 0025 のまま）。外のタグそのものの中身は、こちらで管理できない（だから個人情報の画面には入れない・公表する・帯を出す店では同意を取る）
- 置き換え（2026-10-30）で失うもの: 帯を出さない店では、お客さんがショップの中で送信を止める道が無い（止め方は各事業者の案内。公表のページから辿れる）。欧州などのお客さんを相手にするのに帯を出さないと、その国の決まりに合わない（店の設定の画面で「海外のお客さんを相手にする店向け」と書いて選んでもらう）

## 作って決めたこと（2026-10-29、核の口）

### マニフェストの形（composer.json の extra.ec-sugar）

- App は `PluginDefinition` の `manifest` に自分の composer.json を渡し、登録簿（`PluginRegistry`）が 1 度だけ読んで確かめる。形が違えば登録で止まる（アプリが起動しない。テーマの theme.json と同じ）。知らない書き方は断る（HTML やスクリプトの文字を渡す口は無い）
- 書けるのは `settings`（設定の項目）・`disclosure`（公表）・`storefront`（`scripts`・`csp`・`consent`）と、後から足した `sections`（ADR 0040）・`category`（App の目的。ADR 0025 の「作って決めたこと」）。`storefront.consent` は必ず書く（要らなければ `[]`）。外の宛先（`csp`）を書いた App は `disclosure` を必ず書く
- 足しただけで今までのプラグインはそのまま動くので、プラグイン API は 1 のまま
- 見本は `plugins/plugin-tag-sample`（宛先は実在しない `.test`）。開発とテストだけで入れる（composer の require-dev。本番のイメージには入らない）

### 差し込み（1）

- 画面の種類は `StorefrontView::PAGE_KINDS` に書いた画面だけが「ふつう」（home・products・product・cart・legal・page〔自由なページ。ADR 0039 で足した〕）か「購入の完了」（checkout-complete）。**書いていない画面はすべて個人情報の画面**として扱う（注文の入力と確認・ご注文の確認と状況・エラー・核の画面、これから足す画面）。書き忘れは差し込まない側に倒れる。マニフェストにも `private` は書けない
- スクリプトは App のパッケージの `assets/` の `.js`（256KB まで）。核が `/apps/<App>/<ファイル>?v=<中身の印>` から配る（店がその App を使っていなければ 404。経路の形・宣言・実体の道筋を確かめ、外を指すリンクを断る。`text/javascript`・`nosniff`・`Cross-Origin-Resource-Policy: same-origin`、`?v=` が合えば 1 年キャッシュ）
- 印: `data-sugar-app`・`data-sugar-page`（general / purchase）・`data-setting-<項目>`（`_` は `-`。切り替えは `true`/`false`）、購入の完了は `data-order-number`・`data-order-total`（最小通貨単位の整数）・`data-order-currency`・`data-order-items`（`[{"id","quantity"}]` の JSON）。取り消した注文では購入の値を渡さない。秘密の項目は渡さない
- 入れるべき設定（`required`）が欠けている App は差し込まない

### CSP（2）

- 宛先の形は `CspSources`: `https://` ＋ 英小文字のホスト名（2 語以上、最後の語は英字で始まる）、任意でポートと道筋。`*.` は先頭だけで、後ろは 2 語以上（`*.com` は断る）。`*.co.jp` のような公開の接尾辞の下を丸ごと許す書き方は機械では断れない（審査で見る）
- 足すのは、その応答で実際に差し込んだ App の分だけ（`StorefrontView` が要求に残した `AppsView` を `StorefrontSecurityHeaders` が読む）。個人情報の画面・描いていない応答は元のまま。`frame-src` は元に無いので、足すときだけ新しく置く

### 設定（3）

- 店の DB の `plugin_settings`（App 1 つに 1 行）。秘密でない値は `values`（jsonb）、秘密は `secrets`（店の鍵で暗号化。DB の制約で暗号文だけ）。記録 `plugin.settings_changed` には変えた項目の名前だけを残す
- 文の項目には `pattern`（核が `\A(?:…)\z` で全体に当てる）と `max`（200 まで）を必ず書く。宣言とは別に、核が HTML・引用符・バックスラッシュ・制御文字をいつも断る
- 要求の空の文字は Laravel が null にするので、秘密は null も空も「変えない」とし、消すのは `clear` に名前を書いたときだけ
- 変えるのは管理画面の店の App の画面から、運用の段階で直前の再確認の後（お客さんの情報の送り先を決めるため）
- 管理画面では、店のプラグインの一覧（名前・説明・使うかどうか）から、プラグインごとの画面（`/tenants/{店}/plugins/{名前}`）へ移って入れる（2026-10-30。プラグインごとに設定の画面がある方が分かりやすい）。使っていない App にも先に入れて保存できる（動くのは「使う」にしてから。その間は画面で知らせる）
- **項目の種類に「写真」（`media`）を足した**（2026-11-04、App「納品書・領収書」のロゴ）: 値はショップの写真（`shop_media`）の ID だけ。宣言に `pattern`・`max`・`options`・`default` は書けず、秘密にもできない。形（ULID）は `SettingSpec::problem`、この店の写真にあるかは `PluginSettings` が店の文脈の中で確かめる（ほかの店の写真の ID は断る。保存は小文字）。写真を後で消しても設定は残るので、使う App が「あるか」を確かめてから出す。管理画面の欄は核の写真の欄の部品（区画の写真と同じ。選ぶか新しく上げる）。商品の画面の App の欄（ADR 0050）では使えない（宣言を断る）。プラグイン API は 1 のまま（種類を足しただけで、今の App は変えなくてよい）

### 同意（4）

- **帯を出すかは店の設定**: 店の DB の `shop_settings.consent_banner`（真偽。列の既定は偽＝出さない。行の無い店も出さない）。変えるのは `ShopSettingsService::setConsentBanner` だけで、`EventStore::lock()` の後に、記録 `shop.consent_banner_updated`（`{show}`）を同じトランザクションで残す。管理画面は「設定 › App › 同意の帯」（`PUT /api/tenants/{店}/shop-settings/consent-banner`、`{show: 真偽}`）。ほかの店の設定と同じく運用の段階から（閲覧は 403）。直前の再確認は求めない（タグを読み込むかの大もとは、App を使う・設定を入れる操作で、そちらは直前の再確認の後）
- **帯を出さない店**: `StorefrontApps` は同意の Cookie を読まず、聞く種類を空にする（帯も、フッターの「Cookie の設定」のリンクも出さない）。ふつうの画面と購入の完了には、使っていて設定のそろった App を最初から差し込む（画面の種類・CSP・Trusted Types の関所は帯を出す店と同じ）。区画の App（ADR 0040）で同意の種類を書いた区画も、誰にでも出す。`/consent` は「選ぶものは無い」と出し、`POST /consent` は何も決めない。公表のページの冒頭の文は「表示したときに行う。止め方は各事業者の案内」
- **帯を出す店**: 下のとおり（もとの形のまま）
- Cookie `sugar_consent`（店のホストだけ、SameSite=Lax、HTTPS では Secure、180 日、中身は Laravel が暗号化）。**HttpOnly にした**: 差し込むかはサーバーが決めるので、ページの JavaScript に読ませる理由が無い。外のタグが自分で「同意した」に書き換える道を塞ぐ。決めるのは `POST /consent`（CSRF・回数制限つき）だけで、帯は JavaScript が無くても動くフォーム
- 決めるのは、今この店で同意が要る種類だけ（後で別の種類の App を使い始めたら、その種類はもう一度聞く）。帯は「同意する」「同意しない」を同じ強さで並べ、「選んで決める」は `/consent`。個人情報の画面には帯も出さない。フッターの「Cookie の設定」は、帯のある画面では核の部品（`resources/storefront/consent.js`）が帯を開き直す
- 同意が要る App が 1 つも無い店（使っていない・設定がそろっていない）では、帯もリンクも出さない

### 公表（5）

- `/legal/external`（核の画面をテーマの layout の中に描く）。その店で使っている App の `disclosure` を並べる。**冒頭の文と並べ方は雛形で、公開の前に専門家に確かめる**
- 冒頭の文は、帯を出す店では「同意したときだけ行う」、出さない店（既定）では「ショップのページを表示したときに行う。送り先ごとの止め方（オプトアウト）は各事業者の案内のページ」
- 管理画面の App の設定の欄の下にも、その App の送信の中身を見せる

### Trusted Types の既定の関所（核へ移した）

- **App は関所を作らない。核が作る**。タグの App の JS は、外のスクリプトを読むとき文字の URL を `script.src` に入れるだけでよい（核の関所を通る）
- 既定の関所（default policy）は 1 ページに 1 つしか作れないので、見本の App で作っていた形をやめ、核の `resources/storefront/trusted-types.js`（Vite の入口）に移した。核の差し込み口（`<x-storefront.apps>`）が、App を差し込む画面にだけ、App のスクリプトより前に `<script src defer>` で読む（defer どうしは書いた順に動く）。App を差し込まない画面（個人情報の画面・同意の前・App を使わない店）には出さない
- `createScriptURL` が通すのは、同じオリジンの `/apps/…` と、**その画面で差し込んだ App のマニフェストの `script-src` の宛先**に合う URL だけ。宛先の一覧は核が `data-sugar-script-src`（JSON）で渡す（画面の中に直にスクリプトを書かない）。照らし合わせは CSP と同じ考え方: https だけ・`*.` はサブドメイン（元のドメインそのものは含まない）・ポートは書いた番号だけ（書かなければ 443）・道筋は `/` で終われば前方一致、そうでなければ同じ道筋だけ。利用者名やパスワードの付いた URL は断る
- `createHTML`・`createScript` は通さない。公式の資料と読み取りの範囲（docs/design/tag-apps.md）では、どのタグも HTML の差し込みをしない。実物のタグで HTML の差し込みが要ると分かったら、そのときに「確かめること」にそって決め、ここに書く
- ショップの CSP に `trusted-types default` を足した（`'allow-duplicates'` なし）。作れる関所は default だけ、1 度だけなので、核が作った後に App や外のタグが default を作り直すことも、別の名前の関所を作ることもできない。核の関所が無い画面では誰も default を作れない（文字の URL は止まる側）。**Meta ピクセルは自前の名前の関所を作るので、この指定の下では作れない**（tag-apps.md の Meta の節）。Meta の App で、名前を足すか、関所が作れなくても読み込めるかを確かめる → 確かめた（2026-10-29、Meta の App）: fbevents.js は自前の関所を作れないと例外を握りつぶし、文字の URL のまま `src` に入れるので、核の既定の関所を通って読み込める（`plugins/plugin-meta-pixel/assets/meta-pixel.js` の頭の注）。関所を作ろうとするたびに CSP の違反の知らせが出る件は公開の前にやることに入れた
- 同意の前に何も送らないことのブラウザのテストは、まだ書いていない → 書いた（`tests/e2e/consent-banner.spec.js`。上の「確かめること」）

### タグの JavaScript が読めない画面（2026-11-06、ADR 0088 で足した）

- 「個人情報の画面に差し込まない」だけでは、ふつうの画面のタグがお客さんの Cookie を持ったまま `fetch('/account')` などで個人情報の画面を**読めた**（外の点検の「重」）。個人情報を出す経路に印 `navigation-only` を付け、ブラウザが画面を開く要求（`Sec-Fetch-Mode: navigate`・`Sec-Fetch-Dest: document`）のほかは中身の無い 403 にした。印の画面は控えに残さず（no-store）、別の窓からも読めない（`Cross-Origin-Opener-Policy: noopener-allow-popups`）。詳しくは ADR 0088
- タグの JavaScript が読めない画面: 会員の画面の全部（マイページ・届け先・再確認・メールの変更・パスキー・退会）、ログインのコードの画面、注文の入力と確かめ、ご注文の状況、App の会員の画面と申し込みの流れ（定期便・予約・抽選・チケット・ギフトカード・贈り物・ダウンロード・レビュー・会員ランク・領収書・お気に入りの一覧・友だち紹介・LINE 連携・お問い合わせ・メルマガ・再入荷の受付）。fetch での書き込み（届け先を足す・確定する など）も同じく断る
- 印の画面には、画面の種類の名前にかかわらず App を差し込まない（`StorefrontView` が個人情報の画面に倒す）。差し込まない画面の決まり（`PAGE_KINDS` に書いた画面だけが差し込んでよい画面）は変えていない。2026-11-06 に確かめた: ふつうの画面に出るのはカートの中身・会員かどうか（ヘッダーの「マイページ」）・付くポイントの一言で、名前・メール・住所は出ない。購入の完了は番号・金額・支払いの案内で、贈り物の受け取りのリンクはタグを差し込む画面には出さない（前から）。贈り物の注文の画面への入口（`/p/gift/orders/…`）は今回から印の画面
- Sec-Fetch を送らない古いブラウザでは、この守りは効かない（画面が開けなくなるのを避けて通す。ADR 0088 の 3）
