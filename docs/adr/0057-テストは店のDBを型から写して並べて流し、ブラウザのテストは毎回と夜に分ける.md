# 0057 テストは店の DB を型から写して並べて流し、ブラウザのテストは毎回と夜に分ける

- 状態: 採用
- 日付: 2026-11-05（運営が速くするよう頼んだ）

## 文脈

プルリクエストごとの CI（GitHub での自動の検査）の `check`（PHP のテスト約 990 件・pint・phpstan・依存の監査）が約 12 分、`e2e`（Playwright の 139 場面）が約 4.5 分かかっていた。CI の走らせ役は自前の VM 1 つなので、仕事は 1 つずつ順に走り、待ちが積み上がる。

測ると、PHP のテストの時間の多くは店を作っては消すことに掛かっていた（テストは数百の店を作っては消す）。作るたびに核と全部の App の移行（百本近く）を一から流し、消すたびに Postgres の `DROP DATABASE` が CHECKPOINT（汚れたページを全部書き出して同期する）を待つ。テストは 1 つの処理で順に流していて、手元の CPU も CI の VM の CPU も 1 つしか使っていなかった。ブラウザのテストは、写しや細かい画面もプルリクエストのたびに流していた。

テストを減らす・守りを弱める（決済・店の境界のテストを外す）ことはしない。

## 決定

1. **PHP のテストでは、店の DB を型から写す**（`Tests\Support\TemplatedTenantDatabaseManager`。テストだけ。本番の店の作り方は変えない）
   - テストの実行ごと（並べたときは並べた各々）に 1 度だけ、移行を流し終えた空の店の DB（型。`<店の DB の頭>_template`）を作り、店を作るたびに Postgres の `CREATE DATABASE … TEMPLATE …` で写す。店を作る流れ（DB・移行・初めの行）はそのままで、移行は流し済みなので何もしない
   - 店のロールと権限（ADR 0003・0009）は本番と同じ形にする: ロールは本番の係で作り、DB の持ち主は店のロール、DB への接続は PUBLIC から取り上げる。型の中の物の持ち主（型のロール）は、写した後に店のロールへ移す（`REASSIGN OWNED`。移す間だけ店のロールに型のロールを継がせ、済んだら外す）。型の DB の持ち主は中央のロールにし、型のロールは型の中の物しか持たない（`REASSIGN OWNED` が型の DB や中央の DB を動かさないように）
   - 型は移行のファイルの名前と中身の指紋を注釈に持ち、合わなければ作り直す
   - 本番と同じ形かは `TenantDatabaseTemplateTest` が毎回、一から作った店（本番の係）と比べる（表・列・制約・索引・トリガー・関数・型・持ち主・権限・ロールの付け方・移行の記録・初めの行の数）。店の DB の分離のテスト（`TenantIsolationTest`）は型から写した店で通る
   - 移行を一から流す道を見たいテストは `$tenantDatabasesFromTemplate = false` にする。ブラウザのテストの下ごしらえ（`tests/e2e/fixtures.php` の `tenant`）も同じ部品で写す。管理画面のサーバーが店を作る場面は本番の作り方のまま
2. **PHP のテストは並べて流す**（`php artisan test --parallel`。数は既定で CPU の数）
   - 並べる仕組みは paratest（brianium/paratest。開発だけの依存）。Laravel の `--parallel` が前提にしている部品で、自前で同じこと（処理を立てたまま、空いた処理へファイルを 1 つずつ渡す）を作ると PHPUnit の中の作りに頼ることになる。ファイルを前もって分ける自前の形は、遅いファイルに偏って速くならない
   - 並べた各々の組は `tests/bootstrap.php` が、paratest の渡す番号（`TEST_TOKEN`）から決める: `ec_test` → `ec_test_p1`・`ec_test_p1_t_`・`media-testing-p1`、作業ごとの `ec_test_o` → `ec_test_op1`・`ec_test_op1_t_`・`media-testing-op1`。テストの入口の守りの「1 つの区切り」の決まりのまま通る。各々の中央の DB は無ければ作る。Laravel の「DB の名前に `_test_<番号>` を足す」仕組み（決まりの外の名前になる）は止める
   - `make test` は並べた形、`make test-serial` は 1 つの処理で順に。`make test-clean` は各々の店の DB と型も片付ける
3. **CI の使い捨てのテストの DB は、書き出しの同期（fsync）を止める**（`ALTER SYSTEM SET fsync = off` ほか。`check`・`e2e`・`e2e-full` の DB だけ）
   - Postgres の `DROP DATABASE` は毎回すぐの CHECKPOINT（汚れたページを全部書き出して同期する）を待つ。テストは店を消すたびにこれを待ち、並べると各々がここで詰まる（測ると、並べた各々のほとんどが `CheckpointStart`・`CheckpointDone` の待ちだった）
   - CI の DB は仕事が終われば消えるので、同期を止めても失うものが無い。本番・ステージング・手元の開発の DB の設定は変えない（手元の `make test` は、同期のぶん CI より遅い）
4. **ブラウザのテストは毎回と夜に分ける**
   - プルリクエストの `e2e` は大事な流れだけ（ログイン・商品の登録・カート・注文と支払い・取消と返金・店の境界・権限・App の画面の主なもの・外へ送る物の守り）。夜だけの場面には札 `@nightly` を付け、`npm run e2e:pr`（`--grep-invert @nightly`）で外す。札の無い場面は毎回流す（新しい場面は既定で毎回の側）
   - 全部は main に入った後と毎日 1 回の別の仕事 `e2e-full`（`.github/workflows/e2e-full.yml`）で流す。main の守る設定の必須にはしない。CI の仕事の名前（`check`・`e2e`・`image`・`secrets`）は変えない
   - 振り分けの一覧は開発用の文書に置く

## 結果

得たもの:
- 店を作る時間が移行の分だけ減り、PHP のテストが CPU の数だけ並ぶ（測った時間は「作って決めたこと」）
- 型から写した店が本番の形と同じかを、毎回のテストが一から作った店と比べて見張る。本番の作り方（一から移行を流す道）も毎回 1 度は通る
- プルリクエストのブラウザのテストが大事な流れに絞られ、写しと細かい画面も 1 日 1 回は必ず走る

失ったもの・気をつけること:
- 開発だけの依存が 1 つ増えた（paratest と、それが連れてくる部品。`composer audit` の対象）
- 型を写す道と本番の道で、店の DB の作り方の文が 2 か所になった（本番の係を変えたら、テスト用の係も合わせる。ずれれば `TenantDatabaseTemplateTest` が落ちる）
- 並べると、テストどうしが同じファイルや同じ外の物（決まった名前の置き場など）を使っていると揺れる。各々の DB・店の DB の頭・写真の置き場は分けたが、ほかに共有の物を使うテストは各々の番号で分ける
- 夜だけの場面で壊れたものは、プルリクエストでは気づかず、main に入ってから分かる（気づいたらその日に直す）

## 作って決めたこと

- 2026-11-05: 型の名前は `<店の DB の頭>_template`、型のロールは `<店のロールの頭>_template`（例 `ec_test_o_t__template`・`ec_test_o_t_u__template`）。店の ID は英小文字か数字で始まるので重ならない。どちらも店の DB の頭で始まるので `make test-clean` の対象に入る（消えたら次に作り直す）
- 2026-11-05: 型には誰も入らないようにする（PUBLIC の接続を取り上げ、`ALLOW_CONNECTIONS false`）。入っている者がいると写せず、自動の掃除も接続を受け付けない DB では始まらない
- 2026-11-05: 型の写し方は既定の `STRATEGY = WAL_LOG` のまま。`FILE_COPY` は写すたびに前後で CHECKPOINT を待つので、試すとかえって遅かった
- 2026-11-05 に開発の機械（CPU 11）で測った時間（PHP のテスト全部、約 1,420 件）:
  - 共有の開発用 Postgres（ほかの作業のテストも同じ DB で同時に走っていた）: 直列・型なし 962 秒、直列・型あり 749 秒。ここでは CHECKPOINT 1 回が 2〜3 秒かかり、店を消すたびに待つ
  - CI と同じ形の使い捨ての Postgres（同期あり・ほかの負荷なし）: 店を 1 つ作るのは型ありで約 70 ms、消すのは約 60〜90 ms。並べて（11）・型ありでは 557 秒で、各々のほとんどが CHECKPOINT の待ちだった（各々のファイルの時間の合計は 5,885 秒）。このため CI の使い捨ての DB で同期を止める（決定 3）
  - 同じ使い捨ての Postgres で同期を止めた形（`fsync`・`synchronous_commit`・`full_page_writes` を off）、並べて 6・型あり: **160 秒**、1,425 件すべて通過（ほかの作業の 4〜5 のテストが同じ機械で同時に走っている中。各々のファイルの時間の合計は 923 秒で、直列の基準の 962 秒とほぼ同じ＝待ちが消えた）。CI の VM での時間は別に確かめる
- 2026-11-05 に CI（自前の CI の走らせ役）で測った時間: `check` 15 分 43 秒 → 3 分 15 秒、`e2e`（プルリクエストの大事な流れだけ）4 分 29 秒 → 1 分 49 秒
