# 0089 記録（ドメインイベント）を Transactional Outbox にし、受け手ごとの印から少なくとも 1 回届ける

状態: **採用**（2026-11-06。作ることは運営が決めた。外の点検の「イベントの届き方の約束（失敗・再実行・重複・順序・止めた App・キューの後の店の文脈）を App を作る人向けにまとめる」による）。ADR 0012（ドメインイベント）・0025（App の使う・使わない）・0043（壊れたら知らせる仕組み）・0087（処理を追う ID）の上に置く。拡張点「イベント」（CONCEPT 6.3）の届け方を置き換える（`DomainEventRecorded` は残すが、届かないことのある知らせに格下げ）

## 要点（先に）

1. **記録（`domain_events`）をそのままOutboxにする**。状態の変更と同じトランザクションで残した記録を、コミットの後に**送り出し役**（`App\Core\Event\Outbox\EventRelay`）が**名前のある受け手**（`EventReceivers`）へ届ける。受け手ごとに「どこまで流したか」の印（`event_receiver_positions`）を持つ。コミットの直後にプロセスが落ちても、**毎分の見回り**（`events:relay`）が印から先を拾って流す。店ごとに、店の DB の中で
2. **核の知らせ（支払いが確かになった・入金待ち・期限切れ・発送した・返金が確かになった）も記録に残す**（`notice.payment_confirmed` など。`EventStore::notice()`）。前は `ShouldDispatchAfterCommit` の Laravel のイベントで、コミットの後に同じプロセスで流すだけだった（落ちたら消えた）
3. **届き方は「少なくとも 1 回」**。同じ記録が 2 回届くことがある。**受け手は冪等に書く**（2 回届いてもメール 2 通・ポイント 2 回・チケット 2 枚・請求 2 回にならない）
4. **順序**: 同じ受け手には、**同じ集約（同じ取引など）の記録は記録の順**に届く（前の記録が落ちて届け直しを待つ間、後ろの記録は並んで待つ）。**違う集約の間の順は約束しない**
5. **止めた App には届けない**。App に結びつけた受け手は、店でその App を使っていて、**今の「使う」にした時より後に起きた記録だけ**を受ける。止めていた間の記録は、使うに戻しても届けない
6. **落ちた受け手**: ログと壊れたら知らせる仕組み（種類 `event_failed`、元の記録の処理の ID の下）に残し、1・5・30・120 分と間を空けて届け直す。**5 回落ちたら止めて要対応**（運営の様子の「止めた知らせ」）。止めた記録は後ろを詰まらせない。直した後にオーナーが運営の様子から「流し直す」（再確認つき）か `events:relay --resume`

## 文脈

- `EventStore::append` は記録を同じトランザクションで書いた後、`DB::afterCommit(fn () => event(new DomainEventRecorded($event)))` で同じプロセスの中で知らせていた。支払いの確定・発送・返金の知らせ（`PaymentConfirmed` など）も `ShouldDispatchAfterCommit` の Laravel のイベントで、同じ形
- コミットの直後、知らせを流す前にプロセスが落ちる（記憶の不足・起き直し・デプロイ）と、注文は残るのに、ご注文の確認のメール・店への知らせ・チケットとギフトカードの発行・ダウンロードのリンク・定期便の開始・LINE の知らせが消えた。一部の App は見回りで拾い直していた（ダウンロードの `downloads:grant`、チケットの `tickets:issue` など）が、仕組みとしては無かった
- 受け手は例外を握りつぶして `report()` するだけだった（届け直さない）。`report()` は要求の中の例外しか壊れたことの記録に数えないので、裏の仕事・CLI の中で落ちた受け手は運営の様子に出なかった

## 決めたこと

### Outbox と印

- Outbox は新しい表を作らず、**`domain_events` そのもの**（追記だけ・番号の連番・同じトランザクション）。番号は連鎖のロックの中で決まり、コミットの順が番号の順になる（後の番号が先に見えることは無い）。だから「印より大きい番号」を読めば取りこぼさない
- 受け手ごとの印 `event_receiver_positions`（受け手の名前・番号）。印は「届けた・届けなくてよかった・落ちて届け直しの表へ移した」記録の番号まで進む
- 届け直しの表 `event_retries`（受け手・番号・集約・状態 `waiting`/`stopped`・回数・例外のクラスの名前・次の時刻）。例外の文は残さない（個人情報を含むことがある）。（受け手・番号）で一意
- どちらも状態ではなく、お金と在庫に触れない「流したか」の印（書き方の決まり 3 の例外。連鎖のロックとイベントを使わない）
- **初めて見る受け手**（新しい App・名前を変えた受け手・この仕組みを入れた最初のデプロイ）は、**5 分より前の記録の最後**から始める。前の記録を全部は流さないが、デプロイの前後に流し損ねた分は拾う（受け手は冪等なので、2 回目になっても同じ結果）

### 送り出し役

- 呼ばれ方は 3 つ: コミットの後（`EventStore` の `afterCommit`。同じプロセス）、毎分の見回り（`events:relay`、`withoutOverlapping`）、運営の「流し直す」
- 1 つの店で同時に流すのは 1 本だけ。店の DB のセッションのアドバイザリロックを**待たずに**取り（`pg_try_advisory_lock`）、取れなければ取った方に任せる。待たないので、書き込みの連鎖のロックとのデッドロックは起きない。取った方は鍵を放した後に「印より先が残っていないか」を確かめ直す（その間に積まれた記録を取りこぼさない）。受け手の中の書き込みのコミットから呼ばれた時は、外側の回が同じ回の中で拾う
- コミットの後の回は 200 件まで（要求を長く待たせない）、見回りは 1 店 5000 件まで
- 受け手は登録した順に呼ぶ（同じ記録の中。例: 贈り物のリンクを作ってから注文の知らせのメール）
- 届ける時は、元の記録の処理の ID の下で動かす（`TraceId::within`。ADR 0087）。送ったメールの記録・エラーの記録に元の要求の ID が残る
- トランザクションの中では流さない（受け手のコミットの後の処理が動かないため）。受け手が開いたまま落としたトランザクションは閉じてから次へ

### 受け手

- 登録は `EventReceivers::on(名前, 記録の種類, 受け手, app: App の名前)` と、核の知らせ用の `notice(名前, 知らせのクラス, 受け手, app:)`。受け手は記録（と知らせ）を受け取り、**続けられない時は例外を投げる**（投げずに報告だけすると届け直さない）
- 名前は `<App の名前か core>.<何をするか>`（例 `tickets.issue`）。印と届け直しの鍵なので、変えると最初から数え直す（上の 5 分の決まり）
- `app:` を付けた受け手は、その App を使っている間に起きた記録だけ受ける。払った人への約束を守る受け手（ギフトカードの発行・ダウンロードのリンク・チケットの発行と無効・定期便の開始・予約の確定・紹介の取消）は App に結びつけない（止めた後も前の注文の後始末をする）
- 核の知らせをテストで `event(new PaymentConfirmed(…))` と直に出すと、同じ受け手が動く（届け直しの守りは無く、落ちたら報告だけ）。核のコードは使わない
- `DomainEventRecorded` は残す（同じプロセスの中だけ・届かないことがある）。**書いた要求の文脈が要るものだけ**に使う（友だち紹介の Cookie の印を会員に結ぶ。届け直す先の要求が無いため）

### 今の受け手と、2 回届いた時（2026-11-06 に全部を確かめた）

| 受け手 | 受ける | 2 回届いても同じ結果になる理由 |
|---|---|---|
| `core.gift-link` | 支払いの確定 | 贈り物が「準備中」の時だけリンクを作る（連鎖のロックと行のロック） |
| `core.order-mail.paid`・`.awaiting`・`.lapsed`・`.shipped`・`.refunded` | 各知らせ | 送った記録 `sent_mails` の（注文・種類・受渡・返金）の一意と行のロック。送れたら「送った」で、2 回目は送らない |
| `core.coupon-used` | 支払いの確定 | 「予約中」の時だけ「使った」にする 1 文の更新 |
| `gift-cards.issue` | 支払いの確定 | 核が買った注文ごとに 1 枚だけ発行（2 回目はコードを出さないのでメールも送らない） |
| `gift-cards.stop-on-refund` | 返金の仕訳 | 止まっていないカードだけ止める |
| `shop-notify.paid`・`.awaiting`・`.changes` | 支払いの確定・入金待ち・段の移り・入庫・調整 | 送った知らせ `shop_notify_notices` の一意と行のロック、在庫の印は「無ければ入れる」 |
| `restock.replenished` | 入庫・調整・取消 | 「待っている」登録だけに知らせ、送ったら「知らせた」 |
| `downloads.grant`・`.refunded`・`.stop-on-close` | 支払いの確定・返金・取消 | リンクは無い商品にだけ作り（作った時だけメール）、止めるのは止まっていないリンクだけ |
| `referral.closed`・`.paid`・`.shipped` | 段の移り・支払い・発送 | 紹介の状態を錠の中で確かめてから 1 段だけ進める |
| `tickets.issue`・`.void-on-close` | 支払いの確定・取消と返金 | まだ無い番号の分だけ出す（注文と何枚目かの一意の索引）、有効なチケットだけ無効にする。リセールの注文が閉じたら予約中のリセールだけを戻す・取り下げる（予約中でなければ何もしない） |
| `booking.confirm`・`.cancel-mail` | 支払いの確定・取消 | 確定の印の無い予約だけ確定、遅れた払いの記録は 1 回だけで取消の仕事は頼み直す（仕事は取り消せない注文では何もしない）、取消のメールは送った印 |
| `lottery.paid` | 支払いの確定 | 「請求中・払えなかった」の時だけ paid に |
| `lottery.resale-refunded` | チケットのリセールの注文を渡せずに取り消した（`ticket.resale_cancelled`） | 「請求中・払えなかった・払った」の時だけ refunded に |
| `subscription.paid` | 支払いの確定 | 「支払い待ち」の契約・開いた回だけ進める |
| `line.paid`・`.shipped` | 支払いの確定・発送 | 送った記録 `line_messages` の一意（`insertOrIgnore`） |

- 直したもの: 予約の確定は「今」でなく**払いの確定の記録の時刻**で「枠の始まりの後に払われたか」を比べる（届け直しで遅れて届いても、払った時で比べる。前は遅れて届くと間に合った予約を取り消して返金しうた）。遅れた払いの記録（`booking.paid_too_late`）は 2 回目に重ねない。ダウンロードのリンクを止めた時刻は記録の時刻
- 届け直しで残る小さなずれ（直さない。理由つき）: 定期便の始まりの日（`anchor_on`）は受け手が動いた日（日をまたぐ落ち方の時だけ 1 日ずれる）。紹介の「App を止めていた時の発送は付けない」は受け手が動いた時の App の状態で見る

### 運営の様子と流し直す

- 店ごとの数（ShopDigests。ADR 0042）に、届け直しを待つ記録と止めた記録の**件数だけ**を足す（`event_waiting`・`event_stopped`）。止めたものは要対応、待ちは近いうちに
- 「流し直す」は `POST /api/tenants/{店}/event-retries`（`EnterTenant` の下・オーナーだけ・直前の再確認・回数の制限）。止めた記録を待ちに戻し、待っている記録もすぐの対象にして、その場で流す。入った店の記録だけ。中央の監査ログに `tenant.events_retried`（数だけ）を残し、店の数を数え直す
- 受け手の失敗は、送り出し役が `EventReceiverFailed` を出し、管理画面のサービスプロバイダが壊れたことの記録（`event_failed`）に数える（核は管理画面を知らない）。止めた時は場所を「receiver <名前>」にして受け手ごとに 1 行

## 結果

- 得たもの: コミットした注文の後の仕事が、プロセスが落ちても消えない。落ちた受け手は自動で届け直され、何度も落ちるものは運営の様子に出て、直した後に流し直せる。App を作る人に「届き方の約束」（下）を示せる
- 失ったもの・気をつけること:
  - 記録の数が増える（核の知らせ 1 つにつき 1 行。注文の記録の一覧に `notice.*` が並ぶ）
  - 受け手は冪等でなければならない（書き方の決まりと App の説明に書いた）。外の仕事（メール・Slack・LINE）は「送った」の印を先に作る形でないと、2 回届いた時に 2 通になる
  - 送り出しのセッションのロックは、トランザクションの単位で接続を分け合う仕組み（PgBouncer のトランザクションの形）とは合わない（今は使っていない）
  - コミットの後の回は、ほかの要求が残した記録も流す（その要求の応答が少し遅れることがある。上限 200 件）

## App を作る人への約束（イベントの届き方）

| こと | 約束 |
|---|---|
| いつ届くか | 書き込みのコミットの後。ふつうはすぐ（同じプロセス）、落ちたら 1 分ほどで見回りが |
| 何回届くか | **少なくとも 1 回**。2 回届くことがある（落ちた後・デプロイの前後・運営の流し直し）。受け手は冪等に書く |
| 失敗したら | 例外を投げる。1・5・30・120 分の間を空けて届け直す。5 回落ちたら止めて要対応。止めた後は運営が直してから流し直す。報告だけして握りつぶすと届け直さない |
| 順序 | 同じ集約（同じ取引など）の記録は、その受け手には記録の順に届く。違う集約の間の順は約束しない。違う受け手の間の順も約束しない（同じ記録の中では登録の順に呼ぶ） |
| 止めた App | 店でその App を止めている間の記録は届けない。使うに戻しても、止めていた間の記録は届けない。払った人への約束を守る受け手は App に結びつけない |
| 店の文脈 | 受け手は記録の店の文脈の中で呼ばれる（ほかの店の記録は来ない）。受け手から積んだキューの仕事も、その店の文脈と処理の ID が戻る（ADR 0087） |
| 処理の ID | 元の記録を書いた処理の ID の下で呼ばれる |
| 要求の文脈 | 無いことがある（見回り・キュー）。Cookie・セッション・要求の値を使う仕事は受け手でしない（`DomainEventRecorded` で、届かなければ何もしない形に） |
| 中身 | 記録の中身（ID・金額・列挙の文字）だけ。個人情報は記録に無いので、要る時は店の DB から引く |

## 作って決めたこと（2026-11-06）

- 核の知らせは記録の種類を `notice.*` にし、集約は取引。知らせのクラスが記録への写し方と作り直し方を持つ（`App\Core\Event\Notice`）
- 受け手の失敗を `report()` でなくイベント（`EventReceiverFailed`）で数えるのは、`report()` が要求の中では `http_error` として数え、見回りでは数えないため（どちらでも 1 回ずつ数える）
- main に入ったリセールの抽選（PR 127）の受け手も移した（2026-11-06、main に合わせた時）: 抽選の「リセールの注文を渡せずに取り消した」（記録 `ticket.resale_cancelled`）は `lottery.resale-refunded` に、チケットの「リセールの注文が閉じたら予約を戻す」は `tickets.void-on-close` の中に（同じ記録で、無効にしてから戻す順は前のまま）。どちらも払った人への後始末なので App に結びつけない。リセールを戻す時の締め切りは記録の時刻でなく今で比べる（届け直しで締め切りの後に届いたら、売りに戻さず取り下げて元の人へ知らせる。毎分の `tickets:resale` も同じ形で取り下げる）
- 見回りは毎分（ほかの見回りより短い。落ちた知らせはお客さんが待っている）
- **店の DB を作り直している最中の店には入らない**（2026-11-06。デモの店の毎晩の戻し〔ADR 0086〕と合わせた時）: 戻しは店の DB を消して作り直すので、その間に見回りが入ると DB や表が無くて落ち、`events:relay` が FAILURE を返して定期の処理の失敗として運営に知らせていた。中央の店の行の印（`Tenant::REBUILDING`。DB を消す前に立ち、作り直しが終わってから消える）を、店に入る直前に読み直して（`Tenant::rebuildingNow()`）飛ばす。失敗に数えず、ログに 1 行。作り直した店の記録は、作り直しの中のコミットの後と次の見回りが流す。店ごとに回るほかの定期の処理（App の `PluginTenants`、核のポイント・カート・ギフトカード・払われない注文・返金の見回り、運営の様子の集め）も同じ口（`Tenant::serving()`）で飛ばす。`Core\Event` から `Core\Shop` へは頼らない（印は `App\Models\Tenant` に置いた）
