# 0087 処理を追う ID を要求ごとに決め、ログ・キュー・記録へ持ち越す

状態: **採用**（2026-11-06。作ることは運営が決めた。外の提案「問い合わせの受付からメール送信まで、注文から決済・返金までを共通の処理 ID で追えるように。個人情報や秘密をログへ増やさず、テナント ID・注文 ID・処理 ID で関連づける」による）。ADR 0012（ドメインイベントのハッシュ連鎖）・0013（監査ログ）・0043（壊れたら知らせる仕組み）の上に置く。次に来る「非同期の確かさ（Outbox）」が同じ所（イベントとキュー）に乗る

## 要点（先に）

1. **処理の ID（trace ID）は ULID（小文字の 26 文字）**。要求ごと・定期の処理ごと・CLI のコマンドごとに、こちらで新しく決める。**外から来る `X-Request-Id`・`traceparent` は信じない**（形が正しくても使わず、記録にも残さない）
2. **置き場は Laravel の Context（キー `trace_id`）**。ログの各行に自動で付き、キューの仕事の中身にも自動で載って、処理する時に戻る。店の文脈に入っている間は店の ID（`tenant_id`）もログに添える。足すのはこの 2 つだけ
3. **記録の表に写す**: ドメインイベント（`domain_events.trace_id`）・監査ログ（`audit_events.trace_id`）・壊れたことの記録（`incidents.last_trace_id`、最後に起きた時）・送った知らせのメール（`sent_mails.trace_id`）・支払いの画面と返金の頼み（`checkout_plans`・`refunds` の冪等キーの横の `trace_id`）・決済代行の通知（`webhook_events.trace_id`）。**ハッシュ連鎖の本文には入れない**
4. **応答の見出し `X-Request-Id` に返すのは管理画面のホストだけ**。ショップ・Webhook の受付・確かめ口（`/up`）には返さない
5. **管理画面に「処理を追う」**（`GET /api/tenants/{店}/traces/{ID}`、画面 `/tenants/{店}/traces/{ID}`）。オーナーだけ・読むだけ・入った店の記録だけ。運営の様子のエラーから、店の中で起きたものは「関係する記録」で開ける

## 文脈

- お問い合わせの受付から知らせのメールまで、注文から支払い・返金まで、1 つの操作が要求 → イベント → キューの仕事 → メール・決済代行へと広がる。今は「どの要求のどの仕事が、どのメールを送ったか」をつなぐ印が無く、障害の時に時刻と注文の ID から推し量るしかなかった
- ログ・記録に個人情報を増やさない決まり（ADR 0010・0043）は守ったまま、つなぐための印だけを足したい
- この後の「非同期の確かさ（Outbox）」は、イベントと同じトランザクションで「後で送るもの」を積み、別の処理が送り出す。積んだ時の ID で送り出せる形にしておく

## 決めたこと

### ID の決め方と持ち越し方

- 部品は核の `App\Core\Trace\TraceId`（ほかの核の文脈に頼らない。管理画面・ショップ・どの文脈からも使える）。`start()`（新しく決める）・`current()`（今の ID。形の違う値は null）・`ensure()`（無ければ決める）・`within($id, fn)`（決まった ID の下で動かし、前に戻す。Outbox の送り出しの口）
- **要求**: いちばん外側のミドルウェア `App\Http\Middleware\AssignTraceId`（全部の要求。`bootstrap/app.php` で `prepend`）が毎回 `start()`。管理画面のホストの応答にだけ `X-Request-Id` を付ける
- **キュー**: Laravel が積む時に Context を仕事の中身（`illuminate:log:context`）へ載せ、処理する前に戻す（`ContextServiceProvider`）。店の ID は stancl/tenancy が別に載せて戻す（`QueueTenancyBootstrapper`）。戻した直後（`Context::hydrated`）に ID が無ければ、仕事ごとに新しく決める（ID の無い処理から積んだ仕事・前の版で積まれた仕事）。処理役は仕事ごとに Context を入れ替えるので、前の仕事の ID が次の仕事に残らない。失敗した仕事の中身（`failed_jobs.payload`）にも ID が残り、やり直し（`queue:retry`）も同じ ID で動く
- **定期の処理**: `ScheduledTaskStarting` で処理ごとに `start()`。同じプロセスで動く関数・仕事も、別のプロセスで動くコマンドも（コマンドへは Laravel が Context を環境変数 `__LARAVEL_CONTEXT` で渡し、子のプロセスは始まりでそれを使う）
- **CLI**: `CommandStarting` で `ensure()`（人が流したコマンド・処理役・定期の処理の親は新しく、定期の処理から渡された子はその ID）。店の文脈に入っていなければ、環境変数から戻った店の ID を外す
- **店の ID**: `TenancyInitialized` で Context の `tenant_id` に置き、`TenancyEnded` で外す（ログの行に店を添えるため）

### 記録に写す

- ドメインイベントと監査ログは、`EventStore::append`・`AuditLog::record` が書く時に `TraceId::current()` を添える。**ハッシュの本文（`v` が 1 のまま）には入れない**: 無い頃の記録の検証を変えず、ID は記録を引くための参考の印で、改竄の検知の対象ではないため。後から書き換えられないことは、追記だけのトリガー（UPDATE・DELETE・TRUNCATE を断る）が守る
- 送ったメール・支払いの画面・返金・決済代行の通知は、トレイト `App\Core\Trace\RecordsTrace` が行を作る時に写す（後から直しても変えない＝最初に作った処理を指す）。知らせのメールの行はキューの仕事の中で作るので、積んだ要求の ID になる
- 壊れたことの記録は指紋ごとに 1 行で回数を数える表なので、最後に起きた時の ID だけを持つ（`last_trace_id`。ID の無い所で起きたら前の値のまま）
- 列はどれも空でよく（前からの行・ID の無い処理）、DB の制約で ULID の小文字の形だけを受ける。引くための索引は値のある行だけ
- App が自分で持つ送った記録（メルマガ・LINE・店への知らせなど）にはまだ写していない。Context はキューの仕事の中で戻るので、ログの行には ID が付く。表に写すのは、要るものから `RecordsTrace` を足す

### 処理を追う口

- `GET /api/tenants/{店}/traces/{ID}`（`EnterTenant` の下・`RequireOwner`・読むだけ。ID は `whereUlid`、大文字でもよい）。`App\Admin\Services\TraceRecords` が並べる
  - 店の DB: イベント（番号・種類・集約の種類と ID〔注文の ID など〕・actor・時刻）・送ったメール（種類・注文の ID・状態・時刻）・支払いの画面（何回目・冪等キー）・返金（目的・状態・冪等キー）・決済代行の通知（決済代行・通知の ID・種類・結果）
  - 中央: 監査ログ・壊れたことの記録・失敗した裏の仕事は、**入った店の ID の行だけ**（同じ ID でもほかの店の行は出さない）。失敗した仕事は中身の店の ID と Context の ID で絞る
  - 返さないもの: イベントの中身（payload）・監査の中身と接続元・メールの件名と宛先・例外の文・仕事の中身
  - 1 つの種類に 100 件まで
- オーナーだけにした理由: 監査ログ（ほかの運営の操作）・壊れたことの記録（コードの場所）・失敗した仕事は、運営全体の様子（オーナーだけ。ADR 0042）と同じ重さの情報のため。スタッフは店のお金まで任されていても 403

## 結果

- 得たもの: 障害の時に「この要求から何が起きたか」を、ログ（`grep <ID>`）と管理画面の両方から 1 つの ID でたどれる。注文の ID からイベント → 処理の ID → 送ったメール・返金の頼み・失敗した仕事へ広げられる。Outbox は積む行に `trace_id` を持ち、送り出す時に `TraceId::within` で同じ ID の下で動かせばよい
- 失ったもの・気をつけること: ID はハッシュの本文の外なので、DB の所有者（トリガーを外せる人）は ID だけを書き換えられる（中身の改竄は連鎖が見つける）。壊れたことの記録は最後の 1 回の ID しか持たない（前の回はログで引く）。テストの中では Laravel がコマンドの始まりの出来事（`CommandStarting`）を出さないので、CLI の ID はテストで出すようにして確かめた
- 残したこと: App の送った記録への `RecordsTrace`、外の HTTP の呼び出し（Slack・LINE など）の記録の表（今はログの行だけ）、ショップのエラーの画面に問い合わせ用の番号を出すか（今は出さない）、Outbox（次のタスク）

## 作って決めたこと（2026-11-06）

- 外の `X-Request-Id` は形が正しくても記録の参考にも残さない（攻め手の決めた文字をログに入れない。Cloudflare の `CF-Ray` などで前段と突き合わせたくなったら、決まった形だけを別のキーで残すかを改めて決める）
- 返す見出しの名前は広く使われている `X-Request-Id` にした（中身はこちらの ID。外の値を返すのではない）
- 決済代行へ ID を送らない（Stripe のメタデータ・外の HTTP の見出しに載せない）。Stripe の通知は新しい要求として来るので、通知の処理は自分の ID を持ち、注文の ID でつながる
