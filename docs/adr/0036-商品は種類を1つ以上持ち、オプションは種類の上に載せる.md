# 0036 商品は種類を 1 つ以上持ち、オプションは種類の上に載せる

状態: **採用**（2026-10-29。商品によってはオプションやバリエーションがある → 形は「案 A 種類を 1 つ以上」、名入れ・ギフト包装のようなオプションは「一緒に作る」）。

## 文脈

- 今は 1 つの商品（`listings`）が 1 つの在庫・1 つの価格・1 つの品番を持つ。在庫（`inventory_stocks`・`inventory_units`）、カート（`cart_lines`）、取引の行（`transaction_lines`）が、すべて商品に直に結び付いている
- 服の色とサイズ、器の色、容量違いのように、**選ぶと在庫と価格が変わるもの**（種類。SKU＝在庫を数える単位）を持てない
- 名入れ・ギフト包装・のし のように、**在庫は無いが値段が足されたり文字を入れたりするもの**（オプション）も持てない
- 案 B（色・サイズを子の商品として持つ）は早いが、商品の一覧・カテゴリ・写真のどこでも子を除く必要が出て、核が散らかる

## 決めたこと

### 種類（バリエーション）

1. **どの商品も種類を 1 つ以上持つ**（`listing_variants`）。色やサイズの無い商品は、軸の無い種類を 1 つだけ持つ。在庫・カート・取引の行は、商品ではなく**種類に結び付く**（商品の ID も持ち続ける）
2. **選ぶ軸は 3 つまで**（`listing_options`。例: 色・サイズ・素材）。軸ごとに値を並べ（`listing_option_values`）、値の組み合わせが 1 つの種類になる。同じ組み合わせの種類は 2 つ作れない（DB の一意の制約）
3. 種類が持つもの: 品番（店の中で一意、空でもよい）、価格（空なら商品の価格）、写真（商品の写真から 1 枚、空でもよい）、販売中かどうか、並び順
4. **種類が商品に属することを DB で守る**: 在庫・カートの行・取引の行は `(variant_id, listing_id)` で種類を指す（種類の表の `(id, listing_id)` への外部キー）。別の商品の種類を指す行は DB が断る
5. 今の商品は、移行で**軸の無い種類を 1 つずつ作り**、品番をそこへ移し、在庫・カート・取引の行に種類を入れる。移行の後も、今の画面と API はそのまま動く（種類が 1 つの商品は今と同じに見える）
6. 取引の行には、合意のときの**種類の名前（「赤 / M」）と品番を写して残す**。種類を後で変えたり消したりしても、注文の記録は変わらない（取引の行は合意後に書き換えない。ADR 0011）
7. 在庫の確保・解除・出庫（StockService）は種類 × 拠点で行う。行ロックの形は今のまま

### オプション（在庫の無い追加）

8. 商品ごとに、オプションを並べる（`listing_addons`。10 個まで）。形は 3 つ:
   - **選ぶ**（例: ギフト包装 なし／あり +330 円、のしの種類）: 選択肢ごとに足す額（0 以上の整数）
   - **入れる文字**（例: 名入れ）: 最大の文字数（100 まで）と足す額。改行・制御文字・文字の向きを変える印は断る
   - **付ける／付けない**（例: 保証の延長 +1,000 円）
   - それぞれ「必須」を付けられる（→ 「付ける／付けない」は必須にしない。2026-10-30 に決めた。下の「作って決めたこと」）
9. お客さんの選んだオプションは、カートでは行ごとに持ち（同じ種類でもオプションが違えば別の行）、注文のときにサーバーで今の定義と照らして確かめ直し、額を計算し直す（カートに入れた後の額の変更は、今の価格の変更と同じ扱い）
10. 取引の行では、オプションの額は**商品の行に従う行**（親の行を指す）として持ち、名前・選んだもの・額を写して残す。税率は親の行と同じ。在庫は動かさない
11. **入れる文字は個人情報として扱う**（名入れは人の名前になりうる）。カートでも取引の行でも、店の鍵で暗号化して持つ（ADR 0010）。管理画面の注文の詳細では見せるが、記録（ログ）とイベントには入れない。タグの App（ADR 0034）にも渡さない

### 画面

12. 管理画面: 商品の編集に「種類」（軸と値を入れると組み合わせの表ができ、行ごとに価格・品番・在庫・写真・販売中）と「オプション」の欄を足す
13. ショップ: 商品の画面で軸ごとに選び、売り切れの組み合わせを示し、選んだ種類の価格と写真に切り替える。**JavaScript が無くても**種類の一覧から選んでカートに入れられる。テーマ API に種類とオプションのデータを足し、4 つのテーマの商品の画面とカートを合わせる

## 区切り

1. 核: 表・移行・在庫とカートと取引の行を種類へ（画面は今のまま動く）
2. 管理画面の種類の編集と、ショップでの選択とテーマ API
3. オプション: 核（表・確かめ・額の計算・暗号化・取引の行）と画面

## 作って決めたこと（2026-10-29〜30）

- 種類の値の外部キーは種類が商品に属すること・値がその番の軸のものであることをトリガーで、品番の重なりは出品者ごとの一意の索引で守る（種類に出品者を DB が写す）
- 軸を決め直すと、名前の同じ組み合わせの種類は残し（価格・品番・在庫を保つ）、無くなった組み合わせは消す。確保中の在庫がある種類は消せない。軸の無い商品に初めて軸を足すと、今の種類（品番と在庫）は引き継がない（どの組み合わせに渡すかが決まらないため。管理画面は保存の前に知らせる）→ 置き換え（2026-10-30。選んで渡す）: お店の人が選んだ組み合わせへ渡せる（この節の最後の項）
- オプションの行は、調整の行（kind = addon）で、数の分を 1 行にまとめ、`parent_position` で従う商品の行を指す。税率は商品の行と同じ。名前は「ギフト包装：あり（×2）」の形で、入れた文字は名前に入れない
- 入れた文字は、カートでは選び方ごと暗号化し（`cart_lines.addons`）、同じ選び方かは店の鍵つきの印（`addons_key`）で見る。取引の行では `addon_text` に暗号化。提示（jsonb）には持たせない。管理画面では「個人情報を見る」入口（見るたびに記録が残る）でだけ返す
- 画面を見て決めたこと（2026-10-30）: 付けるは必須にしない（「付けない」も選び方。管理画面は切り替えを出さず、核と DB の CHECK も断り、今ある値は false に直した）。商品の画面の合計は数を掛けた額（「2 点で ¥5,400」。カートの小計と同じ計算。はじめは「5,400 円」と書いていたが、同じ画面の値段「¥2,000」とそろえて、お客さんに見せる金額はすべて ¥ の形にした。2026-10-30）。必須の選ぶは空の「選んでください」から始め、ブラウザの required で止める。断られて商品の画面に戻ったら、入れていた値を次の 1 回だけ欄に戻す（セッションには Crypt で暗号化して flash で置き、平文で残さない）
- オプションの形（選ぶの選択肢・入れる文字の最大・額）は DB の CHECK でも守る（NULL の比べで素通りしないよう COALESCE で倒す。テストが見つけた）
- 軸の無い商品に初めて軸を足すときは、今の 1 つの種類を、お店の人が選んだ組み合わせへ渡せる（2026-10-30）。種類の行そのものを付け替えるので、品番・価格・写真・在庫（確保中の分も）がそのまま移る。既定は最初の組み合わせ、「渡さない」も選べる。渡せるのは軸の無い商品だけ（軸の決め直しは今までどおり、同じ名前の組み合わせが残る）

### 商品の CSV（2026-11-04。形と使い方は docs/design/product-csv.md）

- **App でなく核の画面にした**: ファイルを上げる・確かめの画面を挟む・ファイルを返すは、App の画面の口（ADR 0051。核の型の値と決まった欄だけ）では描けない。書くのも商品・種類・在庫・カテゴリ・オプションの核のサービスだけで、どの店にも要る乗り換えの入口なので、核（`app/Core/ProductCsv`）に置いた。核のほかの文脈からは頼らない（依存は一方向）
  - 2026-11-18 に**中身だけを App へ出した**（ADR 0107 の段 1。配送の CSV が App なのに商品の CSV が核にあったため）。画面と受け口は上の理由のまま核で、動いたのは実装の居場所と名前空間だけ（`plugins/plugin-product-csv`・`EcSugar\PluginProductCsv`）
- **1 行 1 種類**。商品は 商品ID → 品番 → 商品名 の順で決める。消さない、今の商品の選ぶ項目の名前と順は変えない（値を足すのはよい。足すと全部の組み合わせの種類ができる）
- **確かめも反映もキューの仕事、反映は商品 1 つずつ**（2026-11-04 の で作り直した）: 最初は反映を 1 つのトランザクションで全部か無しにしたが、反映の間（1,000 行で約 20 秒）店の連鎖のロックを持ち続けて注文を止めること、行が多いと入れ子のセーブポイントのロックで Postgres の枠を使い切るのを Laravel の中の仕組みの差し替えで避けていたことが受け入れられず、捨てた。今は、確かめで全部の行に誤りが無いことを先に保証し（商品ごとに書いてみて巻き戻す）、反映は商品 1 つずつ核のサービスの短いトランザクションで確定する。途中で断られたらそこで止め、記録（`product_imports`）に入った行の数・止まった行・理由を残す。同じ CSV を入れ直すと、ID・品番（と、前の取り込みで作った商品名）で合わせるので残りだけが入る
- **上限は 2,000 行・5MB**。確かめもキューにした（2,000 行で約 26〜41 秒〔手元〕と、nginx の既定の 60 秒に近いため）。1 回の仕事は約 45 秒で区切って続きの仕事を出す（本番の走らせ役の `--timeout=75` と送り直しまでの 90 秒より短く）
- **反映は店に 1 つだけ**: 待ち・進行中があれば 409、DB でも部分の一意の索引で断る。走らせ役が落ちて進行中のまま残ったものは、15 分進み具合が書かれなければ止まった扱いにする
- **在庫は「この数にする」**で、今の数との差を棚卸しの調整（`InventoryOperations::adjust`、理由 `stocktake`）に渡す。拠点は出品者の最初の拠点（書き出しも同じ）
- **確かめた CSV だけを反映する**: 反映は確かめ済みの記録を指して頼み、記録に置いた同じ CSV を使う（ファイルを送り直さない）。反映を頼んだら誰が・何件を中央の監査ログ（`operator.listings_imported`）に
- **CSV の差し込みよけ**: 書き出しで `= + - @`・タブ・CR（全角も）で始まる文字の欄に `'` を付け、取り込みで外す。文字は UTF-8 と CP932（表計算ソフトの既定）を読む
- 出品者は最初の出品者（マーケットの形で選ぶのは後）
- **写真もまとめて取り込む**（2026-11-05。区切り 2。形と守りは docs/design/product-csv.md の「写真」）:
  - 列は `写真1`〜`写真10`（1 つの欄に区切りで並べない。URL にはカンマ・セミコロンが入りうる）。CSV の末尾に足す。値は https の URL か、一緒に上げる ZIP の中のファイル名
  - 書き出しはショップの写真の公開の URL。取り込みは道筋の写真の ID でこの店の写真と見分け、同じ商品なら何もしない（往復で二重に作らない）。ほかの商品の写真なら置き場から写す
  - 足すだけで消さない。同じ写真は、元のファイルの中身の SHA-256 と URL の SHA-256（URL そのものは残さない）で見分ける
  - **確かめでは取りに行かない**（形・http・住所そのもの・ZIP の中身・枚数だけを見て「写真が取れない行」に出す）。取りに行くのは反映で、商品を全部入れた後の写真の段。確かめで 2,000 枚を取りに行くと確かめが長くなり、取った写真を反映まで置いておく場所も要るため。取りに行って分かる失敗（つながらない・画像でない・大きすぎ）は反映の後に出す
  - 1 枚が駄目でも商品の取り込みは止めない。写真の置き場の量の上限（店の合計・その日の量）では止める。1 分の回数は、走らせ役を眠らせずに遅らせた続きの仕事で待つ
  - ZIP は 90 MB まで（前に置く Cloudflare の 1 回の要求の上限 100 MB に収めた。指示の例は 500 MB だったが、Tunnel を通らない）。入口の nginx はこの経路だけ本文を 100m まで受け、ほかの経路は 12m のまま（2026-11-06 で、ほかは管理画面の API が 12m・それ以外が 1m に。ADR 0018 の作って決めたこと）
  - 外へ取りに行くのは核の `Media\RemoteImages`（ショップのサンプルの写真の `SamplePhotos` は決まったホストだけなので別のまま）

## 結果

- 得るもの: 色・サイズごとの在庫と価格、名入れやギフト包装。在庫の数え方は「いつも種類」で 1 つになり、後から定期・買取を載せても形が崩れない
- 失うもの: 在庫・カート・取引・管理画面・テーマのすべてに手が入る（核で 20 ファイルほど）。テーマは商品の画面を直す必要がある
- 気をつけること: 種類が商品に属することと、取引の行の写しは DB で守る。オプションの額はいつもサーバーで計算し直す（カートの値を信じない）
