# 0113 使用状況の共有は既定を「はい」にして聞き、ランダムな ID とバージョンと店の数だけを週 1 回送る

状態: **採用**（2026-11-26）。ADR 0098（パッケージを配る形）・0102（外への通信）の上に足す。置き換えるものは無い

## 要点（先に）

1. インストーラーが「使用状況を開発元と共有しますか?」を聞く。**既定は「はい」[Y/n]**。質問の文に、送るもの・送らないもの・止め方を書く
2. 送るのは 7 つだけ: ランダムな ID（UUID v4）・バージョン・event（`install`・`weekly`）・OS の名前とバージョン・CPU の種類・そのサーバーの店の数（数だけ）。**入れた時に 1 回と、そのあと週 1 回**
3. 店の名前・ドメイン・店の ID・注文・お客さん・メールアドレス・設定の値は送らない。受け取る側は IP アドレスを残さない
4. 「使っている」と数えるのは、**違う週に 2 回以上報告し、最後の報告が 14 日以内**のサーバーだけ（試しに入れてすぐ消したものと、1 回きりの偽の送信を除く）
5. **端末が無く、設定ファイルにも `USAGE_SHARE` が無ければ「いいえ」**。前から入っているサーバーは、更新しても勝手に始めない
6. 後から `sudo ec-sugar usage`（送る中身を見る）・`usage on`・`usage off`（ID も消す）
7. メールアドレスはインストーラーで集めない。お知らせは公式の店のメルマガ（確認のメールで確定する二段階）へ案内する
8. 送るのはホストの root の `curl`（https だけ・10 秒）。アプリの送信用プロキシ（ADR 0102）は通らない。送れなくてもインストールと timer を止めない

## なぜ

1.0.0 を公開した後、開発元には「どれだけの台に、どのバージョンが入っているか」を知る手段が無い。セキュリティの修正を出す時に、古いバージョンが何台残っているか、どの OS と CPU の種類を確認し続けるべきかを決められない。公開したソフトウェアでよく見る「使用状況を共有しますか?」の形にした（運営の判断、2026-11-26）。

## 決めたこと

### 既定を「はい」にした

- 公開したソフトウェアで既定を「はい」にすると、気づかずに送らせる形になりうる。そこで、**聞くこと自体は省かない**（端末で実行すれば必ず質問が出る）・**質問の文の中で**送るものと送らないものと止め方を全部言う・**聞けない時は「いいえ」**、の 3 つと組にした
- 端末が無い実行（設定ファイルで実行する自動のインストール）は、ほかの項目なら「設定ファイルに無く、端末も無ければ止まる」。この質問だけは止めずに「いいえ」にする。設定ファイルを書いた人は質問の文を読んでいないので、「はい」に倒すと聞いていないのに送ることになる
- 前から入っているサーバー（この仕組みの前のバージョンで入れたもの）には聞かない。更新の後の `install-units` も、設定ファイルに `USAGE_SHARE=yes` が無ければ timer を有効にしない。`sudo ec-sugar status` に「しない（始めるには sudo ec-sugar usage on）」の 1 行を出すだけにした（更新は人が見ていない夜にも走るので、そこで勝手に送り始めない）

### 送るものを最小にした

- ID は `/dev/urandom` から作る UUID v4。ホスト名・ドメイン・IP アドレス・MAC アドレスから作らない（作ると、ID からサーバーや店にたどれる。同じ値から作り直せるので、`off` で消しても消えない）
- 数えたいのは「台数」「バージョン」「OS と CPU の種類」「店の数」だけ。店の数は、1 台に何店が載っているか（1 店舗か、複数の店か）で使われ方が大きく違うので、数だけを足した（下の「作って決めたこと」）。注文の数・売上・App の使われ方は、店の業績や個人情報に近く、送れば「何を送っているか」の説明が長くなって、入れる人が判断できなくなるので送らない。足したくなったら、この ADR とインストーラーの質問の文の書き換えと一緒にする（黙って項目を増やさない。送る側の `ec_usage_payload` の雛形をテストが 7 つと照らす）
- どの値も、送る前に決まった形に絞る（違えば `unknown`）。値に引用符や空白が入って JSON を壊すこと・思わぬ文字列が漏れることを防ぐ
- `off` で ID を消し、`on` にし直したら新しい ID にする（止める前と後をつなげない）

### IP アドレスを残さない

- 受け取る側の表には ID ごとの最初と最後に見た時刻・バージョン・OS・CPU の種類だけを持つ
- 大量の送信を断るには接続元を数える必要がある。そこで、**日ごとに替える秘密**での IP アドレス（IPv6 は /64）の HMAC を、その日の間だけ持つ。日が替わったら秘密と数を消すので、前の日の印から IP アドレスを確認し直すことも、日をまたいで同じ接続元をつなぐこともできない
- 受け取る側の Web サーバーのアクセスログには、ほかのページと同じく接続元が残る（下の「残る危険」）

### メールアドレスを集めない

- インストーラーでメールアドレスを聞くと、確認のメールが無いので、他人のアドレスを入れられる（迷惑メールの踏み台になり、特定電子メール法の同意の記録も取れない）。サーバーの中に平文のメールアドレスも増える
- 公式の店にはメルマガの App があり、登録は確認のメールのリンクで確定する二段階（ダブルオプトイン）で、同意の記録と配信の停止もそろっている。インストールの最後にその登録ページ（`https://official.ec-sugar.jp/p/newsletter`）を案内するだけにした

### 送り方

- 送るのはホストの root の `curl`（`-q` で root の `~/.curlrc` を読まない・`--proto =https`・10 秒で切る・転送を追わない・本文は標準入力から）。コンテナを通らないので、アプリの送信用プロキシ（ADR 0102）を通らない。ADR 0102 は対象をアプリのコンテナ（app・queue・scheduler）にし、ホストの root の通信（更新の GHCR・Sigstore・GitHub など）を対象の外に置いている。アプリのコンテナの許す一覧に開発元を足さないので、アプリから開発元へ送る道は増えない
- ホストの防火壁（`ec-sugar firewall`）が塞ぐのは root でない利用者からコンテナの網への接続とコンテナからホストへの接続で、root のホストから外への通信には触らない
- 週 1 回は systemd の timer（`OnCalendar=weekly`・`RandomizedDelaySec=6d`・`FixedRandomDelay=true`・`Persistent=true`）。サーバーごとに送る時刻を 1 週間の中にばらし、止まっていた間の回は起動の後に 1 回だけ送る
- 送れなくても 0 で終わる（標準出力の 1 行だけ。timer では journal に残る）。インストールを止めるほどの理由ではない
- 送信先は既定 `https://ec-sugar.jp/usage/v1`。確認のために環境変数 `EC_SUGAR_USAGE_URL` で替えられるが、https の URL のほかは断る
- 隔離した複製環境（`restore --isolated`）からは送らない（本番の ID のコピーが別の台として数えられない・外へ何も出さない形を保つ）

### 受け取る側

- 開発元が ec-sugar.jp のサーバーで動かす。このリポジトリ（公開のツリー）には入れない
- `POST /usage/v1` だけ。JSON・2 KB まで・項目はちょうど 7 つで、送る側と同じ形（違えば 400。`shops` は 0〜100000 の整数か `null`）。接続元ごとに 1 日 30 回、新しい ID は 1 日 300・全体で 10 万、新しいインストールの通知は 1 日 50 回まで
- 新しい ID が来たら開発元に通知する（今までどおり最初の報告で）。週 1 回、使っている台数・その店の数の合計・この 7 日の新しいインストール・バージョンごとの内訳をまとめる。開発の進み具合の画面（運営者だけがパスキーで見る）にも同じ数え方で出す

## 選ばなかった案

- **既定を「いいえ」にする**: 入れる人の多くは既定のまま進むので、台数がほとんど分からない。送るものを最小にし、質問の文で全部を見せ、聞けない時は「いいえ」にすることで、既定「はい」でも入れる人が知らずに送ることは無いと判断した
- **アプリ（管理画面）から送る・管理画面で選ばせる**: アプリのコンテナから外へ出る道が増え、送信用プロキシの許す一覧に開発元を足すことになる。入れた人がサーバーの上で選び、サーバーの上で止められる形の方が分かりやすい
- **更新の確認（GitHub への問い合わせ）に乗せて数える**: release チャネルの更新はタグの一覧を取るだけで、台を数えられない。数えられる形にすると、更新を止めた人の台が見えなくなり、更新の通信に識別子が載る
- **ホスト名やマシンの ID（`/etc/machine-id`）から ID を作る**: 作り直せるので、`off` で消しても同じ ID に戻る。ほかの所で使われる値とつながる

## 残る危険

- ID は誰でも作れ、署名もしないので、偽の送信を足せる。上限の中で台数と通知を汚せる。違う週に 2 回以上の報告だけを数えるので 1 回きりの偽の送信は数えないが、週をまたいで送り続ければ数えられる。店の数も送る側の申告。台数は「おおよそ」として読む
- 送る時に、受け取る側と途中の経路には送り元の IP アドレスが見える。受け取る側の Web サーバーのアクセスログには残る（受け取る側の表には残さない）
- 受け取る側を Cloudflare のプロキシの後ろに置くと、接続元が Cloudflare の IP アドレスになり、接続元ごとの上限がまとめて掛かる（受け取る側で本当の接続元を戻す設定が要る）

## 作って決めたこと（2026-11-26 数え方と店の数）

運営から「何人が使っているかを正確に知りたい」と依頼があり、3 つを足した。

- **「使っている」の数え方**: ある時刻 T の時点で、T までの最後の報告が ① 最初の報告の週より後の週で、② T から 14 日以内のサーバー。週は UTC の月曜 0 時から 7 日。入れた週の中の報告（`install` とその週の `weekly`）だけのサーバーは、まだ数えない。受け取る側は ID × 報告した週を 1 行（その週の最後の報告の時刻つき）で持ち、8 週を過ぎた行は消す（4 週の推移と 14 日の数え方に足りる分）。過ぎた週の推移も同じ決まりで「その週の終わりの時点」を数える
- **数え方は 1 つのファイル**（受け取る側の `Stats`）で、週 1 回のまとめと開発の進み具合の画面が同じものを使う。画面は受け取る側の SQLite を読み取り専用で開く（書き換えない）。画面に ID は出さない
- **店の数**（`shops`）: ホストの root が `docker compose exec` で中央の DB に `SELECT count(*) FROM tenants` だけを送る。店の名前・ドメイン・店の ID は読まない。0 以上の整数で、100000 で切る。DB に届かない・形の違う答えは `null` で送り、止めない（店の数が分からないサーバーは、合計から除いて数を別に出す）。インストーラーの質問の文と `sudo ec-sugar usage` の表示にも足した
- 週 1 回の unit は、店の数を読むのに docker の CLI が root の設定を読むので、`ProtectHome`・`ProtectSystem` を掛けない（`NoNewPrivileges`・`PrivateTmp` は掛ける）
