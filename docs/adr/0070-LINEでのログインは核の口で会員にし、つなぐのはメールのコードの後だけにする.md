# 0070 LINE でのログインは核の口で会員にし、つなぐのはメールのコードの後だけにする

状態: **採用**（2026-11-05。「LINE でログイン＋知らせ」は運営が決めた。要点の 1〜7 を先に決めた。再確認にしない・鍵の段階・公表とプライバシーポリシーの一言・認証済みアカウントの一言は、運営にセキュリティを聞かれて足した。細部は作りながら決め、下の「作って決めたこと」に書いた）。ADR 0010（個人情報）・0025（プラグイン）・0034（外部送信の公表）・0044（会員）・0051（App の画面）の上に足す。置き換えるものは無い

## 文脈

- 日本のお客さんは LINE をよく使う。メールのコードより LINE のアカウントで入りたい人がいて、注文や発送の知らせもメールより LINE で見る人が多い
- 会員のログインは核（ADR 0044。メールのコードとパスキー、ガード `auth:customer`）が持つ。App が自分で会員の印を作ると、核の守り（セッションの作り直し・止めた台帳・まとめた台帳・回数）を通らない入口ができる
- LINE ログインの ID トークンにはメールを入れられる（申請すれば）。そのメールで既存の会員に自動でつなぐと、LINE 側のメールの確かさに店の会員の乗っ取りが懸かる

## 決定

1. **App「LINE 連携」**（`plugins/plugin-line`、名前 `line`、目的 `customers`）。店が LINE Developers の 2 つのチャネルの鍵を App の設定に入れる: LINE ログインのチャネル ID・チャネルシークレット、Messaging API のチャネルアクセストークン・チャネルシークレット（Webhook の署名用）。秘密は店の鍵で暗号化し、入れた後は「設定済み」とだけ出す。コールバックの URL（ショップのドメインの `/p/line/callback`）と Webhook の URL を App の画面に出し、店が LINE の管理画面に写せるようにする
2. **ログイン**: ショップのログインの画面に「LINE でログイン」。**核に足す口は 2 つ**: ログインの画面に App の入口を置く口（`LoginEntryProvider`）と、App が確かめた後に会員としてログインさせる口（`MemberSignIn::forApp`。核の守り〔セッションの作り直し・会員の印の行・回数の上限・止めた台帳とまとめた台帳を断る〕を必ず通る）。認可コードフロー ＋ PKCE ＋ state（セッションに結ぶ・1 回きり・10 分）＋ nonce。ID トークンは LINE の決まりどおりに確かめる（署名・iss・aud＝チャネル ID・exp・nonce）。戻り先は自分のショップの決まった経路だけ。bot_prompt で公式アカウントの友だち追加も促す
3. **つなぎ方**: つないだ会員がいればその会員で入る。いなければ、**LINE から来たメールで既存の会員に自動でつながない**。メールを入れてもらい、核のメールのコードで本人を確かめてから、そのメールの会員につなぐ（無ければ作る）。ログインしている会員はマイページから「LINE をつなぐ／外す」。1 つの LINE は 1 人の会員だけ（DB の一意）
4. **知らせ**: つないで友だちの会員に、注文を受けた・発送した（追跡番号があればそれも）を push で。中身は店の名前・注文番号・ご注文の状況へのリンクだけ（住所・金額の明細は載せない）。メールは今までどおり。送れなかったら記録して止まらない（送り直さない）。Webhook（署名を確かめる）の unfollow で送らない、follow で戻す。送る回数の上限
5. 退会・LINE を外すとつなぎの記録を消す。App を止めたらログインの入口も知らせも止まる
6. 外部送信の公表（ADR 0034）に LINE を足す
7. App の画面: つないだ会員の数・友だちの数・直近の送った数と失敗の数（個人情報は出さない）
8. **LINE でのログインは本人の再確認にならない**（2026-11-05）: 今の会員で本人の再確認（ADR 0044 の 3）を求めている操作（メールの変更・パスキーの追加と削除・退会・LINE を外す）は、LINE で入った直後でもメールのコードかパスキーで確かめ直す。LINE のログインで再確認の時刻を進めない
9. **店の LINE の鍵の段階**（2026-11-05）: 設定を変えるのは運用の段階から・直前のパスキーの再確認の後（App の設定の今の決まりのまま。ADR 0034）。閲覧の段階の人は、秘密でない値（チャネル ID・切り替え）と秘密が入っているかだけを見る。秘密の中身は誰にも出さない。変えたことは中央の監査ログ（誰が・どの経路・結果）と店の記録（変えた項目の名前だけ）に残し、値は入れない
10. App の設定の画面に「プライバシーポリシーに LINE での知らせを書き足してください」の一言。App のヘルプに、鍵が漏れた時の作り直しと、LINE の認証済みアカウントにしておくと偽のアカウントと見分けてもらいやすいことを書く

## 確かめた LINE の公式の資料（2026-11-05）

- LINE ログイン v2.1 のウェブのログイン（認可の画面の値・bot_prompt・認可コードは 10 分で 1 回だけ・トークンの窓口）: https://developers.line.biz/en/docs/line-login/integrate-line-login/
- PKCE（code_verifier は英数字と `-._~` の 43〜128 文字、code_challenge は SHA-256 の Base64URL、S256 だけ）: https://developers.line.biz/en/docs/line-login/integrate-pkce/
- ID トークン（ウェブのログインは HS256・鍵はチャネルシークレット、iss は `https://access.line.me`、aud はチャネル ID、exp・iat・nonce・amr）: https://developers.line.biz/en/docs/line-login/verify-id-token/
- 友だち追加の選択肢（bot_prompt の normal・aggressive、friendship_status_changed、`GET https://api.line.me/friendship/v1/status` は profile のスコープのアクセストークンで）: https://developers.line.biz/en/docs/line-login/link-a-bot/
- LINE ログインの API の一覧: https://developers.line.biz/en/reference/line-login/
- Webhook の署名（受けた本文そのものの HMAC-SHA256 を Messaging API のチャネルシークレットで作り Base64 にして `x-line-signature` と比べる。LINE は送り元の住所を公開しない）: https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/
- Webhook の知らせ（follow は友だち追加とブロックの解除、unfollow はブロック。timestamp はミリ秒）: https://developers.line.biz/en/docs/messaging-api/receiving-messages/
- push（`POST https://api.line.me/v2/bot/message/push`、`X-Line-Retry-Key`、ブロック・友だちでない相手へは 200 でも届かない、429 は回数・月の上限）: https://developers.line.biz/en/reference/messaging-api/#send-push-message

## 結果

- 得たもの: お客さんは LINE のアカウントで入れ、知らせも LINE で受け取れる。核の会員の守りは 1 か所（`MemberSignIn`）のままで、ほかのログインの App（例: Apple・Google）も同じ 2 つの口で足せる
- 失ったもの・気をつけること: 初めて LINE で入る人は、メールのコードを 1 回入れる手間がある（乗っ取りを防ぐため。メールの持ち主を確かめずにつながない）。LINE の利用者の ID はプロバイダーごとに違うので、LINE ログインのチャネルと Messaging API のチャネルは同じプロバイダーに作る必要がある（違うと知らせも友だちの印も合わない）。LINE 公式アカウントの無料の枠には月の送れる数の上限がある（超えると LINE が断り、「送れなかった」と記録される）

## 作って決めたこと（2026-11-05）

- **核の口**: `App\Core\Plugin\LoginEntry`（App・文字・行き先。行き先は自分の `/p/<名前>/…` だけ、文字は 1〜20 文字）と `App\Core\Plugin\Contracts\LoginEntryProvider`（`PluginDefinition::$loginEntry`。設定が足りなければ null で入口を出さない）。ショップの `App\Storefront\Members\LoginEntries` が使う店の App だけに聞き、落ちた App は飛ばす。ログインの画面（`account-login.blade.php`）はパスキーの下に「または」と入口を並べる
- **会員にする口は `App\Storefront\Members\MemberSignIn`**: `start`（前の印を取り消し → セッションを作り直す → 新しい印。核のメールのコードとパスキーのログインもここを通すように寄せた）と `forApp`（入口の口を持ち、この店で使っている App だけ。台帳は核が引き直し、会員で・止めていない・まとめられていない時だけ。接続元ごとに 1 分 10 回・会員ごとに 1 時間 20 回）。ログインの記録は核の会員の印の行（`customer_sessions`。いつ・どの会員）で、新しい記録の表は足していない。新しい印は確かめた時刻が空なので、LINE のログインは再確認にならない（決定 8。テストで見張る）
- **本人の再確認から App の画面へ戻る**: 核の再確認（`MemberSecurityController`）に行き先 `next=app` を足した。`return=/p/<名前>/…`（核の `AccountController::returnable` の形だけ）をこのブラウザのセッションに 1 回分置き、確かめた後（メールのコードでもパスキーでも）そこへ戻る。形の違う戻り先はマイページへ
- **Webhook は準備中の関所の外**（`RequireShopAccess::OUTSIDE` に `storefront.plugin.line.webhook`）: 友だちの追加・ブロックの知らせは、ショップを準備中に戻しても受ける。守りは署名（CSRF の確かめは外す。LINE は合い言葉を持たない）。回数は店 × 接続元で 1 分 300 回（App の `line-webhook`。見直しで店の ID をキーに入れた）
- **メールは求めない**: スコープは `profile openid` だけ（email の申請もしない）。ID トークンにメールが来ても読まない。だから「LINE のメールで自動でつなぐ」道そのものが無い
- **確かめた LINE の ID の持ち回り**: つないでいない時は、このブラウザのセッションに Laravel の暗号（APP_KEY）で包んで 10 分だけ置き（見直しで 30 分から縮めた）、メールのコード（核の `MemberLogin::send`・`verify`。回数も核）が合ったらつなぐ。コードが合えば、つなげなかった時（ほかの会員につないである LINE・ほかの LINE をつないだ会員）でも会員としては入れる（ふつうのコードのログインと同じ）
- **ログインの戻り先は 1 つ目のドメインだけ**: ほかのドメインで「LINE でログイン」を押したら、先に 1 つ目のドメインの同じ経路へ移る（セッションと戻り先のホストをそろえる）
- **友だちの印**: ログインの時は `friendship/v1/status` に 1 回聞く（アクセストークンは持たない）。Webhook の follow・unfollow は知らせの時刻（ミリ秒の整数 `friend_at_ms`）が前の印より新しい時だけ変える（秒に丸めると同じ秒の前後を取り違えるのをテストで見つけた）。つないでいない LINE の知らせは何も残さない
- **連鎖のロックとイベントの決まり**: つなぐ・外すはログインの手段を足す・消す操作なので、パスキーと同じく連鎖のロックとイベント（`line.linked`・`line.unlinked`〔`reason`: `member`・`left`〕。LINE の ID は入れない）。友だちの印（`line_links.friend`・`friend_at_ms`）と送った記録（`line_messages`）は例外（conventions.md の 3 の 3 つの条件。送ってよい相手かの印と「送ったか」の印）
- **知らせ**: 核の `PaymentConfirmed`・`FulfillmentShipped` を聞いて仕事に載せる（種類と注文・受渡の ID だけ。宛先もトークンも載せない）。宛先は送る時に注文のお客さんの台帳 → つなぎ → 友だちで引く（台帳が会員で止めていない時だけ）。リンクはマイページ（`/account`）で、合い言葉も署名も入れない（トークに残るため。見るには会員のログイン）。同じ知らせは 1 回（`dedupe_key` の一意。`insertOrIgnore` で先に行を作った仕事だけが送る）。店ごとに 1 分 60 通・1 人に 1 時間 10 通、超えたら「上限で送らなかった」。答えの番号を理由の言葉にして記録（401 はトークンの誤り、429 は LINE の上限）
- **App の画面**: 絞り込み「つなぎ方と数」の 1 件（ID は 0 の ULID）に、写す URL 2 つ（写すボタンつき）・設定がそろっているか・つないだ会員の数・友だちの数・7 日の送った数と送れなかった数。一覧は送った知らせ（種類・状態・日時、1 件から注文へ）。ホームのやることに「24 時間に送れなかった知らせ」
- **設定の項目**: `login_channel_id`（10 桁の数字）・`login_channel_secret`（秘密、英小文字と数字 32 文字）・`messaging_access_token`（秘密、200 文字まで）・`messaging_channel_secret`（秘密、32 文字）・`bot_prompt`（normal・aggressive・off、既定 normal）・`on_paid`・`on_shipped`（既定は切り替えが入）。使う直前にも形を確かめ直す
- **届け先の追加・直す・消すは、本人の再確認を求めないまま**（ADR 0044 の決めたこと）。代わりに、足した・直した時は会員のメールへ事後に知らせる（下の見直し 中 1）。LINE ログインのボタンは核の見た目（`sugar-account__secondary`）のままで、LINE のボタンの決まり（緑の地と LINE の印）にはしていない

## 見直しで直したこと（2026-11-05、見直し。結論は「取り込んでよい、中 1 は公開前に塞ぐ」。同じブランチで直した）

- **中 1（LINE を乗っ取られた時にお金が抜かれる道）**
  - 定期便の**届け先の変更と数を増やす変更**は、本人の再確認（メールのコードかパスキー。10 分のうち）の後だけ（`plugin-subscription` の `SubscriptionAccountController::update`。確かめていなければ `next=app&return=/p/subscription/account` で核の再確認へ送り、確かめた後に定期便の画面へ戻る）。数を減らす・お休み・解約・周期の変更は今のまま。LINE のログインは再確認にならないので、LINE で入った人は必ず確かめ直す
  - **事後の知らせ**: 核に会員への知らせ `App\Storefront\Members\AccountNotice`（仕事 `SendAccountNotice`・メール `AccountNoticeMail`）を足した。載せるのは何をしたかの一言と日時だけ（住所・届け先・金額は載せない。仕事にも台帳の ID と一言と時刻だけで、宛先は送る時に台帳から読む）。届け先を足した・直した（核の `MemberAddressController`）、LINE をつないだ・外した（App）で送る。定期便の届け先と数の変更は、前からある「定期便を変えました」のメール（届け先の値は載せない）が本人へ届くので、二重に送らない。ポイントを使った注文は今の注文のメールに使った数が出るので足さない
  - **定期便の新しい申し込みは再確認を求めない**（確かめた結果）: 申し込みの支払いの画面は `mode=payment`・`customer`・`setup_future_usage=off_session` で作っており、`saved_payment_method_options` を渡していない。Stripe の資料（https://docs.stripe.com/payments/checkout/save-during-payment.md?ui=full-page 。2026-11-05 に読んだ）では、`setup_future_usage` で預けたカード（定期便のカード・カードの登録の画面で替えたカード）は `allow_redisplay` が `limited` になり、Checkout は前のカードを出さない（`always` だけが出る）。だから乗っ取った会員で申し込んでも、被害者のカードは選べず、カードの番号を入れ直すことになる。この前提を `SubscriptionSignupTest` が見張る（支払いの画面の値に `saved_payment_method_options` が無い）。Stripe のダッシュボードの設定で出し方を変える道もある（Stripe の支援の記事「Prefilling saved cards in Checkout」は JavaScript が要り読めなかった）ので、店が Stripe の側で変えた場合は前提が崩れる。Link（Stripe のカードの保存）は Link 側の本人の確かめ（Link のコード）を通る
- **中 2（コード 1 つで消えない LINE の裏口）**
  - LINE をつないだ・外した時に、会員のメールへ事後に知らせる（`AccountNotice`）
  - LINE をつなぐ道で送るコードのメールは、件名を「LINE をつなぐためのコード」にし、本文に「心当たりがない場合は、このコードをだれにも伝えないでください。だれかがこのメールアドレスの会員に、自分の LINE をつなごうとしています」を入れる（核の `MemberLogin::send` に、つなぐ手段の名前の引数を足した。`SendLoginCode`・`LoginCodeMail` が持ち回る）
  - マイページの見出しのすぐ下に「LINE をつないでいます」（核の口 `LoginEntryProvider::linkedLabel` に足した。核の `LoginEntries::linkedLabels`）
  - メールアドレスを変えた時の前のアドレスへの知らせに、つないでいるログインの手段（「LINE をつないでいます」）を載せる（`SendEmailChangedNotice` に台帳の ID を足した）
- **軽 3**: 確かめ待ちの LINE（`line_pending`）は 10 分。核のログインの画面を開いたら消す（核は App の途中の値だけを消し、核のコードの控えは残す。コードの画面へ戻れるように）。違うコードを入れたら消して最初から（当てずっぽうは LINE の 1 回の確かめで 1 回）
- **軽 4**: `MemberSignIn::start` は、戻り先を取り出した後に、核のログインと再確認の途中の値（コードを送ったメール・再確認のコード・新しいメール・再確認の戻り先・パスキーのチャレンジ。`MemberSignIn::CORE_KEYS`）と App の途中の値（`LoginEntryProvider::sessionKeys`。LINE は `line_oauth`・`line_pending`。`member_` で始まる名前は App に名乗らせない）を名指しで消してから、セッションの番号を作り直す。セッションごと消さないのは、注文の入力の途中の値を残すため
- **軽 5**: `forApp` は、呼んだ経路がその App のショップの経路（`storefront.plugin.<名前>.*`）の時だけ通す。会員の印の行に入り方（`customer_sessions.via`。`code`・`passkey`・App の名前だけ。店の移行で列と形の制約を足した）を残す
- **軽 6**: Webhook の回数の上限のキーに店の ID を入れた（App の `line-webhook`。店 × 接続元で 1 分 300 回）
- **軽 7**: 今のまま。ログインしている会員が LINE をつなぐ時、本人の再確認（10 分のうち）は始める時（connect）に見て、LINE から戻った時には見直さない。state の期限も 10 分なので、再確認から最大 20 分まで効く。始めた会員と戻った時の会員が同じかは確かめるので、別の人につながることはない（2026-11-05）
