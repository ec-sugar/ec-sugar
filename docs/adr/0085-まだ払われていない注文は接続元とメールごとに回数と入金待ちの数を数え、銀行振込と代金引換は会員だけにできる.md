# 0085 まだ払われていない注文は、接続元とメールごとに回数と入金待ちの数を数え、銀行振込と代金引換は会員だけにできる

状態: **採用**（2026-11-06。直すことは運営が決めた〔システム全体の見直し 11-06 の中 1、公開の前に直す〕。形を先に決め、数と細部は作りながら決めて下の「作って決めたこと」に書いた。見直し〔中 1〜4・軽 1〜6〕を同じ日に直した）。ADR 0044（会員）・0054（クーポン）・0058（入金待ち）・0065（値引きの 1 人の回数）・0068（ポイント）・0074（銀行振込・代金引換）の上に足す。（0 円の注文の上限）を同じ仕組みに寄せる。置き換えるものは無い

## 要点（先に）

1. **注文の確定の 1 時間の上限**
   - 払う額のある注文（Stripe・銀行振込・代引き）: **接続元 20 回**（試みで数える）・**メール 5 回**（確定できた注文で数える）
   - 0 円の注文: 今までどおり **3 回・3 回**
   - IPv6 は /64 に加えて **2 段目の /48** でも数える（3 倍。1 時間 60 回）
2. **入金待ちの数の上限**: 同じメールは **3 つ**、同じ接続元は **5 つ**（/48 は 15）まで
   - 数える入金待ち: 銀行振込・**発送の前の**代引き・コンビニ払いの払込票
   - 越えたら銀行振込・代引きを「同じメールアドレスまたは同じ回線から、お支払いの済んでいないご注文が続いています」の理由で選べなくする（カードなどは選べる）
3. **店の設定「銀行振込・代金引換は会員だけ」**（既定は切る）
   - 入れた店では、ゲストに銀行振込・代引きを出さず「会員の方だけ」と添え、確定でも断る
   - Stripe の鍵が無い店のゲストには「ログインすると選べる」とログインへのリンクを出し、確かめの画面へは進めない
4. 2 と 3 は**支払いの選び方（`PaymentChoices`）の中**で決める
   - 注文の入力・確かめの画面・確定（錠の中）が同じ部品で同じ答えを出すので、確かめの画面と確定がずれない
   - メールの 1 時間の数と入金待ちは、連鎖のロックの中で数え直す
5. **メールは数えるときだけ正規化**してから印にする
   - 全角・IDN・小文字・`+` 以降・Gmail のドットの違いを同じ受け箱として数える
   - 保存するメールとブラインドインデックスは変えない
6. **断った試み**は数え、中央の監査ログに**回数だけ**を残す
   - 1・10・100… 回目に 1 件。接続元・メール・注文は入れない
   - 確定の錠の中では書かず、ロールバックの後に確定の経路が書く
7. 数え方は 1 か所の小さな部品にまとめる（`App\Storefront\Checkout\UnpaidOrderLimits`）
   - 数えるのは核の `App\Core\RateLimit\Throttle`（ADR 0081。取り込みの時〔〕に寄せた。キーは `Throttle::shopKey`、接続元の 2 段〔/64 と /48〕はどちらも数える）

## 文脈

- 0 円の注文には「接続元ごと・メールごとに 1 時間 3 回まで」の上限があった。払う額が 1 円以上の注文には、経路の `throttle:storefront-cart`（接続元ごとに 1 分 60 回）しかなかった
- 払われないまま注文が在庫・クーポン・ポイントを押さえる期間:
  - 銀行振込: ゲストでも選べ、入金待ちのまま最長 14 日＋24 時間。注文の受付のメールは入れたメールへ出す
  - 代引き: 発送できる段へ進み、店への知らせも出る
  - Stripe のカードなど: 払われるまで最長 180 分
  - コンビニ払い: 払込票を出してから払う期限（最長 30 日）＋猶予 24 時間
- 起きること:
  - 1 つの接続元から振込の注文を 1 分に 60 件作り、限定の品やクーポンの回数を 2 週間押さえる
  - 他人のメールへ店の名前で注文のメールを送り続ける
  - 代引きのいたずらで送料の損を出させる
- これまで何度も「確かめの画面から抜けられない」不具合があった（確かめの画面と確定の判定のずれ）。上限は両方で同じ答えにする

## 決定

### 1. 1 時間の上限

**接続元**（確定の経路で、錠の前に）
- `CheckoutController::place` が `PlaceOrder` を呼ぶ前に、`hitSource` で**先に足してから比べる**
  - 同時に送っても上限を超えない
  - 確定できなかった試み（内容が変わった・在庫が無い）も数える
  - で直した 0 円の注文の形のまま
- 越えたら確かめの画面へ戻し、「同じメールアドレスまたは同じ回線から、ご注文が続いています。…」を出す
- IPv6 は `ClientSource` の /64 と、`ClientSource::wide` の /48 の 2 段で数える（/48 は 3 倍）
- 数える置き場（キャッシュ・Redis）に届かない時は、500 にせず「ただいまご注文を受け付けられません。…」で断る（数えられないまま通さない）

**メール**（確定の錠の中で、確定できた注文だけ）
- `PlaceOrder` が連鎖のロックの後に、過去 1 時間にそのメールで確定できた注文を数える
  - 数え先は `checkout_orders.email_mark` と `created_at`
  - 0 円の注文と払う額のある注文は、注文の合計で分けて数える
- 試みで数えない理由: いたずらの人が他人のメールで確定を押し続けると、本人の 1 時間の枠を、注文を作らずに使い切れてしまう

**共通**
- 数える単位は**店ごと**（キーに店の ID を入れる）
- キーと印は店の鍵の HMAC（`TenantCipher::index`）で、**キャッシュにも表にも平文のメール・IP アドレスを置かない**
- 接続元の窓は最初に数えた時から 1 時間（Laravel の RateLimiter の形）

### 2. 入金待ちの数の上限（支払いの選び方の中で）

**数える入金待ち**（共通の条件: ショップの注文で、注文が開いていて、支払いの記録が `awaiting` のまま、注文の印を持つ日数のうちに作ったもの）

| 種類 | 数える間 |
|---|---|
| 銀行振込 | 払う期限と猶予（`DirectPayments::lapseAt` と同じ）を過ぎていない。期限切れの見回りの前でも外す |
| 代金引換 | **発送の前**（受渡がどれも発送の前）だけ。発送した後は荷物が動いているので数えない。店の人が入金を確かめるまで数え続けることはしない |
| コンビニ払いなど決済代行の入金待ち（払込票を出した注文。ADR 0058） | 払う期限と猶予を過ぎていない |

- 予約の当日払い（会員だけの App の道）と、カートを通らない 1 品の注文（定期便・チケット）は数えない

**数える単位**
- メール: 注文の印 `checkout_orders.email_mark`（数えるときだけの正規化の後の HMAC）
- 接続元: `checkout_orders.source_index`（/64）と `source_wide_index`（/48）
- 印はショップのすべての注文（Stripe の注文も）に付ける

**判定と出し方**
- `PaymentChoices::offer` が数え、越えていれば銀行振込・代引きを「選べない」にして理由 `UnpaidOrderLimits::PENDING` を添える
- メールを入れる前の注文の入力の画面では、会員ならそのメールで、ゲストなら接続元だけで数える（入れた後の答えと食い違わないように）
- 注文の入力・確かめの画面・確定の錠の中の 3 か所が同じ部品を通る。確定では連鎖のロック（`EventStore::lock`）の後で数えるので、同時に 2 つ確定しても上限を越えない
- コンビニ払いは決済代行の画面で選ぶ手段なので、ここでは選べなくしない（数に入れるだけ）

### 3. 会員だけ

- 設定は `payment_method_settings.direct_members_only`（既定 false）
  - 読む・変えるのは `DirectMethodSettings`（`membersOnly()`・`update` の `members_only`）
  - 送らない保存では今のまま。記録 `payment.direct_methods_updated` に `members_only` を残す
- 入れた店では、ログインした会員（`Member` で今の店のもの）でなければ:
  - `PaymentChoices` が銀行振込・代引きを並べない
  - `PaymentOffer::note` に添え書きを入れ、核の部品 `<x-storefront::payment-choice>` がログインへのリンクと一緒に出す（選び方が無くても）
- 添え書き:
  - Stripe の鍵がある店: 「銀行振込・代金引換は、ログインした会員の方だけお選びいただけます。」（使う手段の名前だけ）
  - Stripe の鍵が無い店: 「このショップのお支払いは銀行振込・代金引換です。ログインすると、銀行振込・代金引換でご注文いただけます。」。払う手段が無いので、注文の入力でこの文を欄の誤りにして、確かめの画面へは進めない
- 確定の錠の中も同じ決め方。確かめの画面の後にログアウトした・店が設定を変えた注文は確定せず、確かめの画面 → 入力の画面で選び直してもらう

### 4. 断った試みの記録

- 決まりごと（`free_hourly`・`orders_hourly`・`pending`）に、店ごとの 1 時間の数を数える
- 1・10・100… 回目に、中央の監査ログ（`AuditLog`）へ `storefront.orders_limited` を 1 件残す
  - 中身は `rule`・`refused`・`window_minutes` だけ
  - 接続元・メール・注文の ID・運営は入れない（`ip` も空）
- 記録に失敗しても、数える置き場に届かなくても、断ることは変えない
- 確定の錠の中で断った時（メールの 1 時間・入金待ち）は、`OrderException::limitedBy` に決まりの名前を持たせる。ロールバックの後に `CheckoutController` が記録する（店の連鎖のロックを握ったまま、中央の監査ログの錠を待たない）
- 入金待ちの上限は、注文の入力・確かめの画面で選んだ手段が断られた時と、確定の錠の中で断った時に数える（画面を開いただけでは数えない）

## 作って決めたこと（2026-11-06）

### 数

| 上限 | 数 | 理由 |
|---|---|---|
| メールの 1 時間（払う額のある注文） | 5 回 | ふつうのお客さんが 1 時間に 6 回確定することはまず無い。他人のメールへの注文のメールを 1 時間 5 通までに抑える（今までは 1 分 60 回の範囲で無制限）。確定できた注文で数えるので、内容が変わってもう一度押した分は数えない |
| 接続元の 1 時間 | 20 回 | 家族・会社・学校・携帯の回線（CGNAT）で 1 つの IP アドレスを分け合う分と、店の人が試しに続けて買う分を見込む。下の「接続元の 20 回」も |
| 入金待ち・メール | 3 つ | 振込・代引きは店が入金を確かめるまで残る。まとめ買いを分けて注文する人を見込む |
| 入金待ち・接続元 | 5 つ | 回線を分け合う分を見込んでメールより多く |
| IPv6 の 2 段目（/48） | 1 段目の 3 倍（1 時間 60 回・入金待ち 15・0 円の注文 9） | 1 つの拠点に /48 が丸ごと配られることがあり、/64 を替えながら逃れられる。3 倍は、1 つの拠点の中に複数の家庭・部署があることを見込んだ目安 |
| 0 円の注文 | 3 回 | まま（同じ部品に移しただけ）。払う額のある注文の数とは別に数える。メールは確定できた注文で数える形に変わった |

- 数は店の設定で変えない（引き継ぎの決まり）
- **接続元の 20 回**:
  - 本物の Stripe での通しの確かめ（`npm run e2e:flow`）は 1 つの店で 13 回確定するので、1 回なら収まる
  - それでも今の 1 分 60 回（1 時間 3,600 回）の 180 分の 1
  - Stripe のカードの注文は 180 分で片付くので、1 つの接続元が同時に押さえられるカードの注文は最大 60 程度
- **全額をギフトカードで払う注文**（払ってもらう額 0 円、合計は 1 円以上）は、払う額のある注文の 1 時間の数に入れる（合計で分ける。今の 0 円の注文の決め方と同じ）

### メールの数えるときだけの正規化

順に:
1. NFKC（全角 → 半角）
2. ドメインを IDN の ASCII の形（`idn_to_ascii` を Symfony Mailer の `IdnAddressEncoder` と同じ指定で）
3. 小文字
4. ローカル部の `+` 以降を落とす
5. `gmail.com`・`googlemail.com` はローカル部のドットも落とし、`gmail.com` にそろえる
- ASCII の形にできないドメインは、その形のまま（小文字）で数える
- **保存するメール・`email_index` と `CheckoutInput` の正規化は変えない**（別のタスク）。数えるための印 `email_mark` は、保存するブラインドインデックスとは別の HMAC

### 注文の印を持つ日数

- 払える期限のいちばん長いものに合わせて計算する（`UnpaidOrderLimits::markSeconds()`。今は 32 日）
  - 式: `max(銀行振込の最長 14 日, コンビニ払いの最長 30 日) ＋ 1 日（期限は注文の日の N 日後の 23:59）＋ 猶予の時間`
  - コンビニ払いの入金待ちも数えるので、銀行振込だけでなくコンビニ払いの最長に合わせた
- 期限切れの見回り（`storefront:expire-unpaid-orders`、5 分ごと）が、それより前の注文の 3 つの印を 1 文で空にする（状態ではない印。conventions の例外の一覧に足した）
- この日数より前の発送の前の代引きは、入金待ちとして数えない
- DB の制約: 3 つの印は空か 16 進 64 文字だけ（`checkout_orders_<列>_hex`。アプリの誤りで平文の IP アドレス・メールが入っても DB が断る）
- この移行の前にできた注文には印が無いので、メール・接続元の数に入らない（入る前は上限が無かったので、今より緩くはならない）

### 断る文と、他人のメールを入れた時の漏れ

- 断る文は「同じメールアドレスまたは同じ回線から」とし、メールと接続元のどちらで越えた時も事実と食い違わない言い方にした
- 注文の番号・数・確認のリンクを出さない（お支払いの方法と期限は「ご注文の時のメールでお知らせしています」とだけ）。会員でも文を変えない（会員かどうかで文を変えると、別の手がかりになる）
- 残る漏れは「このメールか接続元に、払われていない注文が上限まである」の 1 つの事実だけ。値引きの 1 人の回数（ADR 0065。買い手のメールで「使用済み」と出る）と同じ程度として受け入れる

### ショップから管理画面の部品を使う例外

- 監査ログ（`App\Admin\Services\AuditLog`）は `UnpaidOrderLimits` だけが使う
- `tests/Unit/ArchitectureTest.php` の一覧に理由つきで足した（テーマの試し見の `ThemeSelector` と同じ）
- `Throttle` が核に入る時に、監査の口も核へ寄せられないかを見る

### 接続元の決め方への依存

- 上限は `$request->ip()` に頼る。決め方は install.md のとおり:
  - Caddy が、外から来た `X-Forwarded-For` を捨てて自分が見た住所を付ける。Cloudflare Tunnel の形では、`cloudflared` の住所から来た時だけ `CF-Connecting-IP` を使う
  - nginx がそれを前の Web サーバー（Caddy。ソケットから来た要求）からだけ信じ（`set_real_ip_from`・`real_ip_recursive off`）、PHP には本当の接続元を `REMOTE_ADDR` で渡す
  - PHP には代理の見出しを渡さず、Laravel の `TRUSTED_PROXIES` は空のまま
- 入口の設定を誤ると、すべてのお客さんが 1 つの接続元に見え、1 時間 20 回・入金待ち 5 つで店全体が止まる（今の `throttle:storefront-cart` も同じ前提）
- Cloudflare の「Pseudo IPv4」を「上書き」にすると、IPv6 のまとめ（/64・/48）も効かなくなる（install.md）

### 見直しで受け入れたこと（軽 6）

- 同じ注文の合い言葉で確定が二度、同時に届くと、接続元の 1 時間の数（試みで数える `hitSource`）が 2 つ進む。前の注文を合い言葉で探すのは 1 回目の確定が済んだ後なので、2 回目も試みとして数えられる
- 受け入れた理由: 進むのは押した本人の接続元の数だけで、注文は 1 つしかできない（合い言葉と錠で守る）。上限は 1 時間 20 回あり、二度押しで 1 つ余分に進んでも、ふつうのお客さんが当たることはまず無い。メールの数は確定できた注文を DB で数えるので、二度押しでは進まない

## 結果

**得たもの**
- 1 つの接続元・メールから、払われない注文で在庫・クーポン・ポイントを押さえ続ける・他人へ注文のメールを送り続けることを、時間と数の両方で抑えた
- メールの書き方の違い・IPv6 の /64 の付け替え・他人の枠を試みで使い切る締め出しを塞いだ
- 店は銀行振込・代引きを会員だけにして、いたずらをさらに減らせる
- 確かめの画面と確定が同じ部品で決めるので、抜けられない画面を作らない

**失ったもの・気をつけること**
- 回線を分け合うお客さんが多い店（会社のまとめ買い）では、接続元の上限に当たることがある
- 数はコードの定数で、店ごとには変えられない
- キャッシュ（Redis）が消えると接続元の 1 時間の数は 0 に戻る。メールの 1 時間の数と入金待ちの数は DB で数えるので戻らない
- キャッシュに届かない間は、ショップの注文の確定を断る（数えられないまま通さない）
- コンビニ払いそのものは、入金待ちの上限で選べなくならない（決済代行の画面で選ぶため。1 時間の上限だけ）
