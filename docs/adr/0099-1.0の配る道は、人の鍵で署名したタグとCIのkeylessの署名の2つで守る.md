# 0099 1.0 の配る道は、人の鍵で署名したタグと CI の keyless の署名の 2 つで守る

状態: **採用**（2026-11-12）。
- 11-12 に、公開用は ec-sugar/ec-sugar に非公開で先に作ると決めた。Mac の指紋認証も鍵にできるかも調べた（できる。Mac の Secure Enclave に作った SSH の鍵は、使うたびに Touch ID を求め、秘密の鍵は機械の外へ出せない。物理の鍵と同じ形でタグに署名できる）。
- ADR 0030 の「自動の更新の形」と「リポジトリが乗っ取られても配れないようにする」、ADR 0098 の 3 と「守り」を、公開用のリポジトリの形で 1.0 の範囲に絞って決める。

## 文脈

- ADR 0030 は、CI がイメージを作って keyless で署名し、サーバーが確かめてから入れる形と、署名を 2 つ（CI の keyless ＋ 人の鍵）にすることを決めた。署名つきの「新しいバージョンの知らせ」・緊急の印・止血も同じ ADR にある
- ADR 0098 で開発用と公開用のリポジトリを分けた。イメージを作るのは公開用のリポジトリの CI（GitHub の走らせ役）
- 1.0 は範囲を絞る（ADR 0098）。配る道のうち、1.0 に要るのは「誰が作ったイメージか」「人が出すと決めたバージョンか」を入れる側が確かめられることまで

## 決めたこと（配る側と入れる側の共通の約束）

1. **公開用のリポジトリは `github.com/ec-sugar/ec-sugar`**。1.0 までは非公開で作り、公開は 1.0 の日に運営の了承で。GHCR のイメージも同じ日に公開にする（それまでは読む権限のあるログインでだけ取れる）
2. **配るのは semver のタグ `v1.2.3` だけ**（試しの版の `v1.2.3-rc.1` も同じ道。Release に試しの印が付く）。main やほかのブランチの push からは配らない
3. **タグには人の鍵の SSH の署名**（`git tag -s`、`gpg.format=ssh`）。鍵は Mac の Secure Enclave（Touch ID）か物理の鍵（`sk-ssh-ed25519`。鍵が ed25519 に対応しなければ `sk-ecdsa-sha2-nistp256`）。どちらも秘密の鍵は機械の外へ出せず、使うたびに指か触れることを求める。Secure Enclave の鍵の形は `ecdsa-sha2-nistp256`（Secure Enclave は P-256 だけ）。入れる側は鍵の形で断らず、`allowed_signers` にある鍵かだけを見る
4. **人の鍵の公開鍵はリポジトリの中に置かない**。入れる側のサーバーが root の持ち物の `allowed_signers` を持つ（作り方と入れ替えは入れる側の文書）。控えの鍵も初めから並べておく
5. **公開用のリポジトリの CI（`.github/workflows/release.yml`、`runs-on: ubuntu-24.04`）が、タグの push でアプリのイメージ `ghcr.io/ec-sugar/ec-sugar:<タグ>` と入口のイメージ `ghcr.io/ec-sugar/ec-sugar-caddy:<タグ>` を作って GHCR へ置き、cosign の keyless で digest に署名する**
6. **確かめる身元**: 証明書の身元 `https://github.com/ec-sugar/ec-sugar/.github/workflows/release.yml@refs/tags/<タグ>`、発行者 `https://token.actions.githubusercontent.com`。workflow のファイルの名前・リポジトリの名前・タグの名前のどれかが違えば別の身元になり、入れる側が断る
7. **入れる側が確かめること**（どれか 1 つでも通らなければ入れない）:
   - タグの署名が `allowed_signers` の鍵のもの（`git verify-tag`）
   - イメージを**タグの名前でなく digest で**取り、その digest の cosign の署名が 6 の身元と発行者のもの（`cosign verify --certificate-identity … --certificate-oidc-issuer …`）
   - 署名の証明書に書かれた workflow のコミット（`--certificate-github-workflow-sha`）が、署名したタグが指すコミットと同じ。**これで 2 つの署名が結び付く**: 人が署名したコミットから、このリポジトリの release.yml が作ったイメージだけが通る
   - CI の署名だけのイメージ（人の署名の無いタグ・署名したタグと別のコミットから作ったもの）は入れない

## 1.0 の後に回すもの

署名つきの「新しいバージョンの知らせ」・緊急の印・止血のスイッチ・署名つきの取り消し・少しずつ広げる（冷却の時間を含む）・透明性のログ（Rekor）の見張り・バージョンの匿名の知らせ（ADR 0030 の残り）。arm64 のイメージ。イメージの provenance と SBOM の添え物。

## 採らなかった案

- **GPG の鍵でタグに署名する**: 鍵の期限・失効・鍵の配り方の扱いが重い。物理の鍵と Secure Enclave は OpenSSH の鍵として素直に使え、git は SSH の署名を作れて確かめられる（2.34 から）。確かめる側も `ssh-keygen` だけで済む
- **CI の署名だけにする**: リポジトリか GitHub のアカウントを取られると、本物の CI の身元で署名した悪いイメージを配れる（ADR 0030）。人の鍵の署名は、乗っ取った人が持っていない
- **人の鍵の公開鍵をリポジトリに置く**: 乗っ取った人が公開鍵の一覧ごと書き換えれば、自分の鍵の署名が通る。置き場はサーバーの root の持ち物（Web とリポジトリのどちらからも書き換えられない所）
- **人の鍵でイメージにも cosign で署名する**: Secure Enclave と物理の鍵で cosign の署名を作る道が細く、手順が増える。タグの署名と、証明書の workflow のコミットの照らし合わせ（7）で、同じ「人が出すと決めたものだけ」が守れる
- **main の push ごとに配る**（ADR 0030 の初めの形）: 人の署名の無いバージョンが出る。リリースはタグだけにする

## 結果

- 得るもの: リポジトリか GitHub のアカウントを取られても、人の鍵が無ければ入れる側に通るバージョンは作れない。預かる署名の鍵が CI に無い（keyless）
- 気をつけること: 人の鍵を全部なくすと配れない（控えの鍵を別の所に置き、初めから `allowed_signers` に並べる）。keyless の署名は公開の透明性のログ（Rekor）に残り、リポジトリと workflow とタグの名前が公開される（ADR 0030 で受け入れた）。非公開の間は GitHub の走らせ役の時間の枠を使う

## 作って決めたこと（1.0 は鍵 1 本で出す。2026-11-18、運営の判断。Mac の指紋で使う鍵でよい）

**1.0 は Mac の Secure Enclave（Touch ID）の鍵 1 本で出し、控えの鍵は最初の外部のインストールが入る前に足す。** 上の「気をつけること」の「控えの鍵を別の所に置き、初めから `allowed_signers` に並べる」を、この 1 点だけ緩める。

**なぜ緩めてよいか**: 鍵の一覧はリポジトリの中ではなく**入れる側のサーバーの root の持ち物**（`/srv/ec-sugar/trust/allowed_signers`）にあり、後から足す口がある。

| | 鍵をなくしたとき |
|---|---|
| これから入れる人 | 公式サイトで配る鍵の一覧を差し替えるだけ |
| 既に入っているサーバー | `sudo ec-sugar trust add <公開鍵> --name=<名前>`（`deploy/ec-sugar` の `cmd_trust`）。お店の人に 1 回お願いすることになるが、配れなくなって詰むことはない |

**2026-11-18 の時点で外部のインストールは 0 件**（本番は運営自身のもので、`source` の道）。つまり今なくしても誰にも頼まずに直せる。

**条件（必須）**: **最初の外部のインストールが入る前に、控えの鍵を `allowed_signers` に足す。** そこを過ぎると「入れている全員に 1 回お願いする」費用が出る。backlog の「リリース 1.0 までにやること」の R4 に条件として書いた。

**控えの鍵に求めること**（物理の鍵を買うとき）:
- **`resident`（discoverable credential）に対応していること。** これがいちばん大事。`-O resident` を付けずに作ると、鍵を指す控えのファイル（`~/.ssh/ec-sugar-release-1`）が Mac の上にしか無く、**Mac を失うと物理の鍵が手元にあっても署名できない**（控えの意味が無くなる）。`resident` なら新しい機械で `ssh-keygen -K` で取り出し直せる。ファームウェアは 5.2.3 以降（`ykman info` で見る。古ければ `-t ecdsa-sk`）
- **出所が確かなもの。** root of trust になる鍵なので、中古・開封品・出所の分からない並行輸入は使わない
- 指紋のモデルは要らない（署名は 1 回押すだけで、便利さしか増えない）

## 作って決めたこと（配る側、2026-11-12）

- 公開用の CI は開発用のリポジトリの `release/public/.github/workflows/` に置き、書き出しで公開用の `.github/workflows/` になる（ADR 0098。開発用の `.github/` は書き出さない）。`release.yml`（配る道）と `ci.yml`（ふだんの検査）の 2 つ
- **release.yml の流れ**: タグの形を確かめる（semver 2.0。頭に `v`、試しの版の `-rc.1` などは通し、build の印 `+…` はイメージのタグに使えないので断る）→ タグが注記つきで SSH の署名の形を持ち、この走りのコミットを指すかを GitHub の API で見る（取り出し〔checkout〕はタグを軽いタグに置き換えることがあるため。誰の鍵かはここでは見ない。付け忘れに配る前に気づくための早い知らせで、守りの根拠は入れる側の確かめ）→ 核のバージョン（`App\Core\Version::CORE`）がタグとそろうか → ふだんの検査（`ci.yml` を呼ぶ）→ 2 つのイメージを作って置く → 置いたイメージを digest で取り直して書き込みの境界を確かめる（`docker/check-image.sh`）→ cosign で digest に署名し、入れる側と同じ身元で確かめ直す → Release の本文に digest と確かめ方を書く
- **権限は仕事ごとに最小**: 既定は `permissions: {}`。タグを確かめる仕事（`tag`。重い検査の前に動く）とふだんの検査（`tests`）は `contents: read` だけ。イメージを作って署名する仕事だけが `contents: read`・`packages: write`・`id-token: write`。Release を作る仕事は `contents: write` だけで、コードを取り出さず、イメージにも署名にも触れない（`gh` の決まった呼び出しだけ）。値は全部環境変数で渡し、`run:` の中に `${{ }}` で外の値を埋めない
- 外部の action は全部コミットの SHA で固定し、横に何のバージョンかを注記する。出てから 7 日より後のバージョン（11-12 の時点: actions/checkout v7.0.1・docker/setup-buildx-action v4.4.1・docker/login-action v4.7.0〔v4.8.0 は出て 7 日未満〕・docker/build-push-action v7.4.0・sigstore/cosign-installer v4.1.3・shivammathur/setup-php 2.40.0）。cosign は `cosign-release: v3.1.4` で版を固定し、入れる action が action の中に書いた SHA-256 で確かめる。入れる側も cosign の 3 の系を使う
- イメージは毎回キャッシュなしで作る（ほかの走りが残したキャッシュを混ぜない）。1.0 は linux/amd64 だけ。provenance と SBOM の添え物は付けない（digest を 1 つの manifest にして確かめを単純にする。1.0 の後）
- 写し（fork）では、イメージを作る仕事と Release を作る仕事を動かさない（`if: github.repository == 'ec-sugar/ec-sugar'`）
- **ci.yml** は開発用の CI の検査の仕事（pint・phpstan・依存の監査・PHP のテスト。postgres と redis は services）を GitHub の走らせ役に合わせたもの。引き金は push（ブランチだけ）・`pull_request`・手で頼む・release.yml から呼ぶ。外の写しのプルリクエストでも安全な形にした: `pull_request_target` と `workflow_run` を使わない・秘密を使わない（鍵と DB のパスワードは使い捨ての見本の値）・権限は `contents: read`・取り出しの認証を残さない。1.0 は外のプルリクエストを受け付けないが、Issue の直しを確かめるのに使える
- 見張りは `tests/Unit/ReleaseWorkflowTest.php`（action が SHA で固定され注記がある・checkout が認証を残さない・cosign の版の固定・release.yml の仕事ごとの権限が上のとおり・引き金がタグの push だけ・タグの形の正規表現が通すものと断るもの・digest に署名し約束の身元で確かめ直す・署名の前に境界を確かめる・`pull_request_target` を使わない・走らせ役は `ubuntu-24.04` だけ・ci.yml が書かず秘密を使わない）。開発用の木では `release/public/.github/workflows/` を、公開の木では `.github/workflows/` を読む
- 一度 push したタグは付け替えない（同じ名前で別の中身が届く）。失敗したら次の番号（試しの版なら `-rc.2`）で出し直す
